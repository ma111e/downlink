The Enclosed Document Was the Supplier's Logo

A compromised supplier Microsoft 365 mailbox sent a convincing BCC phishing email whose only attachment was a harmless signature logo, while directing recipients to manually type an attacker-controlled hostname. The incident shows why email defenses must detect inconsistencies between message claims, sender behavior, and plain-text lures rather than relying only on authentication and attachment scanning.
KEY POINTS
  • 01A UK plant and tool hire company received a BCC email from a small agricultural supplier's genuine Microsoft 365 mailbox, with the sender listed in the To field and recipients hidden on BCC.
  • 02The message claimed to contain documents, but its only recorded attachment was a 27,804-byte JPEG matching the supplier's inline signature logo and it scanned clean.
  • 03The email instructed recipients to copy and paste a plain-text hostname with no hyperlink, leaving the incident's links array, QR fields, and OCR fields empty.
  • 04The sender passed SPF, DKIM, and DMARC at origin, while final-hop authentication failures were attributed to inbound gateway processing that modified the message body.
  • 05A depot hire desk user reported the email because the supposed document message pointed to an unrelated domain, after which an analyst classified it as malicious and quarantined both recipient mailboxes.

A UK plant and tool hire company received a BCC email from a small agricultural services supplier it had previously corresponded with. The message was sent through the supplier’s genuine Microsoft 365 mailbox, addressed to the sender’s own address, and claimed that documents were enclosed. The only recorded attachment was a clean 27,804-byte JPEG that matched the supplier’s inline signature logo rather than any business document.

The email’s real lure was a sentence telling recipients to copy and paste a plain-text hostname into a browser if they had trouble opening the attachment. Because the hostname was not an actual link, the incident’s links array was empty and there was nothing for a gateway to rewrite or detonate; the destination was described as attacker-controlled and unrelated to the supplier. A depot hire desk user noticed the mismatch between the claimed documents and the unrelated domain, reported the message, and a human analyst classified it as malicious and quarantined both recipient mailboxes. The case illustrates that valid sender authentication, a trusted correspondent, and a harmless attachment can still support a phishing attempt when the overall message story does not add up.

  • A harmless attachment can still strengthen a phishing lure when it makes a false claim of enclosed documents appear technically true, so attachment presence and malware scanning alone do not validate the message's story.
  • A plain-text hostname that recipients are asked to retype can evade controls focused on clickable links, because the message may contain no actual hyperlink for a gateway to rewrite or inspect.
  • Passing sender-authentication checks does not establish that a message is safe when the attack originates from a compromised supplier mailbox.
  • Authentication failures added after gateway processing should not be treated alone as proof of attacker tampering, because modifying a message body can break an original signature check.
  • Comparing a message's claims with the actual role of its attachments and the sender's usual behavior can reveal deception that individual technical signals miss.

Brotli2Shell: Frequently asked questions for Google Brotli decoder vulnerability (CVE-2026-111497)

Organizations should update affected Brotli-dependent software, including Node.js, .NET, Bun, Envoy, Istio, Python packages, and PHP Windows builds, then restart or redeploy affected workloads.

CVE-2026-111497, also called Brotli2Shell, is an out-of-bounds write flaw in Google’s Brotli C decoder library that Google scored 9.2 under CVSSv4.0. An attacker can trigger it by causing an application to decompress crafted Brotli data, including through compressed HTTP responses or request bodies. The possible impact ranges from application crashes and process-memory disclosure to potential remote code execution, and public proof-of-concept code is available.

The flaw affects software that uses a vulnerable Brotli decoder, including Google Brotli, Node.js, Bun, Envoy Proxy, Istio, supported Microsoft .NET releases, Python Brotli packages, and PHP Windows builds. JFrog research also identified reachable paths in FFmpeg, Apache Arrow, and ClickHouse, while Python HTTP clients may be affected when Brotli or brotlicffi is installed. Fixed releases are available for major affected projects, but embedded Brotli copies require updating the application itself, and patched processes, containers, and scheduled jobs must be restarted or redeployed for the fix to take effect.

  • Updating a system-installed Brotli library alone may not resolve the issue because applications such as Node.js and Bun can ship with their own embedded decoder copy.
  • Removing "br" from an HTTP client’s Accept-Encoding header is not a complete mitigation, because a hostile server can still send Brotli-compressed data.
  • Microsoft states that affected .NET packages alone do not make an application exposed: ASP.NET Core request decompression and HttpClient automatic response decompression are disabled by default.
  • Node.js versions that have reached end of support, including versions 20, 23, and 25, will not receive fixed releases.
  • Patches take effect only after affected processes or scheduled jobs are restarted, and containers must be rebuilt and redeployed.

The article describes a serious flaw, called Brotli2Shell, in software used to unpack Brotli-compressed data. It can affect programs such as Node.js, .NET, Bun, Envoy, Istio, Python web clients, PHP on Windows, FFmpeg, Apache Arrow, and ClickHouse when they open compressed data controlled by an attacker. In the worst case, an attacker could crash a program, view parts of its memory, or take control of it remotely, and public demonstration code is available. Updating affected software and restarting or redeploying it is important because changing only the computer’s shared Brotli component may not fix programs that include their own copy.

An insecure neighbor: how a vulnerability chain led to an isolation bypass in cloud infrastructure

The case highlights that provider-side misconfigurations, exposed management interfaces, leaked credentials, and weak network segmentation can create cloud-wide compromise paths.
KEY POINTS
  • 01The cloud provider’s managed Kubernetes service allowed a regular tenant to create a privileged pod with host access, giving root access to a worker node.
  • 02A Konnectivity design flaw let a compromised worker node request network connections from the Kubernetes control plane, which researchers used to execute code on the control-plane host before escalating privileges.
  • 03The provider’s flat shared overlay network exposed management and monitoring services, allowing access to other tenants’ cluster metadata, logs containing root SSH keys, and potentially their managed resources.
  • 04Unauthenticated or improperly exposed services in the overlay network enabled paths to compromise managed Kafka, Redis or Valkey, PostgreSQL, and MySQL instances belonging to other customers.
  • 05A SQL injection in a custom SaltStack component exposed Salt master authentication tokens, which could be used to run commands on cloud minions; the researchers reported the issues through the provider’s bug bounty program and stated they were fully fixed.

Researchers participating in an official bug bounty program chained multiple vulnerabilities and logic errors in an anonymized major cloud provider to bypass isolation between customers. Starting as a regular tenant of the provider’s managed Kubernetes service, they created a privileged container that gave them root access to a worker machine. They then used a Konnectivity service token and a flaw in the service’s handling of connection requests to make the Kubernetes control plane connect to attacker-chosen targets, ultimately obtaining code execution on the control-plane host. A known OverlayFS issue, CVE-2023-32629, was then used to elevate privileges to root on that host.

The provider’s shared overlay network exposed numerous internal managed services and created paths to other tenants’ resources. Monitoring systems exposed metadata and logs for other customers, including root SSH private keys printed by cloud-init; other exposed services enabled potential compromise of managed Kafka, Redis or Valkey, PostgreSQL, and MySQL instances. Researchers also found a SQL injection in custom SaltStack code that exposed Salt master API tokens, which could run commands on cloud minions and potentially provide access to cloud-wide management systems. The article says the issues were responsibly disclosed, fixed in full, and demonstrates how weak service isolation, exposed management interfaces, and credential leakage can combine into a cloud-wide tenant-isolation failure.

  • A reverse-tunnel component intended to let the control plane reach worker nodes accepted connection requests in the opposite direction, allowing a worker-node token to make the control plane connect to attacker-selected network addresses and local system sockets.
  • Shared monitoring systems created a cross-tenant information leak: VictoriaMetrics exposed target metadata for other tenants, while VictoriaLogs contained cloud-init output that included root private SSH keys.
  • Several managed-service exposures were not caused by a single common flaw but by service-specific defaults or interfaces, including a publicly reachable Kafka JMX endpoint, unrestricted PostgreSQL etcd access, and Redis exporter requests that forwarded its own credentials to an attacker-selected server.
  • The final cloud-wide management path came from custom SaltStack code rather than an outdated SaltStack version: attacker-controlled machine metadata was inserted into an SQL query, exposing Salt master API tokens.
  • The article shows that host-level access to one managed Kubernetes worker was especially consequential because the provider’s flat overlay network made numerous internal managed services visible from that host.

Researchers found that a regular customer of an unnamed cloud provider could chain several mistakes to break out of their own rented service and reach the provider’s internal systems. From there, they could potentially access other customers’ Kubernetes clusters, databases, stored backups, and cloud-management controls, including data and login credentials belonging to other tenants. The issues were reported through a bug bounty program and fixed, but the case shows that a cloud provider’s own network design and internal tools can put many customers at risk at once.

The chain persists via scheduled tasks and uses Telegram-seeded DGA domains, Google DNS-over-HTTPS, and signed encrypted tasking to deliver payloads, including an XMRig cryptominer over Tor.
KEY POINTS
  • 01Check Point Research tracked the Yoba campaign, which used fake GitHub repositories and GitHub Pages promoting purported desktop applications named GPT-5.6 Sol, GPT-6 Astra, and Claude Opus.
  • 02The malicious ZIP packages included legitimate signed OpenAI or Anthropic Setup.exe files that loaded a malicious winmm.dll file, a method known as DLL sideloading.
  • 03YobaDropper checks for administrator privileges, creates a ProgramData\WMProcess directory, copies the legitimate Windows WMPDMC.exe there, and uses a scheduled task running as Local System to load its next-stage wmpdui.dll file.
  • 04YobaLoader obtains tasking through a Telegram channel profile image, generates a dedyn.io domain, queries Google DNS-over-HTTPS for a TXT record, verifies an Ed25519 signature, and retrieves a payload from Catbox.
  • 05The observed final payload was XMRig 6.26.0, configured to mine through a Tor proxy, although the loader can deliver PE files or PowerShell scripts.

Check Point Research tracked Yoba, a campaign that uses fake GitHub repositories and GitHub Pages posing as desktop releases for GPT-5.6 Sol, GPT-6 Astra, and Claude Opus. The projects link victims to malicious ZIP files hosted as GitHub releases and appear in Google search results, which the researchers say is likely the result of SEO poisoning. The archives combine malicious components with legitimate signed OpenAI or Anthropic Setup.exe executables.

The signed executables load a malicious winmm.dll, which checks for its expected host name, delays analysis attempts, excludes several CIS-region keyboard languages, and requires administrator privileges. The dropper establishes persistence by copying Windows Media Player components into ProgramData\WMProcess and creating a scheduled task that runs as Local System, while the loader uses a Telegram channel image to generate a domain and retrieves signed, encrypted tasking through Google DNS-over-HTTPS. Researchers observed the chain delivering an XMRig cryptominer through Tor, but noted that the loader can also retrieve and run other executable or PowerShell payloads.

  • The campaign did not need to forge trusted software signatures: it placed malicious DLL files beside legitimate signed OpenAI and Anthropic executables so those executables would load the malware indirectly.
  • Changing the profile image on the attackers’ Telegram channel can change the domain generated by YobaLoader, allowing the operator to rotate its tasking location without changing the malware binary.
  • The loader verifies an Ed25519-signed command retrieved through Google DNS-over-HTTPS before decrypting it, and the command can direct it to deliver either an executable payload or a PowerShell script.
  • The newer Yoba versions exclude several CIS-region keyboard languages, including Russian but explicitly not Ukrainian, before installing the next stage.
  • Although XMRig mining was the observed final payload, the loader is not limited to mining and can receive other attacker-supplied payloads through its encrypted tasking mechanism.

Researchers found fake GitHub projects offering supposed desktop versions of ChatGPT and Claude that secretly install Yoba, a program that can download and run unwanted software. The downloads misuse real, signed files from OpenAI and Anthropic to appear trustworthy, then stay active after a computer restarts and can install a cryptocurrency miner that consumes the victim’s computer power. This matters to anyone searching for unofficial AI tools, because trusted hosting sites and familiar brand names can make harmful downloads look legitimate, while the operators can switch to delivering other harmful programs later.
