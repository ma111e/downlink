TELEPUZ: a modular MaaS malware spreading via CLICKFIX-VIDAR chains

Elastic Security Labs identified TELEPUZ, a fast-evolving modular malware likely offered as MaaS, spreading through CLICKFIX-VIDAR chains and using WebSocket C2, persistence, UAC bypass, evasion, credential theft, keylogging, and web-injection modules. Its active development and growing VirusTotal submissions suggest the threat is likely to expand despite currently limited C2 infrastructure.
KEY POINTS
  • 01Elastic Security Labs is tracking an emerging threat named TELEPUZ that has been spreading via a CLICKFIX-VIDAR infection chain and has been operating since late April 2026 according to collected infrastructure information.
  • 02The infection chain begins with a ClickFix social engineering page that prompts the user to copy, paste, and execute a Windows PowerShell command, which downloads a VIDAR Go variant that then retrieves the TELEPUZ stager and main payload.
  • 03TELEPUZ is a 64-bit Windows DLL written in C that is lightweight, modular, and uses obfuscation techniques including garbage instructions, import hashing, custom RC4 string encryption, and indirect syscalls.
  • 04The malware installs persistence, performs anti-VM and anti-debugger checks, attempts UAC bypass and SYSTEM privilege escalation, registers itself as a Windows service, and communicates with its C2 over WebSockets.
  • 05TELEPUZ supports 36 commands and can download additional modules for functions such as keylogging, stealing data, web injection, Chromium cookie extraction, screenshots, file operations, process listing, and process hollowing.

Elastic Security Labs is tracking TELEPUZ, an emerging full-featured, lightweight, and modular malware family spreading through a CLICKFIX-VIDAR infection chain. The campaign begins with a ClickFix social engineering page that prompts a user to copy, paste, and run a Windows PowerShell command, which downloads a VIDAR Go variant. VIDAR then retrieves the TELEPUZ stager and main payload from staging infrastructure, including domains such as hurgadatour[.]shop.

TELEPUZ is a 64-bit Windows DLL written in C and appears to be in active development, with regular VirusTotal submissions and a growing number of builds observed since activity began around late April 2026. The malware installs persistence, performs anti-VM and anti-debugger checks, attempts privilege escalation through UAC bypass techniques, and can register itself as a Windows service. It also uses evasion methods including indirect syscalls, NTDLL unhooking, AMSI and ETW patching, and removal of third-party DllNotification callbacks.

The malware communicates with command-and-control infrastructure over WebSockets, using fallback methods that include Telegram, Steam profiles, DNS records, and a Polygon blockchain smart contract. The article identifies two primary C2 domains, cal.joycedoula[.]com[.]br and cal.snehamumbai[.]org, while noting a larger set of staging domains used for payload delivery. TELEPUZ supports 36 commands and can download modules for keylogging, stealing data, web injection, Chromium cookie extraction, screenshots, file operations, process hollowing, and other capabilities.

  • The string “telemetriawork” in second-stage download URLs is a strong pivot for finding related TELEPUZ stagers and payloads, with VirusTotal searches returning hundreds of associated files.
  • TELEPUZ uses several public fallback channels for C2 recovery, including a Telegram profile, a Steam profile, DNS records, and a Polygon smart contract, allowing operators to change C2 addresses if the primary server fails.
  • The Polygon smart contract doubles as a kill switch because TELEPUZ exits its communication thread if the returned blockchain data is fewer than 10 bytes.
  • Although many staging domains have been observed, the article identifies only two primary C2 domains, suggesting the payload distribution infrastructure is broader than the command infrastructure.
  • The WebInjector module does not need to inject into browsers; it interacts with Chromium-based browsers through Chrome DevTools Protocol and with Firefox through WebDriver BiDi.

Elastic Security Labs found a new harmful program called TELEPUZ that is spreading when people are tricked by fake web pages into copying and running a Windows command. It first uses another known stealing tool, then installs itself on the person’s computer, tries to hide from security checks, and can add extra parts for stealing browser data, recording keystrokes, taking screenshots, and changing information in web forms. This matters because ordinary Windows users who fall for the trick can have sensitive information stolen, and the many new versions being uploaded suggest the operation is still growing.

Harden-Runner Block Mode Now Available for macOS and Windows GitHub-Hosted Runners

StepSecurity’s Harden-Runner v2.20.0 now supports egress block mode on macOS and Windows GitHub-hosted runners, extending outbound traffic enforcement beyond Linux. This lets teams block unauthorized network calls from compromised workflows or dependencies that could exfiltrate secrets from sensitive build and signing pipelines.
KEY POINTS
  • 01Harden-Runner v2.20.0 extends egress block mode to macOS and Windows GitHub-hosted runners.
  • 02The article says recent GitHub Actions attacks, including Megalodon and GhostAction, relied on outbound calls to exfiltrate secrets.
  • 03Before this release, Harden-Runner supported egress-policy: block on Linux GitHub-hosted runners, while macOS and Windows GitHub-hosted runners only had audit mode.
  • 04macOS runners often build and sign iOS and macOS apps using Apple signing certificates, provisioning profiles, and App Store Connect API keys.
  • 05The recommended path is to start in audit mode, review the recommended policy generated from actual traffic, and then switch to block mode.

Harden-Runner v2.20.0 extends egress block mode to macOS and Windows GitHub-hosted runners. The article says this allows teams to stop secret exfiltration on every operating system their pipelines run on, rather than only observing outbound traffic. Previously, Harden-Runner could enforce egress-policy: block on Linux GitHub-hosted runners, while macOS and Windows GitHub-hosted runners only supported audit mode.

The article highlights recent GitHub Actions attacks, including the Megalodon campaign and GhostAction, as examples where compromised workflows or dependencies made outbound calls to steal secrets. It says macOS and Windows runners can handle sensitive credentials, including Apple signing certificates, provisioning profiles, App Store Connect API keys, and Windows code signing certificates. The article also notes that the Velora DEX SDK compromise shipped an npm package that specifically dropped a macOS backdoor.

With block mode, outbound calls that are not on the allowed endpoints list are stopped, regardless of whether they come from a compromised dependency, poisoned action, or injected script. The recommended rollout is to start in audit mode, review the policy Harden-Runner generates from actual traffic, and then switch to block mode. The article says Harden-Runner protects more than 13,000 open-source projects and enterprises.

  • The article frames outbound network access as the decisive control in recent GitHub Actions secret theft campaigns, arguing that preventing a runner from making an unauthorized external call can turn an incident into a near miss.
  • macOS and Windows runners are presented as high-value CI targets because they commonly handle signing material that could let attackers make malicious software appear legitimate.
  • The release changes Harden-Runner’s role on macOS and Windows from detection-only to prevention, allowing teams to enforce policies built from previously observed workflow traffic.
  • The article recommends using audit mode first because real workflow traffic can be used to generate an allowlist before switching to blocking, reducing the risk of breaking legitimate builds.

StepSecurity released a new version of Harden-Runner that can now block unwanted outgoing internet connections on macOS and Windows GitHub-hosted runners, not just Linux. This matters because these systems often build and sign Apple and Windows software and may handle sensitive keys and certificates. If a hacked workflow or harmful software package tries to send secrets out, the new block mode can stop that connection instead of only showing that it happened.

OPEN SOURCE ↗

This is a specific product release that adds enforcement capability for macOS and Windows GitHub-hosted runners, which is relevant to teams securing GitHub Actions pipelines. It is not a breaking incident, active exploitation report, or critical patch, so it is useful but not urgent for most security professionals.

Runtime Security for Third-Party GitHub Actions Runners: Bitrise, Blacksmith, Depot, Namespace, and Warp

StepSecurity’s Harden-Runner now supports Bitrise Build Hub macOS runners, extending runtime security for GitHub Actions jobs across Bitrise, Blacksmith, Depot, Namespace, and Warp. The key takeaway is that teams using third-party runners can add the same one-step monitoring and egress controls to protect builds from compromised dependencies and actions.
KEY POINTS
  • 01StepSecurity’s Harden-Runner v2.20.0 adds support for Bitrise Build Hub macOS runners alongside existing support for Blacksmith, Depot, Namespace, and Warp Build.
  • 02The article states that moving a GitHub Actions job from GitHub-hosted runners to a third-party runner changes the infrastructure but not the risks, because jobs still check out code, install dependencies, and hold secrets.
  • 03Harden-Runner can be added as the first step of a GitHub Actions job and provides outbound network monitoring, workflow-step correlation, detections in the StepSecurity dashboard, audit mode, and block mode with allowed endpoints on supported providers.
  • 04Bitrise support is presented as important for mobile teams because iOS pipelines may contain Apple signing certificates, provisioning profiles, and App Store Connect API keys.
  • 05The article says Harden-Runner is open source and is used by more than 13,000 open-source projects and enterprises.

StepSecurity says Harden-Runner now supports third-party GitHub Actions runner providers with the same one-step integration used on GitHub-hosted runners. With Harden-Runner v2.20.0, Bitrise Build Hub macOS runners join the supported list alongside Blacksmith, Depot, Namespace, and Warp Build. The article frames this as important because moving a job from GitHub-hosted runners to third-party runners changes the infrastructure, but not the risks from untrusted code, compromised dependencies, or poisoned actions.

The article says Harden-Runner provides outbound network monitoring, correlation of events to the exact workflow step, and detections in the StepSecurity dashboard. It can be added as the first step of a job, while the provider-specific change is the runs-on value, such as a Bitrise Build Hub machine pool label. On Blacksmith, Depot, Namespace, and Warp, the article says standard Harden-Runner capabilities include audit mode, block mode with allowed endpoints, Policy Store integration, and security insights in the job log and dashboard.

Bitrise support is highlighted for mobile teams because iOS pipelines often run on macOS machines and may hold Apple signing certificates, provisioning profiles, and App Store Connect API keys. The article says a compromised dependency in an iOS build could access those credentials and affect an app shipped to end users. StepSecurity presents Harden-Runner as a consistent runtime security model across GitHub-hosted and third-party runners, and says it is open source and used by more than 13,000 open-source projects and enterprises.

  • The article emphasizes that a runner provider’s infrastructure does not meaningfully change the security problem: malicious code from a compromised dependency can execute the same way on GitHub-hosted runners or on third-party runners.
  • The most sensitive workloads may be concentrated on third-party runners because teams often use them for build-intensive pipelines that handle deploy credentials, signing keys, and registry tokens.
  • Bitrise support is especially actionable for mobile teams because macOS iOS build jobs can contain Apple signing certificates, provisioning profiles, and App Store Connect API keys.
  • Harden-Runner’s deployment model is designed to make provider changes low-friction, since the article says the same first workflow step is used across providers and only the runs-on value changes.

The article says StepSecurity’s Harden-Runner now works with Bitrise Build Hub Mac computers, in addition to Blacksmith, Depot, Namespace, and Warp, for teams running GitHub Actions jobs outside GitHub’s own computers. This matters because those jobs can handle sensitive items like deployment credentials, Apple signing certificates, provisioning profiles, and App Store Connect keys, and harmful code from a compromised package can run wherever the build happens. The broader point is that teams using faster or specialized third-party build machines should still be able to watch and control what their build jobs connect to, especially for mobile apps that are shipped to end users.

Introducing Device Policy: Enforce Approved VS Code Extensions Across Your Fleet

StepSecurity launched Device Policy to let organizations approve and enforce allowed VS Code extensions across developer machines using native IDE and OS policy mechanisms. Policies can be deployed through MDM tools like Intune, Jamf, and Kandji or enforced directly by the Dev Machine Guard agent.
KEY POINTS
  • 01StepSecurity announced Device Policy, which lets organizations define approved VS Code extensions and enforce those decisions on developer machines using the IDE's native policy mechanism.
  • 02Device Policy builds policies from the extension inventory observed by Dev Machine Guard, allowing teams to approve extensions already used across their fleet.
  • 03The feature supports version controls such as allowing any version, restricting to stable releases, pinning exact versions, or approving all extensions from a trusted publisher.
  • 04Profiles can be delivered through existing MDM tools such as Intune, Jamf, or Kandji, or enforced directly by the DMG agent when no MDM is available.
  • 05Device Policy can also be managed through Terraform using the StepSecurity Terraform provider and a guided one-time import flow.

StepSecurity announced Device Policy, a feature for defining and enforcing approved VS Code extensions across developer machines. The article says IDE extensions have become a reliable path into developer machines, citing malicious VS Code extensions, a compromised Nx Console VS Code extension, a malicious Cline release that installed OpenClaw, and malicious JetBrains plugins that stole AI API keys. Device Policy builds on Dev Machine Guard’s existing visibility into installed extensions by adding enforcement through the IDE’s own policy mechanism.

Device Policy uses policies and profiles. A policy defines which extensions and versions are allowed or blocked, and it can be built from the extension inventory already observed across the fleet. Rules can allow any version, restrict to stable releases, pin exact versions, or approve everything from a trusted publisher, with a live preview showing the exact VS Code extensions.allowed configuration that devices will enforce.

Profiles bundle policies and deliver them to devices through MDM tools such as Intune, Jamf, or Kandji, with artifacts for macOS, Windows, and Linux. The article says operating-system enforcement makes the policy tamper-proof because developers cannot work around it by changing IDE settings, and the Compliance tab shows each device’s enforcement state, last seen time, and agent version. Organizations without MDM can use the DMG agent to install and continuously enforce profiles, and teams using Terraform can manage Device Policy through the StepSecurity Terraform provider.

  • The feature relies on VS Code’s native extensions.allowed policy format rather than a proprietary enforcement layer, so administrators can preview the exact configuration that the IDE will enforce.
  • Organizations can create approval rules from extensions already observed across their fleet, which reduces the risk of building a policy from guesses instead of actual developer usage.
  • Version control is treated as a policy decision, allowing teams to reject pre-release and preview builds or pin exact versions for higher-risk extensions.
  • Device Policy can still be used without an MDM because the DMG agent can install and continuously enforce profiles directly on assigned devices.
  • Teams using Terraform can move extension governance into code review and version control through the StepSecurity Terraform provider’s import flow.

StepSecurity introduced Device Policy, a feature that lets companies decide which VS Code add-ons developers are allowed to use and apply that rule across all their work computers. This matters because harmful or compromised add-ons have recently been used to put backdoors on developer machines, silently install unwanted software, and steal AI API keys. Developers and security teams are affected because these add-ons run with the same access as the developer, so one unsafe install can put company work and secrets at risk.

This is a product announcement for StepSecurity Device Policy rather than reporting a new incident, active exploitation, or vulnerability. It is relevant to teams managing developer machines and VS Code extensions, but its primary value is awareness of a commercial enforcement feature.
