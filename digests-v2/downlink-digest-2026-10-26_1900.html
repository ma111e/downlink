Authorization Differential Testing in Salesforce

Salesforce authorization should be tested by sending the same request through UI API, GraphQL, and custom Apex, since custom Apex can enforce permissions differently and expose data withheld by native APIs. Review Apex sharing declarations, class API versions, and explicit database access modes—especially for Experience Cloud guest-accessible methods.
KEY POINTS
  • 01Authorization Differential Testing compares the same operation for the same user, record, and field across UI API, GraphQL, custom Apex, and other application paths to identify inconsistent access decisions.
  • 02Salesforce UI API and its GraphQL API enforce the caller’s object permissions, field-level security, and record-sharing access, while custom Apex requires separate review of its authorization behavior.
  • 03Apex classes using `with sharing` enforce record-level sharing but do not, by themselves, enforce object permissions or field-level security for system-mode database operations.
  • 04Apex database operations in classes compiled at API version 66 or earlier default to system mode unless user mode is selected, whereas classes compiled at API version 67 or later default to user mode.
  • 05Experience Cloud guest access to native APIs and to custom Apex methods should be tested separately because guest users may reach different authorization checks through each path.

The article presents Authorization Differential Testing, a method for comparing the same Salesforce request for the same user, record, and field across UI API, GraphQL, custom Apex, and other paths exposed by an application. It highlights a case where a restricted Experience Cloud user cannot see the AnnualRevenue field through UI API or GraphQL, but receives it from a custom @AuraEnabled Apex method. The difference can occur because Salesforce applies record sharing, object permissions, field-level security, Apex class access, and database execution modes at different stages. Teams should investigate any path that returns data or permits changes that another path denies.

The article explains that with sharing enforces record-level sharing but does not independently enforce object permissions or field-level security for system-mode Apex database operations. Apex classes compiled at API version 66 or earlier default to system-mode database operations unless user mode is selected, while classes compiled at version 67 or later default to user mode. It also warns that disabling guest access to native APIs or migrating from Aura to LWR does not automatically secure reachable custom Apex methods. Administrators and developers should test restricted users and Experience Cloud guests separately, document Apex API versions and access modes, and repeat tests after permission, framework, or API-version changes.

  • Two nearly identical Apex controllers can make different authorization decisions solely because one is compiled at API version 66 or earlier and the other at version 67 or later, so an organization can have mixed access behavior at the same time.
  • Removing an old Aura route during an LWR migration or disabling guest access to native public APIs does not automatically secure custom Apex methods that remain reachable by a guest user.
  • A class name found in a JavaScript file does not prove that a guest can invoke the class; Salesforce’s server-side Apex class access check determines whether the call is allowed.
  • When an operation should return only the fields a caller may access rather than fail entirely, the article recommends using `Security.stripInaccessible()` to sanitize the returned records.

The article explains how a Salesforce website can show different amounts of customer or business information depending on which internal route the page uses to request it. A customer, partner, or public site visitor may be blocked from seeing a sensitive field through Salesforce’s built-in services but could receive it through custom code that does not check the same permissions. This matters because changing a website’s design or updating its code can silently change who can view or alter data, so organizations should repeatedly test restricted users and public visitors.

It does not report a specific incident, active exploitation, or newly disclosed vulnerability, so it is lower priority despite its practical technical guidance.

eMudhra, Brotli, and the Long Tail of a Security Fix

Fixing the eMudhra certificate compromise and Brotli flaw requires more than updating Node.js: vulnerable certificate trust paths and bundled decoders may persist across runtimes, applications, and compiled artifacts. Organizations need to inventory what actually shipped, rebuild affected software, and verify that the running application uses the corrected trust store or library.
KEY POINTS
  • 01eMudhra disclosed that a flawed key-generation ceremony in April 2025 produced eight intermediate certificate authority private keys that fit within eight bits, making them easy to recover.
  • 02Chrome and Firefox distributed blocks for the compromised eMudhra intermediate certificates, but other applications may use different certificate stores or verification paths and still trust them.
  • 03Node.js patched both the eMudhra certificate issue and the Brotli decoding flaw, but updating Node.js does not fix separate bundled or compiled copies in other software.
  • 04The Brotli flaw, CVE-2026-111497, can corrupt memory when applications decode malicious compressed data and also affected software including Bun, Python Requests installations with Brotli support, and .NET.
  • 05Organizations should inventory bundled dependencies, rebuild affected artifacts, apply available mitigations, and verify that deployed applications are using corrected decoders and certificate verification settings.

The article examines how the eMudhra certificate compromise and the Brotli decoding flaw created a much wider cleanup effort than a single Node.js update. Eight eMudhra intermediate certificate authority private keys were recoverable because they fit in eight bits, despite being intended as 384-bit keys. Chrome and Firefox distributed blocks for the affected certificates quickly, but other software could still trust them if it used a separate certificate store or verification path.

The Brotli flaw, CVE-2026-111497, could corrupt memory when software decoded malicious compressed input, and affected copies appeared in Node.js, Bun, Python environments using Requests with Brotli support, and .NET. Updating a runtime or library does not necessarily fix compiled applications or bundled copies: Go applications require rebuilding with a patched toolchain, and Bun executables built with bun build --compile retain their own runtime until rebuilt. The article urges teams to track bundled components and certificate settings, maintain rebuild paths, use temporary mitigations where possible, and verify that the corrected code or certificate decision is actually present in deployed and running software.

  • A compromised certificate can be blocked in a browser while a command-line tool on the same computer still accepts it because the two programs may use different certificate trust stores.
  • Installing a patched Go compiler does not change existing Go executables; applications must be rebuilt with the corrected toolchain to receive the verifier change.
  • A Bun executable created with `bun build --compile` contains its own runtime, so it remains affected until that executable is rebuilt even after Bun itself is updated.
  • The absence of certificates in Certificate Transparency logs did not prove the compromised eMudhra keys were unused, because some clients do not require that logging.
  • A security release being published does not mean the corrected component is running, since bundled copies may need replacement and shared libraries may require a service restart.

The article explains how two security problems—a set of easily guessed eMudhra certificate keys and a flaw in software that opens Brotli-compressed data—can affect far more programs than the first update suggests. Web browsers quickly blocked the unsafe certificates, but other tools on the same computer may use different lists of trusted certificates and could still accept them; similarly, many programs may contain their own copy of the flawed Brotli code. This matters because installing one update, such as a Node.js update, may not protect applications that were built with older bundled components, so organizations must find, rebuild, and check every affected program.

OPEN SOURCE ↗

The article provides a concrete, technically grounded analysis of the eMudhra certificate compromise and CVE-2026-111497 in Brotli, which affected widely used runtimes and libraries. Its main value is the actionable reminder that patched upstream software does not automatically fix bundled runtimes, compiled executables, or separate certificate trust stores.

Cross-request KV cache exposure in the GLM-5.3 Workers AI model, and our remediation with SGLang

Cloudflare disclosed that a misconfigured KV-cache pool and an SGLang disaggregated-inference bug caused 155 GLM-5.3 Workers AI responses to expose data from recent requests by other customers between August 27 and September 9, 2026. Cloudflare took the model offline, corrected the configuration and engine behavior, restored service, and worked with SGLang on upstream fixes and broader KV-cache safety hardening.
KEY POINTS
  • 01Cloudflare disclosed that 155 responses from its GLM-5.3 Workers AI model contained data from other customers’ recent requests between August 27 and September 9, 2026.
  • 02The exposure occurred only for prompts longer than 681,280 tokens, because the model’s configured 1,048,576-token context window exceeded the capacity of its prefill memory cache.
  • 03An SGLang disaggregated prefill/decode bug allowed rejected oversized requests to transfer only placeholder data while decode systems read leftover memory pages from earlier requests.
  • 04Cloudflare disabled the model on September 9, increased the prefill cache capacity to about 2.04 million tokens, patched the inference engine, and restored the model later that day.
  • 05Cloudflare stated that no other Workers AI model was affected and recommended that disaggregated SGLang operators update to version 0.5.22 or later.

Cloudflare disclosed a tenant-isolation issue in its GLM-5.3 Workers AI model that caused some customers to receive responses containing data from other customers’ recent requests. The exposure was present from the model’s August 27, 2026 launch until Cloudflare disabled it on September 9, and it affected 155 responses to prompts longer than 681,280 tokens. Cloudflare stated that it found no evidence of deliberate exploitation and confirmed that no other Workers AI model was affected.

The issue resulted from a mismatch between GLM-5.3’s 1,048,576-token context window and a prefill memory cache that could hold only 681,280 tokens, combined with an SGLang bug in its distributed processing mode. Oversized prompts were internally replaced with a one-token placeholder, but the system still treated the transfer as complete and generated output using leftover memory pages from earlier requests. Cloudflare increased the cache capacity to about 2.04 million tokens, patched the rejection path, validated the changes, and restored the model on September 9. It also worked with SGLang maintainers on upstream fixes, broader safeguards for memory-transfer races, integrity checks, and recommendations for operators to use SGLang v0.5.22 or later.

  • Cloudflare knew the memory cache was smaller than the model’s advertised input limit before launch, but its testing checked successful HTTP responses rather than whether long-input output was correct and coherent.
  • The exposed data did not require an attacker to directly read memory: the model generated normal-looking responses while using leftover internal data that had not been overwritten by the new request.
  • Increasing cache capacity prevented valid requests from reaching the faulty rejection path, but Cloudflare also patched SGLang because future configuration changes could recreate the same unsafe condition.
  • Cloudflare’s broader hardening addresses cases where a cancelled request can still be writing data into memory later assigned to another request, showing that safe cleanup must be coordinated across both parts of the AI serving system.
  • Cloudflare is pursuing checks that verify a request owns each memory page before it is used, aiming to stop an affected request instead of returning another user’s data.

Cloudflare said that a flaw in the system running its GLM 5.3 AI model sometimes let customers receive pieces of other customers’ recent requests when they submitted extremely long inputs. The issue affected 155 responses between August 27 and September 9, 2026, and Cloudflare found no evidence that anyone deliberately abused it. This matters because private information entered into an AI service can be exposed to unrelated users if the service does not fully clear and separate data between requests. Cloudflare temporarily disabled the model, fixed the problem, and worked with the software’s maintainers on wider safeguards.

OPEN SOURCE ↗

This is a concrete cross-tenant data-exposure incident affecting a public AI service, caused by an SGLang flaw in disaggregated KV-cache handling. It is especially relevant to operators of SGLang and similar distributed AI inference systems because it provides specific remediation and hardening guidance, although the affected Cloudflare service has already been fixed.
