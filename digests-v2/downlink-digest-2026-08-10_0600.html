Critical Progress LoadMaster flaw now actively exploited in attacks

CISA says attackers are actively exploiting a critical Progress Kemp LoadMaster command injection flaw, CVE-2026-8037, that allows unauthenticated remote command execution on unpatched appliances. Federal agencies have been ordered to patch immediately, and all organizations using affected LoadMaster or MOVEit WAF versions should prioritize updates.
KEY POINTS
  • 01CISA warned that hackers are exploiting CVE-2026-8037, a critical Progress Kemp LoadMaster command injection vulnerability.
  • 02CVE-2026-8037 allows unauthenticated attackers to execute arbitrary commands on unpatched LoadMaster appliances by exploiting unsanitized API inputs in multiple command endpoints.
  • 03Progress Software released security updates in June for affected Kemp LoadMaster versions and said the flaw also impacts all MOVEit WAF versions before GA v7.2.63.2.
  • 04CISA added CVE-2026-8037 to its Known Exploited Vulnerabilities catalog and ordered U.S. Federal Civilian Executive Branch agencies to secure affected servers within three days.
  • 05Shadowserver reported that nearly 300 Kemp LoadMaster instances are exposed online, though it is unknown how many are honeypots or already secured against CVE-2026-8037 attacks.

CISA warned that hackers are exploiting a critical Progress Kemp LoadMaster command injection vulnerability tracked as CVE-2026-8037. Kemp LoadMaster is an Application Delivery Controller and server load balancer used by technology companies and government entities worldwide. Progress Software says 80% of Fortune 500 companies use its products and services, and Kemp LoadMaster has more than 100,000 deployments worldwide.

The flaw allows unauthenticated attackers to execute arbitrary commands on unpatched LoadMaster appliances by exploiting unsanitized API inputs in multiple command endpoints. Progress released security updates in June for Kemp LoadMaster GA v7.2.63.1 or older and LTSF v7.2.54.17 or older. The company also confirmed that all MOVEit WAF versions before GA v7.2.63.2 are affected.

CISA added CVE-2026-8037 to its Known Exploited Vulnerabilities catalog and ordered U.S. Federal Civilian Executive Branch agencies to secure their servers within three days under Binding Operational Directive 26-04. CISA said this type of vulnerability is a frequent attack vector for malicious cyber actors and poses significant risks to the federal enterprise. Shadowserver reported nearly 300 Kemp LoadMaster instances exposed online, though the article says it is unclear how many are honeypots or already secured.

  • CISA gave federal civilian agencies only three days to secure affected servers, signaling unusually high urgency for this actively exploited flaw.
  • The issue is not limited to Kemp LoadMaster appliances because Progress also confirmed that all MOVEit WAF versions before GA v7.2.63.2 are affected.
  • Although Kemp LoadMaster has more than 100,000 deployments worldwide, Shadowserver observed nearly 300 instances exposed online, making internet-facing systems a particularly actionable patching priority.
  • Progress has dealt with multiple security issues across its products recently, including the LoadMaster flaw and a separate ShareFile path traversal zero-day that prompted customer shutdown guidance.

The U.S. cybersecurity agency CISA warned that hackers are now abusing a serious flaw in Progress Kemp LoadMaster, a widely used tool that helps spread website traffic across servers so online services stay fast and available. The issue affects older, unpatched LoadMaster systems and some MOVEit WAF versions, and Progress released fixes in June. This matters because the product is used by technology companies and government organizations worldwide, including U.S. federal agencies, and attackers could use the flaw to make vulnerable systems run commands they should not.

Solidity Pro VS Code Extensions Steal Crypto Wallets, API Keys, and Credentials

Malicious VS Code extensions posing as Solidity Pro tools targeted Web3 developers by stealing crypto wallets, API keys, source-control tokens, SSH keys, and other credentials, then exfiltrating them via Telegram. Researchers warn the extensions used obfuscation and delayed activation to evade marketplace review and automated scanning.
KEY POINTS
  • 01Cybersecurity researchers flagged malicious Microsoft Visual Studio Code extensions named helper-beeps.solidity-pro and web3devtoolsx.solidity-pro that delivered a browser wallet and credential stealer.
  • 02Yeeth Security said early versions 1.0.0 through 2.4.x retrieved an encrypted Python payload from Cloudflare Workers endpoints and executed it.
  • 03Versions starting with 3.0.0 shifted to an information stealer that collects browser profiles, crypto wallets, source-control tokens, API keys, SSH keys, and Telegram bot tokens, then exfiltrates the data through a Telegram bot upload.
  • 04The malware used heavy obfuscation, intermediate clean versions, and randomized delayed activation to bypass marketplace review, static scanning, and casual sandboxing.
  • 05Users who installed the extensions are advised to remove them, inspect dependency graphs, block known command-and-control domains, and alert on use of cscript, mshta, cmd, curl, and powershell commands.

Cybersecurity researchers flagged malicious Microsoft Visual Studio Code extensions named Solidity Pro, including helper-beeps.solidity-pro and web3devtoolsx.solidity-pro, that delivered a browser wallet and credential stealer. The extensions are no longer available on Open VSX, but the GitHub repository for web3devtoolsx/solidity-pro remained accessible at the time of writing. Yeeth Security said earlier versions retrieved an encrypted Python payload from Cloudflare Workers endpoints and executed it.

Starting with version 3.0.0, the extensions shifted to a full information stealer that could collect browser profiles, crypto wallets, source-control tokens, API keys, SSH keys, and Telegram bot tokens. The captured data was exfiltrated through a Telegram bot upload. The stealer targeted data including GitHub, GitLab, AWS, Cloudflare, OpenAI, Telegram, MetaMask, Phantom, Rabby, Coinbase, Trust, Keplr, Bitcoin, SSH, URL credentials, and 1Password MFA tokens.

The malware used heavy obfuscation, clean intermediate versions, and randomized delayed activation to bypass marketplace review, static scanning, and casual sandboxing. Yeeth Security said the activity shares a high-level playbook with WhiteCobra, a threat cluster previously detected distributing Lumma Stealer through malicious VS Code extensions. Users who installed the extensions are advised to remove them, inspect dependency graphs, block known command-and-control domains, and alert on use of cscript, mshta, cmd, curl, and powershell commands.

  • The extensions used intermediate clean versions to build trust before malicious behavior appeared in later releases, so prior benign versions are not enough to treat a developer extension as safe.
  • Randomized delayed activation means short automated scans can miss malicious behavior because the harmful code may run only hours or days after installation.
  • The article highlights that malicious VS Code extensions can steal sensitive data without relying only on obvious dangerous patterns, such as the cited clipboard stealer that used a first-party VS Code clipboard API rather than child_process, network access, or file writes.
  • The campaign specifically targets high-value developer secrets, including GitHub, GitLab, AWS, Cloudflare, OpenAI, Telegram, SSH, and crypto wallet data, making installed extensions a direct risk to both personal funds and development infrastructure.

Researchers found that fake VS Code add-ons called Solidity Pro were built to steal from developers, including crypto wallet data, API keys, source-control tokens, SSH keys, and other credentials. People who installed these add-ons, especially Web3 and Ethereum developers, could have had sensitive information taken and sent out through Telegram. The broader concern is that harmful add-ons can look useful, wait hours or days before acting, and hide from quick checks, making software marketplaces and developer tools a risky place to trust blindly.

Agents and the EU Act: Navigating Your Responsibilities

Companies deploying AI agents that EU users can interact with are likely covered by the EU AI Act, even though the Act does not explicitly use the word “agent.” At minimum they must meet Article 50 transparency duties, and higher-risk or model-modifying uses can trigger broader provider and high-risk system obligations.
KEY POINTS
  • 01Companies anywhere in the world that deploy public-facing AI applications reachable by EU citizens may fall within the scope of the EU AI Act.
  • 02Article 50 and the European Commission’s transparency guidelines require deployers of AI agents that interact with people to inform those people that they are interacting with AI.
  • 03Agents that generate or manipulate synthetic text, image, audio, or video content must mark human-perceptible content as AI-generated under Article 50(2).
  • 04The article states that AI agents are treated as AI systems under the EU AI Act, so rules that apply to AI systems can also apply to AI agents.
  • 05Deployers that modify models above the Act’s threshold can become providers with additional obligations, and agents used as safety components or for sensitive or personal information can trigger high-risk system requirements under Chapter III.

The article explains how the EU Artificial Intelligence Act applies to AI agents, even though the word “agent” does not appear in the Act itself. It says companies anywhere in the world that deploy public-facing AI applications reachable by EU citizens may fall within the Act’s scope. The author emphasizes that Article 50 creates minimum transparency duties for companies deploying agents that interact with humans.

The article cites European Commission guidance stating that AI agents are covered by Article 50 when they can interact with the people instructing them or with other natural persons while carrying out tasks such as bookings, correspondence, contract negotiation, or purchases. It gives examples including voice assistants, chatbots, AI hotlines, humanoid robots, AI companions, social media bots, and coding agents. Deployers must inform people that they are interacting with AI, using written, visual, auditory, or verifiable AI identity disclosures as appropriate.

The article also explains that AI agents are treated as AI systems under the Act, so broader AI system rules can apply to them. If a company heavily modifies a model and attaches agents to it, the company may become a provider and face additional obligations under Articles 53, 54, and 55. Agents used as safety components or for activities involving sensitive or personal information can trigger high-risk system requirements under Chapter III, along with Article 50 and possible general-purpose AI obligations depending on whether the model is modified.

  • The absence of the word “agent” from the EU AI Act does not reduce compliance duties, because later European Commission guidance explicitly says AI agents can be covered by Article 50 when they interact with people.
  • A company can move from being only a deployer to also being a provider if it modifies an AI model enough, which changes the applicable obligations from basic transparency duties to additional provider duties under Articles 53, 54, and potentially 55.
  • Simply attaching an agent to a model is not treated as modifying the model, so the article separates agent-building from model modification when determining provider obligations.
  • The article recommends treating systemic-risk model obligations as a default planning assumption because it says contemporary models now exceed the Act’s training-compute threshold.
  • High-risk classification can be triggered by what the agent does, such as acting as a safety component or processing sensitive or personal information, regardless of whether the underlying model was modified.

The article explains that companies using AI agents people in the EU can interact with may have legal duties under the EU AI Act, even though the law does not directly use the word “agent.” It says these companies generally need to tell people when they are dealing with AI, and may face stricter rules if the agent handles sensitive or personal information, is part of a safety-related system, or is built on a heavily changed AI model. This matters because public-facing AI tools used by EU citizens can create real compliance responsibilities for companies anywhere in the world.

AI Governance Fails Without Identity Intelligence – Part 1

AI governance must extend beyond models, data, and outputs to the human and machine identities that build, deploy, modify, and operate AI systems. Without identity intelligence, organizations cannot prove accountability, traceability, or security for AI decisions and changes.
KEY POINTS
  • 01The article argues that AI governance has a blind spot because organizations often govern models, data, use cases, outputs, and regulations while failing to govern the identities that create, train, authorize, modify, deploy, and operate AI systems.
  • 02The article says AI governance must cover more than generative AI, including systems that produce predictions, recommendations, classifications, decisions, or autonomous actions across areas such as credit, healthcare, hiring, industrial operations, biometrics, cybersecurity, logistics, and autonomous vehicles.
  • 03The article distinguishes identity intelligence from traditional identity and access management by saying identity intelligence connects identities through attribution and examines relationships, behavior, external exposure, historical activity, privilege, device use, and signs of compromise.
  • 04The article states that governance requires attributable accountability, meaning organizations should be able to identify the business owner, technical owner, approving identities, data sources, authorized override identities, affected individuals, and responsible person for an AI system.
  • 05The article warns that attackers may compromise AI systems through trusted identities such as stolen credentials, compromised service accounts, excessive privileges, exposed API keys, weak workload authentication, or unmonitored administrative access.

The article argues that AI governance has a dangerous blind spot because organizations often govern models, data, use cases, outputs, and regulatory obligations while failing to govern the identities behind AI systems. It says AI systems are created, trained, authorized, modified, deployed, and operated by people, pipelines, service accounts, applications, data sources, administrators, and increasingly autonomous agents. Every one of those interactions involves identity, authority, and trust.

The article emphasizes that AI governance must cover more than generative AI, including classifiers, recommendation engines, predictive models, autonomous systems, computer vision, behavioral analytics, robotics, and biometric recognition. These systems already influence areas such as credit and fraud decisions, medical diagnostics, hiring, industrial operations, cybersecurity response, logistics, and autonomous vehicles. The article says identity intelligence goes beyond traditional identity and access management by connecting identities through attribution and examining relationships, behavior, exposure, privilege, device use, historical activity, and indicators of compromise.

The article states that governance requires attributable accountability, meaning organizations should be able to identify the people and identities responsible for approvals, deployments, overrides, data sources, system versions, and outcomes. It warns that attackers may compromise AI systems through trusted identities such as stolen credentials, compromised service accounts, excessive privileges, exposed API keys, weak workload authentication, or unmonitored administrative access. The article concludes that the real governance boundary is not the model itself, but the full ecosystem of identities and authority surrounding it.

  • AI audit logs may be insufficient on their own because a record such as a service account changing a model threshold has limited value unless it can be tied to an accountable human, application, approval, and business purpose.
  • The article frames the governance boundary for AI as the full ecosystem of identities and authority around the model, rather than the model itself.
  • A practical governance test is whether the organization can build an identity-based chain of custody for a GenAI system, from data sourcing and transformation through training, approval, deployment, invocation, modification, and retirement.
  • The article highlights that an attacker may not need to defeat an AI model directly if they can impersonate a trusted identity that already has authority to change data, replace models, alter thresholds, disable monitoring, or approve actions.

The article argues that organizations are paying too much attention to AI systems themselves and not enough attention to the people, accounts, apps, and automated tools that create, change, approve, and run them. This affects businesses using AI for things like credit decisions, medical diagnostics, hiring, fraud detection, factories, recommendations, cybersecurity, robots, and autonomous vehicles. It matters because if a trusted account is stolen or has too much power, someone could change a model, poison its data, steal it, disable monitoring, or make an automated system do something unsafe, while the organization may not be able to prove who was responsible.
