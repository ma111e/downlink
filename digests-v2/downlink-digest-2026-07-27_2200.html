Hackers target US firms in FastJson RCE zero-day attacks

Hackers are actively exploiting a critical FastJson 1.x zero-day (CVE-2026-16723) to achieve remote code execution against mostly U.S. organizations, especially Spring Boot fat-JAR deployments. No patch is available, so affected users should enable SafeMode or move to an unaffected version such as fastjson2.
KEY POINTS
  • 01Hackers are actively exploiting CVE-2026-16723, a remote code execution vulnerability in the FastJson open-source Java library that requires no user interaction or elevated privileges.
  • 02The vulnerability affects FastJson versions 1.2.68 through 1.2.83 and is being used in attacks targeting a wide range of mostly U.S.-based organizations, with some attacks in Singapore and Canada.
  • 03Imperva said the attacks target organizations across Financial Services, Healthcare, Computing, Retail, Business, and other industries.
  • 04Alibaba said the issue is exploitable in the common Spring Boot executable fat-JAR deployment model and that specifying a target class during deserialization does not mitigate the vulnerability.
  • 05There is currently no fix for CVE-2026-16723, and developers using affected versions are urged to enable SafeMode immediately or switch to a non-impacted build.

Hackers are actively exploiting CVE-2026-16723, a remote code execution vulnerability in the FastJson open-source Java library. The issue affects FastJson versions 1.2.68 through 1.2.83 and can be exploited without user interaction or elevated privileges. ThreatBook observed the malicious activity last week, and Imperva said attacks are targeting a wide range of organizations, mostly in the United States, with some activity in Singapore and Canada.

FastJson is an Alibaba-developed Java library used to serialize Java objects to JSON and deserialize JSON back into Java objects. FearsOff discovered the vulnerability and published a technical write-up explaining that the flaw comes from the library’s type-resolution logic, which performs attacker-controlled resource lookups before enforcing AutoType restrictions. The researchers said this allows malicious classes to be loaded and executed in Spring Boot fat-JAR deployments without AutoType enabled or third-party gadget chains.

Alibaba confirmed the vulnerability’s critical severity and said it is exploitable in the common Spring Boot executable fat-JAR deployment model. The vendor said specifying a target class during deserialization does not mitigate the issue because attackers can embed malicious payloads in Object or Map fields. There is currently no fix for CVE-2026-16723, and developers using affected versions are urged to enable SafeMode or switch to a non-impacted build.

  • FastJson 1.2.60 and earlier are not affected, so upgrading is not the only possible version-change path; moving to a non-impacted build is also cited as mitigation.
  • The flaw can be exploited even when AutoType is not enabled and without third-party gadget chains, which weakens assumptions that those conditions would prevent this class of issue.
  • Specifying a target class during deserialization is explicitly not a mitigation because attackers can place malicious payloads inside Object or Map fields.
  • The vulnerable type-resolution logic is absent from fastjson2, which uses an allowlist-first model for polymorphic deserialization, making migration to fastjson2 a more durable remediation path than waiting for a FastJson 1.x patch.

Hackers are using a newly reported weakness in FastJson, a widely used Java tool from Alibaba that helps software handle JSON data, to make targeted systems run their code without anyone clicking anything. The affected versions are FastJson 1.2.68 through 1.2.83, mainly when used in common Spring Boot applications packaged as executable files, and attacks are mostly hitting U.S. organizations in finance, healthcare, computing, retail, business, and other sectors. This matters because there is currently no fix for the issue, FastJson 1.x is no longer actively maintained, and the attacks are expected to spread beyond the current countries mentioned.

Arista patches VeloCloud Orchestrator zero-day exploited in attacks

Arista has patched a maximum-severity unauthenticated command injection zero-day in on-premises VeloCloud Orchestrator that is already being exploited. Administrators should upgrade immediately, restrict web interface access, and check logs for compromise indicators.
KEY POINTS
  • 01Arista patched CVE-2026-16812, a maximum-severity unauthenticated OS command injection vulnerability in on-premises VeloCloud Orchestrator deployments that is being actively exploited.
  • 02The vulnerability allows remote attackers with network access to the VCO web interface to access privileged functionality without VCO tenant or operator credentials.
  • 03Affected versions include VCO 5.2.x before 5.2.3.14, 6.1.x before 6.1.3.4, 6.4.x before 6.4.2.4, and 7.0.x before 7.0.0.1.
  • 04VeloCloud Orchestrator Hosted and Dedicated deployments were patched before the advisory, and VeloCloud Gateway and VeloCloud Edge products are not vulnerable.
  • 05CISA added CVE-2026-16812 to its Known Exploited Vulnerabilities catalog and ordered U.S. federal civilian executive branch agencies to mitigate it by July 30, 2026.

Arista has patched CVE-2026-16812, a maximum-severity unauthenticated OS command injection vulnerability in on-premises VeloCloud Orchestrator deployments. The flaw is being actively exploited in attacks and has a severity score of 10.0. VeloCloud Orchestrator is a centralized management platform used to configure, monitor, and manage VeloCloud SD-WAN deployments and associated edge devices.

According to Arista, attackers only need network access to the VCO web interface and do not need VCO tenant or operator credentials. Successful exploitation could compromise the confidentiality, integrity, and availability of the orchestrator and the data it manages, and Arista warns that attackers could also gain access to VeloCloud Edge devices. Affected versions include VCO 5.2.x before 5.2.3.14, 6.1.x before 6.1.3.4, 6.4.x before 6.4.2.4, and 7.0.x before 7.0.0.1.

VeloCloud Orchestrator Hosted and Dedicated deployments were patched before the advisory was published, and VeloCloud Gateway and VeloCloud Edge products are not vulnerable. CISA added the flaw to its Known Exploited Vulnerabilities catalog and ordered U.S. federal civilian executive branch agencies to mitigate it by July 30, 2026. Arista advised administrators to restrict access to the VCO web interface, monitor for malicious IP addresses, review logs for signs of exploitation, rotate credentials, and consider restoring or replacing compromised instances.

  • Arista says the VCO web interface is exposed by default and has no built-in configuration option to prevent that exposure, so administrators are advised to restrict access to administrative networks while patching.
  • Installing the security update may not be sufficient for already compromised systems because successful exploitation can compromise both the orchestrator host and the data it manages.
  • The three malicious IP addresses shared by Arista are not a complete indicator set, so organizations should review logs for broader signs such as unusual web requests, unexpected outbound traffic, and unauthorized configuration changes.
  • If compromise is suspected, Arista advises preserving logs and filesystem timestamps before remediation, indicating that evidence collection is an important part of the response.
  • End-of-support VCO versions have not been assessed for exposure, so customers on unsupported release trains are directed to contact Arista Technical Assistance Center about upgrade options.

Arista fixed a serious flaw in on-premises VeloCloud Orchestrator, a tool organizations use to manage VeloCloud SD-WAN networks and edge devices, after it was already being used in attacks. Organizations running certain on-premises versions are affected, while hosted and dedicated deployments were patched before the warning and VeloCloud Gateway and Edge products are not vulnerable. The issue matters because attackers do not need a login to abuse it and could take control of the orchestrator and the sensitive network data and devices it manages.

Socket Releases Free Certified Patches for Nuxt Security Vulnerabilities

Nuxt released security updates for multiple 3.x and 4.x vulnerabilities, including server-side RCE, authorization bypass, denial of service, payload disclosure, and a critical development-only RCE in @nuxt/devtools. Users should upgrade to Nuxt 4.5.1 or 3.21.10 and @nuxt/devtools 3.3.1, or use Socket’s free Certified Patches where immediate upgrades are not practical.
KEY POINTS
  • 01Nuxt released security updates for multiple vulnerabilities affecting Nuxt 3.x and 4.x, along with a separate critical development-only vulnerability in @nuxt/devtools.
  • 02Nuxt 4.5.1 and 3.21.10 address issues including server-side remote code execution, authorization bypass, denial of service, and cross-user payload disclosure.
  • 03@nuxt/devtools 3.3.1 fixes a critical remote code execution vulnerability affecting development servers.
  • 04Socket published free Certified Patches for GHSA-9473-5f9j-94wq and GHSA-48hr-524c-v5w3 and is preparing patches for the remaining Nuxt advisories.
  • 05Organizations using authenticated pages with Nuxt cache, swr, or isr route rules should purge CDN and edge caches after upgrading because previously cached _payload.json responses may remain available until explicitly evicted.

Nuxt released security updates for multiple vulnerabilities affecting Nuxt 3.x and 4.x, along with a separate critical development-only vulnerability in @nuxt/devtools. Nuxt 4.5.1 and 3.21.10 address issues including server-side remote code execution, authorization bypass, denial of service, and cross-user payload disclosure. @nuxt/devtools 3.3.1 fixes a critical remote code execution vulnerability affecting development servers.

The most serious production issue, GHSA-9473-5f9j-94wq, can enable server-side remote code execution through server island props. It requires vue.runtimeCompiler to be enabled, which is off by default, and an application pattern where attacker-controlled island props reach Vue’s dynamic component resolution. A related vulnerability, GHSA-48hr-524c-v5w3, can allow unauthorized instantiation of HTML elements or globally registered components through server island props, but does not enable code execution.

Socket has published free Certified Patches for GHSA-9473-5f9j-94wq and GHSA-48hr-524c-v5w3, and is preparing patches for the remaining Nuxt advisories. Nuxt recommends upgrading to Nuxt 4.5.1 or 3.21.10 and refreshing lockfiles to ensure @nuxt/devtools@3.3.1 or later is resolved. Teams using authenticated pages with Nuxt cache, swr, or isr route rules should purge CDN and edge caches after upgrading because previously cached _payload.json responses may remain available until explicitly evicted.

  • The highest-severity production remote code execution issue requires vue.runtimeCompiler to be enabled, which is not the default, and also depends on attacker-controlled server island props reaching Vue dynamic component resolution.
  • The Nuxt DevTools remote code execution issue is limited to development environments, but it can still be reached through another local process, an exposed dev server on the local network, or a malicious site visited while the dev server is running.
  • Upgrading alone may not fully remove exposure for authenticated pages using Nuxt cache, swr, or isr route rules because previously cached _payload.json responses can remain available until CDN and edge caches are purged.
  • The route-rule authorization bypass specifically involves appMiddleware used with route rules containing uppercase characters, making route-rule key casing an actionable review target.

Nuxt released fixes for several security problems in Nuxt 3.x and 4.x, plus a separate serious problem in @nuxt/devtools used during development. Organizations using affected Nuxt versions could face risks such as attackers running code on a server, bypassing access checks, causing outages, or exposing cached page data between users. The article says users should upgrade to Nuxt 4.5.1 or 3.21.10 and @nuxt/devtools 3.3.1, or use Socket’s free patches if they cannot upgrade right away.
