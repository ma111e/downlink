BOFScale: A CDN-Fronted Tailnet from a BOF-PE

NetSPI’s BOFScale demonstrates a fully in-memory Tailscale/Headscale tailnet for red-team C2, running inside an implant with no driver, service, disk state, or child processes while tunneling DERP and control traffic as CDN-friendly WebSockets. The key defensive takeaway is to hunt for unexpected processes making WebSocket connections using Tailscale DERP or TS2021 subprotocols, in-memory BOFScale signatures, and unusual local SOCKS5 listeners.
KEY POINTS
  • 01BOFScale consists of three tools: a modified in-process Tailscale daemon called tailscaled, a C++ BOF-PE client called tailscale, and socksportfwd for forwarding local ports through the daemon’s SOCKS5 server.
  • 02The modified Tailscale implementation adds RFC 6455 WebSocket support for both DERP relay traffic and the TS2021 control channel so Headscale and DERP can sit behind CloudFront or Fastly.
  • 03The tailscaled BOF-PE runs in userspace networking mode with memory-only state, no TUN driver, no Windows service, no disk state, and no child processes after startup.
  • 04The Headscale Docker Compose stack uses Headscale’s embedded DERP relay, disables Logtail, keeps DERP traffic within the operator-controlled stack, and configures ephemeral implant nodes to be removed after ten minutes offline.
  • 05The article provides defensive guidance including YARA rules for BOFScale components, hunting for WebSocket upgrades with derp or ts2021 subprotocols, and checking for a SOCKS5 listener bound to 0.0.0.0:1080.

BOFScale is a set of three tools that run Tailscale as an in-memory network layer for C2 traffic from a BOF-PE. The modified tailscaled daemon runs inside the implant process as an async background job with no driver, no service, no disk state, and no child processes. A lightweight tailscale client controls the daemon over a named pipe, while socksportfwd forwards local ports through the SOCKS5 server exposed by the daemon.

The article explains that Tailscale needed patching because its normal TS2021 control channel and DERP relay upgrades are not standard WebSockets and are rejected by CDN providers such as CloudFront and Fastly. BOFScale modifies Tailscale so both the control plane and DERP relay can use RFC 6455 WebSocket connections, allowing Headscale and its embedded DERP relay to sit behind a CDN. The Headscale stack uses Docker Compose, disables Logtail, uses verified DERP clients, and removes ephemeral implant nodes after ten minutes offline.

The practical workflow shows an operator enrolling an attack VM with the same modified Tailscale binary, starting tailscaled inside a sacrificial process on the compromised host, enrolling it with a Headscale pre-auth key, advertising victim subnets, and using socksportfwd for cases where traffic must originate from the victim network. The article demonstrates this with an NTLM relay scenario involving ntlmrelayx, PetitPotam, a domain controller, and an AD CS server. Defensive guidance includes memory YARA rules for BOFScale components, hunting for WebSocket upgrades with derp or ts2021 subprotocols, and looking for a SOCKS5 listener bound to 0.0.0.0:1080.

  • The strongest network signal described is not simply outbound WebSocket traffic to a CDN, but WebSocket traffic whose subprotocol is derp or ts2021 and whose source process is not a legitimate tailscaled.exe service.
  • BOFScale’s named pipe uses a random UUID path and a permissive world-access SDDL, which makes the pipe functional for the client BOF but also different from what a legitimate Tailscale installation creates.
  • A compromised host running BOFScale may expose a SOCKS5 listener on 0.0.0.0:1080, making the proxy visible to other hosts that can reach the machine rather than limiting it to local-only access.
  • The article notes that the Go runtime can crash after the memory-mapped PE is unloaded, so the recommended operational approach is to run tailscaled inside a sacrificial process and terminate that process when finished.
  • The attack VM must use the same modified Tailscale binary as the implant because a stock Tailscale client will not connect to the CDN-fronted Headscale setup without the RFC 6455 WebSocket patches.

The article describes BOFScale, a set of tools that lets a security testing implant quietly create a private network connection from a compromised Windows computer to an operator’s machine, without installing a normal service, driver, or files on disk. Its traffic can look like ordinary encrypted web connections to services such as CloudFront or Fastly, which makes it harder for organizations to notice. This matters because the same setup can let an operator reach internal machines through one compromised computer, so defenders need to look for unusual memory signs, unexpected local proxy listeners, and specific Tailscale-related web connection patterns.

AWSHound: An OpenSource AWS OpenGraph Collector

AWSHound is a new open-source, read-only collector that turns AWS accounts or entire Organizations into BloodHound OpenGraph data so teams can find real AWS attack paths after evaluating IAM policies, SCPs, resource policies, boundaries, and conditions offline. Its key value is showing how individually boring AWS permissions can combine into practical privilege-escalation and cross-account compromise paths.
KEY POINTS
  • 01AWSHound is a free, self-hosted, read-only collector that turns an AWS account or AWS Organization into a BloodHound Community Edition OpenGraph dataset.
  • 02Before creating graph edges, AWSHound runs offline IAM policy evaluation so edges exist only when effective permissions resolve to Allow after SCPs, RCPs, permissions boundaries, and relevant resource policies are considered.
  • 03AWSHound has separate collect, process, emit, and ingest phases, with collection using only read actions such as List, Get, and Describe and emit producing a compressed graph.zip file for BloodHound ingestion.
  • 04The tool models AWS principals and resources as nodes and capabilities as edges, with only 36 of its 156 edge kinds marked as traversable for BloodHound pathfinding.
  • 05AWSHound currently includes collectors for IAM, Organizations, S3, KMS, SSM, EC2, Lambda, CloudFormation, and EKS, with future collectors planned for Bedrock, ECR, ECS, and CodeBuild.

AWSHound is a free, self-hosted, read-only collector that turns an AWS account or an entire AWS Organization into a BloodHound Community Edition OpenGraph dataset. It is intended to answer where an attacker or defender could move from the AWS access they currently have. The tool runs offline IAM policy evaluation before drawing edges, so BloodHound can use pathfinding to map attack pathways between AWS principals and resources.

The article emphasizes that AWS permissions are difficult to evaluate because access depends on the principal, action, resource, and request context, and because policies can come from identity policies, permissions boundaries, service control policies, resource policies, and other layers. AWSHound handles service-specific differences, such as S3 and Lambda using different same-account and cross-account composition rules, STS requiring both identity and trust policies, and KMS using a separate key-policy-centered model. It also carries unknown conditions on edges and leans toward possible attacker paths when a condition cannot be proven or disproven offline.

AWSHound’s model represents both AWS principals and resources as nodes, while edges represent concrete capabilities such as updating Lambda code, sending SSM commands, assuming roles, or creating and assuming an administrator role. The tool currently includes collectors for IAM, Organizations, S3, KMS, SSM, EC2, Lambda, CloudFormation, and EKS, and emits a compressed graph.zip file for BloodHound ingestion. In one cited run across more than 500 AWS accounts, AWSHound produced about 160,000 nodes and 10.5 million edges in about 15 minutes of processing time.

  • AWS authorization cannot be accurately modeled with one universal policy-combination rule because services differ: S3 and Lambda can allow same-account access through either identity or resource policies, STS always requires both sides, and KMS uses its own key-policy-centered evaluation path.
  • AWSHound deliberately treats unknown policy conditions in a way that favors possible attacker paths by keeping allows it cannot disprove and dropping denies it cannot confirm, so some resulting paths are explicitly hypothetical rather than fully proven.
  • A permissions boundary can remove an escalation path without containing any explicit deny, as shown by the example where a role’s broad iam:PassRole permission is clipped simply because the boundary does not allow iam:PassRole.
  • Not every useful relationship should be traversable in attack-path analysis: AWSHound keeps facts like role trust and policy attachment visible for hunting, but prevents pathfinding from walking them unless they represent effective access.
  • AWSHound’s composite edges are actionable because they collapse combinations such as create role, attach administrator policy, set trust, and assume role into a single account-takeover edge while preserving the policy sources that made each step possible.

SpecterOps released AWSHound, a free tool that reads information from Amazon Web Services accounts and turns it into a map showing where someone could move if they got access to one account or role. This matters because in real companies, many small permissions that look harmless by themselves can combine into a path that lets an attacker reach sensitive systems or even take over an account. The people most affected are teams responsible for securing AWS environments, especially smaller teams managing many accounts without money for a large cloud security platform.

It is useful for cloud security professionals, but it does not report active exploitation, a breach, or an urgent vulnerability, so it is lower urgency.

Emerging Threat: (CVE-2026-60702) Oracle WebLogic Server Takeover via T3 and IIOP

Oracle patched CVE-2026-60702, a critical WebLogic Server flaw that can let a low-privileged attacker with T3 or IIOP network access take over affected servers. Organizations should urgently identify exposed WebLogic instances, apply the August 2026 Oracle patches, and restrict T3/IIOP access on ports such as 7001 and 7002.
KEY POINTS
  • 01CVE-2026-60702 is a critical Oracle WebLogic Server Core vulnerability that allows a low-privileged attacker with network access over T3 or IIOP to compromise the server.
  • 02Oracle assigned CVE-2026-60702 a CVSS v3.1 base score of 9.9 and released fixes in its August 18, 2026 Critical Security Patch Update.
  • 03The affected Oracle WebLogic Server versions are 12.2.1.4.0, 14.1.1.0.0, 14.1.2.0.0, and 15.1.1.0.0.
  • 04The article says T3 is enabled by default and shares the same listener as the HTTP interface, so WebLogic systems exposed on TCP/7001 or TCP/7002 may also expose T3.
  • 05Recommended actions include inventorying WebLogic instances, confirming versions, restricting T3 and IIOP access, blocking TCP/7001 and TCP/7002 from untrusted networks, auditing accounts, and monitoring logs for unexpected T3 and IIOP connections.

Oracle published CVE-2026-60702 on August 18, 2026, as part of its August 2026 Critical Security Patch Update. The issue affects the Core component of Oracle WebLogic Server, part of Oracle Fusion Middleware, and has a CVSS v3.1 base score of 9.9. Oracle describes it as easily exploitable, with network access, low attack complexity, low privileges required, and no user interaction required.

The vulnerability can be exploited over the T3 or IIOP protocols and can result in takeover of the WebLogic Server instance. The affected versions listed by Oracle are 12.2.1.4.0, 14.1.1.0.0, 14.1.2.0.0, and 15.1.1.0.0. The article notes that T3 is enabled by default and shares the same listener as the HTTP interface, meaning WebLogic systems exposed on TCP/7001 or TCP/7002 may also expose the T3 listener.

CyCognito’s observed exposure data shows Industrials at 33.6% of observed assets and Information Technology at 30.2%, based predominantly on service fingerprinting rather than confirmed version detection. The article says WebLogic often sits underneath applications such as Oracle Identity Manager, SOA Suite, WebCenter, PeopleSoft, E-Business Suite, and bespoke Java applications, which can make ownership and exposure harder to track. Recommended actions include confirming WebLogic versions, applying Oracle’s cumulative patches where available, restricting T3 and IIOP access, blocking TCP/7001 and TCP/7002 from untrusted networks, auditing WebLogic accounts, and monitoring logs for unexpected T3 and IIOP connections.

  • The article emphasizes that the risk is easy to underestimate because T3 can be exposed unintentionally when WebLogic’s HTTP interface is published, since T3 is enabled by default and shares the same listener.
  • The vulnerability is described as post-authentication, but the practical barrier is low because any low-privileged account able to reach the T3 or IIOP listener may be sufficient.
  • Older unsupported WebLogic deployments are effectively stuck with permanent exposure because Oracle provides patches only for versions covered by Premier Support or Extended Support.
  • The article frames WebLogic exposure as an asset visibility problem because WebLogic is often recorded only as the business application it supports, while its remote invocation protocols are not inventoried.
  • CyCognito’s observed exposure pattern shows Industrials and Information Technology leading observed potentially affected assets, with 33.6% and 30.2% respectively.

Oracle fixed a serious problem in WebLogic Server, software used underneath many business applications, that could let someone with even a basic account take over the server if they can reach it over the network. The affected versions include both older and current WebLogic releases, so this is not limited to outdated systems. This matters because WebLogic often sits behind important tools like identity, business, supplier, and custom company applications, and a takeover could affect more than just the server itself.
