North Korean Hackers Publish 108 Malicious Packages and Extensions in PolinRider Campaign

North Korea-linked Contagious Interview actors are actively spreading the PolinRider supply-chain campaign through 108 malicious npm, Composer, Go, and Chrome packages/extensions, using compromised maintainer access and developer tooling to infect repositories. Developers who installed affected packages should assume compromise, rotate secrets from a clean machine, and audit repositories for hidden VS Code tasks and suspicious config-file changes.
KEY POINTS
  • 01North Korean threat actors linked to the Contagious Interview campaign have published 108 unique malicious packages and web browser extensions across npm, Packagist, Go, and Google Chrome as part of the active PolinRider campaign.
  • 02Socket reported that the 162 malicious release artifacts include 19 npm libraries, 10 Composer packages, 61 Go modules, and one Google Chrome extension.
  • 03PolinRider has compromised 1,951 public GitHub repositories associated with 1,047 unique owners as of April 11, 2026, and has merged with the TaskJacker cluster that adds malicious VS Code task files to repositories.
  • 04The malware searches infected computers for configuration files such as postcss.config.mjs, tailwind.config.js, eslint.config.mjs, next.config.mjs, babel.config.js, and app.js, then appends malicious JavaScript code to them.
  • 05The latest payload reaches out to TRON, Aptos, and BNB Smart Chain services to fetch an encrypted second-stage payload that unpacks to DEV#POPPER RAT and OmniStealer.

North Korean threat actors linked to the Contagious Interview campaign have published 108 unique malicious packages and web browser extensions across npm, Packagist, Go, and Google Chrome as part of the active PolinRider campaign. Socket reported 162 malicious release artifacts tied to those packages and extensions, including 19 npm libraries, 10 Composer packages, 61 Go modules, and one Google Chrome extension. The campaign targets software developers and people in cryptocurrency through fake recruiting activity that tricks victims into running malicious code.

PolinRider was first flagged by OpenSourceMalware in March 2026 as a campaign implanting obfuscated JavaScript payloads in public GitHub repositories to deliver a new variant of BeaverTail. As of April 11, 2026, the activity had compromised 1,951 public GitHub repositories associated with 1,047 unique owners and had merged with the TaskJacker cluster. TaskJacker drops malicious VS Code task files into repositories, including a setting that can execute code when a folder is opened in tools such as VS Code or Cursor.

The malware searches infected computers for files such as postcss.config.mjs, tailwind.config.js, eslint.config.mjs, next.config.mjs, babel.config.js, and app.js, then appends malicious JavaScript to them. The campaign also uses Git history rewriting, force pushes, anti-dated commits, whitespace padding, fake .woff2 font files, and developer tooling to hide or trigger malicious code. The latest payload reaches blockchain infrastructure including TRON, Aptos, and BNB Smart Chain services to fetch an encrypted second stage that unpacks to DEV#POPPER RAT and OmniStealer.

  • Visible GitHub commit history is not a reliable way to rule out compromise because the actors use force pushes, anti-dated commits, and last-commit modification to make malicious changes appear older or authored by the original maintainer.
  • Defenders should inspect repository activity logs, package release metadata, VS Code task configuration, and changes to configuration files because the campaign hides execution paths outside the places developers may normally review.
  • The use of VS Code task files with the runOn folderOpen option means opening an infected repository in tools like VS Code or Cursor can trigger code execution without the developer intentionally running the malicious file.
  • Affected users are advised to rotate exposed secrets from a clean machine, indicating the article treats installation of the malicious packages as a full environment compromise rather than a simple package removal issue.

Hackers linked to North Korea have been placing harmful code inside 108 software packages and browser add-ons used by developers, often by taking over maintainer accounts or altering real public code projects. The campaign targets software developers and people in cryptocurrency through fake job interviews, tricking them into running code that can steal data and give attackers remote access. This matters because one infected developer’s computer or project can spread the harmful code into many other public projects and software releases, making normal-looking code and version history hard to trust.

U.S. Government Entity Paid Kairos $1 Million in Data-Theft Extortion Case

A U.S. government entity believed to be Union County, Ohio paid Kairos about $1 million after attackers stole sensitive data and threatened to leak it, despite no evidence of file encryption. The case highlights the shift from traditional ransomware to pure data-theft extortion, where paying offers no real proof stolen files were deleted.
KEY POINTS
  • 01A U.S. government entity paid about $1 million to Kairos to prevent stolen files from being leaked, according to a Ransom-ISAC case study based on a leaked negotiation chat and blockchain tracing.
  • 02Rakesh Krishnan did not name the victim, but evidence in the chat points to Union County, Ohio, which reported a May 2025 cyber incident affecting 45,487 residents and staff.
  • 03Krishnan found no sign that Kairos encrypted any machines, used a locker, or demanded payment for a decryption key; the threat was to publish stolen data.
  • 04The negotiation lasted about a month, with Kairos lowering its demand from $3 million to a final $1 million payment made on June 13, 2025.
  • 05The payment was about 9.44 bitcoin and was later split and moved through wallets toward deposit addresses tied to Bybit, OKX, and BELQI.

A U.S. government entity paid about $1 million to keep stolen files from being leaked, according to a Ransom-ISAC case study by Rakesh Krishnan based on a leaked negotiation chat and blockchain trail. The group that received the money calls itself Kairos, but Krishnan found no sign that it locked machines, used an encryptor, or demanded payment for a decryption key. The article says the threat was to steal files and charge the victim not to publish them.

Krishnan did not name the victim, but the chat points to Union County, Ohio, with file names such as Union.xlsx, 1 union co psi template.doc, and union.rar. Union County reported detecting ransomware in May 2025 and later notified 45,487 residents and staff that data had been taken, including Social Security and financial details, fingerprints, and passport numbers. Neither the county nor Kairos confirmed the connection, and the article says the county did not publicly disclose a $1 million payment if the link holds.

The negotiation lasted about a month, with Kairos starting at $3 million and the county eventually paying about 9.44 bitcoin on June 13, 2025. Krishnan traced the funds as they were split and moved toward deposit addresses tied to Bybit, OKX, and BELQI. Kairos provided a “proof of deletion” file, but the article says a list of file names only shows the attacker once had the files, not that the originals were deleted.

  • Kairos was labeled in connection with a ransomware incident, but the case study found no encryptor, locker, or decryption demand, underscoring that many incidents still called ransomware may now be pure data-theft extortion.
  • The so-called proof of deletion provided by Kairos was only a list of file names, meaning the victim had no reliable evidence that the stolen data was actually erased after payment.
  • The leaked negotiation followed a pattern similar to Black Basta chats, with a multimillion-dollar opening demand, a much lower victim counteroffer, and a final payment near $1 million.
  • The article highlights that a dark leak site going offline does not necessarily mean an extortion crew is inactive, since a Kairos-linked wallet was still moving funds months later.
  • For small government networks, the article identifies simple password guessing as a claimed entry method, making multi-factor authentication and monitoring repeated failed logins especially relevant.

A U.S. government entity believed to be Union County, Ohio appears to have paid about $1 million to a group called Kairos after files were stolen and the group threatened to publish them. The people affected were county residents and staff, with exposed information reportedly including things like Social Security numbers, financial details, fingerprints, and passport numbers. The case matters because the payment could not truly prove the stolen files were deleted, and it shows that criminals increasingly pressure victims by threatening to release private data rather than by locking computers.

The File Format Your Gateway Forgot: EPS Macros Hidden in a Logo ZIP

A real supplier’s DKIM-passing email delivered a logo ZIP that looked harmless but contained EPS vector files with macro-like code, exposing a blind spot in gateways that don’t deeply parse programmable file formats. The key lesson is that authenticated senders and clean first-pass scans are not enough when compromised vendors can send unusual attachment types hidden inside legitimate-looking archives.
KEY POINTS
  • 01A marine manufacturing company received an Italian email from a known supplier with a ZIP attachment named Logo nuovo.zip that appeared to contain new company logo materials.
  • 02A first-pass attachment scan marked the ZIP as clean, but deeper content analysis unpacked it and rated it CRITICAL with a 0.90 score.
  • 03The archive contained a brand-manual PDF and two EPS vector files that were flagged for VBA-like or macro-like strings, while the DOCX files had no macro hits and a PNG signature image was judged low risk.
  • 04The article explains that EPS is a programmable PostScript format that email gateways may treat like a simple image and fail to parse deeply.
  • 05The message passed DKIM from the supplier’s real domain but had no SPF record and no DMARC policy, and the article describes this as likely vendor email compromise.

A marine manufacturing company received a short Italian email from a known supplier announcing a new company logo and attaching a ZIP file named Logo nuovo.zip. The message passed DKIM from the supplier’s real domain and did not ask for money, credentials, or urgent action. The article says the likely pattern was vendor email compromise, where a genuine supplier mailbox is used to send malicious content to trusted contacts.

The ZIP was initially marked clean by a first-pass attachment scan, but deeper content analysis unpacked it and rated it CRITICAL with a 0.90 score. The archive contained 63 entries, including a brand-manual PDF, two EPS logo files, DOCX files, and a PNG signature image. The PDF streams and the two EPS files were flagged for VBA-like or macro-like strings, while the DOCX files had no macro hits and the PNG was judged low risk.

The article highlights EPS as the key blind spot because it is a programmable PostScript format that can be treated by gateways as a simple image rather than parsed as executable instructions. It maps the case to MITRE ATT&CK Spearphishing Attachment T1566.001, with obfuscation and deobfuscation-related techniques also listed. The article’s main defensive point is that attachment scanning should unpack nested archives, inspect document and vector file internals, and not treat a passing authentication result as proof that the sender or attachment is safe.

  • A clean result from a first-pass attachment scan can be misleading when the scan does not unpack archives and inspect the internal streams of less common file types such as EPS.
  • A passing DKIM result can increase trust in a malicious email when the sender’s real supplier account or domain is being abused, because DKIM verifies signing but not intent or attachment safety.
  • Design and branding workflows create a practical blind spot because EPS files are legitimate business assets but are also programmable PostScript files rather than simple static images.
  • The absence of malicious links does not reduce the risk in this case, because the article states the danger was entirely contained in the attachment.
  • Defenders should treat code-like content in formats where it does not belong, including vector and document formats, as a reason to stop delivery rather than relying on file extensions or known-bad hashes.

A marine manufacturer received a short, believable email from a real supplier about a new company logo, with a ZIP file attached that looked like normal design materials but included risky hidden code-like content inside logo files. The first scan said the attachment was clean, while a deeper check found the danger, showing how harmful files can get through when they are disguised as ordinary business documents. This matters because trusted supplier emails can be taken over and used to spread harmful attachments, and one missed email can start a costly security incident.

The article reports a concrete malware-delivery case involving a real supplier email, a DKIM-passing message, and EPS files hidden in a logo ZIP that bypassed first-pass scanning. It is broadly relevant for security professionals because it highlights a practical attachment-scanning blind spot, though it is not a major breach, critical patch, or named threat actor operation.
