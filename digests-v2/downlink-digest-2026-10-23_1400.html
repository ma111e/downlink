Signed, Sealed, and Relayed, NTLM-style: Bypassing LDAP Signing Through Reauthentication

Researchers found that pre-October 2026 Windows Server domain controllers could be vulnerable to NTLM relay to LDAP even with LDAP signing enforced, by reusing an attacker-controlled signed LDAP session and stacking a victim bind with a privileged LDAP operation. Organizations should patch domain controllers with the October 2026 update, patch the related SMB issue, enforce LDAP signing and channel binding, and reduce NTLM use.
KEY POINTS
  • 01Researchers described an NTLM relay technique that bypassed required LDAP signing by reusing an existing signed LDAP connection whose session key was known to the attacker.
  • 02The attack placed a victim’s final NTLM authentication message and a malicious LDAP modification request in the same signed SASL record, causing the domain controller to verify the record under the attacker’s original session while executing the modification as the victim.
  • 03The technique targeted plain LDAP on TCP port 389 and did not directly apply to LDAPS on TCP port 636 because TLS protects the connection differently and channel binding applies there.
  • 04The researchers tested domain controllers running Windows Server 2016 and later and reported that they were vulnerable until Microsoft’s October 2026 cumulative update, KB5126646.
  • 05Microsoft’s LDAP fix tracks identity changes on an LDAP connection and discards remaining data in a signed SASL record when the identity changes during processing.

Researchers described an NTLM relay technique that bypassed required LDAP signing on Windows Server domain controllers before Microsoft’s October 2026 update. An attacker could first establish a signed LDAP session using credentials or, where accepted, an anonymous NTLM SASL context, retaining a session key they controlled. They could then coerce a victim, such as a domain controller or server, to authenticate over SMB and relay that authentication through the existing LDAP connection.

The attack worked by placing the victim’s final authentication message and a malicious LDAP request into the same signed SASL record. The domain controller verified that record using the attacker-controlled session key, completed authentication as the victim, and then processed the malicious request with the victim’s permissions. This could enable computer-account takeover techniques such as resource-based constrained delegation or shadow credentials, potentially leading to DCSync and complete domain and forest compromise.

The technique applied to plain LDAP on TCP port 389 and did not directly work against LDAPS on port 636, where TLS protects the connection differently. Microsoft’s October 2026 fix, KB5126646, tracks identity changes during processing and discards remaining requests in a signed record if the connection identity changes. The article recommends patching domain controllers and servers, enforcing LDAP signing and channel binding together, restricting LDAP on port 389 where possible, and reducing NTLM use.

  • LDAP signing failed in this case because the server verified a whole protected data record only once, then allowed the connection’s authenticated identity to change before processing another request in that same record.
  • The Windows SMB client’s request for NTLM message signing, normally an obstacle to SMB-to-LDAP relaying, was required for the described reauthentication technique to work; HTTP/WebDAV authentication did not produce the same result.
  • Enforcing LDAP signing and channel binding together was still insufficient before the patch when plain LDAP on TCP port 389 remained reachable, because channel binding applies only to TLS-protected LDAP connections.
  • Microsoft’s fix did not change NTLM cryptography; it added connection identity tracking so the server discards any remaining requests after an identity switch occurs within a signed record.
  • The article states that an attacker could establish the initial signed LDAP session using valid domain credentials or, where accepted, an anonymous NTLM SASL context, potentially reducing the privileges needed to begin the attack.

Researchers found a flaw in Windows Server systems that manage user accounts and access across an organization, allowing an attacker to trick one server into proving its identity and then use that trust to make unauthorized changes. The issue affected Windows Server domain controllers from 2016 through 2025 before fixes released in September and October 2026, even when protections intended to prevent this kind of impersonation were enabled. In the worst case, an attacker could take control of the organization’s account system and gain access across the entire network.

OPEN SOURCE ↗

This is a high-impact technical finding affecting Windows Server domain controllers from 2016 onward before the October 2026 patch, enabling NTLM relay to LDAP despite required signing. Successful exploitation could allow domain-controller takeover and complete domain and forest compromise, making the patch and mitigations broadly relevant to Active Directory environments.

Cloudflare Introduces a Faster TypeScript Compiler Written in Rust

Cloudflare has brought tsrs, a Rust port of the TypeScript compiler, into its Oxc toolchain, claiming up to 8× faster type checking and roughly 70% lower memory use than TypeScript 7.0 in matched tests. The project is collaborating with Microsoft’s TypeScript team, with some optimizations already being upstreamed into TypeScript 7.1.
KEY POINTS
  • 01Cloudflare announced on October 20 that it is bringing tsrs, a Rust port of the TypeScript compiler, into its Oxc toolchain, with its VoidZero team responsible for development and maintenance.
  • 02Cloudflare reports that tsrs is up to eight times faster and uses about 70% less memory than TypeScript 7.0 when compared using the same number of type-checking workers.
  • 03The tsrs project began after Owner.com found that checking its roughly 37,000-file TypeScript backend took 80 seconds and 19 GiB of memory with a single-threaded TypeScript 7.0 check.
  • 04Microsoft’s TypeScript team is collaborating with tsrs maintainers, and some optimizations found in tsrs are contributing to TypeScript 7.1.
  • 05The @tsrs/wasm package can check in-memory project files in browsers, but its current WebAssembly build is single-threaded and does not support watch mode or an editor language server.

Cloudflare announced on October 20 that it is bringing tsrs, a Rust port of the TypeScript compiler, into its Oxc toolchain. VoidZero, which Cloudflare acquired in June, will develop and maintain the project alongside its existing Rust-based tools such as Oxc, Rolldown, Oxlint, and Oxfmt. The project originated at Owner.com, where type checking a large TypeScript backend consumed enough time and memory to make running several coding agents on a laptop impractical.

Cloudflare reports that, in matched configurations with the same number of type-checking workers, tsrs can be up to eight times faster and use about 70% less memory than TypeScript 7.0. The company notes that benchmark results vary with machine size and compiler settings, and tsrs uses more memory by default in exchange for faster checking. Microsoft’s TypeScript team is collaborating with the maintainers, says some improvements are not solely the result of using Rust, and is bringing optimizations discovered through tsrs into TypeScript 7.1.

The Rust implementation is also intended to make type checking practical in constrained environments through WebAssembly. The @tsrs/wasm package can check in-memory project files in browsers, although it currently runs on one thread, lacks watch mode and language-server support, and has a 4 GiB memory limit per instance. Cloudflare and the Oxc team are working to maintain compatibility with the official compiler, merge related work from tsc-rs, and resolve remaining differences such as diagnostic ordering.

  • The reported performance advantage depends heavily on matching compiler settings and machine resources; tsrs uses additional memory by default to increase checking speed, so headline benchmark figures are not directly comparable across all configurations.
  • The TypeScript team says much of tsrs’s speed does not come solely from Rust, and optimizations identified in the Rust port are already helping make the official TypeScript 7.1 compiler faster and leaner.
  • A faster compiler could also enable type-aware linting in Oxlint, allowing related development tools in the Oxc ecosystem to use the compiler’s understanding of code.
  • The Rust implementation is intended to support browser and Cloudflare Worker environments where checking can happen near the code, but the current WebAssembly version is limited to one thread, lacks watch mode and editor support, and is capped at 4 GiB of memory.
  • The main long-term challenge is behavioral compatibility rather than creating the initial port: tsrs maintainers are still resolving differences from the official compiler, including the order in which errors are reported.

Cloudflare is taking over development of tsrs, a version of TypeScript’s code-checking tool rewritten in Rust, which it says can run much faster while using far less computer memory. This matters to teams with very large TypeScript projects, especially those running several AI coding helpers at once, because code checks can otherwise consume enough time and memory to make laptops struggle. Microsoft’s TypeScript team is working with the project and is incorporating some of its improvements into the official tool, while Cloudflare also aims to make these checks work inside browsers and other constrained environments.

OPEN SOURCE ↗

This is a specific product and open-source tooling development event involving Cloudflare, Microsoft, and Rust-based TypeScript compiler ports. It has limited direct cybersecurity impact, though faster and lower-memory code checking could matter to developers maintaining large codebases and security tooling.
