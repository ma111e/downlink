Alpine Linux rebuilds GitLab after attempted RCE attack

Alpine Linux rebuilt its GitLab infrastructure and reset passwords after attackers attempted to exploit the critical CVE-2026-97229 GitLab RCE flaw. No compromise was confirmed, but incomplete logs meant the project could not rule out code execution or exposure of GitLab data and secrets.
KEY POINTS
  • 01Attackers attempted to exploit CVE-2026-97229 against Alpine Linux’s GitLab development infrastructure on October 20–21, causing eight worker-process crashes.
  • 02CVE-2026-97229 is a maximum-severity GitLab remote-code-execution flaw involving the Onigmo regular-expression compiler bundled with Ruby.
  • 03Alpine Linux initially deployed unpatched GitLab versions, and its custom container image lacked the Ruby patch required to fix the flaw even after an upgrade to GitLab 19.3.6.
  • 04Alpine found no evidence of altered commits, packages, or releases through October 27, but rebuilt its GitLab instance because missing logs prevented it from ruling out code execution.
  • 05Alpine advised GitLab users to reset their passwords and use the alpinelinux/gitlab:19.3.6 image published October 27, which includes Ruby 3.3.13 and addresses the flaw.

Attackers attempted to exploit CVE-2026-97229 in Alpine Linux’s GitLab development infrastructure on October 20–21. The maximum-severity flaw affects GitLab’s CI/CD regular-expression compiler, Onigmo, bundled with Ruby, and can allow unauthenticated code execution through a specially crafted CI/CD configuration. The attempts caused eight GitLab worker crashes, with four described as partially successful but not apparently completing exploitation.

Alpine found no evidence of altered repository commits, packages, or releases through October 27, but could not rule out code execution because relevant logs and outbound-connection records were unavailable. It rebuilt the GitLab server from scratch and reset passwords because the instance hosts development repositories, code review, CI jobs, and the build recipes used for Alpine packages. Alpine initially used GitLab 19.3.4 and later 19.3.6, but its custom container image lacked the Ruby patch needed to fix the issue; it advised users to pull the October 27 alpinelinux/gitlab:19.3.6 image containing Ruby 3.3.13.

  • Updating GitLab alone did not resolve the issue for Alpine because its custom container image lacked the required Ruby patch, unlike GitLab’s official packages.
  • Although Alpine found no evidence of tampering, missing logs and absent outbound-connection records prevented it from conclusively excluding a successful break-in, leading it to rebuild the server.
  • Alpine stated that signing keys were not stored on the GitLab server, limiting the risk that those keys were exposed during the incident.
  • The attackers downloaded Alpine’s GitLab container image, which Alpine said may indicate preparation for a supply-chain attack.

Attackers tried to use a serious flaw in Alpine Linux’s code-hosting system, GitLab, which is used to manage the software and updates that Alpine produces. Alpine found no proof that anyone got in or changed its software, but missing records meant it could not be certain, so it rebuilt the system from scratch and reset passwords. This matters because Alpine Linux is widely used as a base for Docker application containers, so a successful break-in could potentially have spread altered software to many downstream users.
