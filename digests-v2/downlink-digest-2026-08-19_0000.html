BOFScale: A CDN-Fronted Tailnet from a BOF-PE

NetSPI details BOFScale, an in-memory BOF-PE implementation of Tailscale that lets implants join a CDN-fronted Headscale tailnet over standard WebSockets without drivers, services, disk state, or child processes. The key defensive takeaway is to hunt for unusual in-process Go/Tailscale artifacts, permissive random named pipes, local SOCKS5 listeners, and WebSocket traffic using DERP or TS2021 subprotocols from non-Tailscale processes.
KEY POINTS
  • 01BOFScale consists of three tools: a modified in-process Tailscale daemon called tailscaled, a C++ BOF-PE client called tailscale, and a SOCKS5-based port forwarder called socksportfwd.
  • 02The modified Tailscale implementation makes both DERP relay traffic and the TS2021 control protocol use standard RFC 6455 WebSocket connections so Headscale and DERP can sit behind CloudFront or Fastly.
  • 03The tailscaled component runs inside the implant process with userspace networking, in-memory state, no kernel driver, no Windows service, no disk state, and no child processes after startup.
  • 04The included Headscale Docker Compose stack configures Headscale, embedded DERP, and Headplane to operate behind a CDN, with Logtail disabled, client-verified DERP, ephemeral node cleanup, and auto-approved subnet route advertisements.
  • 05The article provides defensive guidance including YARA rules for BOFScale components and network hunting for WebSocket upgrades using DERP or TS2021 subprotocols from unexpected processes.

NetSPI describes BOFScale, an implementation that runs the entire Tailscale daemon inside an implant process as a BOF-PE. The setup uses three tools: a modified in-process tailscaled daemon, a lightweight C++ tailscale client, and socksportfwd for forwarding local ports through the daemon’s SOCKS5 server. The article explains that this allows C2 traffic to use a Tailscale network layer without a driver, service, disk state, or child processes.

A central change is patching Tailscale so both DERP relay traffic and the TS2021 control protocol can use standard RFC 6455 WebSocket connections. This allows DERP servers and a self-hosted Headscale control plane to sit behind CloudFront or Fastly, because the traffic appears at the CDN edge as ordinary WebSocket upgrade requests with derp or ts2021 subprotocols. The included Headscale stack uses Docker Compose to run Headscale, embedded DERP, and Headplane with CDN-oriented configuration, client-verified DERP, disabled Logtail, and ephemeral node cleanup.

On the implant side, tailscaled defaults to userspace networking, in-memory state, no log upload, and a random named pipe used by the client for local API commands. Because userspace networking does not let ordinary victim-host processes route directly into the tailnet, socksportfwd binds a local TCP port and relays inbound connections through the daemon’s SOCKS5 proxy to a tailnet target. The article also provides defensive guidance, including YARA rules for the BOFScale components and hunting for DERP or TS2021 WebSocket traffic from unexpected processes.

  • A stock Tailscale client will not work with the described CDN-fronted Headscale setup because CloudFront and Fastly reject Tailscale’s normal non-standard upgrade mechanisms, so both the implant and the operator’s attack VM need the modified WebSocket-capable build.
  • The implant-side daemon should run in a sacrificial process because the Go runtime may crash after the BOF-PE is unmapped, and the article says the practical way to stop it is to kill that host process rather than rely on graceful shutdown.
  • The daemon’s local SOCKS5 server binds to 0.0.0.0:1080 rather than loopback, making it visible to any host that can reach the compromised machine on that port and giving defenders a concrete local-network hunting opportunity.
  • The named pipe used by the daemon is randomly generated but deliberately uses a permissive world-access security descriptor, which differs from a legitimate Tailscale installation and can help distinguish BOFScale activity.
  • The article’s strongest network-level detection depends on seeing inside TLS traffic: defenders need to observe WebSocket upgrade headers and identify DERP or TS2021 subprotocols coming from a process other than the legitimate tailscaled.exe service.

NetSPI describes BOFScale, a set of tools that can run Tailscale inside a hidden implant process and send its traffic through common web services like CloudFront or Fastly so it looks like ordinary secure web traffic. This matters because a compromised Windows computer could be quietly connected to an operator-controlled private network without installing a normal service, driver, or files on disk. The people most affected are organizations whose machines may be used this way, because the traffic can be hard to separate from normal web use unless defenders look for the specific signs the article lists.

AWSHound: An OpenSource AWS OpenGraph Collector

AWSHound is a new open-source, read-only collector that turns AWS accounts or entire Organizations into BloodHound OpenGraph data so teams can find real AWS attack paths after evaluating IAM policies, SCPs, resource policies, boundaries, and conditions offline.   • 03AWSHound has separate collect, process, emit, and ingest phases, with collection using only read actions such as List, Get, and Describe and emit producing a compressed graph.zip file for BloodHound ingestion.

  • 05AWSHound currently includes collectors for IAM, Organizations, S3, KMS, SSM, EC2, Lambda, CloudFormation, and EKS, with future collectors planned for Bedrock, ECR, ECS, and CodeBuild.

AWSHound is a free, self-hosted, read-only collector that turns an AWS account or an entire AWS Organization into a BloodHound Community Edition OpenGraph dataset. It is intended to answer where an attacker or defender could move from the AWS access they currently have. The tool runs offline IAM policy evaluation before drawing edges, so BloodHound can use pathfinding to map attack pathways between AWS principals and resources.

The article emphasizes that AWS permissions are difficult to evaluate because access depends on the principal, action, resource, and request context, and because policies can come from identity policies, permissions boundaries, service control policies, resource policies, and other layers. AWSHound handles service-specific differences, such as S3 and Lambda using different same-account and cross-account composition rules, STS requiring both identity and trust policies, and KMS using a separate key-policy-centered model. It also carries unknown conditions on edges and leans toward possible attacker paths when a condition cannot be proven or disproven offline.

AWSHound’s model represents both AWS principals and resources as nodes, while edges represent concrete capabilities such as updating Lambda code, sending SSM commands, assuming roles, or creating and assuming an administrator role. The tool currently includes collectors for IAM, Organizations, S3, KMS, SSM, EC2, Lambda, CloudFormation, and EKS, and emits a compressed graph.zip file for BloodHound ingestion.   • Not every useful relationship should be traversable in attack-path analysis: AWSHound keeps facts like role trust and policy attachment visible for hunting, but prevents pathfinding from walking them unless they represent effective access.
  • AWSHound’s composite edges are actionable because they collapse combinations such as create role, attach administrator policy, set trust, and assume role into a single account-takeover edge while preserving the policy sources that made each step possible.
