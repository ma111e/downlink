StealC Is Back, and This Time It's a RAT

The StealC operator has resurfaced after Operation Endgame with Stadia, a subscription-based RAT that retains StealC’s credential-stealing code while adding hidden remote desktop control, command execution, file management, process control, and in-memory loading. Defenders should hunt for its ProgramData-based persistence, hidden scheduled tasks, Defender exclusions, and HTTP POST C2 traffic carrying Base64-encoded RC4 ciphertext.
KEY POINTS
  • 01Europol’s Operation Endgame disrupted StealC in June by seizing 326 servers and 142 domains and recovering more than 25 million stolen credentials from 385,000 infected machines.
  • 02On October 16, the StealC seller resurfaced with Stadia, a subscription-based remote-access trojan that includes StealC-derived credential theft alongside hidden desktop control, remote command execution, file exploration, process management, and loading capabilities.
  • 03Varonis Threat Labs found that Stadia contains a 26,112-byte Chromium App-Bound Encryption helper that is byte-for-byte identical to a helper present in StealC 3.5 builds.
  • 04Stadia installs under a randomized 12-character directory in C:\ProgramData\, creates a hidden scheduled task that runs at logon and every 15 minutes, and may add a Microsoft Defender exclusion for its installation directory when elevated.
  • 05The analyzed Stadia build communicates over plain HTTP with hard-coded IP-address servers, sending RC4-encrypted and Base64-encoded data in HTTP POST bodies labeled as application/json.

After Europol’s Operation Endgame disrupted StealC in June, the malware seller returned on October 16 with Stadia, a subscription-based remote access trojan. Stadia retains StealC’s credential-stealing capability but adds hidden remote desktop control, command-shell access, file browsing, process management, and file loading from disk or memory. The seller offered former StealC customers a free month of Stadia’s $900 Pro tier, aiming to bring the earlier customer base to the new platform.

Varonis Threat Labs obtained and analyzed a Stadia build and found direct code overlap with StealC 3.5, including a byte-for-byte identical Chromium App-Bound Encryption helper. The analyzed Windows executable installs in a randomized folder under C:\ProgramData\, uses a hidden scheduled task for persistence, and may add a Microsoft Defender exclusion when run with elevated privileges. It communicates with hard-coded HTTP servers using POST bodies labeled as JSON even though the data is RC4-encrypted and Base64-encoded, while its browser-theft behavior includes injecting code into legitimate Chrome, Edge, or Brave processes.

  • Stadia’s seller offered former StealC customers a free month of the $900 Pro tier, indicating an explicit effort to preserve the customer base after Operation Endgame disrupted the prior infrastructure.
  • Although Stadia’s C2 addresses, RC4 key, and access token vary by build, its HTTP requests claim to contain JSON while actually carrying Base64-encoded encrypted data, creating a behavioral network detection opportunity.
  • Its scheduled task is registered through Windows’ Component Object Model interface rather than schtasks.exe, so detections that only monitor schtasks.exe would miss this persistence method.
  • The browser-theft component creates and quickly deletes a GUID-named text file in C:\ProgramData\ containing a 64-character hexadecimal key, providing a short-lived but distinctive host artifact.

After police disrupted the StealC password-stealing operation, its seller returned four months later with Stadia, a more powerful tool that can steal account information and let criminals secretly control an infected Windows computer. People and organizations whose computers are infected could have their passwords, financial information, cryptocurrency wallets, messages, and online game or work accounts taken, while attackers can also watch screens, run commands, and move files. It shows that shutting down criminal servers can help but may not stop the people behind them, who can quickly rebuild and offer even broader tools to other criminals.

A Norwegian Toll Bill Written From a Membership Template

A phishing email impersonated Norway’s AutoPASS toll system with a small 95 NOK payment demand, but reused a Danish membership-renewal template that exposed clear inconsistencies. Although SPF and DMARC passed, behavioral analysis flagged the malicious payment link and classified the message as phishing.
KEY POINTS
  • 01A role mailbox at a Norwegian IT consultancy received a payment reminder impersonating AutoPASS that requested 95 NOK, consisting of a 60 NOK toll charge and a 35 NOK late fee.
  • 02The email contained signs of a reused Danish membership template, including a Danish HTML language declaration, the Danish sign-off “Med venlig hilsen,” a “Medlemsservice” footer, and references to suspending a membership.
  • 03The message did not provide expected toll-bill details such as a vehicle registration, passage date, or toll station, despite referring to an invoice that was not shown.
  • 04The sender’s unrelated European domain passed SPF and DMARC checks, but the payment button linked to a path on an unrelated Portuguese company website that returned HTTP 404 during analysis.
  • 05Themis assigned the message 90% confidence and flagged its button link as malicious, resulting in automatic classification of the incident as phishing.

A role mailbox at a Norwegian IT consultancy received a payment reminder impersonating AutoPASS, seeking 95 NOK for an alleged 60 NOK toll charge plus a 35 NOK late fee. The email used the display name “Siren fra Autopass” and included a “Se og betal faktura” payment button, but supplied no vehicle registration, toll-passage date, or toll-station information. It also referred to an invoice “above” that was not present. AutoPASS is Norway’s road-toll collection brand, and the article notes that it has no members whose membership could be suspended.

The message exposed signs of having been adapted from a Danish membership-renewal template, including an HTML lang="da" declaration, the Danish sign-off “Med venlig hilsen,” a “© 2026 Medlemsservice” footer, and a leftover HTML comment referencing a Renew Membership button. The sender used an unrelated European domain that passed SPF and DMARC checks, but those checks only confirmed that the domain’s server sent the mail rather than verifying an AutoPASS connection. The payment button led to a path on an unrelated Portuguese company website, which returned HTTP 404 during analysis. Themis assessed the message at 90% confidence, flagged the link as malicious, and automatically classified the incident as phishing.

  • Passing SPF and DMARC only confirmed that the sending domain’s server sent the email; it did not establish that the message genuinely came from AutoPASS.
  • A quick relationship check can expose the impersonation: AutoPASS is a road-toll collection brand and does not have members whose memberships can be suspended.
  • The reused template left multiple independent clues—Danish metadata and wording, a membership-service footer, and a leftover Renew Membership button comment—showing that brand reskinning can be detected through details beyond the sender address.
  • The article notes that a reputation-based filter had limited obvious indicators because the sender was authenticated, new to the organization, and used only one link, while behavioral analysis flagged the message as inconsistent with its claimed sender.

A Norwegian IT consultancy received a fake AutoPASS toll-payment reminder asking for 95 kroner and directing the recipient to a payment link. The email looked believable in some ways, but it mistakenly referred to a “membership,” used Danish wording, and provided none of the details a real toll bill would include, such as a vehicle number or toll crossing. This matters because scammers can use small, ordinary-looking bills to persuade people to pay or share information before they notice the inconsistencies.

The article documents a concrete phishing incident with useful indicators and a clear example of how authenticated email can still impersonate a trusted brand. Its impact appears limited to a single recipient organization, with no evidence of a broader active campaign or confirmed compromise.

eMudhra CA compromise: eight private keys, and one of them is 4

eMudhra generated eight intermediate CA private keys with catastrophically weak values—one was simply 4—allowing attackers to forge certificates for arbitrary domains until clients block or remove the affected trust chains. Browsers have revoked them, but servers, containers, CLI tools, and bundled runtimes may remain vulnerable until their CA bundles and images are updated.
KEY POINTS
  • 01eMudhra generated eight intermediate certificate authority private keys incorrectly, and the article states that all eight are below 256, with one key equal to 4.
  • 02Anyone holding one of the compromised intermediate keys could sign a certificate for any domain, enabling impersonation for clients that still trust the affected certificate chains.
  • 03Firefox and Chrome blocked the certificates on October 17, 2026, while Apple blocked them on October 19 and Microsoft blocked them on October 20.
  • 04Command-line tools, containers, CI environments, and language runtimes may still trust the compromised intermediates because many do not check certificate revocation and may carry outdated certificate bundles.
  • 05The article advises updating operating systems and certificate bundles, rebuilding container images, restarting services, and testing whether clients reject the affected certificate chains.

eMudhra generated private keys for eight intermediate certificate authorities incorrectly, with the article’s analysis finding that every key was below 256 and one was simply 4. An intermediate certificate authority can sign certificates for any domain, so possession of one of these keys could allow an attacker to create a certificate that clients accept as valid. The affected intermediates chain to emSign ECC Root CA - G3, and two were also trusted for Microsoft code signing.

Firefox and Chrome blocked the certificates on October 17, 2026, followed by Apple on October 19 and Microsoft on October 20, but many non-browser clients may still trust them. Command-line tools, container images, CI systems, language runtimes, and IoT devices can carry old certificate bundles or ignore revocation information, leaving them exposed until updated. The article recommends updating certificate bundles and relevant runtimes, rebuilding container images, restarting services, and testing affected clients against the provided domains, where a secure result is an SSL error with HTTP 000.

  • A browser and built-in command-line tools on the same macOS device can disagree about the same certificate: Apple blocks the compromised certificates at the operating-system level, while tools such as curl may still use an unchanged local certificate file.
  • Rebuilding a container is necessary because a running container retains the certificate bundle present when its image was built, even after the host or upstream base image has been updated.
  • Clients that enforce certificate transparency, including Firefox, Chrome, Edge, and Safari, could not have been attacked with these intermediates because the article says the affected certificates did not appear in transparency logs before the block.
  • Two of the compromised intermediates were trusted for Microsoft code signing, meaning the incident could also allow malware to be signed under any publisher name, not only fake website certificates.
  • The article provides a practical validation method: requests to two specified test domains should fail with an SSL error and HTTP 000, while an HTTP 200 response indicates the client still trusts the compromised chain.

eMudhra, a company trusted to help prove that websites are genuine, created eight secret signing keys so poorly that one was simply the number 4. Someone who got one of these keys could make fake website identities that appear legitimate and potentially intercept people’s connections on hostile Wi-Fi or a compromised router. Major browsers and device makers have already blocked the bad certificates, but many servers, software tools, and older internet-connected devices may still accept them until they receive updates. The problem also affects two certificates used to approve software, which could let attackers make harmful programs appear to come from a trusted publisher.

OPEN SOURCE ↗

This is a high-impact certificate authority compromise in which eight intermediate signing keys were trivially recoverable, potentially enabling forged website and code-signing certificates. Although major browsers and platforms have blocked the affected certificates, many servers, containers, command-line tools, and bundled runtimes may remain exposed until their trust stores are updated.

How to contain shadow AI, as it takes on multiple forms and spreads throughout your environment

Shadow AI now includes local models, coding assistants, agents, MCP servers, browser extensions, and other unmanaged tools, creating major data leakage, compliance, and access-control risks. Organizations should pair employee education and clear, practical AI acceptable-use policies with continuous exposure management to discover, prioritize, and remediate unauthorized AI use.
KEY POINTS
  • 01Shadow AI has expanded beyond chatbots to include local models, coding assistants, autonomous agents, browser extensions, Model Context Protocol servers, APIs, and embedded AI features across enterprise environments.
  • 02IBM reported that 43% of organizations experienced security incidents involving shadow AI assets, and the average cost of a shadow AI-related data breach was $5.39 million.
  • 03Nearly half of shadow AI security incidents resulted in data loss or compromise, while 42% caused operational disruption and 21% triggered regulatory fines, according to IBM.
  • 04The article recommends educating employees and leaders about shadow AI, understanding why employees use unapproved tools, and creating an AI acceptable-use policy with approved tools and data-handling rules.
  • 05The article recommends treating shadow AI as part of broader exposure management by maintaining an inventory of AI assets, identifying security flaws and excessive permissions, prioritizing risks, and monitoring sensitive-data flows.

Shadow AI has expanded from employees sharing work information with personal chatbots into a broad range of unapproved AI assets, including local models, coding assistants, autonomous agents, browser extensions, Model Context Protocol servers, APIs, and embedded AI features. The article gives examples such as employees connecting AI assistants to internal customer databases, granting browser extensions access to confidential CRM dashboards, and submitting proprietary source code or financial data to public AI tools. These activities can create blind spots for security teams and expose sensitive company information without IT or security approval. The article says the growth of autonomous AI agents makes shadow AI more difficult to detect and control.

IBM’s 2026 Cost of a Data Breach Report found that 43% of organizations experienced security incidents involving shadow AI assets, up from 20% the prior year, with an average shadow AI-related breach cost of $5.39 million. Almost half of these incidents resulted in data loss or compromise, 42% caused operational disruption, and 21% resulted in regulatory fines. The article recommends educating employees and leaders, understanding why staff use unapproved tools, and creating a practical AI acceptable-use policy with approved tools, data-handling rules, and clear accountability. It also recommends treating shadow AI as part of broader exposure management by maintaining an inventory of AI assets, finding flaws and excessive permissions, prioritizing risks, monitoring data flows, and preventing sensitive information from being shared through AI prompts or uploads.

  • Strictly blocking AI by default can drive employees to hide their use of productivity tools, so the article recommends practical guardrails and approved alternatives instead.
  • Employees may deliberately use unapproved AI because sanctioned tools are inadequate or because their organization lacks a clear AI strategy, making employee needs assessment a security control as well as a governance exercise.
  • The article recommends evaluating discovered AI tools individually rather than automatically banning them, including whether vendors train public models on user data, encrypt data, disclose incidents, and meet relevant compliance requirements.
  • During a 30-day period, Tenable One identified 457 million AI-related security issues across 7,000 customer environments, averaging about 62,000 AI-related exposures per customer.
  • Shadow AI risks should be correlated with an organization’s other security issues to identify paths that could lead to its most critical systems and data.

The article warns that employees are increasingly using unapproved AI tools at work, including chatbots, browser add-ons, coding helpers, and automated assistants that can access company information. This can expose private customer records, financial plans, source code, and other sensitive data without the knowledge of IT and security teams. It affects businesses and their employees, customers, and partners, and can lead to data loss, disrupted operations, regulatory fines, and expensive breaches. Organizations should teach staff about the risks, provide approved AI options and clear rules, and keep track of where AI tools are being used.

This is an evergreen best-practice article about managing shadow AI rather than coverage of a specific incident, active threat, or urgent vulnerability. It offers useful examples and cited trend data, but its primary value is general awareness, governance, and exposure-management guidance.

Localizing compliance at scale: achieving South Korea’s ISMS certification

Cloudflare has obtained South Korea’s ISMS certification after a KISA-led audit, demonstrating that its security, privacy, and data-handling controls meet Korean regulatory requirements. To support compliance, Cloudflare implemented Korea-specific itemized consent during sign-up and disabled social sign-up paths that could bypass those required consents.
KEY POINTS
  • 01Cloudflare obtained South Korea’s ISMS certification under the ISMS-P framework following an audit by KISA-appointed auditors that reviewed 80 controls over ten days.
  • 02For South Korean sign-ups, Cloudflare presents separately labeled consent items, requires agreement to three required items before account creation, and makes marketing consent optional.
  • 03Cloudflare does not offer Google, Apple, or GitHub social sign-up in South Korea because those flows would bypass its required consent form.
  • 04The Korean sign-up experience is selected using the user’s chosen country and IP-based location, with the country selected by the user overriding the IP-based default.
  • 05The ISMS certificate is valid for three years and requires an annual audit to maintain it.

Cloudflare obtained South Korea’s Information Security Management System (ISMS) certification under the ISMS-P framework after KISA-appointed auditors reviewed 80 controls over ten days. The certification examines whether security and privacy controls operate in accordance with Korean law, Korean-language requirements, and regulator expectations. It is valid for three years and requires an annual audit to remain in effect.

For South Korean users, Cloudflare changed account registration to show separate Korean-language consent items, with three required agreements that must be accepted before an account can be created and a separate optional marketing agreement. Cloudflare disabled Google, Apple, and GitHub social sign-up in South Korea because those account-creation flows would bypass the required consent form. The sign-up experience defaults based on IP-derived location, but the country selected by the user overrides that default because IP geolocation can be inaccurate.

The audit reviewed personal-information data flows, access controls, public-facing websites, event pages, the Cloudflare dashboard, consent wording, and the full lifecycle of user data through destruction. ISMS coverage is defined by the certified service boundary, including the teams, infrastructure, information assets, and personal-information flows involved, rather than by a list of named products. Cloudflare states that the certification gives Korean organizations a local assurance benchmark alongside its broader compliance certifications.

  • Cloudflare treated IP-based location only as a default because VPNs, travel, mobile carrier networks, and changing IP ownership can make it inaccurate; the country selected by the user takes precedence for the consent experience.
  • Rather than build a South Korea-only consent screen after authentication, Cloudflare removed social sign-up options in South Korea to ensure no account-creation path could bypass the required consent choices.
  • The ISMS audit required data-flow diagrams that auditors could directly examine, rather than relying on narrative descriptions of how personal information moves through Cloudflare’s systems.
  • ISMS product coverage is determined by whether a service is delivered through the certified operational, infrastructure, and data-flow boundary, not by whether the product is explicitly named on the certificate.
  • Because ISMS audits cover a specific annual period, preparations extending into another audit year required Cloudflare to update translations, evidence, and privacy documentation for the new period.

Cloudflare received South Korea’s ISMS certification after government-appointed auditors reviewed how it protects personal information and follows Korean privacy rules. People signing up from South Korea now see separate Korean-language choices for required agreements, and they cannot create an account until they actively accept the required ones; sign-up through Google, Apple, or GitHub is unavailable there because it would skip those choices. This matters to Korean customers and organizations because it provides independently verified evidence that Cloudflare’s services were reviewed against local legal and privacy expectations.

OPEN SOURCE ↗

Cloudflare’s South Korean ISMS certification is a concrete compliance milestone that may matter to organizations operating in Korea or assessing Cloudflare as a vendor. However, it is not an urgent security event, incident, vulnerability, or broadly actionable technical finding.
