Check Point warns of SmartConsole zero-day exploited in attacks

Check Point patched an actively exploited SmartConsole zero-day, CVE-2026-16232, that lets unauthenticated attackers obtain admin tokens and change security policies on exposed management servers. Admins should patch urgently, restrict Trusted Clients and management access, and check audit logs for signs of compromise.
KEY POINTS
  • 01Check Point addressed an actively exploited zero-day flaw in its SmartConsole graphical user interface admin panel.
  • 02CVE-2026-16232 is an authentication bypass vulnerability that lets unauthenticated attackers obtain an application login token and authenticate with administrator privileges.
  • 03Successful exploitation can allow attackers to change the security configuration and security policy on a vulnerable Security Management Server or Multi-Domain Security Management Server.
  • 04Check Point said remote exploitation requires internet access to the Management Server IP address and a configuration that does not restrict Trusted Clients.
  • 05CISA added CVE-2026-16232 to its Known Exploited Vulnerabilities catalog and ordered U.S. federal agencies to patch vulnerable SmartConsole instances by July 25.

Check Point Software has addressed an actively exploited zero-day flaw in its SmartConsole graphical user interface admin panel. The flaw is tracked as CVE-2026-16232 and is an authentication bypass vulnerability. It allows unauthenticated attackers to obtain an application login token that can be used to authenticate with administrator privileges.

After gaining access to a vulnerable Security Management Server or Multi-Domain Security Management Server, attackers can change the security configuration and security policy. Check Point said successful remote exploitation requires internet access to the Management Server IP address and a configuration that does not restrict Trusted Clients. The company said it is aware the vulnerability is being exploited and has affected a very small number of customers.

Admins who cannot immediately upgrade are advised to follow Check Point hardening guidance, limit Trusted Clients to trusted IP addresses or subnets, and block management access for non-authorized IP addresses. Check Point also provided a way to check SmartConsole audit logs for signs of compromise by searching for “Authentication method: application token” after running a query for listed IP addresses. CISA added CVE-2026-16232 to its Known Exploited Vulnerabilities catalog and ordered U.S. federal agencies to patch vulnerable SmartConsole instances by July 25.

  • Exposure is narrowed by two specific conditions: remote exploitation requires the Management Server IP to be reachable from the internet and Trusted Clients not to be restricted.
  • Organizations that cannot patch immediately still have concrete mitigations available: restrict Trusted Clients to trusted IP addresses or subnets and block management access from unauthorized IP addresses.
  • Check Point provided a specific audit-log hunting method, including the phrase “Authentication method: application token” and a set of IP addresses to query in SmartConsole.
  • CISA gave federal agencies an unusually short remediation window, requiring vulnerable SmartConsole instances to be patched by July 25 after adding CVE-2026-16232 to the Known Exploited Vulnerabilities catalog.
  • The article places this flaw in a pattern of recent Check Point issues exploited in the wild, citing separate Check Point vulnerabilities in 2026 and 2024 that were also tied to active exploitation.

Check Point fixed a serious flaw in its SmartConsole admin tool that attackers are already using to get administrator-level access without logging in normally. Organizations are affected if their Check Point management servers can be reached from the internet and are not limited to trusted computers. This matters because attackers who get in can change security settings and rules, and CISA has told U.S. federal agencies to patch affected systems urgently.

New msaRAT malware uses Chrome, Edge browsers to route C2 traffic

The Chaos ransomware gang is using a new Rust backdoor called msaRAT that hides its command-and-control traffic by controlling headless Chrome or Edge through the Chrome DevTools Protocol. Its use of Cloudflare Workers, WebRTC, and Twilio TURN relays makes the attacker infrastructure harder to detect and trace.
KEY POINTS
  • 01The Chaos ransomware gang is using a new Rust-based backdoor called msaRAT that routes command-and-control communication through Chrome or Edge browsers.
  • 02Cisco Talos observed recent Chaos ransomware attacks that began with email or voice phishing and continued with remote management software used for persistence.
  • 03Attackers downloaded an MSI installer posing as a Windows update, which loaded msaRAT as lib.dll directly in system memory.
  • 04msaRAT launches Chrome or Microsoft Edge in headless mode, enables the browser’s remote debugging interface, and uses the Chrome DevTools Protocol to inject JavaScript into a new browser tab.
  • 05The malware uses Cloudflare Workers, WebRTC, Twilio TURN servers, and two layers of encryption to hide the attacker’s server and make the traffic look like normal web activity.

The Chaos ransomware gang is using a new Rust-based backdoor called msaRAT that hides command-and-control communication by routing it through Chrome or Edge. Cisco Talos observed recent Chaos ransomware attacks beginning with email or voice phishing, followed by the installation of remote management software for persistence. Once inside, the attacker downloaded an MSI installer posing as a Windows update, which loaded msaRAT directly in system memory as lib.dll.

msaRAT searches for Chrome or Microsoft Edge, launches the browser in headless mode, enables the remote debugging interface, and connects through the Chrome DevTools Protocol. It opens a new browser tab and injects JavaScript that builds the communication channel, bypasses Chrome’s Content Security Policy, and registers bindings that enable communications. The browser then contacts a Cloudflare Workers endpoint to obtain WebRTC connection information and establish an encrypted channel.

Cisco Talos says the malware uses WebRTC DTLS plus ChaCha20-Poly1305 and ECDH encryption, while relaying communications through Twilio TURN servers to avoid direct peer-to-peer connections. This design prevents the attacker’s real server IP address from appearing in network traffic and makes tracing the infrastructure significantly more difficult. The article notes that blocking the workers.dev domain broadly could disrupt legitimate Cloudflare Workers deployments, and Cisco Talos published indicators of compromise for attacks using msaRAT.

  • msaRAT lowers detection risk because it does not directly connect to the attacker’s command-and-control infrastructure, instead burying its exchanges inside browser-generated web traffic.
  • The malware’s use of Cloudflare Workers and Twilio TURN means the attacker’s real server IP address does not appear in network traffic, making tracing the infrastructure significantly harder.
  • Blocking the workers.dev domain broadly would disrupt legitimate Cloudflare Workers deployments, limiting the practicality of simple domain-wide blocking as a defense.
  • The attackers intentionally omit normal WebRTC ICE candidates so communications are forced through TURN relays rather than direct peer-to-peer connections.

The article says the Chaos ransomware gang is using a new harmful program called msaRAT after tricking people through email or phone scams and installing it as a fake Windows update. The program secretly uses Chrome or Edge in the background to send instructions and data through well-known services like Cloudflare and Twilio, making the attacker harder to find. This matters because the traffic can look like normal web activity, so organizations hit by these attacks may have a harder time noticing and stopping the intruders.

Nine-Year-Old RefluXFS Linux Flaw Gives Local Users Root on Default RHEL Installs

A nine-year-old Linux kernel flaw in XFS reflink handling, CVE-2026-64600 “RefluXFS,” can let local unprivileged users overwrite root-owned files and gain persistent root on affected default RHEL-family, Fedora Server, and Amazon Linux installs. Administrators should install the fixed kernel and reboot, as there is no practical mitigation once an XFS filesystem was created with reflink enabled.
KEY POINTS
  • 01RefluXFS, tracked as CVE-2026-64600, is a Linux kernel flaw disclosed on July 22 that lets an unprivileged local user overwrite root-owned files on an XFS filesystem and gain persistent root access.
  • 02Qualys said default installations of Red Hat Enterprise Linux and its derivatives, Fedora Server, and Amazon Linux can meet the conditions for exploitation when XFS was created with reflink enabled.
  • 03Exploitation requires Linux 4.11 or later without the RefluXFS fix, an XFS filesystem created with reflink=1, and a readable target plus an attacker-writable directory on the same XFS filesystem.
  • 04The upstream fix was merged on July 16, and vendors including Red Hat and Debian have begun shipping backported kernel updates for affected releases.
  • 05Qualys said there is no practical mitigation or temporary configuration change, so systems must install the vendor kernel update and reboot to run the fixed kernel.

RefluXFS, tracked as CVE-2026-64600, is a Linux kernel flaw disclosed on July 22 that lets an unprivileged local user overwrite root-owned files on an XFS filesystem and gain persistent root access. Qualys said default installations of Red Hat Enterprise Linux and its derivatives, Fedora Server, and Amazon Linux can meet the conditions for exploitation. The overwrite happens at the block layer, survives reboot, and leaves ownership, permissions, timestamps, and the setuid bit unchanged.

Exploitation requires Linux 4.11 or later without the fix, an XFS filesystem created with reflink=1, and a readable target plus an attacker-writable directory on the same XFS filesystem. The bug is a race in XFS reflink handling where the kernel uses a stale data-fork mapping after dropping and reacquiring a lock. Qualys demonstrated the race against /etc/passwd and setuid-root binaries, and said the race usually won in under ten seconds on its test machine.

The fix was merged upstream on July 16, and vendors have begun shipping backported kernels, including Red Hat advisories across affected RHEL 8, 9, and 10 streams. Debian’s tracker listed fixes for some branches while other releases were still marked vulnerable as of July 23. Qualys said there is no practical mitigation or temporary configuration change, and the article says administrators must install the vendor kernel update, reboot, and verify the fixed kernel is running.

  • The overwrite happens at the block layer and bypasses the target file’s normal metadata path, so ownership, permissions, timestamps, and the setuid bit can remain unchanged even after a protected file is modified.
  • Qualys reported that SELinux in Enforcing mode, seccomp, kernel lockdown, and container boundaries did not stop exploitation in its testing, leaving patching and rebooting as the required response.
  • Red Hat errata for some affected streams began landing on July 14, before the public disclosure on July 22, so organizations may already be protected if they applied those kernel updates and rebooted.
  • The patch fixed two XFS helper functions with the same lock-cycle pattern, including one that the article says did not appear in the Qualys advisory.
  • Qualys said Anthropic’s restricted-access Claude Mythos Preview model found the race, wrote a working root exploit, and drafted the advisory before researchers reproduced and validated the issue.

Researchers disclosed a long-standing Linux problem called RefluXFS that can let someone who already has basic access to a computer change protected system files and become the top-level user on that machine. It can affect some default installs of Red Hat Enterprise Linux and related systems, Fedora Server, and Amazon Linux when they use a certain XFS file setup; Debian, Ubuntu, SLES, and openSUSE are generally affected only if that setup was chosen manually. This matters because the changes can survive a restart and may leave normal signs such as file ownership and timestamps unchanged, making the takeover harder to notice. The fix is to install the updated kernel from the system vendor and reboot, since the article says there is no practical temporary setting that blocks the issue.
