VMware patches vCenter zero-day exploited in attacks since September

Broadcom has patched CVE-2026-123890, a critical VMware vCenter authentication-bypass flaw that Mandiant says Chinese-linked Armory Castle exploited as a zero-day since September 2026 to gain administrator access and compromise virtualized environments. Organizations should urgently update affected vCenter deployments, as no official workaround is available.
KEY POINTS
  • 01Broadcom released security updates on November 19 to fix CVE-2026-123890, a critical VMware vCenter Server authentication-bypass vulnerability.
  • 02Mandiant and Google Threat Intelligence Group reported that the suspected Chinese state-sponsored group Armory Castle exploited the flaw in attacks beginning in early September 2026.
  • 03Exploitation can create an authenticated vCenter session as administrator@vsphere.local, enabling attackers to execute commands and obtain files such as the vCenter directory database.
  • 04Mandiant observed attackers using the BONESAW tool to create a vCenter SSO administrator account, steal the directory database, and extract SAML signing keys.
  • 05Broadcom urged organizations to install the patches promptly because no official workaround is available, although network restrictions and firewall controls can reduce exposure.

Broadcom released security updates on November 19 for CVE-2026-123890, a critical authentication-bypass flaw in VMware vCenter Server’s Directory Service. The company said an unauthenticated attacker with network access could bypass authentication and gain unauthorized access to a vulnerable vCenter server. Successful exploitation can provide administrative control over the virtual machines managed by vCenter, and Broadcom urged organizations to install the patches promptly.

Mandiant and Google Threat Intelligence Group reported that the suspected Chinese state-sponsored group Armory Castle exploited the flaw as a zero-day beginning in early September 2026. The attackers reportedly used a custom Golang tool called BONESAW to create a vCenter SSO administrator account, obtain the directory database, and extract SAML signing keys; they then used SAWSNAKE to forge authentication tokens and bypass multifactor authentication. The campaign also involved a BeyondTrust Remote Support zero-day, Linux web shells, lateral movement into VMware infrastructure, access to ESXi hosts, and theft of sensitive information from virtual machines, including Windows Active Directory database files.

  • The campaign combined a BeyondTrust Remote Support zero-day with the VMware vCenter flaw, allowing the attackers to move from compromised remote-support appliances through internal Linux systems to VMware infrastructure.
  • By stealing SAML signing keys and using SAWSNAKE, the attackers could forge login tokens, bypass multifactor authentication, and impersonate legitimate users after the initial vCenter compromise.
  • The vCenter flaw affects deployments whether or not Enhanced Linked Mode is enabled, so that setting does not limit exposure to this issue.
  • Mandiant observed multiple platform-specific tools and web shells in the campaign, including BONESAW for vCenter and SLIMSAVAGE on Linux systems, which supported persistence, credential theft, and movement through the victim environment.

Broadcom released an urgent fix for a serious flaw in VMware vCenter, software many organizations use to manage large groups of virtual computers. Google researchers say a suspected Chinese government-backed group had already used the flaw since September 2026 to get administrator-level control, steal sensitive data, and move deeper into victims’ computer systems. This matters because control of vCenter can give intruders access to many of an organization’s virtual machines, potentially exposing important files and account information.

OPEN SOURCE ↗

This is an urgent, actively exploited zero-day affecting VMware vCenter Server, a platform that can control many virtual machines in an organization. Mandiant reports a suspected Chinese state-sponsored group used the flaw to gain administrator access, steal directory data and SAML signing keys, and move into ESXi and virtualized environments.

nginx2root (CVE-2026-123007): HTTP/2 Flaw Lets Attackers Run Code on Unpatched nginx Servers

CVE-2026-123007 (nginx2root) is a critical HTTP/2 flow-control flaw affecting nginx 1.9.5–1.31.8 that can enable unauthenticated worker-process code execution under favorable conditions. Upgrade to nginx 1.31.9 or 1.30.7 (or a vendor-backported fixed package) and restart nginx; disable HTTP/2 if patching is not immediately possible.
KEY POINTS
  • 01CVE-2026-123007 is an integer-underflow flaw in nginx HTTP/2 flow-control accounting that affects nginx 1.9.5 through 1.31.8 when HTTP/2 is enabled.
  • 02The flaw can allow unauthenticated code execution as the nginx worker user, and researchers reported a public exploit that requires a direct connection, high bandwidth, an otherwise idle server, and AVX-512 support for the published full exploit.
  • 03nginx fixed the issue in versions 1.31.9 and 1.30.7 by tracking queued response bytes and including them when validating HTTP/2 WINDOW_UPDATE frames.
  • 04The article reports that its tests crashed nginx 1.31.8 workers with a proof of concept and ran a command with the full exploit, while the same attempts failed against nginx 1.31.9.
  • 05Organizations should upgrade to a fixed package and restart nginx, or temporarily disable HTTP/2 if they cannot patch immediately.

nginx released versions 1.31.9 and 1.30.7 on November 18, 2026, fixing CVE-2026-123007, an HTTP/2 flaw included in the nginx2root disclosure. The issue affects nginx 1.9.5 through 1.31.8 when HTTP/2 is enabled and can allow unauthenticated code execution as the nginx worker user. A public exploit is available, although the article reports no known exploitation in the wild as of November 19, 2026.

The flaw results from HTTP/2 connection flow-control accounting that can refund queued response data twice, allowing nginx’s send-window value to exceed its allowed maximum and eventually trigger a memory-corrupting copy. The published full exploit reportedly requires a direct connection to nginx, about 119 GiB of traffic within nginx’s one-hour connection limit, an otherwise idle server, and AVX-512 support on the server CPU; a smaller proof of concept can crash a worker without AVX-512. The article’s tests found that version 1.31.9 rejected the malicious extra credit, while vulnerable version 1.31.8 could be crashed and, under the tested conditions, made to run a command.

Organizations should upgrade to nginx 1.31.9 or 1.30.7, or install their distribution’s backported fix, and then restart nginx because a configuration reload does not replace the running binary. If patching cannot happen immediately, disabling HTTP/2 blocks both HTTP/2 nginx2root bugs, though it can break gRPC through nginx. The article also advises verifying distribution package versions rather than relying only on nginx’s displayed upstream version, since distributions may backport the fix without changing that version string.

  • A normal nginx configuration reload does not replace the vulnerable executable; a full restart or nginx on-the-fly binary upgrade is required after updating the package.
  • The public full exploit needs roughly 119 GiB of traffic on one connection within nginx’s default one-hour connection limit, making bandwidth of about 300 Mbit/s or more necessary, while the crash proof of concept sends about 60 GiB.
  • A reverse proxy that terminates HTTP/2 and connects to the vulnerable backend over HTTP/1.1 stopped the tested public exploit, but the article emphasizes that the backend still requires patching.
  • Distribution backports can leave nginx reporting an older upstream version even after the security fix is installed, so administrators must verify the installed package version against their distribution advisory rather than relying on nginx -v or external version scans.
  • HTTP/2 WINDOW_UPDATE frames do not appear in nginx access logs, so investigators should also look for a single connection receiving 60 GiB or more, worker exits on signals 6 or 11, and bursts of HEAD requests from one address.

The article describes a serious flaw in nginx, widely used software that serves websites, which can let an outsider run commands on an unpatched server without logging in. It affects nginx versions from 2015 through 1.31.8 when the newer HTTP/2 web connection feature is enabled, including some systems that use nginx to direct traffic into Kubernetes applications. Although no real-world abuse had been reported as of November 19, 2026, a public demonstration can take over a server under certain conditions, so organizations should install the fixed update and restart nginx or temporarily turn off HTTP/2.

OPEN SOURCE ↗

This is a critical patch event affecting widely deployed nginx HTTP/2 deployments, with a public exploit that demonstrated unauthenticated code execution as the nginx worker user. Although no exploitation in the wild was reported, affected organizations need to identify exposed systems, install fixed packages, and restart nginx promptly.

nginx2root: Five new nginx vulnerabilities, and how Cloudflare protects origins from the worst of them

Five newly disclosed nginx2root flaws, especially CVE-2026-123007 in HTTP/2, can enable remote code execution on vulnerable nginx servers and should be patched immediately. Cloudflare-proxied origins are shielded from the HTTP/2 and HTTP/3 attack paths only if attackers cannot directly reach the origin, but resolver and mail-proxy configurations still require remediation.
KEY POINTS
  • 01F5 and nginx.org disclosed five nginx2root memory-corruption vulnerabilities on November 18, 2026, including CVE-2026-123007, an HTTP/2 flaw affecting nginx releases since 1.9.5.
  • 02CVE-2026-123007 can be triggered when HTTP/2 is enabled and, according to the cited research, may allow an unauthenticated attacker to crash an nginx worker or run commands after bypassing address randomization protections.
  • 03Cloudflare says its HTTP proxy protects proxied origins from the HTTP/2 and HTTP/3 nginx2root attacks because client connections terminate at Cloudflare’s edge, but this protection does not apply when an attacker can reach the origin directly.
  • 04The resolver flaw CVE-2026-123634 and the mail-proxy flaw CVE-2026-113425 are not fully protected by Cloudflare’s HTTP proxy and require affected nginx configurations to be patched or restricted.
  • 05Organizations should update to nginx Open Source 1.30.7 or 1.31.9, nginx Plus 37.0.8.1 or 37.3.0.1, or a vendor-provided fixed build, then restart nginx.

F5 and nginx.org disclosed ten nginx vulnerabilities on November 18, 2026, including five memory-corruption flaws collectively called nginx2root. The flaws can allow an unauthenticated attacker to crash an nginx worker and, according to Xint’s research, potentially run commands as the nginx worker. CVE-2026-123007, affecting HTTP/2-enabled nginx releases since 2015, is presented as the most serious because HTTP/2 is commonly enabled and the bug can lead to an out-of-bounds memory read/write. Xint also identified a separate Linux SCTP kernel flaw that could reportedly elevate nginx-worker code execution to root access on the host, including from a Docker container.

Cloudflare states that its edge is not affected and that origins behind its HTTP proxy are shielded from the HTTP/2 and HTTP/3 flaws because client connections end at Cloudflare rather than reaching nginx directly. This protection does not apply if attackers can connect directly to an origin, nor does it fully protect the resolver flaw CVE-2026-123634 or the mail-proxy flaw CVE-2026-113425. Organizations are advised to update nginx Open Source to 1.30.7 or 1.31.9, nginx Plus to fixed 37.x releases, restart nginx after updating, and restrict origins so they are reachable only through Cloudflare. The article also recommends disabling unneeded HTTP/2, HTTP/3, mail-proxy, and SCTP functionality as temporary mitigations where patching is delayed.

  • Cloudflare’s protection is based on ending and recreating web connections at its edge, not on a WAF signature, so attacker-controlled HTTP/2 and HTTP/3 control messages never reach a properly isolated nginx origin.
  • The known CVE-2026-123007 attack path requires unusually large traffic volumes—about 128 GB in Rapid7’s proof of concept—over one long-lived HTTP/2 connection, creating a potentially visible pattern of massive inbound traffic with little response traffic.
  • A configuration reload does not replace nginx’s running program, so organizations must restart nginx or complete a binary upgrade after installing a fixed package.
  • The related Linux SCTP flaw can reportedly turn code execution as an nginx worker into root access on the host, including from an nginx container, and systems that do not use SCTP can block automatic loading of its kernel module as a temporary safeguard.
  • Package version output alone may be misleading because Linux distributions can backport fixes without changing nginx’s reported upstream version, so administrators need to compare full package versions with their distribution’s advisory.

Researchers disclosed five serious flaws in nginx, widely used software that runs websites and routes web traffic, which could let an unauthenticated stranger crash a server or potentially run commands on it. The greatest risk is to organizations whose nginx servers are directly reachable from the internet, while sites placed behind Cloudflare are protected from several of the most serious connection-based attacks only if their underlying servers cannot be reached directly. Because nginx is used on millions of systems and one related Linux flaw could give an intruder full control of a machine, affected organizations need to install fixes and restrict direct access quickly.

This is a critical patch event for widely deployed nginx: five disclosed memory-corruption flaws may enable unauthenticated crashes or code execution, with HTTP/2-enabled deployments broadly exposed. The article also provides concrete fixed versions, affected configurations, mitigations, and important limits on Cloudflare proxy protection.
