PHP2Shell: One Upload, Full Server

PHP2Shell comprises critical PHP flaws affecting versions back to 5.4 that can let unauthenticated attackers leak worker memory and potentially achieve remote code execution through crafted multipart uploads. Organizations should urgently inventory and patch internet-facing PHP systems to fixed releases and rotate secrets that may have resided in vulnerable worker memory.
KEY POINTS
  • 01PHP2Shell consists of two critical PHP CVEs, CVE-2026-109618 and CVE-2026-109619, that can allow unauthenticated attackers to disclose PHP worker memory and, in some cases, execute code remotely.
  • 02The article states that affected PHP versions extend back to PHP 5.4 and include deployments using PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, and LiteSpeed.
  • 03The flaws can be triggered during early multipart file-upload processing before normal application code executes, leaving stale internal references after an out-of-memory failure skips worker cleanup.
  • 04PHP fixed releases are PHP 8.5.12, 8.4.27, 8.3.36, and 8.2.35, while PHP 8.1 and older have no official release.
  • 05The article recommends prioritizing patches for internet-facing PHP servers and rotating credentials, tokens, and API keys that may have been present in PHP worker memory before remediation.

PHP2Shell refers to two critical PHP vulnerabilities, CVE-2026-109618 and CVE-2026-109619, that can allow unauthenticated attackers to read PHP worker memory and, in some cases, run code on a server. Calif reported the flaws to PHP after discovering them in August, while Wiz Research found them independently. The article says the affected versions extend back to PHP 5.4 across PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, and LiteSpeed, and that exploitation was demonstrated against current WordPress, Drupal, and Joomla container images. Because the flaws occur beneath application code and can trigger before that code executes, updated website applications alone do not protect a server running vulnerable PHP.

The described attack chain begins with a crafted multipart file upload that exhausts PHP’s memory during upload-progress handling, causing cleanup to be skipped while the worker remains available for later requests. Stale internal references can then be used to leak memory through a PHPSESSID cookie or to corrupt memory, while a separate OPcache type-confusion issue was reportedly leveraged for code execution across workers. PHP released fixes in versions 8.5.12, 8.4.27, 8.3.36, and 8.2.35; PHP 8.1 and older have no official release. The article recommends inventorying PHP installations, prioritizing internet-facing systems for patching, investigating anomalous upload behavior and process creation, and rotating secrets that may have been exposed in worker memory.

  • Because the flaws are triggered before normal PHP application code runs, application-level logs may capture little or no evidence of an attempted compromise.
  • A single out-of-memory failure can leave a reusable PHP worker in an unsafe state, allowing a later request handled by that same worker to access stale memory.
  • An unusually large or malformed PHPSESSID cookie in a server response can indicate that PHP worker memory is being returned to a client.
  • Process creation by a PHP worker while it is still parsing an upload is identified as a high-confidence signal worth investigating.
  • Fully updated WordPress, Drupal, and Joomla deployments can still be exposed because the weaknesses are in PHP itself rather than in the applications.

The article describes PHP2Shell, two serious flaws in PHP, software used by many websites, that can let an outsider send a specially made file-upload request to steal passwords and other secrets or sometimes take control of a server. The problem can affect websites using PHP even when their WordPress, Drupal, Joomla, or other website software is fully updated, because the weakness is in the underlying PHP software. Organizations running affected PHP versions should update them quickly and replace passwords, access tokens, and keys that may have been exposed, since attackers are already looking for vulnerable servers.

eMudhra incorrectly generated the private keys for eight intermediate certificate authorities, with every affected key reportedly below 256 and one equal to 4.
