AWS, Google, and Vercel Agent Flaws Let Attackers Trigger Tools Without Running the Model

Researchers found flaws in AWS, Google, and Vercel agent frameworks that let attackers trigger agent tools without a legitimate model-authorized turn, bypassing prompts and model guardrails entirely. AWS, Google, and Vercel have issued fixes, but developers must still treat tool-call data and session history as untrusted and enforce authorization at tool execution time.
KEY POINTS
  • 01Security flaws in agent infrastructure from AWS, Google, and Vercel allowed untrusted or forged instructions to reach an agent’s tools without verifying that a model turn had authorized them.
  • 02The affected products include Amazon Bedrock AgentCore’s InvokeHarness API, Google’s Agent Development Kit for Python, and Vercel AI SDK harness packages for the Codex and OpenCode coding agents.
  • 03AWS fixed the managed InvokeHarness service by rejecting caller-supplied tool-use blocks, while Google fixed the ADK issues in version 2.5.0 and Vercel patched @ai-sdk/harness-codex in version 1.0.29 and @ai-sdk/harness-opencode in version 1.0.28.
  • 04The attack conditions differed by vendor: AWS involved an authenticated remote request, Google required attacker-controlled session events or user-authored function calls, and Vercel required untrusted code already running inside a Linux sandbox.
  • 05The researchers said the exposure is limited to what each agent can already do, so an agent connected to no sensitive tools would not give an attacker useful access.

Security flaws in agent infrastructure from Amazon Web Services, Google, and Vercel allowed untrusted or forged instructions to reach agent tools without checking that a model turn had authorized them. In several attack paths, the model never ran, so system prompts, content filters, and model-level guardrails had no chance to intervene. The affected products include Amazon Bedrock AgentCore’s InvokeHarness API, Google’s Agent Development Kit for Python, and Vercel AI SDK harness packages for the Codex and OpenCode coding agents.

The issues were presented by Hedi Ingber and Aviyam Ivgi, co-founders of Stealth, as a cross-platform pattern they call CoreBreak. The vulnerable paths treated data shaped like a model-generated tool call as authoritative, allowing attackers to reach dispatch or authorization paths without persuading the model to break its rules. The conditions differed by platform: AWS involved an authenticated remote request, Google required attacker-controlled session events or user-authored function calls, and Vercel required untrusted code already running inside a Linux sandbox.

AWS fixed the managed InvokeHarness API by rejecting caller-supplied tool-use blocks, Google addressed the ADK issues in version 2.5.0, and Vercel patched @ai-sdk/harness-codex in 1.0.29 and @ai-sdk/harness-opencode in 1.0.28. The article notes that exposure is limited to what each agent can already do, so an agent without sensitive tools gives an attacker nothing. The recommended controls include rejecting caller-authored tool calls, binding tool execution to exact model events and arguments, and reducing each agent’s inherited authority.

  • The article emphasizes that these flaws are not prompt injection because the model may never run, meaning system prompts, content filters, and model-level guardrails cannot protect the tool execution path.
  • The common failure across the vendors was treating data that looked like a tool call as sufficient authority, rather than binding tool execution to a verified model event, exact tool name, arguments, session, and authorization state.
  • AWS fixed the managed AgentCore InvokeHarness service, but the article says a comparable model-skipping shortcut remains documented in the open-source Strands Python code, shifting responsibility to developers who allow untrusted callers to shape message history.
  • The practical impact depends heavily on the agent’s configured powers, since the article states that an agent with no sensitive tools, credentials, cloud roles, or write permissions gives an attacker nothing useful.
  • Vercel’s patched relay moved from trusting a process path to requiring an exact, short-lived, one-time authorization for the tool name and input observed in a model event, showing a concrete execution-layer control for this class of flaw.

  • The article frames CISA’s shift from prescribed gateway locations to required security outcomes as increasing architectural flexibility while keeping agencies accountable for visibility and telemetry quality.
  • The guidance’s softer stance on TLS inspection creates a practical tension: agencies may be compliant with a SASE architecture yet still lack the payload-level detail the article says TIC 3.0 visibility is meant to achieve.
  • The article argues that encrypted-traffic analysis using AI or machine learning can indicate suspicious behavior, but it cannot reveal whether sensitive data, AI prompts, or unauthorized application actions actually occurred inside the encrypted session.
  • Certificate-pinned applications, TLS 1.3, QUIC, and post-quantum cryptography are presented not as reasons to abandon inspection, but as engineering problems that must be handled with selective bypasses, inline proxying, protocol redirection, and compensating endpoint coverage.
  • The article highlights that trusted cloud services such as Microsoft 365 can become blind spots when agencies bypass decryption for trusted domains, because attackers can use those services for malware hosting and command-and-control.

CISA, the U.S. cyber agency, issued guidance saying federal agencies can move away from older centralized internet gateways and use newer cloud-based security setups instead. The article argues that agencies still need to be able to look inside protected internet traffic, because otherwise they may only know that data moved, not what it was or whether sensitive government information was sent somewhere unsafe. This matters for federal agencies because the new rules allow more flexible designs, but they still require strong visibility and reporting to CISA.
