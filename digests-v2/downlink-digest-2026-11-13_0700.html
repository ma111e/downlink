Hackers Exploit PHP2Shell Flaws in Check Point Gateways to Deploy TSGA Backdoor and Wipe ESXi Files

Attackers exploited unpatched PHP2Shell flaws and a Gaia OS privilege-escalation vulnerability on Check Point gateways to deploy the TSGA backdoor, then in some cases pivoted to VMware ESXi hosts to run destructive wiper malware. The campaign initially targeted Israeli organizations before expanding globally, with possible but unconfirmed links to China-aligned actors.
KEY POINTS
  • 01An unknown threat actor exploited PHP2Shell vulnerabilities in unpatched Check Point Security Gateways and used CVE-2026-123039 in Gaia OS to gain root-level control.
  • 02The campaign began on October 30, 2026, against Israeli organizations and expanded on November 2 to organizations in multiple countries and sectors.
  • 03Attackers deployed PHP web shells and the TSGA backdoor, which includes TSProxy and supports encrypted remote access, configuration theft, persistence, process injection, and firewall-log tampering.
  • 04In some compromises, the attackers used SSH access to move from a Check Point gateway to a VMware ESXi host, where they executed the destroy_v6 wiper and dropped DREAM_ANNEXATION.txt notes.
  • 05Check Point said the TSGA and TSProxy components resemble the PhiliKit toolkit associated with the China-nexus group Armory Castle, but it could not confidently attribute the campaign.

An unknown threat actor targeted unpatched Check Point Security Gateways using the PHP2Shell vulnerabilities to gain initial access. The activity began on October 30, 2026, against Israeli organizations, followed by a broader wave on November 2 affecting organizations across multiple countries and sectors. Check Point said some first-wave targets also experienced destructive actions, including the deployment of file-wiping malware.

After entering through vulnerable Mobile Access portals, the attackers exploited CVE-2026-123039, a Gaia OS DynamicCLI authorization flaw, to elevate access from the portal service account to root. They deployed PHP web shells and the persistent TSGA backdoor, which includes TSProxy for concealed attacker connections through existing appliance processes. In some cases, they used the vpxuser service account over SSH to reach VMware ESXi hosts, execute the destroy_v6 wiper, delete files, and leave DREAM_ANNEXATION.txt notes.

Check Point assessed TSGA and TSProxy as Check Point-specific components of the PhiliKit toolkit previously associated by ESET with the China-nexus Armory Castle group. Infrastructure and scanning-hour patterns also suggested possible China-aligned involvement, but Check Point said it could not confidently attribute the operation. The use of wiper malware and politically themed notes referring to the Israeli-Palestine conflict leave open several possibilities, including a false-flag operation or destructive activity intended as a distraction.

  • The attackers chained internet-facing PHP2Shell access with a local DynamicCLI flaw, turning an initial gateway compromise into root-level control of the appliance.
  • The activity began roughly one week after a security fix became available, and Check Point observed active exploitation against a couple of dozen customers.
  • TSGA is designed for long-term concealed access because it combines a standalone backdoor with TSProxy code that intercepts specially marked connections inside existing appliance processes while allowing normal traffic to continue.
  • The destructive phase was not limited to the gateway: attackers used the vpxuser service account over SSH to reach VMware ESXi hosts and run a program that overwrites and deletes files.
  • Although TSGA and TSProxy resemble tooling linked to the China-nexus Armory Castle group, Check Point said the wiper use and Israel-focused political messages prevent confident attribution.

Attackers broke into unpatched Check Point security devices used by organizations, first targeting groups in Israel and then organizations in several countries. They installed hidden programs that let them keep access, stole system settings, and in some cases moved into connected VMware systems and erased files. This matters because a compromised network security device can give attackers a foothold into an organization’s internal systems and cause both spying and serious disruption.

Critical Apache HTTP Server vulnerability can allow remote code execution (CVE-2026-119618)

Apache HTTP Server versions 2.4.55–2.4.70 with HTTP/2 enabled are affected by critical unauthenticated remote code execution flaw CVE-2026-119618; upgrade to 2.4.71 or later immediately, or disable HTTP/2 until patching is possible.
KEY POINTS
  • 01CVE-2026-119618 is a critical flaw in Apache HTTP Server's HTTP/2 module that can allow an unauthenticated remote attacker to execute arbitrary code.
  • 02Apache HTTP Server versions 2.4.55 through 2.4.70 are affected, and version 2.4.71 and later contain the fix.
  • 03The flaw is a race condition in the assign_headers() function that can cause heap corruption and be turned into remote code execution.
  • 04Organizations that cannot patch immediately can reduce exposure by disabling HTTP/2 and restricting Apache to HTTP/1.1.
  • 05The article states that there were no reports of exploitation in the wild at the time of publication.

CVE-2026-119618 is a critical vulnerability in Apache HTTP Server’s HTTP/2 module, mod_http2, affecting Apache HTTP Server versions 2.4.55 through 2.4.70. The flaw can allow an unauthenticated remote attacker to run arbitrary code with the privileges of the web server process. The article states that no exploitation in the wild had been reported at publication.

The issue is a race condition in the assign_headers() function, where improper coordination over shared resources can cause heap corruption that can be converted into remote code execution. Apache HTTP Server 2.4.71 and later fix the issue, while standalone GitHub mod_h2 builds should be updated to versions newer than 2.0.42. Organizations unable to patch immediately can reduce exposure by disabling HTTP/2 and limiting protocols to HTTP/1.1, although this does not fix the underlying flaw.

  • Servers behind a standard HTTP load balancer are not exposed in the usual setup, so what sits in front of Apache can materially change exposure.
  • Where an operating-system vendor has not yet published a fixed package, a vulnerable host may not appear as affected in Aikido detection, so administrators should also check their distribution’s tracker.
  • Disabling HTTP/2 removes the attack path but does not fix the underlying flaw, making it a temporary exposure-reduction measure rather than a replacement for upgrading.
  • In cloud environments, a compromised Apache server can provide a path toward adjacent microservices or cloud metadata endpoints.

A serious flaw in certain versions of Apache HTTP Server could let an outsider take control of a website’s server without needing a password. It affects servers using Apache versions 2.4.55 through 2.4.70 when their newer web connection feature is turned on. This matters because a compromised server could give an attacker access to the services and systems connected to it, so affected organizations should update to version 2.4.71 or turn off that feature until they can update.

OPEN SOURCE ↗

This is a critical patch advisory for Apache HTTP Server, a widely deployed web server, describing unauthenticated remote code execution in affected HTTP/2-enabled versions. Although no exploitation in the wild was reported, affected organizations should urgently upgrade to 2.4.71 or disable HTTP/2 temporarily.

Ransomware at the hypervisor layer: how attackers use ESXi and vCenter features for malicious purposes

A BlackNevas ransomware operation destroyed a virtualized environment by compromising vCenter and abusing legitimate VMware management features to enable ESXi SSH access, disrupt backups, and wipe virtual-machine data without exploiting a hypervisor vulnerability. The key defense is to treat vCenter, ESXi administration, and backup recovery as separate high-trust security boundaries with isolated identities, restricted access, and remotely retained telemetry.
KEY POINTS
  • 01A BlackNevas ransomware campaign destroyed four ESXi hosts, all virtual machines on them, two vCenter Server Appliances, and connected backup infrastructure over a 10-day period.
  • 02The attackers used legitimate VMware management interfaces rather than exploiting a hypervisor vulnerability, enabling ESXi SSH through vCenter Host Profiles before directly accessing target hosts.
  • 03After accessing a vCenter appliance through SSH as root, the attackers deployed MeshAgent and later installed a Ligolo-ng reverse tunnel as a persistent systemd service disguised as vmware-vdma.
  • 04The ransomware payload was delivered to ESXi through SFTP, staged under /tmp, tested roughly three hours before detonation, and then executed against the /vmfs virtual-machine storage path.
  • 05The attackers disrupted backup infrastructure before the ESXi impact by disabling antivirus protection, stopping backup services, encrypting recovery systems, and disrupting administrative access.

Kaspersky’s Global Emergency Response Team investigated a BlackNevas ransomware campaign that destroyed four ESXi hosts, every virtual machine on them, two vCenter Server Appliances, and connected backup infrastructure over 10 days. The attackers did not exploit an ESXi or vCenter vulnerability; instead, they used legitimate VMware management interfaces after obtaining privileged access through systems inside the organization’s perimeter. The case shows how compromise of the virtualization management plane can allow an attacker to affect many systems at once.

After logging in to a vCenter appliance through SSH as root, the attackers installed MeshAgent and a Ligolo-ng reverse tunnel disguised as a VMware-related systemd service. They used vCenter Host Profiles to enable SSH on ESXi hosts, delivered an ESXi payload through SFTP, tested it, and later ran it against the /vmfs/ storage path, while virtual machines were rapidly stopped. Backup defenses and recovery infrastructure were disrupted before the ESXi impact, reinforcing the article’s recommendation to isolate vCenter administration, hypervisor identities, backup systems, and log collection from the wider production environment.

  • A fully patched ESXi environment can still face catastrophic impact if attackers compromise vCenter, because vCenter can legitimately change host settings and enable direct access to managed hosts.
  • The combination of a Host Profile change that enables SSH and a new SSH connection from vCenter to the same ESXi host is a higher-confidence warning than either event alone.
  • Guest-based security software may only see the effects of hypervisor-side disk modification, not the ESXi process that performed it, making vCenter and ESXi logs essential for investigation.
  • Backups are not protected merely because stored data is immutable; recovery also depends on separate identities, management systems, network access, and tested restoration procedures.
  • Rebooting an affected ESXi host before collecting logs can erase evidence because ESXi may store logs on temporary memory-backed storage unless persistent scratch space or remote logging is configured.

The article describes how a ransomware group took control of an organization’s systems that run many virtual computers, then shut those computers down, damaged their data, and disrupted backups needed for recovery. The attackers did not need to break a software flaw; they used stolen or reused access and normal management features to make harmful changes. This matters because control of one central management system can let criminals disrupt many important services at once, including databases, business applications, and backup systems.

CERT-In’s AI Security Auditing Guidelines: Will Your AI System Need an Independent Audit?

CERT-In’s AI Security Auditing Guidelines use an eight-factor risk score to place AI systems into audit tiers, with Tier 2 and above requiring independent audits by CERT-In-empanelled organizations. Adding autonomous actions such as issuing refunds can raise a chatbot’s tier and trigger more frequent, stringent oversight.
KEY POINTS
  • 01CERT-In’s AI Security Auditing Guidelines v1.0, dated 4 November 2026, cover AI systems developed, procured, deployed, or operated in India, as well as systems that process Indian data or serve Indian users.
  • 02The guidelines score AI systems from 1 to 4 across eight factors, producing totals from 8 to 32 that determine one of four risk tiers and associated audit requirements.
  • 03AI systems in Tier 2 and above, with scores of 13 or higher, require an independent audit by a CERT-In-empanelled auditing organization.
  • 04A customer-facing chatbot that can autonomously issue refunds may score higher than one that only answers questions, moving from the article’s illustrative Tier 2 example to Tier 3.
  • 05AI incidents meeting CERT-In’s reportable criteria must be reported within six hours, and the article states that the existing CERT-In Directions require 180-day log retention.

CERT-In issued its Artificial Intelligence (AI) Security Auditing Guidelines v1.0 on 4 November 2026, establishing a risk-based framework for assessing the security, governance, and resilience of AI systems. The guidance covers systems developed, procured, deployed, or operated in India, as well as those processing Indian data or serving Indian users. It applies regardless of whether the underlying model is built internally, supplied by a vendor, open-weight, or accessed through an API.

Organizations score each AI system across eight factors, including impact, autonomy, data sensitivity, exposure, reversibility, sector importance, adversarial exposure, and complexity. Scores determine one of four tiers, with Tier 2 and above requiring independent audits by CERT-In-empanelled auditing organizations and higher tiers requiring more frequent or continuous assurance. The article illustrates that allowing a customer-support chatbot to issue refunds can raise its score from Tier 2 to Tier 3, while reportable AI incidents must be reported within six hours and supported by 180 days of retained logs.

  • Using a third-party AI model or API does not remove an organization’s system from audit scope, and missing vendor evidence is recorded as a scope limitation rather than proof that requirements are met.
  • Risk scoring must reflect what an AI system can actually do without credit for claimed safeguards, so a human approval control does not reduce the system’s inherent-risk score.
  • A system can be escalated to a higher tier regardless of its numerical score if it can autonomously execute transactions, code, or external communications, has privileged access, or cannot be reliably stopped or rolled back.
  • Auditors must independently validate an organization’s risk tier, and the higher tier applies when the auditor’s assessment exceeds the organization’s own assessment.
  • The guidelines instruct audit teams using AI tools to treat documents, logs, and tool outputs from the organization being audited as untrusted because they may contain attempts to manipulate the audit process.

India’s CERT-In issued guidelines for checking whether AI systems are safe, including chatbots and tools that use outside AI services. The rules apply to organizations operating in India, handling Indian data, or serving Indian users, and they become stricter when an AI tool can take actions such as sending money or accessing sensitive information. This matters because companies may need independent safety reviews, must keep records for 180 days, and may have only six hours to report serious AI-related incidents.
