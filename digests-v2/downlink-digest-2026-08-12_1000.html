Researchers disclosed a flaw in how OpenAI, Anthropic, and Google carried hidden AI reasoning between API calls. The weakness affected encrypted reasoning objects used by the providers’ reasoning APIs, where a block created in one session could be replayed into another. During testing, researchers could even hand those blocks to a weaker model in the same provider family and make it reveal hidden content.

The paper, Stealing Reasoning Traces from Proprietary LLM APIs, demonstrated abuse paths including stealing proprietary reasoning for model distillation, extracting private data from published traces, recovering harmful content hidden behind safe visible answers, and hiding prompt injections inside opaque reasoning blocks. Across 6,708 public agent trajectories, the team decoded 315,320 thinking blocks and found 704 distinct privacy artifacts from genuine user sessions after excluding benchmark sources. These included API keys, passwords, access tokens, private keys, and 64 artifacts that appeared only in hidden reasoning and not in the visible trace.

The article says the attack did not crack encryption or require encryption keys, but instead relied on intact opaque blocks being accepted and processed by the providers. The affected risk described is bounded to developers who published raw agent logs with reasoning objects intact, not arbitrary private chats for every API user. The researchers disclosed the findings to the affected providers, Microsoft, and Hugging Face, and said the demonstrated attacks stopped working after mitigations, although the article notes there has been no public vendor acknowledgment of the flaw.

  • Sanitizing only the visible text of AI agent logs was insufficient in this study because 64 recovered privacy artifacts appeared only inside hidden reasoning blocks.
  • The reported attack did not require breaking encryption or stealing encryption keys; it worked by replaying intact opaque reasoning objects that the providers’ systems accepted and processed.
  • The risk was concentrated among developers who published raw agent logs with reasoning objects intact, rather than all users of the affected AI APIs.
  • The article notes an unresolved issue: the researchers say new attacks no longer work after mitigations, but the public record does not say whether already-published reasoning blocks remain decodable.
  • Opaque reasoning blocks were shown to carry hidden prompt-injection instructions, meaning malicious directions could be transferred without appearing in the visible conversation text.

Researchers found that hidden “thinking” data saved by OpenAI, Anthropic, and Google’s AI services could be reused in a way that made weaker AI models reveal what was inside, including some API keys, passwords, access tokens, and private keys from public agent logs. This did not let anyone open random private chats, but it affected developers who shared raw AI session records that still contained these hidden blocks. The issue matters because even if the visible text was cleaned up, secrets could remain buried in hidden AI data, creating privacy and security risks when logs are published.

Control Which Package Registries Your CI Jobs and Developer Machines Use

StepSecurity argues that organizations migrating away from public package registries need visibility across both CI jobs and developer machines, because either can still silently fetch dependencies from npm, PyPI, Docker Hub, or other public sources. Its controls are positioned to detect and help enforce use of internal or secure registries so malicious or compromised packages are blocked before installation.
KEY POINTS
  • 01Many engineering organizations are moving package downloads away from public registries and behind internal registries so policies like cooldown periods and compromised package blocking apply before packages are installed.
  • 02StepSecurity says internal registries cannot show jobs or developer machines that bypass them, because they only log requests that reach the internal registry.
  • 03The Harden Runner control for CI jobs passes when a job’s network baseline contains no calls to public package registries such as registry.npmjs.org, pypi.org, or registry-1.docker.io.
  • 04The Dev Machine Guard control for developer machines reads package manager configuration files such as .npmrc and pip.conf to report the effective registry and where that value came from.
  • 05The article recommends blocking public registries at the network level in CI, centrally setting registry configuration on developer machines, and applying download-time policies at the registry itself.

The article says many engineering organizations are moving package downloads away from public registries and behind internal registries such as JFrog Artifactory, Sonatype Nexus, Cloudsmith, Google Artifact Registry, or StepSecurity Secure Registry. The goal is to apply policies like cooldown periods and compromised package blocking before a package is installed. It cites malicious versions of axios on npm, credential-stealing litellm releases on PyPI, and a republished @bitwarden/cli that stole credentials and used GitHub tokens to inject malicious workflows into CI.

The article argues that declaring a migration to an internal registry is not enough because many CI jobs and developer machines may still call public registries directly. Internal registries cannot reveal those bypasses because they only log requests that reach them. StepSecurity describes two controls on its Overview dashboard: one that checks CI jobs for actual outbound calls to public package registries, and another that checks developer machines by reading package manager configuration.

For CI, Harden Runner evaluates behavior by monitoring outbound network calls and identifying the process that made a public registry request, including attempted calls blocked by egress policy. For developer machines, Dev Machine Guard reads configuration files such as .npmrc and pip.conf and reports the effective registry and where the setting came from, with checks evaluated per device and package manager pair. The article recommends blocking public registries at the network level in CI, setting registry configuration centrally on developer machines, and applying download-time policies at the registry itself.

  • A CI job can still fail the secure-registry control even when egress blocking prevents the connection, because Harden Runner records attempted calls to public registries as evidence that the job is still trying to bypass the internal registry.
  • Developer-machine compliance is evaluated per device and package manager pair, so one laptop can pass for npm while failing for pip, pnpm, or bun because each tool resolves its registry from separate configuration.
  • The source of a registry setting is a key remediation clue: an npm built-in default means no registry was configured, user config means it was explicitly set, and a public registry written into pnpm indicates someone configured the unsafe value by hand.
  • The article frames developer machines as a direct path into CI risk, citing the @bitwarden/cli compromise where stolen GitHub tokens from a developer install were used to inject malicious workflows into pipelines.
  • Appending a device identifier to the Secure Registry API key lets package download decisions be traced back to the specific developer machine or pipeline that made the request.

The article explains that many companies are trying to make sure software downloads used by workers and automated build systems come from a safer internal source instead of directly from public sites like npm, PyPI, or Docker Hub. This matters because attackers have recently placed harmful code inside familiar packages such as axios, litellm, and @bitwarden/cli, and those downloads can steal credentials from developer computers or affect automated pipelines. StepSecurity says teams need to check both company build jobs and developer laptops, because either one may still be quietly downloading from public sources even after a company believes it has moved to a safer setup.
