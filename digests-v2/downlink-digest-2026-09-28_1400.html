JadePuffer agentic AI attacks target Azure, destroy cloud resources

Microsoft observed JadePuffer (Storm-3168) using compromised Azure service principals to rapidly map cloud environments, steal storage keys, and delete storage accounts and other resources. Resource locks and account protections blocked some destructive actions, while one exposed credential may have appeared in a public GitHub issue.
KEY POINTS
  • 01Microsoft observed two June attacks in which JadePuffer, tracked as Storm-3168, used compromised Azure service principals to discover cloud resources, collect credentials, and delete Azure Storage accounts.
  • 02The destructive activity lasted seven minutes and targeted more than 100 storage accounts as well as Azure Key Vaults, Function Apps, virtual machines, and App Services.
  • 03Azure resource locks and storage-account protections prevented the deletion of some targeted storage accounts, while attempts to delete Azure SQL databases and recovery protection locks failed.
  • 04About 30 minutes after the deletion attempts, Storm-3168 made more than 30 requests for storage account keys, most of which succeeded.
  • 05Microsoft could not determine the initial access method, but said credentials for one of the compromised service principals appeared in a public GitHub issue before the attacks.

Microsoft observed two June attacks by JadePuffer, which it tracks as Storm-3168, against Azure tenants. The actor used two compromised service principals from the same tenant: one for reconnaissance and resource discovery, and the other for discovery, credential collection, and destructive activity. Microsoft could not determine the initial access method, but said credentials for one service principal appeared in a public GitHub issue before the attacks.

The destructive phase lasted seven minutes and targeted more than 100 Azure Storage accounts, as well as Key Vaults, Function Apps, virtual machines, and App Services. The actor deleted most targeted storage accounts, while Azure resource locks and storage account-level protections prevented some deletions; attempts to delete Azure SQL databases and recovery protection locks failed. About 30 minutes later, Storm-3168 made more than 30 requests for storage account keys, most of which succeeded, and it had also attempted to remove backup and recovery protections to make restoration more difficult.

  • Azure resource locks and storage account-level protections limited the damage by preventing deletion of some targeted storage accounts.
  • The actor used two separate compromised service principals within the same tenant, with one focused on reconnaissance and the other handling discovery, credential collection, and destructive actions.
  • Attempts to delete Azure SQL databases failed because the attacker used an unsupported API version, showing that not all parts of the campaign succeeded.
  • The apparent exposure of one service principal's credentials in a public GitHub issue highlights public code and issue repositories as a place organizations should check for leaked cloud secrets.
  • The attackers tried to remove Azure Site Recovery locks before wiping resources, indicating an effort to make restoration more difficult.

Microsoft observed the JadePuffer group breaking into two Azure cloud environments by using stolen accounts that let software access the systems. The group quickly searched through resources, obtained keys to stored data, and deleted many storage accounts, while also trying to damage backups, databases, virtual machines, and web services. This matters because businesses that rely on Azure could lose important data and have a much harder time recovering if access credentials are exposed, although built-in protection locks stopped some of the damage in these cases.

In August 2026, a threat actor known as TheHatman advertised approximately 3.6 million employee records allegedly obtained from the Microsoft Azure and Entra environments of nine organizations. Cyera Research found that sampled records appeared to contain genuine corporate directory information, including names, work email addresses, phone numbers, job titles, office locations, group memberships, service accounts, and privileged accounts. However, the available evidence does not establish when or where the data was obtained, whether TheHatman personally accessed the named organizations, or whether nine separate cloud environments were compromised.

Several named organizations disputed evidence of a recent breach, and the article notes that authentic older data can be repackaged and resold. Even without passwords or customer information, directory data can provide criminals with an organizational map that supports targeted phishing, executive impersonation, and requests to reset multi-factor authentication. The article advises organizations to review who and what can read directory information, examine application permissions to Microsoft Graph, reduce standing privileges, and monitor for unusual bulk directory searches or exports.

  • Authentic directory records do not prove a recent breach because old data can be repackaged and resold while remaining accurate.
  • A single privileged application, integration, or service account with directory-reading permissions could provide broad visibility across an environment without requiring separate compromises of every organization named by the seller.
  • Information often treated as non-sensitive, such as reporting lines, job titles, and administrator identities, can become a detailed organizational map for targeted impersonation and phishing.
  • Help-desk and account-recovery processes should not regard knowledge of an employee’s manager, department, title, phone number, or administrator as reliable proof of identity because such details may already be publicly available or circulating on criminal forums.
  • AI agents can create a broader and less predictable exposure than narrowly scoped service accounts because they may retain persistent access to multiple applications, APIs, databases, and cloud resources.

A person using the name TheHatman advertised roughly 3.6 million employee-directory records said to come from nine major organizations, although the evidence does not prove that all of those companies were recently broken into. The records appear genuine and include details such as employee names, work emails, phone numbers, job titles, managers, and administrator accounts, but not passwords or customer information. This still matters because criminals can use those details to create believable fake emails or phone calls that trick employees into giving up access, so companies need to limit how much information any one account or automated tool can see.
