The Phishing Email That Read Backwards in Its Own Source

A phishing email impersonating an e-signature notice hid its visible English text by storing it backwards in the HTML and using CSS bidi override to render it normally, bypassing simple keyword and Unicode-control-character defenses. The lure passed email authentication and routed clicks through reputable trackers to a malicious bot-check page, showing why scanners need to compare rendered text with source and follow full redirect chains.
KEY POINTS
  • 01A senior executive at a national home-care services company received an e-signature completion notice whose visible text rendered normally but was stored backward in the raw HTML source.
  • 02Four inline spans used the CSS declaration `unicode-bidi:bidi-override; direction:rtl; display:inline-block` to display reversed source strings as fluent English without using Unicode control characters.
  • 03The message passed SPF and DKIM through a large email service provider, but the display name impersonated a cloud e-signature service while the authenticated sending domain was an unrelated aged business domain.
  • 04The button link routed through the sending provider's click tracker, then through a second commercial tracking service, and finally to a shared-hosting page that the platform's scanner marked malicious.
  • 05The captured landing page showed a press-and-hold human-verification card, and no credential entry fields were visible in the capture.

A senior executive at a national home-care services company received an e-signature completion notice that appeared ordinary, with a short heading and a button reading “View Completed Document.” In the raw HTML source, the visible text was stored backward, including tnemucoD detelpmoC weiV, while CSS made it render as normal English. The article classifies the case as high-severity credential harvesting, brand impersonation, obfuscation, and email service provider abuse.

The obfuscation used four inline spans with unicode-bidi:bidi-override; direction:rtl; display:inline-block, which caused reversed printable ASCII strings to display left-to-right to the recipient. The article stresses that this was not the better-known Unicode control-character technique, so stripping invisible or directional characters would not fix it. Because the inversion existed in the style layer rather than in unusual characters, ordinary keyword matching would not find the displayed phrases in the source.

The email passed SPF and DKIM through a large email service provider, and ARC was present and consistent, but the display name impersonated a cloud e-signature service while the authenticated domain was an unrelated aged business domain. The button link went through the provider’s click tracker, then a second commercial tracker, and finally to a shared-hosting page that the platform scanner marked malicious. The captured landing page showed a press-and-hold human-verification card, with no credential fields visible, and Themis returned an 84 percent confidence credential-theft classification.

  • Stripping zero-width or directional Unicode characters would not detect this lure because the obfuscation was done with CSS styling while the stored text remained ordinary printable ASCII.
  • Defenses should compare the text a recipient sees with the text stored in the email source, then reverse and re-score content when inline styles use `unicode-bidi:bidi-override` or `direction:rtl` in an otherwise left-to-right message.
  • A message can pass SPF, DKIM, and ARC while still impersonating a brand through the display name, especially when there is no effective DMARC alignment policy for the sending arrangement.
  • Stopping URL analysis at reputable tracking services can miss the final malicious destination, because this click path passed through two shared trackers before reaching the page marked malicious.
  • The press-and-hold human-verification page acted as a gate, so the platform classified the case as credential theft even though the captured page did not show credential fields.

A senior executive at a national home-care services company received an email that looked like a normal e-signature notice with a button to view a completed document, but the hidden email code stored the words backward and used styling to make them appear normal on screen. The email passed common sender checks and sent anyone who clicked through two tracking services to a page that was marked malicious and showed a human-verification screen. This matters because both people and basic filters could see something ordinary while the real message source was disguised, making unexpected document notices risky even when they appear legitimate.

How Aikido finds more vulnerabilities than Claude Security at half the cost

Aikido claims its Code Security Audit found more known vulnerabilities than Anthropic’s Claude Security and Codex Security on the same benchmark while costing significantly less. The main takeaway is that the design of the security-testing harness and cost controls can matter more than the underlying AI model alone.
KEY POINTS
  • 01Aikido compared its Code Security Audit against Anthropic’s Claude Security running on Mythos and Codex Security on the same private benchmark application with 89 known vulnerabilities.
  • 02Aikido’s Code Security Audit found 68 of 89 vulnerabilities for $75, while Claude Security found 60 of 89 for $157 and Codex Security found 58 of 89 for $125.
  • 03Aikido found eight more vulnerabilities than Claude Security, including one critical and three high-severity issues.
  • 04The article says Aikido’s approach uses lower-cost, smaller models for tasks where they are best suited and reserves expensive frontier reasoning for stages where it is most likely to affect the outcome.
  • 05The article says Claude Security did not provide a cost estimate before the run, while Aikido estimates scan cost beforehand and lets users adjust the coverage level before committing.

Aikido compared Anthropic’s Claude Security, which runs on Mythos, with Aikido Code Security Audit and Codex Security on the same private benchmark application. The benchmark contained 89 known vulnerabilities identified beforehand. Claude Security found 60 of 89 vulnerabilities for \(157, Aikido found 68 of 89 for \)75, and Codex Security found 58 of 89 for $125.

The article argues that vulnerability discovery depends heavily on the system around the model, not only on model capability. Aikido says its approach uses lower-cost, smaller models for tasks where they are best suited and reserves expensive frontier reasoning for stages where it is most likely to affect the outcome. The article says this let Aikido spend more of its budget on broader investigation, resulting in higher recall.

Aikido found eight more vulnerabilities than Claude Security, including one critical issue and three high-severity issues. The article highlights a critical cross-tenant authorization flaw that could let users change their organization assignment and access another organization’s data, as well as a timestamp-format mismatch that allowed expired API keys to remain valid. It also emphasizes cost predictability, stating that Aikido provides a pre-scan estimate and adjustable coverage level, while the Claude Security run showed the cost only after completion.

  • Using the strongest available model did not produce the best result in this benchmark, because Aikido’s broader search across more independent leads found more vulnerabilities than Claude Security running on Mythos.
  • Cost predictability is presented as a practical differentiator, since Aikido shows an estimated scan cost and lets users adjust coverage before running, while Claude Security revealed the final cost only after completion.
  • The article highlights that missed findings were not only low-impact issues, since Aikido found a critical cross-tenant authorization flaw and a timestamp-format issue that allowed expired API keys to remain valid.
  • The benchmark suggests that spending more of the budget on breadth of investigation can improve vulnerability recall compared with applying expensive frontier reasoning more broadly.

The article compares Aikido’s Code Security Audit with Anthropic’s Claude Security and Codex Security on the same test app, where 89 security problems were already known. Aikido says its tool found more of those problems while costing less, including serious issues that could let someone move into another organization’s account area or keep using expired access keys. This matters for companies choosing automated code-checking tools because missed problems can expose real customer or company data, and unexpected scan costs can grow as projects get larger.
