GitHub Actions re-enabled with Mini Shai-Hulud payload still active

Two GitHub Actions previously compromised in the Mini Shai-Hulud supply-chain campaign were re-enabled for over a week while their version tags still pointed to malicious code, potentially exposing workflows that used them. Developers should remove or pin the actions to verified clean commits, review runs since September 16, and rotate any accessible secrets.
KEY POINTS
  • 01GitHub Actions actions-cool/issues-helper and actions-cool/maintain-one-comment, previously compromised in the Mini Shai-Hulud campaign, became accessible again from September 16 through September 25 while their release tags still pointed to malicious code.
  • 02Socket reported that workflows referencing either action by a version tag could download and execute the old payload on their next run after the repositories were re-enabled.
  • 03GitHub’s dependency graph lists about 15,000 repositories depending on issues-helper, although Socket said this does not establish how many used mutable tags or were compromised.
  • 04The two actions were disabled again on September 25, causing workflows that reference them to fail instead of running the payload.
  • 05Socket recommends removing references to the actions or pinning a verified clean commit, reviewing workflow runs since September 16, and rotating secrets available to affected workflows.

Two third-party GitHub Actions previously compromised in the Mini Shai-Hulud campaign were re-enabled between September 16 and September 25 while their release tags still pointed to malicious code. The affected actions were actions-cool/issues-helper and actions-cool/maintain-one-comment, which GitHub had initially removed after their May 18 compromise. Socket reported that workflows using version tags for either action could again download and execute the old payload on their next run.

The Mini Shai-Hulud campaign affected 323 npm packages and 639 package versions, using malware that targeted developers’ tokens, credentials, and CI/CD secrets. GitHub’s dependency graph lists about 15,000 repositories depending on issues-helper, although Socket had not established how many used mutable tags rather than pinned commits or were actually compromised. GitHub disabled both actions again on September 25, causing dependent workflows to fail rather than run the payload.

Socket recommends that potentially affected developers find and remove references to the two actions or pin them to a verified clean commit. It also advises reviewing workflow runs since September 16 and rotating secrets that were accessible to workflows that ran an affected tag. The article says the exposure began on September 16 between 11:09 and 18:16 GMT+2, and it remains unclear why the repositories were restored without cleaning their release tags first.

  • Re-enabling a repository without first cleaning its existing release tags can reactivate previously introduced malicious code for workflows that rely on those tags.
  • The potentially affected actions are commonly used for issue-maintenance tasks that may run almost daily, increasing the number of opportunities for a tagged workflow to execute the payload during the exposure period.
  • GitHub’s listing of roughly 15,000 repositories dependent on issues-helper does not show how many were actually exposed, because Socket had not determined how many used mutable version tags rather than fixed commit references.
  • After GitHub disabled the actions again, affected workflows failed rather than running the payload, illustrating that an unavailable external component can be safer than one that remains available with unverified code.

Two GitHub add-ons that had previously been altered to include harmful code were turned back on for more than a week without first removing that code. Projects that used these add-ons could have automatically downloaded and run it, putting developers’ login details, access keys, and other private information at risk. The incident shows how a problem in a widely reused software component can spread to many projects, even after the original problem was thought to be contained.

OPEN SOURCE ↗

This is a concrete software supply-chain exposure involving previously compromised GitHub Actions that resumed serving malicious code to workflows using mutable version tags. It has broad relevance because GitHub’s dependency graph lists about 15,000 repositories depending on one affected action, and accessible workflow secrets may require review and rotation.

Claude Opus 5.5 uses 95% fewer em dashes, but its answers are getting longer

Arena’s analysis finds Anthropic’s Claude Opus 5.5 uses far fewer em dashes, semicolons, and shorter sentences than Opus 5, reducing common AI-writing tells. However, its average responses are slightly longer, rising from 453 to 481 words.
KEY POINTS
  • 01Arena analyzed high-reasoning Text Arena responses from August and September 2026 and reported that 10 of 12 writing measures moved in what it considered a better direction for Claude Opus 5.5 versus Opus 5.
  • 02Claude Opus 5.5 used 0.8 em dashes per 1,000 words, compared with 15.2 per 1,000 words for Opus 5, a reduction of roughly 95%.
  • 03Semicolon use fell from 6.10 to 1.64 per 1,000 words, and average sentence length declined from 12.14 words in Opus 5 to 10.03 words in Opus 5.5.
  • 04Despite its shorter sentences, Claude Opus 5.5 produced longer average answers, increasing from 453 to 481 words.

Arena’s analysis indicates that Anthropic’s Claude Opus 5.5 has changed its writing style compared with Claude Opus 5. The benchmarking tool reviewed high-reasoning Text Arena responses from August and September 2026 and said 10 of 12 writing measures moved in what it considered a better direction. The newer model uses shorter sentences and simpler wording, according to the analysis.

Claude Opus 5.5 used 0.8 em dashes per 1,000 words, compared with 15.2 for Opus 5, a reduction of roughly 95%. Semicolon use also declined from 6.10 to 1.64 per 1,000 words, while average sentence length fell from 12.14 to 10.03 words. Despite shorter sentences, average response length increased from 453 to 481 words, making Opus 5.5 the longest-writing Opus model in the comparison.

  • Claude Opus 5.5’s writing shift is not simply toward shorter output: its sentences became shorter while its average full responses became longer.
  • The roughly 95% drop in em-dash use removes one of the article’s most prominent style cues associated with AI-generated text.
  • Arena’s results indicate that the writing changes extend beyond punctuation, with 10 of 12 measured traits moving in what it considered a better direction.

An analysis by Arena says Anthropic’s Claude Opus 5.5 writes differently from the earlier Opus 5 model: it uses far fewer em dashes and semicolons and generally uses shorter, simpler sentences. People using Claude to write content may get text that has fewer of the stylistic clues often associated with AI-generated writing, although the model’s answers are slightly longer on average. This matters because these writing habits can spread across online content and make it harder for readers to rely on simple style cues to guess whether text was written by a person or an AI.

Microsoft pauses KB5002907 update after Office license deactivations

Microsoft paused the optional KB5002907 update after reports that it deactivated or, in rare cases, removed legitimate perpetual Office 2016 and Office 2019 installations. Affected users may need to reactivate Office with their product key or reinstall it if it was removed.
KEY POINTS
  • 01Microsoft paused the rollout of optional Microsoft 365 update KB5002907 while it investigates reports of unexpected effects on Office 2016 and Office 2019 devices.
  • 02Users and administrators reported that the update caused some perpetual, one-time-purchase Office 2016 and Office 2019 installations to appear as unlicensed, while some systems had Office removed entirely.
  • 03Microsoft says affected users whose Office appears unlicensed should reactivate their purchased product, and users whose Office was removed should download and reinstall their purchased Office 2016 or Office 2019 copy.
  • 04A Belgian managed service provider reported that reinstalling or migrating Office could fail on systems that combine 32-bit Office with 64-bit Microsoft Access Runtime, leaving Office removed, although Microsoft has not confirmed this cause.
  • 05Microsoft states that KB5002907 was intended for Microsoft 365 Apps installations more than 90 days out of date, but the update was also reported to have reached perpetual Office installations.

Microsoft paused the rollout of KB5002907, an optional Microsoft 365 update, after reports that it deactivated or removed perpetual Office 2016 and Office 2019 installations. The update was intended for Microsoft 365 Apps installations that were more than 90 days out of date and used the Current Channel or Monthly Enterprise Channel. Microsoft acknowledged reports of unexpected results on Office 2016 and Office 2019 devices and said it halted the rollout to prevent further impact.

Administrators and users reported that legitimate one-time-purchase Office installations began showing as unlicensed, and that re-entering the original product key restored activation in some cases. Other reports said Office was removed entirely, with Microsoft describing this outcome as rare and advising affected users to download and reinstall their purchased Office copy. One managed service provider reported that reinstallations could fail where 32-bit Office was installed alongside a 64-bit Microsoft Access Runtime, because Office setup does not allow mixed 32-bit and 64-bit Office products, though Microsoft has not confirmed that as the cause.

  • Although KB5002907 was described as an optional update for outdated Microsoft 365 Apps installations, administrators reported that it installed automatically on some customer devices and affected perpetual Office 2016 and Office 2019 licenses.
  • For some affected systems, entering the original Office product key restored activation, but other reports said users needed to sign in with a Microsoft account and select their license.
  • A reported installation failure involved a 32-bit Office 2016 or 2019 suite alongside 64-bit Microsoft Access Runtime, because Office setup does not permit mixed 32-bit and 64-bit Office products.
  • Microsoft characterizes complete Office removal as rare, while acknowledging both license deactivation and removal as possible outcomes of the update.

Microsoft paused an optional update after reports that it made legitimate one-time-purchase copies of Office 2016 and Office 2019 appear unlicensed or removed them entirely. The issue affected customers with these older Office versions, including multiple organizations whose computers were impacted at once. People may need to enter their original product key again, sign in to choose their license, or reinstall Office, which can interrupt access to work documents and applications.

OPEN SOURCE ↗

This is a concrete Microsoft update incident affecting legitimate Office 2016 and Office 2019 installations, potentially causing license deactivation or removal of Office. It is actionable for administrators supporting affected systems, but it is not an active security compromise or critical security patch.
