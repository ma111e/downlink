Exposed GitLab project email addresses let attackers push code

GitLab project incoming-email addresses contain long-lived tokens that let anyone who obtains them create issues or merge requests as the associated user, potentially enabling code changes and CI/CD abuse. Maintainers should remove exposed addresses from public documentation and reset any leaked tokens.
KEY POINTS
  • 01GitLab's "Email work item to this project" feature uses private email addresses containing a long-lived token that lets email messages be converted into project issues or tasks.
  • 02Aikido found a dozen live GitLab incoming email addresses exposed in public READMEs, contributing guides, and support pages in one afternoon.
  • 03An attacker with an exposed address can change its "-issue" suffix to "-merge-request" and create a merge request that GitLab processes as the token owner's request.
  • 04The resulting access depends on the associated user's permissions and can include code changes, CI/CD runs, private repository access, secrets, and confidential issues.
  • 05GitLab advises users to keep these addresses private and reset the token immediately if an address is leaked.

Aikido researchers found private GitLab incoming-email addresses exposed in public READMEs, contributing guides, and support pages. These addresses belong to GitLab’s “Email work item to this project” feature, which turns email messages into project issues or tasks. The addresses contain a long-lived glimt- token tied to a developer’s account.

An attacker who obtains an address can change its -issue suffix to -merge-request and have GitLab create a merge request as the token owner. GitLab does not check that the sending mailbox matches the token owner’s email, and Aikido said incoming email also bypasses IP address restrictions. Depending on the affected user’s permissions, this could enable code changes, CI/CD runs, access to private repositories, secrets, or confidential issues; maintainers should remove publicly exposed addresses and reset leaked tokens.

  • The email token is not limited to creating issues: changing the address suffix from "-issue" to "-merge-request" allows it to create merge requests as the token owner.
  • GitLab does not verify that the sender's email address matches the token owner's email, so any internet mailbox can submit messages that GitLab processes as that user.
  • Aikido found that incoming email use bypasses GitLab IP address restrictions, although the token owner's existing project permissions still limit what an attacker can do.
  • For private projects, an attacker would also need the project path and ID; the article says IDs can be brute-forced, but the path would need to be leaked.

GitLab has private email addresses that let project members turn an email into a bug report or proposed code change, but some of these addresses were posted publicly in project documents. Anyone who finds one can send messages that GitLab treats as coming from the account owner, potentially allowing changes to private code, access to private discussions, or use of stored project secrets. This can affect open-source projects and the many people and organizations that rely on their software, so maintainers should remove exposed addresses and replace their old access tokens.

AI for Offensive Security: What Works, What Does Not, and How to Adopt It

  • 04After an initial foothold, autonomous operation becomes harder because the system must track live identities, credentials, callbacks, attack paths, prior actions, and proof of privilege changes.
