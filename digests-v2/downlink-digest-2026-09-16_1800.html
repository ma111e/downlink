Iranian hackers use CHOSEN BRICK Windows malware to spy on targets

Iranian state-linked hackers are using the CHOSEN BRICK Windows spyware to target dissidents, activists, and journalists through Telegram and WhatsApp lures disguised as trusted software or documents. The malware can steal communications, capture screenshots and audio, and exfiltrate data through Telegram and cloud services.
KEY POINTS
  • 01Government agencies warned that Iranian state-linked hackers are using the CHOSEN BRICK Windows malware to target dissidents, activists, and journalists worldwide, particularly in the United States, United Kingdom, and Netherlands.
  • 02The attackers use WhatsApp or Telegram messages impersonating trusted contacts or technical support to persuade targets to open malicious files disguised as legitimate applications or documents.
  • 03CHOSEN BRICK can collect system information, capture screenshots, record microphone audio, steal email and Telegram or WhatsApp browser data, download additional files, delete files, and wipe a host system.
  • 04The malware establishes persistence through Windows Registry Run keys, adds Microsoft Defender exclusions, and uses a victim-specific Telegram bot for command-and-control.
  • 05Stolen data is sent through Telegram or cloud services including VultrObjects and StorjShare, and may be posted on pro-Iranian leak sites as harassment that can increase physical risks for dissidents abroad.

Government agencies warned that Iranian state-linked hackers are using a Windows malware strain called CHOSEN BRICK to spy on dissidents, activists, and journalists worldwide. The activity primarily targeted people in the United States, United Kingdom, and Netherlands, according to a joint advisory published by those countries’ cybersecurity agencies with the FBI. The attackers use WhatsApp or Telegram messages that impersonate trusted contacts or technical support agents to persuade targets to open malicious files. The files are disguised as familiar applications or documents, including medical-related lures.

The fake applications show convincing interfaces while silently installing CHOSEN BRICK, which persists through Windows Registry Run keys and adds Microsoft Defender exclusions. The malware can collect system details, capture screenshots, record audio, steal email and Telegram or WhatsApp browser data, download more files, delete files, and wipe an entire computer. It sends stolen information through Telegram or cloud services such as VultrObjects and StorjShare, while newer versions use SOCKS5 proxies to conceal communications. Agencies said stolen material may be posted on pro-Iranian leak sites, creating harassment and potentially increasing physical risks for dissidents abroad.

  • The attackers reportedly encourage targets to run malicious files on personal devices, using the claim that corporate security controls would block them.
  • The fake applications display convincing interfaces matching their advertised purpose while installing CHOSEN BRICK silently in the background.
  • Each infected victim is linked to a unique Telegram bot for remote control, while newer variants use SOCKS5 proxies to further hide their communications.
  • CHOSEN BRICK includes the ability to wipe an entire computer, in addition to its surveillance and data-theft functions.

Government agencies say Iranian state-linked hackers are using a Windows spying program called CHOSEN BRICK against dissidents, activists, and journalists, especially in the United States, United Kingdom, and Netherlands. The hackers send convincing messages through WhatsApp or Telegram and trick people into opening files that look like familiar apps or documents. Once installed, the program can read messages and email, take screen images, record microphone audio, and steal files. This matters because stolen information can be published on pro-Iranian leak sites, exposing targets to harassment and potentially greater physical danger.

Windows 11 KB5124008 update breaks domain trust for some users

Microsoft is investigating reports that Windows 11 KB5124008 can break Active Directory domain trust on some enterprise devices after reboot, preventing valid domain logins. Administrators suspect the Machine Identity Isolation/Credential Guard setting is involved, but Microsoft has not issued an official workaround.
KEY POINTS
  • 01Microsoft is investigating reports that the Windows 11 KB5124008 security update can break Active Directory domain trust relationships on some enterprise devices after reboot.
  • 02Affected users may be unable to sign in with valid domain credentials, while cached credentials can continue working when systems are offline.
  • 03Administrators reported that uninstalling KB5124008 and repairing the computer’s secure channel restored access, but reinstalling the update caused the problem to return.
  • 04Reports link the failures to the Machine Identity Isolation feature, particularly when it is set to enforcement mode and moves machine account credentials into Credential Guard.
  • 05Microsoft has not confirmed the root cause or published an official workaround, and its documentation warns that disabling Machine Identity Isolation after enforcement mode can also break domain authentication.

Microsoft is investigating reports that the Windows 11 KB5124008 security update breaks domain trust relationships on some enterprise systems after a reboot. Affected users can be denied access with domain trust or incorrect-password errors despite using valid credentials. Administrators reported that cached credentials still worked offline, indicating the issue is tied to domain authentication.

Reports indicate the issue may be connected to the Machine Identity Isolation feature, particularly when it is enabled in audit or enforcement mode. In enforcement mode, Windows moves the computer account secret into Credential Guard and removes the copy stored in the Local Security Authority (LSA). Some administrators restored affected devices by disabling the setting and repairing the secure channel, but Microsoft documentation warns that disabling it after enforcement mode can itself break domain authentication and may require removing and rejoining the device to the domain. Microsoft has not confirmed the root cause or published an official workaround.

  • The failures can present as incorrect-username-or-password errors even when users’ domain credentials are valid, which can make the issue appear to be a password problem rather than a computer-to-domain trust problem.
  • Cached credentials continuing to work while a device is offline provides a practical distinction: the affected users’ saved local login information may still function even though live domain authentication fails.
  • Changing Machine Identity Isolation is not a universally safe fix: some administrators restored access by setting it to disabled, but another reported that switching from audit or enforcement mode to disabled caused trust failures across systems that had never installed KB5124008.
  • One administrator reported only 11 affected devices out of roughly 256 updated Windows 11 25H2 Enterprise systems, while another reported every workstation in their environment was affected, indicating highly variable reported impact.
  • Microsoft documentation warns that turning off Machine Identity Isolation after it was enabled in enforcement mode can require removing and rejoining the device to the domain.

Microsoft is investigating reports that a recent Windows 11 security update, KB5124008, can stop some work computers from recognizing their connection to an organization’s login system after restarting. Employees may then be unable to sign in with correct work usernames and passwords, although previously saved logins can still work when the computer is offline. The problem appears to affect some organizations using Windows 11 25H2, and Microsoft has not yet confirmed the cause or published an official fix, making it a potential disruption for business operations.

Malware bypasses browser checks to force install Chrome, Edge extensions

Elastic Security Labs reports that the Brazil-focused KREMLIN banking malware bypasses Chromium integrity checks to silently install malicious Chrome and Edge extensions that steal credentials, session data, and browser activity. The campaign uses JavaScript banking-document lures, Ethereum smart contracts for payload resolution, and Internet Archive-hosted payloads.
KEY POINTS
  • 01Elastic Security Labs found that the KREMLIN banking-malware toolkit can install malicious Chrome and Edge extensions without user approval by modifying Chromium browser profile data and recreating its integrity checks.
  • 02The KREMLIN infection chain begins when a target opens a JavaScript file disguised as a bank receipt, invoice, payment record, or business document.
  • 03The malicious extension, disguised as AVSync, can steal cookies, local and session storage, capture typed form data and screenshots, inspect tabs and browsing history, intercept web requests, alter webpages, and redirect clicks.
  • 04KREMLIN campaigns use Ethereum smart contracts to locate additional payloads and have used Internet Archive-hosted JPEG images to conceal payloads.
  • 05Elastic confirmed 1,515 infected systems, almost all in Brazil, and disrupted the current campaign by registering a domain used by the malware's anti-sandbox check.

Elastic Security Labs identified a Brazil-linked banking malware operation using a toolkit called KREMLIN to silently install malicious extensions in Google Chrome and Microsoft Edge. The campaign has been active since mid-2025 and uses JavaScript files disguised as bank receipts, invoices, payment records, or business documents. After anti-sandbox checks, the malware displays a fake error while downloading Node.js, creating a scheduled task for persistence, and locating further payloads through an Ethereum smart contract.

KREMLIN modifies Chromium browser profile files after the browser closes or is terminated, enables developer mode, and recreates the cryptographic integrity checks protecting Secure Preferences. The resulting AVSync extension can steal cookies, session data, typed form data, screenshots, page source, browsing history, and HTTP request information, while also injecting content and redirecting clicks. Elastic confirmed 1,515 infected systems, almost all in Brazil, and disrupted the current campaign by registering a domain used by the malware as an anti-sandbox canary.

  • KREMLIN does not merely force-load an extension; it retrieves Chromium’s own protection keys and regenerates the checks meant to detect unauthorized preference changes, making the extension appear legitimate to the browser.
  • The malware waits for a browser to close or terminates it after detecting idle status before changing the browser profile, reducing the chance that its extension-installation changes are interrupted.
  • The operation separates payload delivery from a fixed attacker-controlled server by using Ethereum smart contracts as lookup points and hiding payloads in JPEG images hosted through the Internet Archive.
  • Elastic disrupted the active campaign by registering the domain used as an anti-sandbox check, causing the malware loader to incorrectly identify otherwise eligible systems as unsuitable for infection.

A Brazil-focused banking malware campaign has been tricking people into opening files that look like bank receipts or invoices, then secretly adding harmful extensions to Chrome and Edge. These extensions can steal passwords, login sessions, browsing information, and data typed into web forms, as well as change webpages or send people to attacker-chosen sites. Elastic identified 1,515 infected computers, almost all in Brazil, showing that ordinary browser add-ons can become a powerful way to take over sensitive online accounts without the user knowingly approving anything.

Although infections are almost entirely in Brazil, the technique targets widely used browsers and enables theft of credentials, sessions, and sensitive web data.

GitHub Actions Adds cache-mode to Limit Cache Poisoning Risk

GitHub Actions introduced cache-mode to restrict cache reads and writes per workflow or job, reducing the risk that untrusted workflows poison caches later used by privileged builds. The feature adds read, write, write-only, and none modes, but does not mitigate other risks from running untrusted code or scripts in CI.
KEY POINTS
  • 01GitHub added cache-mode to GitHub Actions to control cache access at the workflow or job level and reduce cache-poisoning risk.
  • 02Cache poisoning can allow an attacker to place malicious build artifacts or dependencies in a shared Actions cache that a trusted workflow later restores and runs.
  • 03cache-mode supports read, write, write-only, and none settings, with job-level settings overriding workflow-level settings.
  • 04GitHub recommends cache-mode: none for AI agent workflows that process untrusted issue or pull-request text.
  • 05The feature does not address other GitHub Actions risks, including checking out untrusted code, running package lifecycle scripts, or minting OIDC tokens in a runner.

GitHub added cache-mode to GitHub Actions, allowing maintainers to limit cache access for individual workflows or jobs. The feature is intended to reduce cache poisoning, in which an attacker places malicious build files or dependencies into a shared cache for a trusted workflow to later restore and run. The article links this risk to the 2024 Ultralytics PyPI compromise and the May 2026 TanStack package compromise.

cache-mode provides four options: read, write, write-only, and none, with job-level settings taking precedence over workflow-level settings. Cache access is enforced by the cache service, and reusable workflows cannot receive more access than their caller grants. GitHub recommends none for AI agent workflows that process untrusted issue or pull-request text, but notes that the feature does not address other Actions risks such as checking out untrusted code, running package lifecycle scripts, or minting OIDC tokens.

  • Build provenance and Sigstore signatures can still validate a build that used a poisoned cache, because they confirm where and when the build ran rather than the integrity of cached inputs.
  • A reusable workflow cannot gain more cache access than its caller grants, preventing a called workflow from bypassing the caller's cache restrictions.
  • The write-only setting lets a trusted branch populate a cache without restoring any existing entry, a control added after public feedback.
  • GitHub warns when a low-trust event is explicitly granted write or write-only cache access because those settings can restore cache-poisoning risk.
  • Most untrusted triggers already received read-only cache defaults in June 2026; cache-mode adds finer per-job control, a complete cache block, and service-enforced restrictions.

GitHub added a setting for its automated software-building service that lets project owners control whether a task can use or change stored build files. This helps prevent someone from slipping harmful files into shared storage so they run later in a more trusted task with access to sensitive information. The risk has already been linked to compromises involving Ultralytics, TanStack software packages, and the Cline project, affecting developers and people who use software built through GitHub. The change reduces one route for abuse, but it does not stop other dangers from running untrusted code in these automated tasks.

OPEN SOURCE ↗

GitHub’s release of cache-mode is broadly relevant to teams using GitHub Actions because it adds service-enforced controls against cache poisoning, a technique linked to recent supply-chain compromises. It is not an active incident or emergency patch, but it provides an actionable security control for widely used CI workflows.
