Skimming on the Blockchain: A Magecart Campaign That Uses EtherHiding, Found by Malvertising Scanning

Confiant uncovered a Magecart campaign called HexMage that compromises e-commerce checkouts and uses Ethereum Sepolia smart contracts as resilient staging to deliver card skimmers from rotating domains. The key takeaway is that EtherHiding has moved beyond fake-update malware into payment-card theft, with one wallet-linked infrastructure spanning dozens of merchant sites and hundreds of contracts.
KEY POINTS
  • 01Confiant tracks this Magecart card-skimming campaign as HexMage, and it was detected through malvertising scanning of ads run by compromised merchants.
  • 02The attackers compromise legitimate e-commerce storefronts, mostly WooCommerce sites, and inject a small server-side loader disguised as a Google Tag Manager code block.
  • 03The loader usually pulls ethers.js and reads an attacker-controlled smart contract on the Ethereum Sepolia testnet to retrieve a disposable skimmer delivery domain.
  • 04The skimmer overlays or replaces payment forms, steals cardholder data and billing details, exfiltrates them in base64-encoded requests, and then restores the page so the purchase appears to complete normally.
  • 05Confiant analyzed 25 victim storefronts, 20 Sepolia contracts, and 20 skimmer-hosting domains, and found the contracts shared a single owner wallet that had deployed 144 such contracts since March 2026.

Confiant uncovered and tracks a Magecart card-skimming campaign called HexMage, detected through malvertising scanning of ads run by compromised merchants. The attackers compromise legitimate e-commerce storefronts, mostly WooCommerce with some PrestaShop, Magento, and plain WordPress sites, and inject a small server-side loader disguised as a Google Tag Manager block. Confiant observed more than 40 impacted websites across at least 15 countries since roughly April 2026 and analyzed 25 victim storefronts, 20 Sepolia contracts, and 20 skimmer-hosting domains.

The campaign is significant because it applies EtherHiding, previously mostly associated in the article with fake-update and ClickFix malware delivery, to client-side payment card skimming. The loader usually pulls ethers.js, contacts a public Ethereum Sepolia RPC endpoint, and reads an attacker-controlled smart contract to obtain a disposable delivery hostname for the skimmer. Confiant found that the 20 observed contracts shared one owner wallet, which had deployed 144 matching contracts since March 2026, allowing researchers to enumerate additional infrastructure from public on-chain data.

The delivered skimmer overlays or replaces checkout payment forms tailored to specific payment gateways, captures card numbers, expiry dates, CVVs, names, billing emails, and other checkout details, and exfiltrates them in base64-encoded requests. It can restore the original page afterward so the purchase appears to complete normally, and every analyzed sample included logic to avoid showing the skimmer to logged-in staff sessions. The article also notes a second loader variant that skips the blockchain and embeds a base64-encoded skimmer URL directly, while still using the same counterfeit Google Tag Manager-style wrapper.

  • The same blockchain properties that make EtherHiding resilient for attackers also made the campaign enumerable: public getText() and owner() calls let researchers pivot from 20 observed contracts to one owner wallet, 144 deployed contracts, and 35 additional delivery domains without contacting attacker web infrastructure.
  • Detection based only on Ethereum RPC traffic would miss part of the campaign, because two captured pages used the same fake Google Tag Manager wrapper but skipped the blockchain entirely and embedded a base64-encoded skimmer URL directly.
  • A more robust detection signal is a counterfeit Google Tag Manager block that pushes gtm.start and defines GoogleTagManagerLoaderScript but never loads googletagmanager.com/gtm.js, because this pattern covered both the blockchain-backed and blockchain-free loader variants described in the article.
  • The operators had the ability to cheaply rotate delivery domains by rewriting contract storage, but Confiant found only 15 setText calls across 144 contracts in four months, suggesting the observed model was more often fresh contract deployment per campaign batch than rapid rewriting under pressure.
  • The skimmer’s admin-avoidance behavior is particularly persistence-friendly: every sample included excludeAdmins logic that aborts when a logged-in staff session is detected, so a merchant checking their own checkout while signed in may see nothing wrong.

Researchers found that criminals broke into real online stores and added hidden code to their checkout pages so shoppers’ credit card details could be stolen while purchases still appeared to complete normally. The criminals hid the address of the stealing code inside Ethereum smart contracts, making it easier for them to change where the code comes from without altering the infected store pages. This affects both the merchants, who may face payment-card liability and reputational harm, and the shoppers, whose card numbers, expiry dates, security codes, names, and emails can be stolen without anything looking unusual.

Securing Docker images

Securing Docker images is an ongoing vulnerability management process: use minimal hardened bases, remove unused packages, run with least privilege, keep secrets out of layers, pin carefully, and continuously rebuild or patch as new flaws appear. The article argues that patched drop-in replacements for the same base image versions can reduce risk without forcing disruptive distro or version migrations.
KEY POINTS
  • 01Most container vulnerabilities come from the open source packages and libraries included in the base image, including components the application may never use.
  • 02Deleting a file or package in a later Docker layer only hides it, because earlier layers remain immutable and can still contain what the base image shipped.
  • 03Securing Docker images involves shrinking the attack surface, setting permissions correctly, keeping secrets out of image layers, pinning base images carefully, and continuously re-checking images for new vulnerabilities.
  • 04A hardened image can become vulnerable over time because new vulnerabilities are disclosed against packages that are already inside it.
  • 05Aikido provides patched builds of the same base image versions teams already run, delivered as pull requests, so they can stay on tested versions while applying fixes.

The article explains that securing Docker images means controlling what goes into them and keeping them patched after they ship. A Docker image is built from immutable layers, starting with a base operating system and packages, then adding application code on top. Most container vulnerabilities come from open source packages and libraries included in the image, while other risks come from mistakes such as secrets baked into layers or containers running with root privileges.

The article says image hardening is an ongoing vulnerability management problem, not a one-time task. A hardened image can become vulnerable later because new flaws are disclosed in packages already inside it, while an end-of-life pinned image can keep running without upstream fixes. It also warns that always upgrading is not automatically safer, using the xz-utils backdoor as an example where the affected releases were newer and CISA guidance was to downgrade.

The article recommends using minimal or hardened base images, multi-stage builds, removing unused packages, running as a non-root user, using a read-only root filesystem, dropping unneeded Linux capabilities, and keeping secrets out of image layers. It also recommends pinning carefully, generating SBOMs, signing images, treating running containers as immutable, and continuously re-checking images. The article then describes three approaches to keeping base images hardened and presents Aikido Images as a way to provide patched builds of the same base image versions teams already run.

  • Deleting secrets or unwanted tools in a later Dockerfile step is not enough, because earlier image layers can still be unpacked and inspected by anyone who pulls the image.
  • Pinning a base image by digest makes builds repeatable, but it can also prevent patched images from being picked up unless the patching approach provides a fixed build of the same pinned version.
  • Always upgrading to the newest release is not automatically safer, as shown by the xz-utils backdoor, where CISA guidance was to downgrade from the affected newer versions.
  • A container image can accumulate security risk without changing at all, because new vulnerabilities may be disclosed later against packages that were already present.
  • A smaller base image can avoid entire classes of flaws; for example, Alpine was not exposed to Looney Tunables because it uses musl instead of glibc.

The article explains how Docker images, which are packaged bundles used to run apps, can include hidden security problems from the operating system parts, tools, and libraries they contain. Developers and teams that build or run apps in containers are affected because even unused tools or old pinned versions can leave known flaws or accidentally stored secrets inside an image. The real-world risk is that an attacker who breaks into an app may gain more access than needed, use vulnerable built-in software, or find secrets, so images need to be kept small, locked down, and patched over time.

Popular code generator for TanStack Query hit by supply chain worm

A popular npm package, @7nohe/openapi-react-query-codegen, was compromised with a supply-chain worm that runs during install via a binding.gyp/node-gyp sandbox escape. The malware steals developer, cloud, CI/CD, and local credentials and affected multiple published package versions.
KEY POINTS
  • 01Aikido detected TeamPCP-like malware in the npm package @7nohe/openapi-react-query-codegen, which has more than 150,000 weekly downloads and generates type-safe TanStack Query hooks from an OpenAPI schema.
  • 02The malware executes during npm install through a binding.gyp file that abuses node-gyp’s Python condition evaluation to run node 3FWCvzduYZg.js without a preinstall script in package.json.
  • 03The payload, which calls itself “Trinitite: Sponsored by Preview 2 Effects,” uses multiple layers of encryption and obfuscation and includes a credential harvester, a worm, and a destructive command.
  • 04Before running, the payload exits silently under several conditions, including Russian locale settings, certain endpoint security directories, known security-scanner environments, selected GitHub repository owners, and StepSecurity harden-runner activity.
  • 05The malware targets GitHub, npm, PyPI, RubyGems, AWS, Azure, GCP, HashiCorp Vault, Kubernetes, SSH keys, Docker credentials, environment files, crypto wallets, messaging session data, VPN configs, Claude AI files, and JFrog Artifactory tokens.

Aikido detected TeamPCP-like malware in the popular npm package @7nohe/openapi-react-query-codegen, which has more than 150,000 weekly downloads. The package generates type-safe TanStack Query hooks from an OpenAPI schema. The actor behind the malware is unclear, but the payload calls itself “Trinitite: Sponsored by Preview 2 Effects,” a phrase it uses as the description on GitHub repositories created to exfiltrate stolen data.

The malware runs during installation through a binding.gyp file, which normally configures native Node.js addon compilation. The article explains that node-gyp evaluates the conditions field in binding.gyp using Python, allowing the file to execute a Python expression that imports os and runs node 3FWCvzduYZg.js. The payload file is a 5.4 MB single-line JavaScript file with multiple layers of encryption and obfuscation, and the fully decrypted payload contains a credential harvester, a worm, and a destructive command.

Before running, the payload exits in several environments, including systems with Russian locale settings, certain endpoint security directories, known scanner credential prefixes, selected GitHub repository owners, and StepSecurity harden-runner activity. It targets GitHub tokens, npm, PyPI and RubyGems tokens, AWS, Azure, GCP, HashiCorp Vault, Kubernetes credentials, SSH keys, Docker credentials, environment files, crypto wallets, messaging session data, VPN configurations, Claude AI files, and JFrog Artifactory tokens. The article lists multiple affected versions of @7nohe/openapi-react-query-codegen as indicators of compromise.

  • The install-time execution did not rely on a package.json preinstall script, so reviews or defenses focused only on npm lifecycle scripts could miss this compromise.
  • The binding.gyp technique is notable because it turns a file normally associated with native Node.js addon compilation into a hidden execution path through node-gyp’s Python condition handling.
  • The payload specifically avoids several security research and scanning environments, including known fake credential prefixes, StepSecurity harden-runner, and named GitHub repository owners, which can reduce the chance of detection in automated analysis.
  • The malware attempts to validate some stolen credentials, such as npm tokens and AWS credentials, before exfiltrating them, indicating the stolen data is filtered for usability rather than collected blindly.
  • The compromised versions span multiple release lines of the package, so checking only the latest version would not be enough to determine exposure.

A widely used npm package called @7nohe/openapi-react-query-codegen, which helps developers generate code, was found to contain hidden harmful code in several versions. Anyone who installed the affected versions could have had sensitive login keys and files stolen from their computer or from automated software-building systems like GitHub Actions. This matters because those stolen keys can give attackers access to cloud accounts, code repositories, package publishing accounts, and other services used to build and ship software.

OpenAPI React Query Codegen Compromised in Mini Shai-Hulud npm Supply Chain Attack

The npm package @7nohe/openapi-react-query-codegen was compromised with ten malicious versions, including the current latest release, after an attacker abused a comment-triggered GitHub Actions publishing workflow to publish forked code with valid npm provenance. Users should pin to known-good versions, clear caches, and treat any systems that installed affected releases as compromised.
KEY POINTS
  • 01Ten malicious versions of the npm package @7nohe/openapi-react-query-codegen were published on August 28, 2026, and the latest tag still resolved to malicious version 3.0.4 at the time of writing.
  • 02The compromised releases execute a bundled loader during installation that decrypts an embedded AES-128-GCM payload, writes the second stage to a temporary file, executes it, and deletes it afterward.
  • 03All ten malicious versions carry valid npm provenance attestations issued through GitHub Actions trusted publishing, so npm audit signatures will not flag them.
  • 04The suspected publishing vector was a comment-triggered GitHub Actions workflow that allowed an untrusted GitHub account to publish code from a pull request fork under the repository’s trusted publishing identity.
  • 05The article advises users to pin to known-good versions 0.5.3, 1.6.2, 2.2.0, or 3.0.2 and to treat any machine or CI runner that installed an affected version as compromised.

Ten malicious versions of the npm package @7nohe/openapi-react-query-codegen were published on August 28, 2026, in two waves roughly twenty minutes apart. The compromised versions span every maintained release line, and at the time of writing all ten remained installable. The latest tag still resolved to malicious version 3.0.4, meaning a plain install would retrieve a compromised build.

The malicious releases execute attacker-controlled code during installation through a bundled loader named 3FWCvzduYZg.js. The loader is a large obfuscated JavaScript file that decrypts an embedded AES-128-GCM payload, writes a second-stage file to a temporary location, runs it, and then deletes it. The second-stage payload was still under analysis, and the article says it should be treated as arbitrary code execution in the context of the installing user.

All ten malicious versions carried valid npm provenance attestations issued through GitHub Actions trusted publishing, so npm audit signatures would not flag them. The suspected vector was a comment-triggered GitHub Actions workflow that checked only whether a comment said npm publish, then checked out pull request code from a fork and published it with trusted publishing permissions. The article advises users to pin to known-good versions, clear caches and stores, check lockfiles and SBOMs, and treat any machine or CI runner that installed an affected version as compromised.

  • Valid npm provenance did not protect users in this case because the workflow’s attestations identified the trusted GitHub Actions workflow and main branch ref while the tarballs still contained attacker-controlled code from a fork.
  • The issue_comment trigger was especially dangerous because GitHub records GITHUB_REF as the default branch for that event, making the malicious releases appear tied to the last legitimate main-branch commit in provenance data.
  • The attacker added a preinstall script in the second wave even though binding.gyp already provided an install-time execution path, indicating the later releases had a more reliable trigger for running the malicious loader.
  • The two 0.0.0 prereleases appear to have been used to test the publishing path before the main malicious release waves, using environment variables that named the release workflow, repository, and target package.
  • Maintainers using comment-triggered publishing workflows should not rely on matching comment text alone; the article specifically recommends checking the commenter’s repository association before any job with id-token: write can publish.

Someone published ten harmful versions of the @7nohe/openapi-react-query-codegen software package, including the version people get by default, by abusing a GitHub publishing setup that trusted a simple comment. Anyone who installed one of those versions could have had unknown code run on their computer or build system, so the article says to use older safe versions and treat affected machines as possibly compromised. The bigger issue is that these harmful releases still appeared to have official proof that they came from the normal publishing process, showing that this kind of proof does not always mean the code is safe.

The Video That Plays You: Fake MP4 File Carries Malicious Payload

Censys found a malware delivery chain that disguises an encrypted PowerShell payload inside a fake, non-playable MP4 file, which ultimately installs a silent NetSupport Manager client for remote access. The campaign uses rotating Cloudflare-fronted delivery hosts, MP4 carrier files, and C2 gateways to evade basic detection and maintain control of infected systems.
KEY POINTS
  • 01Censys ARC observed a Cloudflare-fronted host serving raw PowerShell over port 80 on 22 August 2026.
  • 02The delivery chain uses a PowerShell loader to retrieve a fake MP4 file that contains 6.5 MB of encrypted NetSupport client data in an ISO Base Media File Format uuid extension box.
  • 03The fake MP4 passes basic file-type checks as an MP4 but is not a playable video, and standard decoders such as ffprobe reject its truncated media structure.
  • 04Censys identified 18 builds distributed across 40 live endpoints in six autonomous systems and four countries.
  • 05The final stage installs a NetSupport Manager client into a randomized C:\Users\Public subdirectory, configures it for silent operation, and establishes persistence through the SecurityHealth Run key.

Censys ARC observed a Cloudflare-fronted host serving raw PowerShell as text/html over port 80 on 22 August 2026. The chain uses a PowerShell loader to retrieve a fake MP4 file from the same host on a different path. The file passes basic MP4 file-type checks but is not a playable video, and it ultimately carries the encrypted payload used to continue the infection chain.

The fake MP4 contains 6.5 MB of encrypted NetSupport client data inside an ISO Base Media File Format uuid extension box. A second-stage parser scans the MP4 box structure for a build-specific 16-byte selector, extracts the embedded data, and uses the key stored in the box to decrypt and decompress a nearly 17 MB PowerShell script. Censys identified 18 builds across 40 live endpoints in six autonomous systems and four countries.

The final stage installs the NetSupport Manager client into a randomized C:\Users\Public subdirectory, configures it for silent operation, and establishes persistence through a SecurityHealth Run key. The deployed client is configured to communicate with two gateway domains on port 443, one active and one staged without an A record. The article highlights detection opportunities such as flagging files that identify as MP4 but fail to decode or store nearly all their data in uuid boxes.

  • Files that identify as MP4 but fail to decode, or that store nearly all of their data in uuid boxes, are highlighted as practical detection targets for this campaign.
  • The operator’s frequent carrier rotation can break older deployments because parsers look for build-specific uuid selectors and exit when the expected selector is absent.
  • Pivoting on stable strings such as "__HideConsole" and "ProgramData" expanded Censys’s view from one initially observed host to a broader live cluster.
  • The same host serving both the initial PowerShell stage and the fake MP4 carrier created a clear infrastructure link between the early delivery step and the embedded payload transport.
  • The repeated cleanup of HKCU Explorer RunMRU in later stages suggests the chain may begin with a command entered through the Windows Run dialog, although the exact lure was not captured.

Censys found a scheme where attackers used a file that looked like an MP4 video but was not a real playable video; it secretly carried instructions that install NetSupport Manager, a legitimate remote-control tool often misused by attackers. People whose Windows computers are tricked into running the first command could have their machine quietly set up for remote access. This matters because simple file checks may say the file is a video, while it is actually being used to hide and deliver a large malicious script.
