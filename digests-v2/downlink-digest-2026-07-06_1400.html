Threat Actors Probe Gitea Docker Flaw CVE-2026-20896 13 Days After Disclosure

Threat actors have begun probing a critical Gitea Docker image flaw, CVE-2026-20896, just 13 days after disclosure. Users should upgrade to Gitea 1.26.3 or later because the bug can let unauthenticated attackers impersonate users, including admins, when reverse-proxy authentication is misconfigured.
KEY POINTS
  • 01Threat actors have been observed attempting to exploit CVE-2026-20896, a critical flaw in Gitea Docker images, according to Sysdig.
  • 02CVE-2026-20896 has a CVSS score of 9.8 and allows unauthenticated internet clients to gain elevated access because Gitea trusts the X-WEBAUTH-USER header from any source IP address.
  • 03Security researcher Ali Mustafa said the issue stems from Gitea Docker images shipping an app.ini template that hard-codes REVERSE_PROXY_TRUSTED_PROXIES = * by default.
  • 04The vulnerability affects Gitea Docker image versions before and including 1.26.2 and was fixed in version 1.26.3 by removing the wildcard and making reverse-proxy authentication opt-in.
  • 05Sysdig said it detected the first in-the-wild exploitation attempt 13 days after public disclosure, with activity so far limited to initial investigation by the threat actor.

Threat actors have been observed attempting to exploit CVE-2026-20896, a recently patched critical security flaw in Gitea Docker images, according to Sysdig. The vulnerability has a CVSS score of 9.8 and stems from Gitea trusting the X-WEBAUTH-USER header from any source IP address. This can allow an unauthenticated internet client to gain elevated access.

Security researcher Ali Mustafa said the issue came from Gitea Docker images shipping an app.ini template that hard-codes REVERSE_PROXY_TRUSTED_PROXIES = * by default. When reverse-proxy login is enabled, that wildcard trusts every source IP, so anyone who can reach the port can send an X-WEBAUTH-USER header and be authenticated as any user. Gitea’s advisory said any process that can reach the container’s HTTP port directly, rather than through the intended authenticating proxy, can impersonate a known or guessable user, with admin accounts being obvious targets.

The vulnerability affects Gitea Docker image versions before and including 1.26.2 and was fixed in version 1.26.3, which removed the wildcard and made reverse-proxy authentication opt-in. Sysdig said it detected the first in-the-wild exploitation attempt 13 days after public disclosure, and the activity so far has been related to initial investigation by the threat actor. The article notes that there are about 6,200 internet-facing Gitea instances and urges users to apply the fixes as soon as possible.

  • The official Gitea Docker image used a less safe default than Gitea’s documented configuration, replacing the localhost-only trusted proxy value with a wildcard that trusts every source IP.
  • Exposure depends not just on the vulnerable Docker image version but also on whether reverse-proxy authentication is enabled and whether the Gitea container’s HTTP port can be reached directly instead of only through the intended proxy.
  • If auto-registration is enabled, the article says using an administrator username can result in administrator access, making common admin account names especially sensitive targets.
  • Sysdig’s observation of probing only 13 days after disclosure shows that internet-facing Gitea instances had a short window before attackers began checking for the flaw.

Attackers have started checking for a serious flaw in Gitea’s official Docker images, which are used to run the Gitea software for managing code projects. The flaw can let someone reach a Gitea server and pretend to be any known user, including an administrator, without a password if a certain login setup is enabled. People and organizations running affected Gitea Docker versions up to 1.26.2 are at risk, especially among the thousands of Gitea servers visible on the internet. The main real-world concern is that attackers could gain powerful access to code-hosting systems, so users are urged to install the fixed version quickly.

Predicting MongoDB ObjectId() continuously in Rocket.Chat

Rocket.Chat had an unauthenticated file access flaw where attackers could use a valid Livechat room token to retrieve arbitrary uploaded files if they knew the file ID. Because MongoDB ObjectId values are predictable once an attacker can generate a probe ID, the researchers showed they could continuously discover and leak uploaded files until patched versions fixed the access-control check.
KEY POINTS
  • 01Aikido researchers found that an unauthenticated Rocket.Chat user could access uploaded files if they knew the file ID, and they reported the issue through HackerOne on April 21.
  • 02Rocket.Chat stored files from authenticated channels and unauthenticated Livechat in the same `/file-upload/{fileId}` location, but did not verify that the requested file belonged to the room used for access authorization.
  • 03The researchers used the Livechat feature to create an anonymous room and token, then supplied that room ID and token while requesting an arbitrary file ID to retrieve private file contents.
  • 04Because Rocket.Chat generated file IDs with MongoDB `ObjectId()`, the researchers showed that a probe upload could reveal the timestamp, static random value, and counter needed to predict other file IDs generated by the application.
  • 05Rocket.Chat fixed the issue in versions 8.5.1, 8.4.4, 8.3.6, 8.2.6, 8.1.6, 8.0.7, 7.13.9, and 7.10.13 by verifying that the requested file matches the specified room ID.

Aikido researchers found that Rocket.Chat could allow an unauthenticated user to access uploaded files if they knew the file ID. The issue was reported to Rocket.Chat through HackerOne on April 21 and was publicly disclosed as report #3687142. The article says the flaw was fixed as of June 12 in versions 8.5.1, 8.4.4, 8.3.6, 8.2.6, 8.1.6, 8.0.7, 7.13.9, and 7.10.13.

The vulnerability involved Rocket.Chat’s Livechat feature, which is enabled by default but not visible unless users navigate directly to /livechat. Files uploaded through authenticated channels and unauthenticated Livechat were stored under the same /file-upload/{fileId} path. Rocket.Chat checked whether the requester had access to the room specified in the query string, but it did not verify that the requested file actually belonged to that room.

The researchers showed that an attacker could create an anonymous Livechat visitor and room, then use that room ID and token to retrieve files from other rooms by supplying an arbitrary file ID. Because Rocket.Chat generated file IDs with MongoDB ObjectId(), the article explains that a probe upload could reveal enough information to predict other IDs. By repeatedly probing and asynchronously requesting predicted IDs, the researchers demonstrated a way to continuously identify and leak uploaded files on an affected Rocket.Chat instance.

  • Rocket.Chat’s Livechat was enabled by default but not visible unless visiting `/livechat`, making it an easy-to-miss unauthenticated attack surface.
  • The exploit did not require brute forcing MongoDB ObjectIds from scratch; a single attacker-controlled Livechat upload provided an anchor point that made nearby file IDs predictable.
  • Repeated probe uploads could shrink the search space enough to continuously discover new uploaded files rather than only recover files from a known time window.
  • The article emphasizes that MongoDB `ObjectId()` should not be treated as a secure random identifier, because its timestamp and counter structure can make IDOR flaws far more exploitable.
  • Rocket.Chat’s fix addressed the root access-control mistake by checking that the requested file actually belongs to the room used for authorization.

Researchers found that Rocket.Chat, a workplace chat app, could let someone without an account download private uploaded files by using the public Livechat feature and guessing file links. The file links were made with MongoDB ObjectId values, which look random but can be predicted after creating a sample upload, letting an attacker keep finding new files as they are added. Any organization hosting an affected Rocket.Chat instance could have exposed shared files to anyone with network access, so the article urges upgrading to fixed versions.
