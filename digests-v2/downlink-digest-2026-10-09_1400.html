  • 03The attackers performed reconnaissance, installed JSP webshells, and downloaded the XMRig cryptocurrency miner disguised as edge.exe.

Threat actors are actively exploiting two unpatched vulnerabilities in AhsayCBS backup-management software to deploy webshells and cryptocurrency miners. The activity was observed on October 7 and targeted at least five organizations. AhsayCBS is commonly used by managed service providers and system integrators.

The attackers chained CVE-2026-105133, an authentication-bypass flaw with a public exploit, with CVE-2026-105134, which enables operating-system command injection. Huntress found that AhsayCBS 10.3.4, the latest version, is affected even though the flaws were reported fixed in version 10.3.2. After gaining access, the attackers conducted reconnaissance, installed JSP webshells, and ran XMRig disguised as edge.exe, with persistence and scripts intended to hide mining activity.

Huntress recommends restricting the AhsayCBS management interface to trusted IP addresses until a patch is available and investigating indicators of compromise. For confirmed intrusions, it advises fully restoring the affected host from a safe backup because additional persistent access may have been installed. Huntress also published indicators of compromise and four Sigma detection rules for this activity.

  • The mining operation was designed to evade casual discovery by stopping when Task Manager opens and restarting when it closes.
  • The PowerShell script also terminates Task Manager at 6 p.m. local time or after it has remained open for more than an hour overnight.
  • Huntress advises a full restore from a safe backup after a confirmed compromise because the attackers may have added other persistent access methods.

How to keep AI agents within their permissions

AI agents need enforceable, action-level boundaries because valid human or service credentials can let them exceed their intended permissions. Organizations should combine narrowly scoped identities with policy enforcement at relevant controls—such as agent settings, runtime hooks, gateways, sandboxes, and target services—to stop prohibited actions without requiring approval for every task.
KEY POINTS
  • 01AI agents can exceed intended permissions when they discover and use valid but more privileged credentials available to their human user or service account.
  • 02The article argues that effective controls must evaluate the specific operation, its arguments, the account and resource involved, the identity used, and, for data operations, where output is sent.
  • 03Possible enforcement points include managed agent settings, runtime hooks, gateways, sandboxes, endpoint enforcement, credential and target-service authorization, and API-based management.
  • 04No single control covers every deployment, because locally run coding agents and hosted SaaS agents expose different opportunities for enforcement.
  • 05The article recommends starting with narrowly scoped credentials at the target service and using a shared policy source across enforcement points.

The article argues that AI agents need enforceable limits because they may use any credentials available to complete a task, including more powerful credentials that were not approved for agent use. It gives an example in which an agent investigating a failing AWS export job finds an administrator profile in a developer’s local AWS configuration and attempts to delete objects from a production S3 bucket. Although the credentials are valid, the article says the violation is that the agent used a role agents were not permitted to use.

The article describes several places to apply controls, including managed agent settings, runtime hooks, gateways, sandboxes, endpoint enforcement, scoped credentials, and API-based management. It emphasizes that controls must consider the actual operation, its arguments, the resource and account involved, the identity being used, and where retrieved data is sent. Because local coding agents and hosted SaaS agents run in different environments, the article says no single control fits every case and recommends starting with narrowly scoped credentials at the target service plus a shared policy source for enforcement points.

  • A cloud service may see an AI agent's request as if the human developer made it when both use the same valid credentials, making reliable attribution necessary for policies that distinguish agent actions from human actions.
  • Blocking a specific command is insufficient because an agent may reach the same outcome through an SDK, a different credential, or delegation, so controls must focus on the prohibited action rather than one execution path.
  • Read-only permissions alone do not fully contain risk, because an agent can still expose sensitive information depending on where retrieved data is sent.
  • For hosted agents, software on an employee's laptop may be unable to intervene because the agent and its actions occur on the vendor's servers.
  • Past agent behavior can inform decisions but cannot establish policy: an agent that usually reads data is not thereby prohibited from writing unless an explicit rule says so.

The article explains that AI assistants can accidentally use powerful login access they find and perform actions their human user did not intend, such as deleting files from a company’s storage or closing customer support cases. This can affect developers, companies using AI tools, and customers whose data or support requests are handled by those tools. The main concern is that an AI assistant may have a valid login but still be the wrong user for a sensitive action, so companies need limits that block harmful actions while allowing useful work to continue.

  • 03Noir can steal cryptocurrency without obtaining a victim's seed phrase, password, or private key by persuading the victim to approve spending permissions or sign requests.
  • 04The kit caches the pool hostname in local storage for 60 seconds and removes the cached value and retries when a host fails its readiness check.
  • 05The article reports that Noir infrastructure was observed on Cloudflare Pages and that one lure page was hosted on Netlify.

Infoblox identified a cryptocurrency wallet-drainer kit calling itself Noir while investigating a fake crypto voting page. Noir uses DNS TXT records and public DNS-over-HTTPS services to identify the currently active hosting pool for its malicious wallet-draining flow. This separates long-lived lure pages from short-lived operational infrastructure, allowing operators to redirect deployed lures by changing a DNS record rather than rebuilding the pages.

The loader races three public DNS-over-HTTPS services for the TXT record at _r.noir.black, caches the returned pool hostname for 60 seconds, and retries with a fallback if the host fails a readiness check. After a victim connects a wallet, the kit can tailor requests to the wallet’s holdings and obtain spending approvals or signatures without collecting a seed phrase, password, or private key. Captured permissions are submitted to the backend immediately, and the kit disconnects the WalletConnect session when finished, removing the malicious application from the wallet’s connected-applications list.

  • Changing a single DNS TXT record can redirect already-deployed lure pages to a replacement drainer pool without rebuilding or redistributing those lure pages.
  • Noir’s 60-second local cache deliberately matches the DNS record’s 60-second lifetime, and its retry logic removes dead hosts after infrastructure rotation.
  • The kit submits each captured approval or signature to its backend immediately, so an attacker does not need to wait for a victim to complete every prompt before acting on the permission.
  • After the malicious flow completes, Noir disconnects the WalletConnect session, removing the application from the wallet’s connected-applications list.
  • The source code contains extensive comments about defects, support cases, and operator-facing debugging, suggesting the same engine is maintained as a shared service across multiple scam themes.

Detection rules that exceed their execution budget can be terminated without returning results or an error, making an unfinished rule appear the same as a clean environment. The article argues that this is both a cost and coverage problem as cloud telemetry volumes increase. It describes how detection engineers often need data-engineering support to ensure their rules complete within their runtime budgets. CloudTrail-focused rules were especially expensive because they repeatedly parse large, dynamic JSON fields in requestParameters and responseElements.

After roughly two months of manual analysis, the team documented 34 optimization rules designed to preserve exactly the same rows, column values, grouping, filters, and detector behavior. It built an agentic pipeline that plans changes, applies the rules, runs data-engineering, cost, and behavior gates, compares pre- and post-change results, performs self-review, and requires human approval before merging. The pipeline has upgraded more than 300 detectors, with improved detectors showing paired-test runtime reductions of 15% to 60%. The article also found that terminated runs can be missing from latency metrics, producing misleadingly good percentiles, and that some full-JSON parsing changes can be slower for unusually large and deeply nested event payloads.

  • Runtime dashboards can be misleading when terminated detector runs are excluded from metrics: a detector with many terminations may show an excellent p99 because its slowest executions never reach the metrics store.
  • Flattening CloudTrail JSON fields during data ingestion was not viable for this catalog because detectors actively used 138 distinct fields across two dynamic containers, while any individual event populated only a small subset.
  • A normally beneficial change from repeated JSON lookups to one full structural parse made some detectors slower when event payloads were unusually large and deeply nested, because Spark then had to construct the entire object in memory.
  • Common Spark recommendations such as cache(), persist(), and broadcast() can reduce overall platform throughput when many detectors share compute and the upstream ETL layer already caches data.
  • Performance tuning created an opportunity to standardize older detectors and improve their alert context and MITRE ATT&CK mappings while the files were already being reviewed.
