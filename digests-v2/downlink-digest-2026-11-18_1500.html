  • 02The issue affects compatible x86-64 systems with AVX-512 VBMI support and is not reported to affect ARM64 systems, standard Java 8, Java 11, or Java 17.0.0 through 17.0.5.
  • 03Oracle and OpenJDK released fixes on November 17, 2026, and Oracle assigned the flaw a CVSS 3.1 score of 8.1 with network access, no privileges, and no user interaction required.

  • 05If patching is delayed, the article recommends temporarily disabling Base64 hardware acceleration with -XX:-UseBASE64Intrinsics or disabling AVX-512 on x86-64 systems with -XX:UseAVX=2.

CVE-2026-114938, nicknamed Java4Shell, is a critical memory-corruption flaw in OpenJDK’s optimized Base64 decoder. On compatible x86-64 systems with AVX-512 VBMI support, attacker-controlled Base64 input can cause the decoder to write beyond its allocated memory before Java rejects malformed input. Oracle assigned the issue a CVSS 3.1 score of 8.1 and described exploitation as difficult, while Calif Research assigned a CVSS 4.0 score of 9.2. Researchers demonstrated pre-authentication remote code execution against default installations of Keycloak, Jira, Confluence, Jenkins, Artifactory, and PingFederate.

The issue affects OpenJDK release lines 17, 21, 25, and 27, including several distributions built from OpenJDK, while ARM64, standard Java 8, Java 11, and Java 17.0.0 through 17.0.5 are not affected according to the article. Successful exploitation depends on the Java version, processor capabilities, and whether an application passes untrusted Base64 data to the vulnerable decoder. Oracle and OpenJDK released fixes on November 17, 2026, and organizations are advised to update affected Java runtimes, including bundled runtimes in containers and appliances. If patching is delayed, the article recommends temporarily disabling Base64 hardware acceleration with -XX:-UseBASE64Intrinsics or disabling AVX-512 on x86-64 with -XX:UseAVX=2.

  • Malformed Base64 input may still corrupt memory before Java rejects it, because the vulnerable decoder can write a full 64-byte block beyond its allocated output buffer.
  • External exposure scanning may not be sufficient to determine risk because both the precise Java runtime and the host processor’s capabilities may not be visible externally.
  • Having the required Linux CPU flags—avx512f, avx512bw, avx512vbmi, and bmi2—does not by itself establish that an application is exploitable; the application must also decode untrusted Base64 data through an affected JDK.
  • A public proof of concept reproduces the memory corruption, but the article reports no known exploitation in the wild and no CISA KEV listing as of November 18, 2026.

KEY POINTS
  • 01CVE-2026-114938, also called Java4Shell, is a heap overflow in an accelerated OpenJDK Base64 decoding routine that can write up to 62 bytes past a Java heap buffer before the decoder throws an exception.
  • 02The issue affects Java 17 from 17.0.6, Java 21, Java 25, Java 27, and some Oracle Java SE 8 Performance Pack builds on x86-64 CPUs exposing AVX-512 VBMI and related instruction-set features.
  • 03OpenJDK 8 and 11, Java 17.0.0 through 17.0.5, ARM64 systems, and x86-64 CPUs without AVX-512 VBMI are not affected.

OpenJDK and Oracle released fixes on November 17, 2026, for CVE-2026-114938, also called Java4Shell, a high-severity memory corruption flaw in the HotSpot JVM’s accelerated Base64 decoder. The flaw affects Java 17 starting with 17.0.6, Java 21, Java 25, Java 27, and certain Oracle Java SE 8 Performance Pack builds. It can allow an unauthenticated attacker to crash a Java service and, in certain application-specific conditions described by researchers, potentially achieve remote code execution.

The issue exists in a hand-written x86-64 routine used when a CPU supports AVX-512 VBMI and related instruction-set features. Malformed Base64 input with padding can cause the routine to write up to 62 bytes beyond the intended Java heap buffer before Java raises an IllegalArgumentException; the vulnerable path is used only after the decoder becomes hot enough for C2 compilation. ARM64 hosts, OpenJDK 8 and 11, Java 17.0.0 through 17.0.5, and x86-64 CPUs without AVX-512 VBMI are not affected.

Organizations should identify every Java runtime in use, including bundled runtimes and container images, and update to vendor-fixed releases before restarting all JVMs. If patching is not immediately possible, the article recommends disabling the accelerated decoder with -XX:+UnlockDiagnosticVMOptions -XX:-UseBASE64Intrinsics, which requires a restart. The article also advises prioritizing internet-facing x86-64 services on compatible AVX-512 hardware and monitoring for unexpected JVM crashes, decoder exceptions, and malformed Base64 input.

  • The vulnerable code path is not reached by a single request to a newly started JVM because the decoder must first become frequently used enough for the JVM to compile and replace it with the accelerated routine.
  • The decoder can throw an IllegalArgumentException for malformed Base64 input only after the out-of-bounds memory write has already occurred.
  • Exposure depends on both the Java version and specific CPU capabilities: ARM64 systems and x86-64 systems lacking AVX-512 VBMI do not execute the vulnerable routine.
  • The basic and URL Base64 decoders use the affected accelerated path, while the MIME decoder follows a different path.
  • A Java runtime bundled inside a third-party product or container image can remain vulnerable even if the system-installed JDK has been updated.
