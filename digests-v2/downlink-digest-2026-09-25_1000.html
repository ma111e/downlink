  • 05Microsoft recommends that customers migrate WDS-backed PXE or multicast dependencies to alternatives such as Microsoft Configuration Manager.

Microsoft plans to deprecate the Windows Deployment Services (WDS) server role starting with the next Windows Server release. WDS allows IT administrators to remotely install Windows operating systems across large numbers of computers over a network. Microsoft will stop actively developing WDS and plans to eventually retire and remove it.

The company had already reduced WDS functionality by removing boot.wim support in 2021 and disabling hands-free deployment by default for customers with the April 2026 Windows updates or later. Microsoft also stopped officially supporting native WDS deployment of standard desktop Windows operating systems beginning with Windows 11, limiting it to Windows Server deployment or custom deployment environments. The WDS role, services, management tools, interfaces, and PXE boot functionality will remain available and supported on currently supported Windows Server releases, including Windows Server 2025 and earlier, according to their servicing lifecycles.

Microsoft Configuration Manager operating system deployment is not affected, but organizations using WDS-backed PXE or WDS-dependent multicast through Configuration Manager should migrate away from those dependencies. Non-Microsoft deployment products and independent PXE implementations that do not depend on WDS are also unaffected. Microsoft recommends that customers begin planning a move to alternatives such as Microsoft Configuration Manager.

  • The deprecation covers more than the WDS server role itself: it also includes WDS services, management tools, interfaces, and its built-in network boot capability.
  • WDS had already been narrowed before this announcement, with Microsoft no longer officially supporting its native setup engine for standard desktop Windows deployments beginning with Windows 11.
  • Microsoft Configuration Manager is not itself affected, but environments using its WDS-backed network boot or WDS-dependent multicast features must move away from those dependencies.
  • Independent network boot implementations and non-Microsoft deployment products that do not rely on WDS are not affected by the change.

Microsoft plans to phase out Windows Deployment Services, a Windows Server feature that lets organizations install Windows on many computers over a network. It will still work on currently supported Windows Server versions, but Microsoft will stop developing it and eventually remove it from a future release. Businesses and IT teams that rely on it, especially for automatically starting installations over a network, should begin moving to alternatives such as Microsoft Configuration Manager to avoid disruptions later.

Running MPC inside TEEs can add defense in depth, but it does not automatically make MPC secure because an untrusted host can still cause rollback, side-channel, and state-freshness failures. Secure deployments require comprehensive attestation verification, measured and hardened code, protected in-enclave communications, and protocol designs that remain safe even when persistent storage is rolled back.
KEY POINTS
  • 01TEEs can provide confidentiality, integrity, and remote attestation, but their security depends on correctly verifying quote signatures, certificate chains, and software measurements against trusted reference values.
  • 02A malicious host can roll back a threshold signer’s filesystem state after a used pre-signature is deleted, causing nonce-share reuse that can disclose the signer’s private key share.
  • 03Incomplete TEE measurements or missing attestation checks can create false assurance because unmeasured code or configuration can be modified while the attestation quote remains valid.
  • 04The untrusted host can still enable denial of service, timing side channels, rollback attacks, and other attacks despite the protections offered by a TEE.
  • 05Using TEEs from multiple manufacturers or cloud providers can reduce the centralization risk of relying on a single vendor’s hardware and attestation infrastructure.

The article examines the security tradeoffs of running multi-party computation (MPC), including threshold signature schemes, inside trusted execution environments (TEEs). MPC spreads trust among participants, while TEEs rely on hardware manufacturers and their attestation systems, so combining them can introduce centralization and new host-controlled attack surfaces. TEEs can help assure parties that others are executing the intended protocol, but only if attestation checks and software measurements are complete and correctly verified.

A key risk is rollback of persistent state by an untrusted host: after a signer deletes a used pre-signature, the host can restore an older filesystem state and cause reuse of a nonce share, potentially exposing that signer’s private key share. The article also highlights incomplete measurements, runtime-loaded code, missing quote or certificate checks, stale backups, side channels, physical memory attacks, and permissive vendor defaults as common deployment pitfalls. It recommends treating TEEs as defense in depth, binding attestations to MPC-party identities, terminating peer connections inside TEEs, writing constant-time code, hardening and measuring images, and diversifying across TEE vendors or cloud providers where practical.

  • A valid attestation quote does not prove the whole environment is trustworthy: if runtime-downloaded tools or configuration files are excluded from measurement, they can be changed without invalidating the quote.
  • Encryption and authenticated storage do not by themselves prevent rollback, because they protect secrecy and modification detection but do not prove that stored data is the newest version.
  • TEE attestation can make a protocol designed for participants that follow rules more resilient to participant misbehavior only when it reliably proves that every party is running the intended implementation.
  • Vendor attestation tools may accept publicly known vulnerable firmware for up to a year after disclosure, so deployments may need stricter version-validation policies than vendor defaults.

The article explains that putting shared digital-signing systems inside special hardware-protected areas can improve security, but it can also create new ways to fail if the surrounding computer is controlled by an attacker. For example, an attacker could restore an old saved copy of a signer’s data and trick it into reusing a one-time secret, which can reveal part of its private signing key. Organizations that use these systems to protect sensitive computations need to verify exactly what software is running and guard against old or altered stored data. The broader risk is that relying too heavily on a hardware maker or cloud provider can undermine the benefit of spreading trust across several independent participants.
