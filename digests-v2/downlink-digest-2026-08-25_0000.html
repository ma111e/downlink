A Microsoft Clarity Field Delivered a PayPal Callback Scam

Attackers abused a legitimate Microsoft Clarity project invite by putting a fake PayPal refund notice and callback number in the project title, causing Microsoft to send a fully authenticated, clean-looking phishing email. The key takeaway is that trusted SaaS notifications can deliver scams without compromised accounts or malicious links, so defenders need semantic/context-based detection and user reporting.
KEY POINTS
  • 01A state health and human services agency mailbox received a genuine Microsoft Clarity collaboration invite whose project title contained a fabricated PayPal transaction for $445.67 and a callback phone number.
  • 02Microsoft composed, signed, and delivered the invite from its own notification address, so SPF, DKIM, DMARC, ARC, and composite authentication all passed correctly.
  • 03The single join link resolved to a legitimate Microsoft Clarity project-join URL and scanned clean, while PayPal impersonation appeared only as text in the project name.
  • 04The article states that nothing in the message chain was compromised and that the attacker appeared to need only a free Microsoft Clarity account to create the project and invite the recipient.
  • 05The recipient, a security officer, recognized the invite as suspicious, reported it, and the message was quarantined roughly 53 minutes after arrival.

A state health and human services agency mailbox received a genuine Microsoft Clarity collaboration invite. The project name had been set to a fabricated PayPal transaction notice for $445.67 USD with a phone number to call for a refund or cancellation. Microsoft composed, signed, and delivered the message from its own notification address, and the only clickable link resolved to a real Microsoft Clarity project-join URL.

The article emphasizes that nothing in the delivery chain was compromised and there was no attacker-owned domain to block. SPF, DKIM, DMARC under a reject policy, four ARC seals, and composite authentication all passed correctly, while link analysis also returned clean results. PayPal impersonation appeared only in attacker-controlled text placed into the Microsoft Clarity project title, which was rendered in the subject, body, and link anchor text.

The message was ultimately stopped because the recipient, a security officer, recognized that an analytics invite quoting a refund amount did not make sense and reported it. The platform tagged the message as vendor impersonation, a scam, and suspicious, and an analyst confirmed the verdict before quarantine roughly 53 minutes after arrival. The article says the case shows the need to evaluate trusted vendor notifications in context and to watch for billing, refund, dispute language, or phone numbers inside user-controlled SaaS fields.

  • Authentication results were not useful for judging this message because every check correctly validated Microsoft as the sender while saying nothing about the scam content placed in the project title.
  • The article highlights an inverted link-analysis problem: the link destination was genuinely Microsoft, but the attacker-controlled project name became the visible link text that carried the fraud.
  • A practical detection opportunity is to flag trusted vendor notification emails when user-controlled fields contain billing, refund, dispute language, dollar amounts, or phone numbers.
  • The attack had no attacker-owned domain to block because PayPal was impersonated only through text, not through headers, links, or lookalike domains.
  • The case shows why low-friction user reporting can matter even when automated checks pass, since the message was ultimately stopped after the recipient recognized the context made no sense.

A state health and human services agency employee received a real Microsoft Clarity invitation, but the project name had been changed to look like a PayPal charge notice with a phone number to call for a refund. The email really came from Microsoft and its link went to Microsoft, so normal checks saw it as clean even though the words inside were a scam. This matters because criminals can use trusted online services to make fake billing messages look legitimate, and the real danger is getting someone to call the scammer.

State divergence enables unauthorized access

A flaw in Provenance Blockchain’s marker access checks let any user grant themselves admin rights over certain token markers with zero balance, enabling unauthorized minting or escrow withdrawals. The bug affected 82 live mainnet markers and was mitigated in v1.28.0, then fully fixed in v1.29.0 by checking live bank supply and rejecting zero-supply cases.
KEY POINTS
  • 01Researchers found and reported a bug in Provenance Blockchain that allowed any user to grant themselves admin control over marker accounts without holding any tokens.
  • 02The vulnerable authorization check used the marker’s stored supply field, which stayed at zero for non-fixed supply markers even when the live circulating supply existed in the bank module.
  • 03An attacker could exploit the bug with a MsgAddAccessRequest to give themselves permissions such as ACCESS_ADMIN, ACCESS_MINT, and ACCESS_WITHDRAW, then mint tokens or withdraw escrowed assets.
  • 04At discovery, 82 active mainnet markers had stored supply of zero while carrying real circulating supply or escrowed assets, including markers holding roughly 30 × 10^15 nhash worth about $500,000 at the time.
  • 05Provenance mitigated the reported attack in v1.28.0 by rejecting zero-supply checks and fully fixed the issue in v1.29.0 by reading live supply from the bank module.

Researchers found and reported a bug in Provenance Blockchain, a public proof-of-stake chain built on Cosmos SDK, that allowed any user to grant themselves admin control over marker accounts without holding any tokens. Markers are Provenance’s core primitive for fungible tokens and control a denomination, an access control list, a supply field, and an escrow balance. The bug affected versions before 1.28.0 and was reported to Provenance on April 1, 2026.

The flaw was in an authorization check used by AddAccess, which allowed access-list changes if the caller controlled 100% of a marker’s circulating supply. For non-fixed supply markers activated with zero supply, the marker’s stored supply field stayed at zero while the live circulating count existed in the bank module. As a result, a caller with zero balance could pass the check because the stale supply value and their balance were both zero.

An attacker could exploit the issue with a MsgAddAccessRequest to grant themselves permissions such as ACCESS_ADMIN, ACCESS_MINT, and ACCESS_WITHDRAW, then mint new tokens or drain assets from a marker’s escrow balance. At discovery, 82 active mainnet markers had a stored supply of zero while carrying real circulating supply or escrowed assets, including markers with roughly 30 × 10^15 nhash worth about $500,000 at the time. Provenance mitigated the reported attack in v1.28.0 by rejecting zero-supply checks and fully fixed the divergence in v1.29.0 by reading live supply from the bank module.

  • The authorization failure came from a default-state match: because both the stale supply value and an attacker’s balance could be zero, a check meant to prove full ownership instead became passable by anyone with no tokens.
  • The initial mitigation blocked the known exploit by rejecting zero supply, but the article notes it did not eliminate the underlying state divergence until the check was changed to read live supply from the bank module.
  • The article highlights that even using live supply is insufficient unless zero-supply cases are explicitly denied, because a newly created but unfunded marker would otherwise still allow the same zero-equals-zero bypass.
  • The flaw exposed both direct escrow theft and less direct token inflation risks, showing that the same broken permission check could threaten assets held by marker accounts as well as the integrity of issued tokens.
  • The authors state that a simple property-based test requiring accountControlsAllSupply to return true only when live supply is positive and fully held by the caller would have caught both stale-state and empty-marker failure modes.

Researchers found a bug in Provenance Blockchain that could let any user give themselves control over accounts used to manage financial tokens, even if they owned none of those tokens. This affected 82 live accounts tied to real assets, including bridged stablecoins, wrapped assets, tokenized loans, yield tokens, and Provenance Foundation grant and validator incentive funds. In the real world, an attacker could have created fake new tokens or drained about $500,000 worth of escrowed HASH from some affected accounts before the issue was fixed.
