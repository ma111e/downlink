Netskope says the campaign has evolved to use a WebRTC stager for covert encrypted code delivery and recommends blocking BSC testnet RPC endpoints and monitoring suspicious WebRTC traffic.
KEY POINTS
  • 01Researchers identified more than 5,400 compromised small-business websites, mostly built on WordPress and PrestaShop, that were injected with scripts to deliver ClickFix payloads.
  • 02The injected scripts retrieve next-stage payloads from smart contracts on the BNB Smart Chain Testnet using a technique known as EtherHiding.
  • 03The ClickFix lure displays a fake CAPTCHA and instructs visitors to open the Windows Run dialog and paste a PowerShell command that downloads and executes the final payload.
  • 04Netskope reported that the threat actor later replaced the ClickFix payload in the smart contract with a WebRTC data-channel stager that establishes a covert encrypted channel and executes received code in browser memory.
  • 05Netskope said the operation uses more than 300 infected websites every day and recommended blocking BSC testnet RPC endpoints and monitoring non-web UDP traffic associated with WebRTC.

A cybercriminal operation is using more than 5,400 compromised small-business websites to deliver ClickFix payloads stored in smart contracts on the BNB Smart Chain Testnet. Researchers found that most of the hacked sites were built on WordPress and PrestaShop, although the initial compromise method is unknown. Each site was injected with a script that retrieves the next-stage payload from a smart contract, a technique known as EtherHiding.

The injected script displays a fake CAPTCHA lure and instructs visitors to open the Windows Run dialog and paste a PowerShell command. If followed, the command downloads and executes the final payload on the visitor’s machine. Because the payload is stored in a smart contract, the attacker can modify it at any time, and Netskope says the technique provides resilient infrastructure that is difficult to take down.

Netskope reported that later in the campaign the attacker replaced the ClickFix payload with a WebRTC data-channel stager. This newer variant establishes a covert encrypted channel to the attacker, receives JavaScript code from a hardcoded command-and-control address, buffers it, and executes it in browser memory without saving it to disk. Netskope said the operation uses more than 300 infected websites every day and recommended blocking BSC Testnet RPC endpoints and monitoring non-web UDP traffic associated with WebRTC.

  • The attackers used the BNB Smart Chain Testnet rather than the production blockchain because it functions similarly to the mainnet but is available free of charge.
  • Storing the payload in a smart contract lets the attacker change what infected websites deliver without reinfecting those websites.
  • The WebRTC variant avoids saving received code to disk by assembling it in browser memory and executing it dynamically through the page DOM.
  • Netskope’s telemetry shows the campaign is still active and growing, with compromised sites contacting BSC Testnet RPC endpoints increasing through spring and reaching nearly 400 per day in August.

Attackers are actively exploiting an unpatched zero-day in Magento Open Source and Adobe Commerce, dubbed StyleSmuggler, to gain unauthenticated code execution and install persistent backdoors on online stores. With no official Adobe patch or CVE yet, admins should urgently look for the published indicators and consider temporary mitigations such as disabling GraphQL and hardening PHP execution.

Attackers are actively exploiting a new unpatched vulnerability in Magento Open Source and Adobe Commerce that Sansec named StyleSmuggler. Sansec said the flaw allows malicious code to run on an online store’s server without logging in, and attacks began on September 4. As of September 6, Adobe had not published an advisory, CVE identifier, patch, or workaround.

Sansec said all current versions are affected, including 2.4.9, and reproduced the unauthenticated chain on clean Magento Open Source 2.4.7, 2.4.8, and 2.4.9 installations. Disrex Group separately handled two compromised Magento Open Source stores and said patch status was irrelevant for those incidents because the stores were breached before defenses for the flaw existed. The researchers’ interim advice includes temporarily disabling GraphQL for stores that can do so until Adobe releases a fix.

The attack first plants PHP code in a Magento-written file and then makes Magento execute it by triggering a standard “Payment Transaction Failed Reminder” email. The backdoor has been seen as a non-root process named [kworker/u:8:0], with a binary under ~/.local/share/.gvfsd/gvfsd-user and cron entries that restart it every five minutes. Disrex said defenders should search both var/report/ and var/log/system.log, preserve evidence before cleanup, remove the cron entry before killing the process, flush session storage, and rotate sensitive credentials.

  • Patch status alone did not protect the compromised stores, because one victim was running Magento Open Source 2.4.8 and another earlier victim had Adobe’s July and August 2026 security updates applied.
  • Sansec’s published check of var/report/ could miss infections, because Disrex found both of its cases were poisoned through var/log/system.log instead.
  • Scanning only the store document root can miss the implant, because Disrex said eComscan reported Store A clean while the backdoor was installed one directory above the document root under the account’s home directory.
  • Removing the cron entry after killing the process may fail, because Disrex said the implant re-added the cron entry within a second of removal and recommends removing the cron entry before killing the process.
  • Blocking only the attacker address in Sansec’s advisory would have stopped less than a quarter of the traffic Disrex observed, because Disrex recorded 26 distinct source addresses across the two stores.

Attackers are breaking into online stores that use Magento Open Source and possibly Adobe Commerce by using a newly found weakness that Adobe has not yet fixed. The break-in can let them run their own program on the store’s server and keep access there, even without logging in. This matters because these stores handle shopping sessions, payment-related systems, admin accounts, and other sensitive credentials, and the article says real stores have already been compromised while no official patch is available.

The key lesson is that a legitimate thread and passing DKIM do not verify a new sender or a cloud-hosted document link.

  • 03The attacker registered a lookalike domain using the real vendor’s second-level label under a different top-level suffix, with WHOIS showing the domain was created on 2026-08-18, one day before the message was sent.
  • 04The quotation portal link first went through a Monday.com click tracker and then to a Google Sites page styled as a Microsoft file-share notification with an Open button and a fake document card labeled `RFQ_&Quote.docx`.
  • 05Email authentication showed DKIM passed through the attacker’s newly created Google Workspace tenant, while SPF and DMARC returned none, and Themis scored the message at 83 percent and mitigated it for one mailbox.

The reply came from a third-party engineering services firm persona that had not previously appeared in the conversation, making use of the real thread’s context rather than starting with a cold message.

The attacker used a lookalike domain that reused a real engineering firm’s second-level label under a different top-level suffix, with WHOIS showing it was created on 2026-08-18, one day before the message went out. The link first passed through a Monday.com project-management click tracker and then led to a Google Sites page styled as a Microsoft file-share notification with a fake document card labeled RFQ_&Quote.docx. The article says DKIM passed because the attacker signed mail from their own newly created Google Workspace tenant, while SPF and DMARC returned none, and Themis scored the message at 83 percent and mitigated it for one mailbox.

  • The attack did not need to impersonate a known sender because procurement workflows commonly involve new participants, making an unintroduced third party seem plausible within a real bid thread.
  • Carefully checking for misspellings would not have exposed the lookalike domain because the visible company label was identical to the real firm’s domain and only the top-level suffix changed.
  • A DKIM pass was misleading in this case because the attacker created a mail tenant for the lookalike domain and signed mail that aligned with that same fraudulent domain.
  • The link chain exploited reputation twice: the first hop used a legitimate project-management tracker, and the final page used Google Sites, so judging the link only by the first or most familiar hostname would miss the deception.
  • The article’s practical control point is to verify any newly introduced sender and compare the full sending domain, including the suffix, against vendor records rather than relying on the legitimacy of the existing email thread.
