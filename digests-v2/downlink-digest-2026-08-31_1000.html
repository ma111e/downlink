One Target List, Six Weeks of Conference Invites

A patient phishing operator used an aged, properly authenticated attacker-owned domain to repeatedly target named employees at one pharmaceutical CDMO with personalized conference-invitation emails carrying a malicious PDF. The key lesson is that SPF, DKIM, DMARC, domain age, and sender familiarity can all look normal, so defenders need payload analysis and per-recipient behavioral detection to catch these campaigns.
KEY POINTS
  • 01On July 9, 2026, a senior commercial leader at a pharmaceutical contract development and manufacturing organization received a personalized industry-summit invitation with a malicious brochure PDF attached.
  • 02Six weeks later, on August 20, 2026, four more individually named mailboxes at the same organization were targeted with similar personalized conference invitations and matching brochure attachments.
  • 03The emails passed SPF, DKIM, DMARC, and Microsoft composite authentication because the attacker owned and correctly configured the sending domain.
  • 04The attacker’s sending domain, nexora-summits[.]com, was created on December 5, 2025, making it roughly seven months old at the first recorded send.
  • 05The attachment scanner returned a malicious verdict on the PDF, and Themis scored the message at 90 percent confidence before mitigating it across the affected mailboxes.

A senior commercial leader at a pharmaceutical contract development and manufacturing organization received a personalized industry-summit invitation on July 9, 2026, with a brochure PDF attached. The subject line named a plausible facility-engineering conference in a specific host city and used a conversational “Re:” prefix. The attachment scanner returned a malicious verdict, and the PDF was about 1.5 MB, roughly the size of a real event prospectus.

The campaign did not stop with the first reported message. Six weeks later, on August 20, 2026, four more individually named mailboxes at the same organization were targeted with similar personalized conference invitations and matching brochure attachments. The article describes this as a curated target list rather than a spray campaign, with the operator rotating conference names and host cities while keeping the delivery mechanism in place.

The messages passed SPF, DKIM, DMARC, and Microsoft composite authentication because the sending domain belonged to the attacker and was correctly configured. The domain, nexora-summits[.]com, had been created on December 5, 2025, making it roughly seven months old at the first recorded send, so domain-age heuristics did not help. Themis scored the message at 90 percent confidence, tagged it against a high-value recipient, and mitigated it across the affected mailboxes before any recipient acted on it.

  • Clean SPF, DKIM, and DMARC results did not reduce risk in this case because the attacker used their own correctly configured domain rather than spoofing someone else’s domain.
  • Domain-age checks were ineffective because the attacker registered the sending domain roughly seven months before the first observed message, aging it past common newly registered domain thresholds.
  • The campaign’s rotation of conference names and host cities meant blocking a single subject line would only stop one version of the mail-merge template, not the broader campaign.
  • The sender was recorded as an established correspondent by the time of the reported message, showing that repeated contact can erode the usefulness of first-time-sender novelty as a warning signal.
  • The article recommends sweeping the whole tenant for the same subject template and sending domain after one malicious attachment is confirmed, because the reported message may be only one part of a broader mail-merge campaign.

A senior commercial leader at a pharmaceutical manufacturing services company got a realistic conference invitation with a brochure attached, but the brochure was harmful. Six weeks later, four more named people at the same company received similar personalized invitations, showing the sender had built a list of specific targets and kept trying. This matters because the emails looked normal in many routine checks, so a real employee could easily believe the message and open the attachment before protection tools catch it.

ValleyRAT masquerading as adware

Kaspersky found that attackers are disguising the ValleyRAT backdoor as signed QN Wallpaper adware, using DLL sideloading to disable defenses, persist, steal keystrokes and clipboard data, and download additional payloads. The campaign is likely linked to Silver Fox and has mainly affected users in China and India.
KEY POINTS
  • 01Kaspersky analyzed an installer initially classified as adware and found that it triggered an infection chain delivering the ValleyRAT backdoor instead of functioning as advertising software.
  • 02The installer deployed a modified version of the Chinese QN Wallpaper desktop wallpaper tool and used a malicious libcef.dll for DLL sideloading under the guise of a signed process.
  • 03The malicious libcef.dll decrypted and loaded AES-encrypted ValleyRAT payloads from either the PeLoader file or its own resources, depending on whether it was running inside QnWallpaper.exe or QnwPlayer.exe.
  • 04ValleyRAT can log keystrokes, capture clipboard contents, collect system information, take screenshots, update C2 addresses, download additional modules, and reboot or shut down the computer on command.
  • 05Kaspersky detected ValleyRAT and associated malware more than 100,000 times in 2026, affecting more than 1,500 unique users primarily in China and India, and attributed the campaign as likely linked to Silver Fox.

Kaspersky analyzed a file submitted by a client and initially classified it as adware, but suspicious network activity led to a deeper investigation. The sample turned out to be an installer that deployed a modified version of the Chinese QN Wallpaper desktop wallpaper tool and triggered an infection chain delivering the ValleyRAT backdoor. The article says the advertising functionality did not work and instead the package was used to run malicious code under the guise of a signed process.

The installer unpacked QN Wallpaper modules and malicious components into a Program Files directory, disabled Windows Defender using the DisableAntiSpyware registry key, and launched QnWallpaper.exe. A malicious libcef.dll was loaded by QnWallpaper.exe and QnwPlayer.exe, enabling DLL sideloading and loading AES-encrypted ValleyRAT payloads from either the PeLoader file or libcef.dll resources depending on the host process. ValleyRAT then parsed a reversed configuration string containing settings such as C2 addresses, protocol, sleep timings, and options for process protection and analysis-tool checks.

ValleyRAT can track keystrokes, capture clipboard contents, collect system information, take screenshots, wipe logs, update C2 addresses, download additional modules, and reboot or shut down the computer on command. The backdoor can also inject code into svchost to restart itself, mark its process as critical, and restart after unhandled exceptions. Kaspersky detected ValleyRAT and associated malware more than 100,000 times in 2026, affecting more than 1,500 unique users primarily in China and India, and said the geography and use of ValleyRAT point to Silver Fox as the likely operator.

  • The adware disguise was especially dangerous because the abused QN Wallpaper application was signed by its developer, and users often manually add such apps to security exclusions so their features are not blocked.
  • The advertising functionality in the modified QN Wallpaper package did not work, indicating that the adware behavior was used as cover rather than as a secondary monetization feature.
  • The malicious libcef.dll contained both automatic execution through DllMain and a separate RunDLL function that QnWallpaper did not call, showing that the same component could support more than one launch method.
  • ValleyRAT’s payload source changed depending on the host process, with one encrypted backdoor loaded from PeLoader under QnWallpaper.exe and another loaded from libcef.dll resources under QnwPlayer.exe, differing only in C2 configuration.
  • The campaign demonstrates that software treated as merely unwanted or annoying can conceal a full backdoor capable of spying on users and delivering additional malicious modules.

Researchers found that a harmful program called ValleyRAT was being delivered through a modified version of a Chinese wallpaper app that looks like ordinary ad-supported software. More than 1,500 users were affected in 2026, mainly in China and India. This matters because the program can steal typed text and clipboard contents, take screenshots, and download more harmful tools, while hiding behind software that users may trust or allow past security checks.

Breaking the Seal: Static Deobfuscation of JSCeal’s Compiled V8 Bytecode

Check Point researchers built and released a fully static pipeline to deobfuscate JSCeal’s compiled V8 bytecode payloads, turning heavily obfuscated Node.js malware into analyzable pseudocode without executing it. The recovered code shows JSCeal is a broad crypto-focused stealer with browser credential theft, keylogging, screenshots, Telegram theft, and local HTTPS interception capabilities.
KEY POINTS
  • 01Check Point Research has tracked JSCeal since early 2025 as a cryptocurrency-focused stealer delivered as compiled V8 bytecode and executed by a bundled Node.js runtime.
  • 02The analyzed JSCeal payloads were protected with javascript-obfuscator techniques including RC4-protected strings, control-flow flattening, proxy functions, and operation wrappers.
  • 03Check Point Research developed and released a fully static deobfuscation toolkit that transforms View8 pseudocode without executing the malware.
  • 04The deobfuscated output exposed JSCeal capabilities including browser credential theft, keylogging, screenshot capture, Telegram session theft, cryptocurrency-focused collection, and HTTPS traffic interception through a local proxy.
  • 05More recent JSCeal developments include V8 code caches generated for a newer Node.js and V8 version, an AES-256-CBC payload-encryption layer, and macOS targeting.

Check Point Research describes a static deobfuscation effort for JSCeal, a cryptocurrency-focused stealer delivered as compiled V8 bytecode and executed by a bundled Node.js runtime. The payloads arrive as JSC files, are Brotli-compressed, and are protected with javascript-obfuscator techniques such as RC4-protected strings, control-flow flattening, proxy functions, and operation wrappers. The researchers built a pipeline based on View8 to transform V8 bytecode pseudocode into code that can be inspected without executing the malware.

The work matters because JSCeal combines a version-specific compiled format with source-level obfuscation, making ordinary JavaScript analysis workflows ineffective. The deobfuscation pipeline reconstructs strings, unflattens control flow, resolves proxy and operation wrappers, propagates values through scopes and dictionaries, and optionally uses LLM-assisted function renaming as a navigation aid. The toolkit, jsc_deobfuscator, was released publicly, and the researchers applied it successfully to 23 JSCeal payloads from their evaluation corpus.

The recovered code exposed a broad capability set, including browser and credential theft, Telegram session theft, keylogging, screenshot capture, cryptocurrency account and balance collection, and HTTPS traffic interception through a local proxy. The article shows that JSCeal can collect browser cookies, passwords, OAuth tokens, wallet mnemonic data, and cryptocurrency platform information, and can install an attacker-controlled certificate for local traffic interception. It also notes more recent JSCeal changes, including a newer Node.js and V8 version, an AES-256-CBC payload-encryption layer supplied through an environment variable, payload renaming, and macOS targeting.

  • JSCeal’s use of compiled V8 code caches creates an analysis burden even when the malware’s higher-level obfuscation patterns remain unchanged, because each new Node.js and V8 runtime generation can require renewed work at the disassembly layer.
  • The deobfuscation pipeline depends on the order of its passes: recovered strings reveal dictionary keys and control-flow order values, which then enable control-flow unflattening, proxy resolution, and operation-wrapper cleanup.
  • The article shows that JSCeal goes beyond passive browser data theft by using recovered cookies and passwords with Puppeteer automation to replay Google sessions and obtain fresh Android-scoped OAuth tokens.
  • JSCeal’s local HTTPS interception proxy is used not only to observe traffic but also to modify service-specific responses, including replacing Binance QR-login values, altering Bybit verification responses, and substituting Ledger web content.
  • The later AES-256-CBC layer is especially effective for isolated-sample analysis because the decryption key is supplied by an earlier deployment stage through an environment variable rather than stored in the malware bundle itself.

Check Point Research studied JSCeal, a program used by criminals to steal cryptocurrency-related data and other private information, and built a tool that lets researchers read its hidden code without running it. The victims are people targeted through fake advertising and downloaded files, especially cryptocurrency users, because the recovered code shows it can steal browser passwords and cookies, Telegram sessions, wallet recovery words, screenshots, and keystrokes. The broader risk is that attackers can cheaply hide powerful stealing tools inside ordinary-looking Node.js files, making them harder to study and easier to keep improving.

Emerging Threat: (CVE-2026-75604) Next.js Remote Code Execution via Windows Path Traversal

A critical Next.js flaw, CVE-2026-75604, can allow unauthenticated remote code execution on self-hosted Windows deployments using affected versions and routing/cache configurations. Organizations should urgently identify Windows-hosted Next.js apps and upgrade to the fixed releases, as there is no reliable workaround.
KEY POINTS
  • 01CVE-2026-75604 is a critical path traversal flaw in Next.js that can allow an unauthenticated attacker to write files outside the framework’s cache directory and reach remote code execution on the host.
  • 02The vulnerability affects Next.js 13.4 up to 15.5.24 and 16.0 up to 16.3.3 when the application runs on a Windows filesystem and uses the Pages Router or the App Router without Cache Components.
  • 03Linux and macOS deployments are not affected, and applications running on Vercel’s managed platform are not affected because that infrastructure runs on Linux.
  • 04Vercel released fixed versions in Next.js 15.5.24 and 16.3.3, and the article states there is no known workaround for affected Windows-hosted applications.
  • 05The article recommends inventorying Windows-hosted Next.js deployments, confirming pinned Next.js versions, monitoring cache paths, blocking percent-encoded backslash sequences, and auditing externally reachable incremental static regeneration routes until patching is confirmed.

CVE-2026-75604 is a critical path traversal flaw in Next.js that can allow an unauthenticated attacker to write files outside the framework’s on-disk cache directory and reach remote code execution on the host. The vulnerability is tracked as CWE-22 and published by Vercel as GHSA-p293-qw3h-jr36. It has a CVSS v3.1 base score of 9.0, with no authentication or user interaction required.

The flaw is specific to self-hosted Windows deployments because Windows treats backslashes as directory separators. Percent-encoded backslash sequences can reach the Next.js routing layer without normalization, and under certain routing and caching conditions can steer a filesystem cache write to a chosen location. Affected deployments include Next.js 13.4 up to 15.5.24 and 16.0 up to 16.3.3 when the application uses the Pages Router or the App Router without Cache Components and runs on a Windows filesystem.

Linux and macOS deployments are not affected, and applications running on Vercel’s managed platform are not affected because that infrastructure runs on Linux. Vercel released fixed versions in Next.js 15.5.24 and 16.3.3, and the article states there is no known workaround for affected Windows-hosted applications. Recommended actions include inventorying Windows-hosted Next.js deployments, confirming pinned framework versions, monitoring cache paths, blocking percent-encoded backslash sequences, and auditing externally reachable incremental static regeneration routes until patching is confirmed.

  • The article frames the exposure as an inventory problem rather than only a patching problem, because many organizations can identify public hosts and domains but not the JavaScript framework version or operating system behind each site.
  • Windows-hosted Next.js deployments are described as a minority pattern often inherited from existing .NET and IIS environments, which can leave them outside inventories focused on Linux web infrastructure.
  • The sector distribution is described as relatively flat, suggesting the risk is driven more by distributed web development practices than by any single industry’s technology profile.
  • The same Next.js security release also changes AVIF image handling by disabling AVIF optimization pending an upstream libheif fix, so teams upgrading for CVE-2026-75604 should expect an operational side effect for AVIF images.
  • The article notes that WAF-layer virtual patching can be useful when applications cannot be rebuilt immediately, but it only filters requests and does not remove the underlying flaw.

The article describes a critical flaw in Next.js that can let an outsider place files where they should not be allowed and, in some cases, run commands on the computer hosting the website. It only affects self-hosted Next.js websites running on Windows, not sites running on Linux, macOS, or Vercel’s managed platform. This matters because many public-facing websites may use Next.js without organizations clearly knowing which version they run or whether they are on Windows, making exposed sites hard to find and fix quickly.
