Hackers exploit SiteGuard WAF flaw to run commands as admins

Hackers are actively exploiting critical OS command-injection flaw CVE-2026-106931 in SiteGuard Server Edition’s default-enabled statistics feature to run commands as root or SYSTEM. Organizations should preserve diagnostic evidence and promptly apply the vendor’s updates or patches.
KEY POINTS
  • 01Hackers are actively exploiting CVE-2026-106931, an OS command-injection flaw in the default-enabled statistics function of SiteGuard Server Edition.
  • 02Successful exploitation can allow attackers to execute commands with root or SYSTEM privileges on affected machines.
  • 03Affected releases include SiteGuard Server Edition for Apache httpd, Nginx, and IIS from version 2.20 up to before 8.00 Update 5, with separate affected FreeBSD releases up to before 7.00 Update 6.
  • 04SiteGuard provides updates and patches, including for end-of-life versions, and warns that remediation may erase attack traces.
  • 05The vendor advises administrators to download diagnostic information before applying updates or patches to preserve potential evidence.

Hackers are actively exploiting CVE-2026-106931, a critical OS command-injection vulnerability in the statistics function of SiteGuard Server Edition. Successful exploitation allows attackers to execute commands with root or SYSTEM privileges on affected machines. The vulnerable statistics feature is enabled by default, and the vendor and JPCERT/CC have confirmed exploitation in the wild.

Affected versions include SiteGuard Server Edition for Apache httpd, Nginx, and IIS from version 2.20 through versions before 8.00 Update 5, except certain IIS editions from 3.10 through 4.00 Update 4. FreeBSD editions for Apache httpd and Nginx are affected from version 2.20 through versions before 7.00 Update 6. SiteGuard has released updates and replacement-file patches, including for end-of-life versions, and advises administrators to download diagnostic information before remediation because updating may erase traces of an attack.

  • The vulnerable statistics feature is enabled by default, so affected installations may be exposed without administrators having deliberately turned on the feature.
  • SiteGuard warns that applying the update or patch may erase evidence of an attack, making collection of diagnostic information before remediation especially important.
  • The vendor offers replacement-file patches even for end-of-life versions, providing a remediation path for organizations that cannot upgrade.
  • IIS editions 3.10 through 4.00 Update 4 are specifically identified as unaffected, despite other IIS-based SiteGuard Server Edition versions being vulnerable.
  • Although exploitation has been confirmed, the vendor and JPCERT/CC do not identify the attackers, victims, attack scale, or methods used.

Hackers are actively taking advantage of a serious flaw in SiteGuard Server Edition, a tool used to protect websites, to run commands with the highest level of control on affected computers. The problem affects certain versions used with Apache, Nginx, and Microsoft IIS, unless they have been updated; a feature involved is turned on by default. This matters because attackers who gain this level of access could take control of the machines protecting websites, and SiteGuard says it protects more than 1.5 million websites. SiteGuard has released updates and patches, including for older unsupported versions, and advises customers to save diagnostic information before installing them because the fix may remove evidence of an intrusion.

The vulnerable statistics feature is enabled by default, and the vendor provides urgent updates and patches for affected versions, including end-of-life releases.

ConnectWise Suspends Cloud Backup After Attackers Compromise Microsoft 365 Tenants

ConnectWise disabled compromised application identities and suspended Cloud Backup after attackers used them to access Microsoft 365 tenants, potentially enabling persistent access through newly added application credentials. Customers should review Entra sign-ins, service principals, permissions, and mailbox rules for suspicious activity, especially from 144.172.64[.]128.
KEY POINTS
  • 01ConnectWise disabled seven application identities on October 17, 2026, after unknown threat actors obtained unauthorized access to them and compromised Microsoft 365 tenants.
  • 02ConnectWise revoked certificates for affected application connections and suspended Cloud Backup, leaving scheduled backups, archive access, and restoration unavailable while stating that existing archives remain encrypted, isolated, and preserved.
  • 03Huntress reported that it confirmed abuse of the ConnectWise Cloud Management Microsoft Teams application in one tenant and assessed that Exchange Online, Teams, and SharePoint applications were also targeted.
  • 04Huntress identified nearly 1,000 Entra tenants with sign-in activity from IP address 144.172.64[.]128, including about 300 successful sign-ins, although some lacked the required service principal for access.
  • 05Attackers could create new application credentials or assign elevated roles in affected tenants, allowing them to retain or expand access even after the original compromised credential is revoked.

ConnectWise disabled seven application identities after unknown threat actors obtained unauthorized access to them and compromised Microsoft 365 tenants. On October 17, 2026, it revoked certificates used by affected connections and suspended Cloud Backup, while also taking SaaS Security and Cloud Management offline as it investigated. The company said that existing backup archives remain encrypted, isolated, and preserved, with no evidence they were accessed, but scheduled backups, archive access, and restoration remain unavailable.

The incident is significant because the compromised application credentials could let attackers access customer Microsoft 365 environments without obtaining each customer’s password. Depending on permissions, attackers could access mailboxes, SharePoint documents, Teams messages, and directory information, and could potentially create new application credentials or elevate access to retain control. Huntress identified almost 1,000 Entra tenants with sign-in activity tied to IP address 144.172.64[.]128, about 300 of which succeeded, and reported a second unsuccessful targeted wave against 16 tenants in policy, national security, trade, and critical-mineral sectors.

  • Disabling the compromised ConnectWise connections stops new authentication but does not undo changes already made inside customer tenants, and previously issued access tokens may remain valid until they expire or are invalidated.
  • Attackers could preserve access by adding new credentials to trusted applications, creating an alternative route back into a tenant even if the original compromised ConnectWise credential is revoked.
  • Although Cloud Backup was suspended and restores are unavailable, ConnectWise said the existing backup archives remain encrypted, isolated, preserved, and show no evidence of attacker access.
  • A second unsuccessful wave focused on only 16 tenants in policy, national security, trade, and critical-mineral sectors, using manual activity against several Microsoft services.
  • Some successful sign-ins did not result in tenant access because those tenants lacked the required service principal, showing that sign-in success alone did not always provide usable access.

ConnectWise found that unknown attackers obtained access to its connections for Microsoft 365, a widely used workplace email and file-sharing service, and used them to enter some customer organizations’ accounts. The company shut down several connections and paused its backup service, but customers may still need to check whether intruders created new ways to return. This matters because one stolen company connection can give attackers access to many organizations’ email, documents, chat messages, and account information without needing each employee’s password.

OPEN SOURCE ↗

This is a high-impact, ongoing compromise involving ConnectWise application identities that enabled unauthorized access attempts across nearly 1,000 Microsoft Entra tenants. The potential for attackers to establish persistent access through added application credentials and elevated permissions makes it urgently relevant to affected Microsoft 365 customers and service providers.

The Security Vendor Hop Was on the Sender's Side

A phishing email reached a CEO’s inbox because the sender used Trend Micro Email Security as an outbound relay to generate an aligned DKIM signature, allowing DMARC to pass despite an SPF softfail. Security-vendor hops in email headers must be interpreted directionally: a vendor may be serving the sender, not protecting the recipient.
KEY POINTS
  • 01A phishing email targeting the CEO of a French calibration and metrology company passed DKIM, DMARC, and Microsoft composite authentication checks and was delivered to the Inbox with an SCL of 1.
  • 02Trend Micro Email Security acted as the sender’s outbound relay and signed the message using the sending domain’s DKIM key, rather than serving as an inbound security gateway for the recipient.
  • 03SPF softfailed because the sending domain did not authorize the Trend Micro relay IP, but DMARC still passed because the aligned DKIM signature passed.
  • 04The email contained a single PDF attachment with a raster QR code directing recipients to a subdomain of lunwah.com, with no clickable links, embedded files, forms, JavaScript, or auto-open action.
  • 05IRONSCALES classified the incident as phishing, identified the PDF as malicious and the display name as company impersonation, and quarantined the messages from both targeted mailboxes.

A phishing email targeting the CEO of a French calibration and metrology company passed DKIM, DMARC, and Microsoft composite authentication checks and was delivered to the Inbox with a spam confidence level of 1. The message traveled through Trend Micro Email Security, but the service was operating as the sender’s outbound relay rather than as the recipient’s inbound protection. It contained a PDF attachment named for the CEO with “2FA-Confirmation” appended, and two executive mailboxes received personalized variants about an hour apart.

The sender’s domain did not authorize the Trend Micro relay in its SPF record, so SPF softfailed, but DMARC still passed because Trend Micro signed the message with an aligned DKIM signature using the sender’s domain and the selector TM-DKIM-2025120882751. The PDF contained a raster QR code pointing to a subdomain of lunwah[.]com, with no clickable links, embedded files, forms, JavaScript, or auto-open action. The article emphasizes that a security-vendor hostname in Received headers does not indicate which side the vendor served, and that authentication passes alone cannot establish that an email is safe.

  • A recognized security-vendor hostname in an email’s delivery path does not show that the recipient’s security service inspected or approved the message; it may instead be the sender’s outbound service.
  • An aligned digital signature can allow a fraudulent message to pass domain-based authentication even when the sender’s authorized-server check returns a soft failure.
  • The combination of the sending domain in the digital-signature field and a vendor-style selector is evidence that the vendor signed mail for that sending domain as an outbound service.
  • A PDF containing only a QR code can avoid conventional link scanning because it provides no clickable web address for scanners to follow.
  • A sending domain that had no prior incident history and later disappeared can still have valid authentication records during a short-lived phishing campaign.

A fake document-sharing email was sent to the chief executive and another executive at a French calibration and measurement company, carrying a PDF with a QR code that could lead recipients to a suspicious website. It reached their inboxes because the sender used a real email-security company’s sending service, making the message appear properly verified even though it was fraudulent. The case matters because familiar security-company names and email verification checks do not always mean a message is safe, especially when criminals use legitimate services to make phishing look trustworthy.

This is a concrete phishing incident showing how an attacker used a legitimate outbound email-security service to obtain aligned DKIM and DMARC passes despite an SPF softfail. It is a useful, actionable case study for email-security professionals, but it describes a limited campaign rather than a broadly active exploitation event or major breach.

OpenCode Security Breach: Distillation Attack Hit Console Users With Linked AI Providers. How to Find OpenCode on Developer Machines and Respond

OpenCode disclosed an ongoing breach tied to a large-scale distillation attack affecting 1.4% of Console users with linked Anthropic, OpenAI, or Google providers. Organizations should identify developers using OpenCode, verify whether provider credentials were linked, and rotate relevant API keys while monitoring provider usage for unauthorized activity.
KEY POINTS
  • 01OpenCode disclosed an ongoing security breach on October 18, 2026, related to what it described as a large-scale distillation attack.
  • 02OpenCode said the incident affected 1.4% of OpenCode Console users who had linked external providers, including Anthropic, OpenAI, and Google.
  • 03OpenCode stated that it emailed every affected user on the morning of October 18 and that users who did not receive an email were not impacted.
  • 04OpenCode has not published a root cause, a list of affected versions, or details about what data was accessed.
  • 05The article recommends that users with linked provider credentials rotate relevant API keys and review provider usage dashboards for unexpected requests.

OpenCode disclosed an ongoing security breach on October 18, 2026, which it said was related to a large-scale distillation attack. The company said 1.4% of OpenCode Console users were affected, specifically users who had linked external AI providers. The named providers were Anthropic, OpenAI, and Google, and OpenCode said it notified every affected user by email that morning.

OpenCode has not published a root cause, a list of affected versions, or details about what data was accessed. The article notes that an installed OpenCode CLI version does not by itself establish exposure; the relevant factors are an OpenCode Console account and linked provider credentials. It recommends identifying machines with OpenCode installed, checking the local auth.json file for linked providers, rotating connected API keys, and reviewing provider usage dashboards for unexpected requests.

  • The installed OpenCode version does not determine exposure because OpenCode has not identified affected versions and scoped the incident to Console accounts with linked external providers.
  • An OpenCode installation alone does not confirm that a user was affected; the relevant distinction is whether the user had an OpenCode Console account with linked Anthropic, OpenAI, or Google credentials.
  • On macOS and Linux, the presence of a provider entry in ~/.local/share/opencode/auth.json identifies credentials that should be considered for rotation, while the equivalent Windows file is located under %USERPROFILE%\.local\share\opencode\auth.json.
  • Fleet inventory can identify devices running the OpenCode CLI, but it cannot establish whether a developer has a Console account or which providers they linked, so follow-up checks are still required.

OpenCode says that 1.4% of its online-console users who connected Anthropic, OpenAI, or Google accounts were affected by a security breach. OpenCode says it emailed everyone affected, while users who did not receive an email were not impacted. The concern is that connected account keys may have been exposed, allowing someone else to use paid AI services or potentially reach data those keys can access. People and organizations using OpenCode should find out who has it installed, check which AI accounts were connected, replace those keys, and review account activity for unexpected use.

OPEN SOURCE ↗

This is a specific, ongoing breach affecting OpenCode Console users with linked Anthropic, OpenAI, or Google accounts, creating a need to identify potentially exposed credentials and rotate keys. Its relevance is strongest for organizations with developers using OpenCode or managing AI-provider accounts.
