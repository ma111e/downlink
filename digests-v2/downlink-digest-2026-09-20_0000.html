Researchers escape OpenAI Codex sandbox to run commands on host

Researchers found two Codex sandbox escapes—Heapjack and Overpatch—that could let malicious repositories execute commands or write outside intended boundaries on developers’ machines. OpenAI fixed the issues in Codex Desktop 26.818.21641 and Codex CLI 0.149.0, so users should update.
KEY POINTS
  • 01Researchers at Accomplish AI reported two OpenAI Codex sandbox escapes, Heapjack and Overpatch, on August 12, and OpenAI fixed them within eight days.
  • 02Heapjack could allow a malicious repository opened in Codex to run commands on a developer’s machine from Codex’s read-only mode without an approval prompt or visible output.
  • 03Heapjack exploited node_repl by reading a trusted authorization token from the shared memory heap of a Node.js process and using it to communicate with an unsandboxed parent process.
  • 04Overpatch abused Codex CLI’s apply_patch tool in workspace-write mode to expand write permissions and append a line to a user’s .zshrc through a symlink.
  • 05OpenAI fixed Heapjack in Codex Desktop build 26.818.21641 and Overpatch in Codex CLI version 0.149.0.

Researchers at Accomplish AI discovered two methods for escaping OpenAI Codex’s sandbox, named Heapjack and Overpatch. Heapjack could allow a malicious repository opened in Codex to run commands on a developer’s computer even from Codex’s read-only mode, without an approval prompt or visible output. Overpatch could let Codex CLI write outside its intended project folder in workspace-write mode.

Heapjack targeted the default-enabled node_repl component, where trusted and untrusted JavaScript contexts shared a single Node.js process and memory heap. Untrusted code could scan memory for the trusted context’s authorization token, then use that token to send requests to an unsandboxed parent process. Overpatch abused the apply_patch tool’s handling of patch paths to widen write permissions and append a line to .zshrc through a symlink. OpenAI fixed Heapjack in Codex Desktop build 26.818.21641 and Overpatch in Codex CLI version 0.149.0, and users are advised to update.

  • Codex Desktop installed the node_repl component in the shared ~/.codex/config.toml file by default, causing Codex CLI users to inherit it without being asked.
  • Heapjack worked even in Codex’s read-only mode, showing that a mode intended to prevent file changes could still be used to reach an unsandboxed parent process.
  • In Overpatch, including /tmp as a path in a patch caused apply_patch to grant write access to the disk’s root directory, even though that patch change did not need to modify anything useful.
  • Both flaws resulted from placing a security check inside the environment controlled by untrusted code: one trusted an attacker-supplied path, while the other stored its authorization secret in memory accessible to untrusted JavaScript.

Researchers found two flaws in OpenAI’s Codex coding assistant that could let a harmful project run commands on a developer’s computer or change files outside the project folder, even when Codex was supposed to be tightly restricted. This affects people using Codex Desktop or its command-line version, especially if they open code from someone else. The problems show that safety limits can fail when the restricted code can influence the very checks meant to contain it, potentially giving attackers access to a user’s machine. OpenAI fixed the flaws, and users should update Codex Desktop to build 26.818.21641 or newer and Codex CLI to version 0.149.0 or newer.

Although the flaws were patched and the article does not report active exploitation, the sandbox escapes and required version updates have broad relevance for developers using Codex.

Malicious npm packages evade install-script defenses at runtime

Malicious npm packages led by indexed-btree evaded install-script protections by embedding a runtime loader in a commonly used library method, allowing malware to execute only when triggered by application behavior. Developers who installed the affected packages should rotate secrets and restore affected environments from known-safe backups.
KEY POINTS
  • 01Checkmarx identified indexed-btree as a malicious npm package impersonating the legitimate sorted-btree library, with roughly 2 million weekly downloads.
  • 02The package avoids npm install-script protections by placing its loader in the BTree.prototype.set() function, where it runs only when the application calls the function with a specific key value.
  • 03After execution, the malware collects system details and sends them through hardcoded Slack and Telegram channels, then retrieves command-and-control information from an Ethereum Sepolia test-network smart contract.
  • 04Checkmarx linked nine additional npm packages to the operation, and npm has removed them.
  • 05Developers who installed indexed-btree or the related packages are advised to rotate all secrets and restore their development environments from safe backups.

Checkmarx researchers identified an npm malware campaign involving indexed-btree, a package that impersonates the legitimate sorted-btree library and has amassed 2 million weekly downloads. The package avoids npm’s install-script approval protections by hiding a malicious loader in the normal BTree.prototype.set() method rather than using preinstall, install, or postinstall scripts. This means installation appears clean, while the malicious code can run later when an application calls the method with a specific key value.

Once triggered, the malware gathers system details such as architecture, hostname, CPU, memory, and uptime and sends them through hardcoded Slack and Telegram channels. It also polls an Ethereum Sepolia test-network smart contract for command-and-control information, using X25519 key exchange and AES decryption to retrieve a second-stage payload. Checkmarx linked nine additional removed npm packages to the operation, and advises anyone who installed the affected packages to rotate all secrets and restore their development environment from a safe backup.

  • Blocking installation scripts alone did not stop this campaign because the malicious code was embedded in a normal library function and activated during ordinary runtime use.
  • The runtime trigger was placed in BTree.prototype.set(), described by Checkmarx as the library's main function that users would call frequently, increasing the likelihood that affected applications would activate the loader.
  • The operators used an Ethereum Sepolia test-network smart contract to hold encrypted second-stage payload information, while X25519 key exchange and AES were used to decrypt it.
  • The malware includes a cleanup capability that can delete its files and remove the malicious package trigger, making it possible for operators to erase traces when ending the operation.
  • The campaign's apparently legitimate GitHub repository, fabricated commit history, and curated developer account show that package reputation signals can be deliberately constructed to appear trustworthy.

A malicious software package called indexed-btree pretended to be a legitimate tool and was downloaded about 2 million times per week. Instead of running harmful code when it was installed, it waited until the software was being used, which helped it avoid common safety checks. It could gather details about affected computers and send them to the attackers, while related packages reached hundreds of thousands or millions more downloads. This matters because developers cannot rely only on checks that run during installation and may need to replace affected systems and change exposed passwords or other access credentials.

OPEN SOURCE ↗

This reports an active npm supply-chain malware campaign affecting packages with substantial download counts, including indexed-btree at roughly 2 million weekly downloads. It is particularly relevant because the malware bypasses install-time protections by activating during normal package runtime use, requiring affected users to rotate secrets and restore environments.

The Phishing Kit That Emailed Us Its Own Billing Meter

A phishing-as-a-service campaign accidentally pasted its live operator console into a document-invite email, exposing its Enterprise subscription, 138,291 lifetime sends, 4,043 loaded targets, SMTP configuration, and delivery logs. The message passed conventional email authentication and bypassed the recipient gateway, showing why behavioral and content-based detection is needed against legitimate-account abuse and credential-harvesting lures.
KEY POINTS
  • 01A document-invite phishing email delivered to the chief executive of a US Midwest grocery retailer on September 4, 2026 accidentally included a copy of the phishing service's live operator console in its HTML body.
  • 02The exposed console showed an active Enterprise plan with 23 days remaining, 138,291 lifetime emails, 4,043 loaded leads, one SMTP server, 25 concurrent sends, and no batch delay.
  • 03Its delivery log showed 50 successful deliveries with SMTP 250 responses, while the displayed sending rates and completion estimates were consistent with the log timestamps.
  • 04The recipient gateway assigned the message a total score of 0.50 against a blocking threshold of 3.0, and its only weighted signal came from a non-standard HTTP port shown in the accidentally exposed console log.
  • 05The article states that detection ultimately relied on a malicious final-destination verdict, display-name impersonation, and community reputation similarity, and that the single affected mailbox was mitigated six seconds after receipt.

A document-invite phishing email sent to the chief executive of a US Midwest grocery retailer on September 4, 2026 accidentally included the live web console of the phishing-as-a-service platform that delivered it. The pasted panel showed an active Enterprise subscription with 23 days remaining, 138,291 lifetime emails, 4,043 loaded leads, one SMTP server, 25 concurrent sends, and zero batch delay. Its delivery log contained fifty successful SMTP 250 responses to distinct recipients across forty-nine domains, and the reported throughput and completion estimates matched the displayed timestamps.

The receiving cloud gateway assigned the email a score of 0.50 against a blocking threshold of 3.0, with the only nonzero signal caused by a non-standard HTTP port exposed in the pasted console log. The message passed SPF at the true inbound edge because it was sent through an abused legitimate provider account, while later authentication failures resulted from the recipient-side mail-routing topology and body rewriting after signing. Detection instead relied on a malicious final destination, exact display-name impersonation, and community reputation similarity; Themis assessed it at 88% confidence, and the single affected mailbox was mitigated six seconds after receipt.

  • The console’s throughput and remaining-time estimates matched the elapsed timestamps, providing evidence that the pasted panel reflected live campaign activity rather than static or fabricated text.
  • The only gateway rule with a nonzero score was triggered by the exposed relay port inside the accidental console log, meaning the leaked operational data—not the lure itself—supplied the message’s entire conventional gateway score.
  • The email passed SPF at the actual inbound edge because it was sent through an abused legitimate provider account, illustrating that successful sender-authentication checks did not establish that the message was safe.
  • The article distinguishes infrastructure controlled by the sender from infrastructure merely abused or compromised, including a legitimate insurance-brand domain, an older relay host, and a compromised personal website.
  • Because custom HTML can be appended to generated phishing templates, kit banners, licence meters, lead-loader lines, and delivery-log patterns can serve as inexpensive high-confidence body-content detection signals.

A fake document-invitation email sent to the chief executive of a US Midwest grocery retailer accidentally included the sender’s own control panel, revealing that it was part of a paid service used to send large numbers of scam emails. The panel showed thousands of intended recipients and logs of successful deliveries to real people at unrelated companies. The email slipped past standard automated checks because it came through legitimate but abused services, but it was stopped shortly after delivery. This matters because criminal email scams can be run like subscription businesses at large scale, putting employees and organizations at risk of having their login details stolen.

This is a concrete phishing incident with unusually detailed, live operational data from a phishing-as-a-service console, including campaign volume, sending configuration, and delivery evidence. It offers broadly relevant detection lessons on legitimate-account abuse, authentication limits, URL rewriting, and high-confidence kit-content indicators, although it does not identify an active named threat actor or a broadly exploited software flaw.
