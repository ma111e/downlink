WHMCS SQL Injection Could Expose Customer Data and Admin Password Hashes without Login

WHMCS released fixes for three vulnerabilities, including an unauthenticated SQL injection (CVE-2026-82981) that could expose customer data and administrator password hashes from internet-accessible installations. Self-hosted users should upgrade immediately, while the email-campaign flaw also requires deleting existing campaigns and clearing the template cache.
KEY POINTS
  • 01WHMCS disclosed CVE-2026-82981, an unauthenticated SQL injection flaw in its shopping cart that could expose customer records and administrator password hashes.
  • 02WHMCS released versions 9.0.10 and 8.13.8 to address the vulnerabilities, while the security advisory identifies version 9.1.2 as the fix for the 9.1 series.
  • 03A second SQL injection flaw, CVE-2026-82979, requires a logged-in client with View & Manage Contacts permission and could expose other customers' personal, billing, and support information.
  • 04CVE-2026-93700 affects email campaigns and could allow a logged-in client to read sensitive server configuration files, including database credentials, and run code on the server.
  • 05For CVE-2026-93700, WHMCS advises administrators to delete planned or active email campaigns, clear the template cache, and update to a fixed release.

WHMCS disclosed and fixed three vulnerabilities, including CVE-2026-82981, an SQL injection flaw in its shopping cart that requires no login. Anyone able to access the shopping cart of a vulnerable internet-facing installation could potentially retrieve customer records and administrator account data, including password hashes. WHMCS assigned the flaw a CVSS 4.0 score of 8.7 and said it had not reported attacks using any of the three issues.

Fixed releases include WHMCS 9.0.10 and 8.13.8, while the advisory identifies version 9.1.2 as the fix for the 9.1 series. Installations running versions 8.0 through 8.12 must upgrade to a supported fixed release, and self-hosted administrators are responsible for installing updates; WHMCS Cloud is updated automatically. The other SQL injection, CVE-2026-82979, requires a logged-in client with the View & Manage Contacts permission and could expose other customers’ personal, billing, and support information, as well as administrator records and password hashes.

The third issue, CVE-2026-93700, affects email-campaign processing and could allow a logged-in client to read sensitive server configuration files, including database credentials, and run code on the server. It has a CVSS 3.1 score of 9.0, and its CVE record indicates some user interaction is required. In addition to updating, WHMCS tells administrators to delete every planned or ongoing email campaign and clear the template cache, though the advisory does not explain why existing campaigns must be removed.

  • The most urgent flaw can be reached by anyone able to load the shopping cart on a vulnerable internet-facing WHMCS installation, because it does not require a login.
  • Although the affected administrator passwords are stored as hashes rather than usable passwords, the article notes that attackers could attempt to crack stolen hashes offline.
  • Organizations running WHMCS versions 8.0 through 8.12 cannot receive a direct fix and must upgrade to a supported release.
  • For the email-campaign flaw, applying the update alone is not the full vendor-recommended response: administrators are also told to delete all planned or ongoing campaigns and clear the template cache.
  • WHMCS Cloud installations are updated automatically, but administrators of self-hosted installations are responsible for deploying the fixes.

WHMCS, software used by many web-hosting companies to manage billing and customer accounts, fixed a serious flaw that could let anyone online view customer records and protected administrator password data without signing in. The exposed information could include personal, billing, and support details, creating privacy risks and giving criminals material they may try to use to access accounts. Companies that run their own WHMCS systems need to update them, while WHMCS Cloud systems are updated automatically; another flaw also requires removing email campaigns and clearing stored page templates after updating.

Microsoft Fixes Azure API Management Classic Flaw as Actor Targets Customer Secrets

Microsoft closed a flaw in Azure API Management Classic that may have exposed stored secrets, subscription keys, and management tokens from improperly configured instances. Norwegian authorities say an unknown actor actively sought these credentials, prompting affected customers to identify and rotate secrets.
KEY POINTS
  • 01Microsoft identified and closed an access path affecting Azure API Management Classic tiers on November 19, 2026, while version 2 tiers were not affected.
  • 02The issue could have allowed unauthorized access to management functions and secrets in Classic instances that were not configured according to Microsoft’s documented security best practices.
  • 03Norway’s National Security Authority said an unknown actor was actively looking for access tokens, secrets, and named values in Azure API Management.
  • 04Potentially exposed information included named-value secrets, identity-provider and OpenID Connect client secrets, subscription keys, and tokens for direct management APIs.
  • 05Microsoft published guidance on November 21, 2026, to help customers identify and rotate credentials configured in their Azure API Management instances.

Microsoft fixed a security issue in Azure API Management (APIM) Classic tiers that could have allowed unauthorized access to certain management functions. The company identified the issue on November 18, 2026, and closed the access path the following day. APIM v2 tiers were not affected. Microsoft said customers were exposed if their services were not configured according to documented security best practices.

Norway’s National Security Authority (NSM) said an unknown actor had actively searched APIM for access tokens, secrets, and named values. NSM said the issue affected multiple Norwegian organizations, including energy companies Equinor and Skagerak Energi, as well as entities outside Norway, but it had not seen evidence of impact on Norwegian businesses. Microsoft said an unauthorized party could have accessed stored secrets before the issue was fixed.

Potentially exposed information includes Named Values secrets, client secrets for identity and OpenID Connect providers, subscription keys, and tokens used to call direct management APIs. Microsoft issued guidance on November 21, 2026, to help customers identify and rotate secrets and credentials configured in APIM. A researcher noted that a taken credential could be used against the protected service directly, depending on its permissions and whether it remains valid.

  • The risk extends beyond Azure API Management itself because any credential taken from its configuration could be used directly against the separate service it protects, depending on that credential’s permissions and validity.
  • Microsoft’s remediation closed the access path, but customers may still need to rotate previously stored secrets because exposure could have occurred before the issue was identified.
  • The issue was limited to Azure API Management Classic tiers, while v2-tier instances were not affected.
  • Although an unknown actor was actively seeking credentials and multiple Norwegian sectors were affected by the issue, Norway’s National Security Authority said it had not seen evidence of impact on Norwegian businesses.

Microsoft fixed a security problem in an older version of its Azure API Management service that may have let unauthorized people access stored passwords, keys, and other login information. Norway’s security agency said an unknown party was actively searching for this information, and several Norwegian organizations, including energy companies Equinor and Skagerak Energi, were affected by the issue. Microsoft says the problem was closed on November 19, 2026, but organizations using the older service may need to replace their stored credentials because stolen ones could still be used to reach other protected services.

Patching vCenter Zero-Day Is Only Step One

Broadcom’s patch for the actively exploited CVE-2026-123890 vCenter authentication bypass must be installed immediately, but organizations should also assume possible compromise if vCenter was reachable since September 2026. Hunt for attacker persistence and rotate vCenter SAML signing keys, privileged credentials, ESXi access, and potentially Active Directory secrets.
KEY POINTS
  • 01CVE-2026-123890 is a critical VMware vCenter Directory Service authentication bypass that can let a network-reachable attacker obtain an administrator@vsphere.local session without a password.
  • 02Google Threat Intelligence Group and Mandiant reported that the suspected China-nexus group ARMORY CASTLE exploited the flaw as a zero-day from early September 2026.
  • 03Broadcom released fixes on November 19, 2026, for vCenter 9.1, 9.0, and 8.0 product lines, while vCenter 7.0 has no public fix.
  • 04Attackers in the investigated intrusion stole vCenter’s SAML token-signing key, master encryption key, PostgreSQL password, and Active Directory data extracted from virtual-machine disks.
  • 05Patching prevents use of the login flaw but does not invalidate stolen signing keys, remove unauthorized accounts, or reverse credential theft, so the article recommends hunting for compromise and rotating affected secrets.

CVE-2026-123890 is a critical authentication bypass in VMware vCenter’s Directory Service that can allow a network-reachable attacker to obtain an administrator@vsphere.local session without a password. Google Threat Intelligence Group and Mandiant reported that the suspected China-nexus group ARMORY CASTLE exploited the flaw as a zero-day from early September 2026. Broadcom released fixes on November 19, 2026, and CISA added the issue to its Known Exploited Vulnerabilities catalog with a November 23 deadline for U.S. federal agencies.

In the investigated intrusion, attackers entered through a BeyondTrust Remote Support zero-day, moved through internal Linux appliances, and used a custom tool called BONESAW to take over vCenter through TCP port 2012. They copied vCenter’s directory database and SAML token-signing key, enabled SSH on the vCenter appliance, accessed ESXi hosts, and extracted Active Directory data from a virtual machine disk. The article stresses that patching is necessary but does not undo prior compromise, so affected organizations should hunt for unauthorized accounts and persistence, replace the SAML signing certificate, reset relevant vSphere and ESXi credentials, and consider Active Directory passwords exposed where domain-controller disks may have been accessed.

  • Keeping vCenter off the public internet did not prevent the reported intrusion, because the attackers first compromised a remote-support appliance and then reached vCenter from inside the network.
  • Replacing the vCenter SAML signing certificate is essential after suspected compromise because someone holding the stolen key can continue creating administrator login tokens even after the authentication flaw is patched.
  • An organization may need to treat its entire Active Directory environment as exposed if a domain controller’s virtual disk was accessible through compromised VMware hosts, since attackers extracted the directory database and registry files from a virtual machine disk.
  • The article says vCenter’s built-in appliance firewall cannot restrict access by individual port, meaning access controls managed through that interface may not adequately protect port 2012 or separate management services.
  • vCenter 7.0, as well as presumed-affected 6.5 and 6.7 systems, present a particularly difficult risk because there is no public fix for vCenter 7.0 and network restriction is the main protection until an upgrade or supported fix is available.

The article warns of a serious flaw in VMware vCenter, software companies use to manage large numbers of virtual computers, which let attackers take full control without a password. A suspected China-linked group reportedly used the flaw for months to steal powerful login materials, access server systems, and copy company directory data containing employee account passwords. Organizations using affected vCenter versions need to install the update quickly, but may also need to search for intruders and replace passwords and digital keys because installing the update alone does not undo earlier theft.
