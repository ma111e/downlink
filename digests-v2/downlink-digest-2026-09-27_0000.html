Citrix confirms two NetScaler RCE zero-days exploited in attacks

Citrix confirmed that two critical NetScaler RCE zero-days, CVE-2026-88771 and CVE-2026-88772, are actively being exploited and released patches for affected ADC and Gateway appliances. Organizations should urgently upgrade to the fixed builds or reduce Internet exposure until patching is possible.
KEY POINTS
  • 01Citrix confirmed that CVE-2026-88771 and CVE-2026-88772, two critical NetScaler remote code execution flaws with severity scores of 9.5, have been exploited as zero-days.
  • 02CVE-2026-88771 affects all NetScaler ADC and NetScaler Gateway deployments, including default configurations, and lets an unauthenticated attacker execute arbitrary commands because of improper input validation.
  • 03CVE-2026-88772 can enable remote code execution or denial of service when DTLS is enabled, which Citrix says is enabled by default on VPN virtual servers.
  • 04Citrix released patches for affected NetScaler ADC and Gateway versions, while Secure Private Access Hybrid deployments using NetScaler instances must also be upgraded to recommended builds.
  • 05The Dutch National Cyber Security Center reportedly warned organizations before public disclosure that exploitation had been identified at multiple Citrix customers worldwide.

Citrix confirmed that two critical NetScaler remote code execution zero-days, CVE-2026-88771 and CVE-2026-88772, have been exploited in attacks. The company released security updates for affected customer-managed NetScaler ADC and NetScaler Gateway appliances. These internet-facing devices are widely used for remote access and application delivery, so their compromise can provide attackers a route toward internal corporate systems.

CVE-2026-88771, rated 9.5, results from improper input validation and allows an unauthenticated attacker to run arbitrary commands on all NetScaler ADC and Gateway deployments, including default configurations. CVE-2026-88772, also rated 9.5, is a memory overflow that can cause remote code execution or denial of service when DTLS is enabled; Citrix says DTLS is enabled by default on VPN virtual servers. Before public disclosure, the Dutch NCSC reportedly warned organizations that exploitation had been found at multiple Citrix customers worldwide, and Citrix now advises affected administrators to upgrade promptly or reduce internet exposure until they can patch.

  • One of the flaws affects NetScaler deployments even in their default configuration, while the other applies where DTLS is enabled, which Citrix says is the default on VPN virtual servers.
  • Citrix discovered the issues while investigating incidents in customer environments, and the Dutch NCSC said exploitation had been identified at multiple Citrix customers worldwide before public disclosure.
  • The bulletin applies to customer-managed appliances; Cloud Software Group is handling updates for Citrix-managed cloud services and Citrix-managed Adaptive Authentication.
  • Because upgrades can cause downtime, the Dutch NCSC’s early warning was intended to let organizations prepare and deploy safeguards before patches became available.

Citrix says criminals are already taking advantage of two serious flaws in NetScaler devices, which many organizations use to let employees and applications connect to internal company systems from the internet. The affected customers are those that manage their own NetScaler ADC or Gateway devices, including some Secure Private Access Hybrid setups. If attackers take over one of these internet-facing devices, they may gain a way into a company’s internal network, so affected organizations should install Citrix’s updates as soon as possible or limit the devices’ internet access until they can.

Cloudflare fixes Containers cross-tenant flaw exposing customer data

Cloudflare fixed a cross-tenant storage flaw in its Containers and Sandboxes service that could have let paid Workers users recover residual data from other customers’ deleted container disks. Cloudflare says it completed mitigations, found no evidence of real-world exposure, and customers need take no action.
KEY POINTS
  • 01Cloudflare fixed a flaw in its Containers and Sandboxes service that could have allowed Workers Paid customers to recover residual data from other customers’ containers on the same physical host.
  • 02The issue arose because reused 64 KiB storage blocks were not fully cleared before being reassigned, leaving up to 60 KiB of prior data readable after a 4 KiB write.
  • 03Researchers reported the flaw through HackerOne on September 4 and found residual material on 18 of 24 container placements across 20 of 22 underlying nodes tested.
  • 04Cloudflare removed the configuration that skipped clearing reused blocks, retired existing container disks, and cleared cached snapshots by September 19, 2026.
  • 05Cloudflare said the researchers collected only aggregate test results rather than disk contents and that its review found no evidence of customer data exposure through this method.

Cloudflare fixed a cross-tenant flaw in its Containers and Sandboxes services that could have allowed Workers Paid customers to recover residual data from other customers’ containers on the same physical host. The issue was reported through HackerOne on September 4 by Oren Yomtov of Accomplish. Potentially exposed material included filesystem metadata, directory structures, SQLite database pages, Chromium profiles, configuration files, and credentials.

The flaw involved a shared storage pool that did not clear reused 64 KiB blocks before assigning them to a new customer’s container. By writing 4 KiB into an unused disk region, researchers could receive a reused 64 KiB block, potentially leaving the remaining 60 KiB readable if it contained prior customer data. Cloudflare removed the setting that skipped block clearing, retired existing container disks, cleared cached snapshots with old mappings, and said its review found no evidence that customer data was exposed through this method.

  • A write of only 4 KiB could cause allocation of a reused 64 KiB storage block, leaving the other 60 KiB potentially readable if it contained data from a previous customer.
  • The researchers found residual material in 18 of 24 container placements and on 20 of 22 underlying nodes they tested, indicating the condition was present across much of their test environment.
  • The reported method could not target a particular victim or host and could not read a disk while it was actively attached.
  • Cloudflare’s mitigation addressed both newly assigned storage blocks and historical exposure paths by retiring existing container disks and clearing cached snapshots with old mappings.

Cloudflare fixed a problem in its container service that could have let one paying customer find leftover files from another customer on the same physical machine. The leftover information could have included folder names, databases, browser profiles, configuration files, and credentials, although researchers say they did not view actual customer data during testing. Cloudflare says it found no evidence of misuse, removed the cause of the problem, and customers do not need to do anything; the issue matters because cloud services must keep each customer’s information separated from everyone else’s.

OPEN SOURCE ↗

This is a significant cross-tenant isolation failure in Cloudflare’s container platform that could have exposed filesystem and application data between customers sharing a host. Although Cloudflare reports no evidence of exploitation and has completed remediation, the finding is broadly relevant to organizations using Cloudflare Workers Paid, Containers, or Sandboxes.

Google Calendar Phishing: One Link, Two Scanner Verdicts

Attackers abused Google Calendar to send a fully authenticated phishing invite containing a Google redirect link to a domain registered only 29 minutes earlier, causing URL scanners to rate the trusted wrapper clean while the underlying destination received only a partial warning. The incident shows that email defenses must resolve and assess final destinations rather than trust platform redirectors or sender authentication.
KEY POINTS
  • 01An attacker placed a voicemail lure in a Google Calendar event description and invited a VIP mailbox at a digital advertising group, prompting Google to send an authenticated calendar notification.
  • 02The malicious destination voiceml[.]space was registered 29 minutes and 26 seconds before Google sent the notification, and the bare URL received a partial "Mixed Result" scanner verdict.
  • 03Google Calendar rewrote the lure link through a google.com redirector, which was scanned as clean even though its q parameter led to the same destination.
  • 04SPF, DKIM, and DMARC all passed because the message was genuinely sent by Google Calendar rather than forged by the attacker.
  • 05The recipient reported the suspicious message, and the message was mitigated after a human manual approval recorded the malicious finding.

An attacker created a Google Calendar event titled “New Voice Recording Received,” placed a voicemail-themed lure in its description, and invited a VIP mailbox at a digital advertising group. Google Calendar sent the notification through its legitimate infrastructure, with SPF, DKIM, and DMARC all passing. The message included a “Listen to voicemail” link that Google rewrote through its own google.com URL redirector.

The final destination, voiceml[.]space, was registered only 29 minutes and 26 seconds before Google sent the notification. A scan of the bare destination returned a partial “Mixed Result” verdict, while the Google redirect URL was marked clean, despite leading to the same site. The article argues that URL defenses should resolve redirectors and evaluate the final destination, while calendar notifications should assess the event organizer and Reply-To rather than relying only on Google’s trusted sender identity.

The message was ultimately reported by its recipient and mitigated after a human manual finding identified the voicemail link as malicious. The article notes that Google’s duplicated description text in hidden preview and metadata fields was normal template behavior, not attacker obfuscation. It presents the incident as an example of attackers borrowing trusted productivity platforms for delivery and authentication while using newly registered infrastructure that has little or no established reputation.

  • A clean verdict for a Google redirect URL assessed the trusted Google wrapper rather than the website ultimately reached by the recipient, demonstrating why redirectors should be resolved before reputation scoring.
  • Sender-history and authentication checks were ineffective by design because the attacker used Google’s legitimate Calendar notification service, which already had an established relationship with the recipient organization.
  • The event organizer and Reply-To address provided more useful attribution signals than the visible Google sender, because both pointed to an unrelated third-party mailbox.
  • The message body repeated the event description in hidden preview and metadata fields due to Google’s standard notification template, so treating those duplicates as attacker obfuscation would create a false finding.
  • The recipient’s report was the control that resolved conflicting automated URL verdicts and led to mitigation of the message.

An attacker created a real Google Calendar event with a fake voicemail message and invited a VIP employee at an online entertainment technology company. Google sent the invitation from its legitimate systems, making the message appear trustworthy and hiding the harmful website behind a Google web address. Automated checks gave different results depending on which link they examined, but the employee reported the suspicious invite before it caused harm. The case matters because criminals can use trusted everyday services to reach people, so a simple way for employees to report strange messages can prevent damage when automated tools miss them.

OPEN SOURCE ↗

This is a concrete phishing incident showing how attackers can abuse Google Calendar’s legitimate notification and URL-redirection mechanisms to bypass sender reputation and create conflicting link-scanning results. It is broadly relevant to email-security teams, though it does not describe a widespread campaign, major breach, or active exploitation of a software flaw.
