  • 03The attackers harvested credentials from 280 victims, obtained operating-system or domain secrets from 147, and gained administrator privileges at 12 organizations.

The campaign began on August 31 and used Netlas to generate lists of internet-accessible targets. It compromised at least 440 PaperCut instances linked to 395 organizations across 48 countries.   • The AI agents did not consistently honor the attacker’s list of countries to avoid, meaning the campaign also affected locations the operator had reportedly sought to exclude.
  • PaperCut deployments running on a domain controller or using a domain-administrator service account created a direct path for the attacker to add a new account to the Domain Admins group.
  • In every observed attack path, the attackers ultimately used DCSync to obtain a complete copy of domain credential data.

Cisco Talos reported that three threat clusters exploited two recently patched Cisco Secure Firewall Management Center (FMC) flaws: CVE-2026-20079 and CVE-2026-20316. CVE-2026-20079 is a maximum-severity authentication bypass that lets unauthenticated remote attackers execute scripts as root, while CVE-2026-20316 permits login through static credentials for a low-privileged account. The intruders used compromised FMC devices to deploy web shells, steal credentials, establish reverse shells and proxies, and in some cases deploy Qilin ransomware or Cyclops Blink malware.

Talos attributed UAT-11988 with high confidence to Qilin ransomware affiliates, which used the static credentials to conduct network reconnaissance, collect credentials and infrastructure data, and encrypt endpoint files. UAT-11823, attributed with high confidence to an actor whose tooling overlaps with the Sandworm group, exploited one or both flaws, used a modified license.tmp file and Cisco’s package_info.pl utility to obtain root-level execution, and deployed a Cyclops Blink variant. A third cluster, UAT-12197, exploited CVE-2026-20079 to install a web shell and a malicious JAR file that queried internal databases for authentication data; Cisco has released hotfixes for both flaws and urged customers to install them immediately.

  • Talos confirmed that UAT-11823 used both FMC flaws and the same malicious license.tmp mechanism cited in both Cisco advisories, resolving the previously unclear connection between the July exploitation activity.
  • Attackers abused legitimate FMC utilities, including package_info.pl, to run a modified license file as root, allowing malicious activity to blend with built-in management functions.
  • In the Qilin-linked activity, collected network and credential data was staged in publicly accessible files on the compromised FMC server and retrieved through HTTP GET requests before ransomware deployment.

Unmasking SCCM Application Execution

SCCM application deployments do not launch directly from CcmExec.exe; CcmExec uses CITaskMgr.dll to submit a WMI EnforceApp request, after which WmiPrvSE.exe loads SCCM provider DLLs and creates the deployed process. Defenders can detect anomalous SCCM application execution by correlating WmiPrvSE.exe instances that load AppProvider.dll with their child processes and baselining uncommon deployments.
KEY POINTS
  • 01SCCM client script execution typically produces a process chain in which CcmExec.exe launches PowerShell.exe, while SCCM client application execution can result in WmiPrvSE.exe being the parent of the deployed application.
  • 02For application deployments, CcmExec.exe loads CITaskMgr.dll, which submits a CCM_AppDeliveryType.EnforceApp request through WMI with deployment details including the application delivery type, content path, action type, user SID, and session ID.
  • 03WmiPrvSE.exe hosts AppProvider.dll and related SCCM DLLs, which process the WMI request and ultimately call CreateProcessW to launch the deployed application.
  • 04A detection approach can correlate WmiPrvSE.exe processes that load AppProvider.dll with their child processes, then identify uncommon child processes or command lines across SCCM clients.
  • 05SCCM package deployments followed a different chain in the author’s testing, using CcmExec.exe and Ccm32BitLauncher.exe without WmiPrvSE.exe.

The article examines why SCCM client script execution and client application execution create different process artifacts. Script execution commonly follows CcmExec.exe launching PowerShell.exe, while application execution can result in WmiPrvSE.exe launching the deployed program. This difference matters because detections focused on direct children of CcmExec.exe may miss SCCM application deployments used to run an unwanted executable.

The author’s analysis found that CcmExec.exe loads CITaskMgr.dll, which submits an asynchronous WMI request for CCM_AppDeliveryType.EnforceApp with deployment and execution-context details. WmiPrvSE.exe then hosts AppProvider.dll, ScriptHandler.dll, AppExcnLib.dll, and ccmcore.dll, ultimately using CreateProcessW to start the deployed application. A proposed detection method correlates a WmiPrvSE.exe process that loaded AppProvider.dll with its child process, then identifies uncommon child processes or command lines across SCCM clients; package deployments are a separate blind spot because they may use Ccm32BitLauncher.exe without WmiPrvSE.exe.

  • The connection between CcmExec.exe and WmiPrvSE.exe during SCCM application deployment is indirect: CITaskMgr.dll posts deployment details through an asynchronous local WMI request rather than CcmExec.exe directly creating the application process.
  • The specific WmiPrvSE.exe instance responsible for an SCCM deployment can be distinguished from other WMI provider processes by identifying one that loads C:\Windows\CCM\AppProvider.dll and correlating it to its child process using Sysmon process GUIDs.
  • An administrator or adversary can run PowerShell through SCCM application deployment, producing WmiPrvSE.exe rather than CcmExec.exe as PowerShell’s parent, but PowerShell Script Block Logging Event ID 4104 can still expose decoded script activity.
  • Package deployments were observed to use CcmExec.exe followed by Ccm32BitLauncher.exe and bypass WmiPrvSE.exe, meaning detection logic focused only on AppProvider.dll-loaded WmiPrvSE.exe does not cover that deployment method.

The article explains how Microsoft Configuration Manager (SCCM), a tool organizations use to install software and updates across many computers, starts applications in a less obvious way than it runs simple scripts. Organizations that use SCCM could be affected if an attacker abuses its software-deployment features to run unwanted programs on selected employee computers. This matters because normal SCCM activity can make malicious activity hard to spot, so defenders need to identify unusual programs launched through the SCCM process.

PuzzleMask: Abusing Plain Prose as a Covert AI Attack Vector

Check Point Research describes PuzzleMask, a plain-prose obfuscation technique that can hide policy-violating prompts from lightweight LLM gatekeepers while stronger, tool-enabled target models recover and act on them. The findings show that input-only “quick check” moderation is vulnerable and should be supplemented with paraphrasing, suspicious-pattern detection, and output/action monitoring.
KEY POINTS
  • 01Check Point Research introduced PuzzleMask, a technique that embeds a policy-violating prompt in ordinary-looking prose so a quick LLM gatekeeper may classify it as safe while a stronger target model recovers it.
  • 02The researchers tested 23 crafted prompts against gpt-4o-mini, gpt-oss-safeguard, Claude 3 Haiku, and Llama Guard 3, and every gatekeeper trial classified the crafted prompts as safe despite blocking the same payloads when sent plainly.
  • 03In tests using gpt-5-thinking with high reasoning effort and a Python code interpreter, the target recovered, considered, and acted on embedded instructions in 17 of 18 tested prompts.
  • 04The article recommends mitigations including paraphrasing untrusted input, adding a gatekeeper rule to flag quantitative self-referential phrases, monitoring model outputs and actions, and using a gatekeeper as capable as the target model.

Check Point Research describes PuzzleMask, a plain-prose technique for concealing a policy-violating instruction inside ordinary-looking text. It is designed to bypass a pipeline in which a fast LLM first screens prompts for safety before passing approved prompts to a more capable target model. The researchers emphasize that PuzzleMask is not itself a jailbreak: it can get an arbitrary hidden prompt considered by the target, but does not itself cause the target to override its own safeguards.

The researchers generated 23 crafted prompts based on requests to print a flag, reproduce the full lyrics to “Macarena,” or encrypt documents and remove the originals. In all reported gatekeeper trials, gpt-4o-mini, gpt-oss-safeguard, Claude 3 Haiku, and Llama Guard 3 classified the crafted prompts as safe, even though they blocked the same instructions in plain form. In target testing, gpt-5-thinking with high reasoning effort and a Python code interpreter recovered and acted on the hidden instructions in 17 of 18 trials; the article recommends paraphrasing untrusted input, detecting certain self-referential quantitative phrases, monitoring outputs and actions, and, where feasible, using a gatekeeper as capable as the target.

  • The attack depends on an imbalance in capability: successful target recovery in the reported tests required more than a minute of reasoning and more than two Python script executions, resources the quick gatekeepers did not have.
  • The researchers found that adding one policy clause directing a gpt-4o-mini gatekeeper to reject quantitative phrases that refer to the entire text caused it to flag all 23 crafted prompts, although they expect this approach to create false positives.
  • PuzzleMask bypasses an external screening step rather than the target model’s own safeguards, so it only gets a hidden instruction considered by the target and does not itself make the target disobey its safety training.
  • The technique reportedly failed against Anthropic Opus-class models because built-in classifiers terminated conversations when they detected the model processing an obfuscated prompt, illustrating the value of monitoring model behavior in addition to incoming text.

Researchers found that harmful instructions can be hidden inside ordinary-looking writing so that a quick AI safety check may approve the text, while a more capable AI later discovers and follows the hidden request. This can affect AI services that use a fast, cheaper model to screen what users submit before sending it to a stronger model that can reason longer or use tools. In tests, all of the quick checkers missed the hidden requests, while the target model recovered and acted on them in 17 of 18 attempts. The risk is that hidden requests could seek files, damage documents, request copyrighted material, or try to steer an AI’s behavior unless services also inspect what the AI does and says, not only what users initially send.

The malware was delivered through a multi-stage ClickFix infection chain that used finger.exe to retrieve a batch script, followed by downloads of IronPython, CastleLoader, CastleRAT, and a SloppyRAT DLL. SloppyRAT is designed to establish a foothold for reconnaissance, command execution, and movement to other systems within an organization. Its code contains multiple flaws, suggesting that the malware remains under development.

SloppyRAT uses several methods intended to hinder analysis and monitoring, including encrypted code that is decrypted while running, obfuscated strings, junk code, indirect Windows system calls, and certificate pinning for HTTPS connections. It communicates with its control server using JSON-formatted HTTPS requests, API-key authentication, session tokens, and RC4-encrypted system information and command results. Some variants can use a Polygon blockchain-based EtherHiding mechanism as a backup way to obtain control-server information, though ThreatLabz had not observed samples with a smart-contract address.

The malware supports 47 built-in commands that imitate PowerShell commands but are implemented directly in C++ using Windows APIs. It can also run PowerShell through the .NET runtime, start a PowerShell process with a falsified parent process, execute commands through WMI, and create a reverse SOCKS connection that can allow access to internal corporate systems. Its persistence code attempts to use a Windows Run registry key or COM hijacking, but both observed implementations omit required DLL execution details and appear not to function correctly.

  • Blocking outbound TCP port 79 and preventing execution of finger.exe can disrupt the observed initial delivery method, because the ClickFix chain used Finger protocol traffic to retrieve its next-stage script.
  • SloppyRAT’s certificate pinning verifies the SHA-256 hash of the entire server certificate, which prevents TLS interception tools from inspecting its traffic unless they present the expected certificate.
  • Many commands that look like PowerShell cmdlets are implemented directly in C++ with Windows APIs, so they can provide reconnaissance and system-management functions without launching PowerShell.
  • The malware’s two observed persistence methods appear incorrectly implemented: its Run key entry omits the DLL path and export, while its COM hijacking logic creates a new CLSID instead of replacing an existing one.
  • Although SloppyRAT includes a Polygon blockchain-based backup method for finding its control server, ThreatLabz had not identified samples containing the required smart-contract address, indicating that this capability had not been observed in active use.
