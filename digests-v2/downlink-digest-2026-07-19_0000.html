Hackers abuse ViPNet software to target Russian govt agencies

Kaspersky says there is no evidence ViPNet’s update infrastructure was compromised, and attribution to a Chinese-speaking APT is low confidence.
KEY POINTS
  • 01An advanced threat actor dubbed HelloNet is abusing the update mechanism for the ViPNet private networking product suite to target Russian organizations, including government agencies.
  • 02Kaspersky says HelloNet has impacted organizations in Russia’s government, energy, transport, education, and logistics sectors.
  • 03Attackers placed a malicious wtsapi32.dll file named HelloInjector inside the local ViPNet Update System directory so it would be sideloaded at system startup by the legitimate itcsrvup64.exe process.
  • 04HelloInjector injects into svchost.exe and runs an embedded payload called HelloProxy in memory, which contacts a command-and-control server to receive additional modules.
  • 05Kaspersky has tentatively attributed the campaign to an unidentified Chinese-speaking APT group with low confidence and recommends monitoring ViPNet systems for traffic on ports 5003, 5060, and 443.

An advanced threat actor is abusing the update mechanism for the ViPNet private networking product suite to target Russian organizations, including government agencies. The campaign is dubbed HelloNet and has been active since at least May. Kaspersky says it has impacted organizations in the government, energy, transport, education, and logistics sectors.

ViPNet is a Russian information-security product suite from InfoTeCS that provides VPN, endpoint and network access protection, firewall, certificate management, centralized administration, and secure messaging and file transfer. The software is commonly used in Russia and is certified for use in government and other regulated environments. The article notes that ViPNet’s market reach in Russia, especially among high-value organizations, has made it a frequent target for hackers.

In the latest campaign, attackers placed a malicious file named wtsapi32.dll, dubbed HelloInjector, inside the local ViPNet Update System directory so it would be sideloaded at system startup by the legitimate itcsrvup64.exe process. HelloInjector injects into svchost.exe, runs the HelloProxy payload in memory, and contacts a command-and-control server to receive additional modules including HelloExecutor, HelloCleaner, and HelloBackdoor. Kaspersky does not describe how the attackers gained initial access and does not claim that ViPNet’s update infrastructure was compromised.

  • The campaign abuses a local ViPNet Update System directory and a legitimate ViPNet updater process, but Kaspersky does not claim that ViPNet’s update infrastructure itself was compromised.
  • Because ViPNet is certified for Russian government and regulated environments, abusing it gives attackers a path into high-value organizations that are likely to trust the software.
  • The malware set includes a dedicated log-cleaning component, HelloCleaner, specifically designed to remove ViPNet log data and hide the malicious activity.
  • Kaspersky’s attribution to a Chinese-speaking APT is low confidence because it is based mainly on weak indicators, including an unused sina.com reference and a malware mirror hosted by the University of Science and Technology of China.
  • Traffic on ports 5003 and 5060 for HelloProxy and port 443 for HelloBackdoor is specifically highlighted by Kaspersky as monitoring focus for systems running ViPNet.

Critical NGINX Vulnerability Can Crash Workers and May Allow Remote Code Execution

F5 patched a critical NGINX heap buffer overflow, CVE-2026-42533, that can let unauthenticated attackers crash worker processes and may enable remote code execution in certain configurations. Organizations should upgrade to nginx 1.30.4/1.31.3 or NGINX Plus 37.0.3.1 because temporary mitigations may not fully close the issue.
KEY POINTS
  • 01F5 patched CVE-2026-42533 on July 15 in nginx 1.30.4, nginx 1.31.3, and NGINX Plus 37.0.3.1.
  • 02The flaw can let a remote, unauthenticated attacker trigger a heap buffer overflow in the nginx worker process using crafted HTTP requests.
  • 03Triggering the vulnerability can crash or restart the worker process and may allow remote code execution where ASLR is disabled or can be bypassed.
  • 04Exposure depends on configuration and involves a regex-based map whose output variable is referenced in a string expression after a capture from an earlier regex match.
  • 05F5’s temporary mitigation is to switch affected regex maps to named captures, but researcher Stan Shaw said upgrading is the only complete fix.

F5 shipped fixes for CVE-2026-42533, a critical nginx flaw that allows a remote, unauthenticated attacker to trigger a heap buffer overflow in the worker process with crafted HTTP requests. The issue was patched on July 15 in nginx 1.30.4 stable, nginx 1.31.3 mainline, and NGINX Plus 37.0.3.1. Triggering the flaw can crash or restart the worker process, causing denial of service, and F5 says it may allow remote code execution where ASLR is disabled or can be bypassed.

The vulnerability depends on configuration, not just version, and appears in a specific pattern involving a regex-based map whose output variable is referenced after a capture from an earlier regex match. The article explains that nginx’s two-pass script engine first measures the needed buffer size and then writes the result, but the shared capture state can be overwritten between those passes. As a result, the buffer may be sized for one capture while the write uses a different attacker-sized capture, producing an overflow controlled by the request.

F5 lists the flaw as affecting core nginx, NGINX Plus, NGINX Ingress Controller, Gateway Fabric, App Protect WAF, and Instance Manager, though fixed builds for the latter four were not listed at publication. F5 recommends upgrading and offers a temporary mitigation of switching affected regex maps to named captures, but researcher Stan Shaw says upgrading is the only complete fix because a narrower named-capture path remains. As of July 20, CVE-2026-42533 was not in CISA’s Known Exploited Vulnerabilities catalog and no public exploit code had appeared, while Shaw said he would publish a proof-of-concept 21 days after the patch.

  • The vulnerability is configuration-dependent, so simply running a vulnerable nginx version is not enough to confirm exposure; administrators need to inspect whether regex-based maps and capture variables are used in the specific ordering described.
  • Researcher Stan Shaw claims the bug can leak uninitialized heap data when the clobbered capture is smaller than the original, potentially providing the address information needed to bypass ASLR on a default Ubuntu 24.04 build.
  • F5’s suggested mitigation of switching affected regex maps to named captures may not fully address the issue, because Shaw says a map that defines the same named group as the location regex can still reach the overflow through another code path.
  • The article says no public exploit code or CISA Known Exploited Vulnerabilities listing existed as of July 20, but Shaw plans to publish a proof-of-concept 21 days after the patch, creating a limited window to upgrade before exploit details may become public.

F5 fixed a serious problem in NGINX, a widely used web server, that can let someone on the internet send specially made web requests to crash parts of the server and may even let them run their own code in some cases. Not every NGINX server is affected, but systems using certain configuration patterns in older versions of nginx, NGINX Plus, and related F5 NGINX products may be at risk. This matters because the issue can take websites or services offline, and researchers say a public demonstration of how to exploit it may be released soon, making upgrades especially urgent.

The Policy PDF That Hid Its Link From Every Scanner

A phishing email that passed SPF, DKIM, and DMARC used a mostly image-based PDF with hidden URI annotations to redirect finance leaders through a compromised WordPress site toward the Microsoft 365 admin portal. The key lesson is that authenticated email and clean static file scans do not prove safety when malicious links are embedded outside readable text.
KEY POINTS
  • 01A finance team at an insurance company received a “Revised Policy” email that passed SPF, DKIM, DMARC, and Microsoft compauth checks.
  • 02The attached scanned PDF was judged clean by static scanners because it contained no JavaScript, forms, macros, or embedded executables and had very little extractable text.
  • 03Forensic extraction found seven URI annotations in the PDF, including one that redirected through a compromised WordPress site to the Microsoft 365 admin sign-in portal.
  • 04The only visible text-level warning sign was a phone number in the signature block that was one digit different from the sender organization’s real published line.
  • 05Themis flagged the message at 90% confidence using behavioral and contextual signals and quarantined it across four affected mailboxes before anyone clicked.

A finance team at an insurance company received a “Revised Policy” email from a life-insurance administrator they had corresponded with before. The message passed SPF, DKIM, DMARC, and Microsoft compauth checks, and its visible body contained only a corporate signature block and data-protection disclaimer. The attached scanned PDF was named Policy_Revision...KY.pdf and was judged clean by static engines because it had no JavaScript, forms, macros, or embedded executables.

The malicious element was hidden in the PDF’s URI link annotations rather than in the email body or readable PDF text. Forensic extraction found seven URI annotations, including one that redirected through a compromised WordPress site to hxxps://admin[.]microsoft[.]com/AdminPortal/Home?ref=Domains. The article says this targeted admin-tier credentials for tenant takeover, because Microsoft 365 admin access can allow control over accounts, security settings, mail-flow rules, domains, and mailboxes.

The only visible text-level warning sign was a phone number in the signature block that was one digit different from the sender organization’s real published line. Themis flagged the message at 90% confidence using behavioral and contextual signals, including the low-text scanned attachment, redirecting link annotations, administrative sign-in destination, signature inconsistency, and VIP finance recipients. The message was quarantined across four affected mailboxes within minutes of delivery before anyone clicked.

  • Passing SPF, DKIM, and DMARC can still indicate that a real authorized sender infrastructure was used, which makes authenticated mail a useful delivery path for credential harvesting rather than proof of safety.
  • PDF URI annotations need to be treated as links during attachment analysis because they can exist outside the readable text that many scanners inspect.
  • A low-text scanned PDF can be suspicious when the business context normally calls for a text-based document such as a policy, invoice, or contract.
  • The final destination of a redirect chain matters more than the reputation of the first domain, especially when a link resolves to an administrative sign-in surface such as the Microsoft 365 admin portal.
  • Out-of-band verification should use already-known contact details because even a one-digit phone-number change in a signature block can redirect a callback to an attacker.

A finance team at an insurance company received a real-looking “Revised Policy” email from a sender they had dealt with before, and all the usual sender checks said it was legitimate. The attached PDF looked like a scanned document, but hidden clickable areas inside it led through a hacked WordPress site toward a Microsoft 365 admin sign-in page to steal high-level account access. This matters because those accounts can control an entire company’s email and Microsoft 365 setup, so one stolen login could let attackers take over much more than a single mailbox.

The affected packages were git_credential_manager versions 2.8.0 through 2.8.3, Dendreo versions 1.1.3 and 1.1.4, and fastlane-plugin-run_tests_firebase_testlab version 0.3.2. The releases were published directly to the registry with no matching commit or tag in the source projects, and two of the gems had been dormant for years before suddenly receiving new versions.

The malicious gems acted as loaders that checked for continuous integration environment variables and exited if they appeared to be running in a build system. On a developer machine, the loader downloaded deploy.sh and a native git-credential-manager binary from an attacker-controlled Forgejo host at git.disroot.org, using certificate verification disabled and a User-Agent of Git. StepSecurity ran the compromised versions with Harden-Runner in audit mode and captured the process tree, network connections, and file activity showing the full chain.

In git_credential_manager version 2.8.3, the installer copied the downloaded binary to $HOME/.local/share/gcm/git-credential-manager, launched it as a background daemon, and installed persistence through both a systemd user service and a cron entry named git-credential-manager. The script also probed the sudo and wheel groups and included a code path that, if run as root, planted a setuid root shell at /usr/local/sbin/ping6. The article advises anyone who installed or required the affected gems on a developer machine to treat the machine and all reachable secrets as compromised, remove the dropped artifacts and persistence, check for the setuid shell, and rotate credentials.

  • A clean CI run does not rule out compromise because the malicious gems deliberately exit when they detect common build-system environment variables, so developer-machine checks are necessary.

  • The attackers appeared to iterate their payloads in public: git_credential_manager 2.8.2 downloaded the payload but did not execute it, while 2.8.3 ran the full chain.
  • For git_credential_manager 2.8.2 and later, merely requiring the library can trigger the loader, so exposure is not limited to package installation time.
  • The article notes that credential harvesting and exfiltration live in the dropped native daemon rather than in the gem source itself, meaning file and process artifacts on developer machines are central to confirming impact.
