Microsoft shares manual fix for WSUS sync delays and timeouts

Microsoft provided manual cleanup steps for existing WSUS servers still suffering from synchronization delays and timeouts caused by excess publishing metadata. Admins should back up SUSDB, run Microsoft’s cleanup query, reindex and clean up WSUS, then reset IIS or recycle WsusPool to restore normal update scans.
KEY POINTS
  • 01Microsoft shared manual mitigations for Windows Server Update Services servers affected by a known issue that causes Windows Update scans to fail or time out.
  • 02The issue affects Windows 10 version 1607 and later, as well as Windows Server 2012 and later, and can prevent admins from deploying the latest Windows updates through WSUS or Configuration Manager.
  • 03Microsoft said synchronization times and operations have been restored for new WSUS installations and rebuilds after a service-side mitigation was rolled out.
  • 04For existing affected WSUS installations, Microsoft recommends backing up each SUSDB database, running a cleanup query against all SUSDB databases, and resetting MaxXMLPerRequest to its default setting.
  • 05After cleanup, Microsoft says administrators should reindex SUSDB, run the WSUS Server Cleanup Wizard, and run IISReset or recycle the WsusPool application pool to clear cached catalog state.

Microsoft shared manual mitigations for Windows Server Update Services servers affected by a known issue that causes Windows Update scans to fail or time out. The issue affects Windows 10 version 1607 and later and Windows Server 2012 and later. On impacted WSUS servers, administrators may be unable to deploy the latest Windows updates through WSUS or Configuration Manager because of increased synchronization times or sync operation timeouts caused by a buildup of publishing metadata.

Microsoft rolled out a service-side mitigation on Saturday for newly installed or rebuilt WSUS servers after heightened impact was observed starting July 13. The company said synchronization times and sync operations have been restored and are operating normally for new WSUS installations and rebuilds. For organizations with existing WSUS installations that still have long sync times, Microsoft said unneeded metadata can be safely removed.

Microsoft’s manual steps require administrators to back up each SUSDB database, run a cleanup query from SQL Management Studio against all SUSDB databases including WSUS replicas, and update the MaxXMLPerRequest value to its default setting. After cleanup, Microsoft says the first Windows Update scan may take longer than usual, but later scans should return to normal timing. Microsoft also recommends reindexing SUSDB, running the WSUS Server Cleanup Wizard, and running IISReset or recycling the WsusPool application pool to clear cached catalog state.

  • Microsoft’s service-side mitigation only restores normal synchronization for newly installed or rebuilt WSUS servers, so organizations with existing affected servers may still need to perform the manual cleanup.
  • The problematic metadata in existing WSUS installations can be safely removed, according to Microsoft, making database cleanup an endorsed remediation rather than a risky workaround.
  • Microsoft specifically says the cleanup query must be run against all SUSDB databases, including WSUS replicas, which means partial cleanup may not fully resolve the issue in replicated environments.
  • The first Windows Update scan after cleanup may still take longer than usual, so administrators should not treat one slow post-cleanup scan as evidence that the fix failed.
  • Microsoft says the client-side DataStore.edb file does not shrink automatically after the metadata is removed, but this is expected and does not affect scan performance.

Microsoft said some organizations’ Windows update servers were taking too long or failing when trying to get the latest update information, which could stop administrators from sending Windows updates to their computers. The problem affects existing Windows Server Update Services setups used with Windows 10 and Windows Server systems. Microsoft has already improved the issue for new or rebuilt servers, and it published manual steps for administrators with older affected servers so they can clean up unneeded data and get update checks working normally again.

  • 02LegacyHive was disclosed by a researcher using the handle Nightmare Eclipse and affects the Windows User Profile Service.

  • 04Microsoft said it is aware of the reported vulnerability and is actively investigating its validity and potential applicability.
  • 05ACROS Security provides micropatches for Windows 10 2004 or later and Windows Server 2022 or later, and says the flaw does not affect Windows versions older than Windows 10 2004 and Windows Server 2019.

Free unofficial patches are available for a recently disclosed Windows zero-day flaw called LegacyHive. The flaw allows attackers to escalate privileges on up-to-date Windows systems and was found in the Windows User Profile Service by a researcher using the handle Nightmare Eclipse. Microsoft said it is aware of the reported vulnerability and is actively investigating the validity and potential applicability of the claims.

After analyzing the proof-of-concept exploit, Tharros principal vulnerability analyst Will Dormann said non-admin users can exploit LegacyHive to modify the classes registry hive and gain automatic code execution when an admin account logs into a compromised device. ACROS Security CEO Mitja Kolsek said the vulnerability allows a regular non-admin user to mount any other user’s registry hive in full access mode, extract stored secrets, or modify registry values that affect what runs the next time that user logs in. Cybersecurity expert Kevin Beaumont confirmed that the exploit works and published LegacyHive detection queries for Microsoft Defender for Endpoint.

ACROS Security, the company behind the 0Patch platform, released free micropatches for Windows 10 2004 or later and Windows Server 2022 or later. The company said the flaw does not affect systems running Windows versions older than Windows 10 2004 and Windows Server 2019. According to ACROS Security, with 0patch enabled, the exploit still appears to work but loads a temporary user profile hive instead of the admin user’s hive, which is of no use to the attacker.

  • The unofficial 0Patch fix does not stop the exploit from appearing to run, but redirects it to load a temporary user profile hive that ACROS Security says is useless to the attacker.
  • LegacyHive can be abused without administrator rights, making it relevant to any scenario where an attacker or local user already has ordinary access to a Windows system.
  • Detection content for LegacyHive was published for Microsoft Defender for Endpoint shortly after the proof-of-concept was released, giving defenders an option to hunt for activity while Microsoft investigates.
  • The disclosed proof-of-concept was intentionally stripped down to make weaponization harder, but multiple experts still confirmed the exploit works.

A newly disclosed flaw in Windows, called LegacyHive, can let a regular user on an up-to-date Windows computer gain more control than they should, including changing settings that could make code run when an administrator logs in. It affects Windows 10 version 2004 or later and Windows Server 2022 or later, while older Windows versions are not affected. Microsoft is still investigating and has not released an official fix, but free unofficial patches are available from ACROS Security’s 0patch service.

New ENCFORGE Ransomware Targets AI Model Files in Langflow RCE Attack

A threat actor tracked as JADEPUFFER is exploiting an unauthenticated Langflow RCE flaw to deploy ENCFORGE, a new Go-based ransomware built to encrypt AI model weights, vector indexes, and training datasets. Organizations should urgently patch Langflow, rotate exposed credentials, remove unnecessary Docker socket access, and keep immutable backups of AI assets.
KEY POINTS
  • 01Sysdig linked a second attack on the same Langflow server to JADEPUFFER, an AI-agent-driven operator previously documented earlier in the month.
  • 02The attacker deployed ENCFORGE, a new compiled Go ransomware designed to encrypt AI-related files such as model weights, vector indexes, training datasets, PyTorch and TensorFlow checkpoints, SafeTensors, ONNX, GGUF, FAISS indexes, Parquet, Arrow, NumPy arrays, and TensorFlow records.
  • 03The entry point was CVE-2025-3248, an unauthenticated remote code execution flaw in Langflow versions before 1.3.0 affecting the /api/v1/validate/code endpoint.
  • 04After finding the Docker socket at /var/run/docker.sock, the operator created and revised six Python scripts through Langflow RCE to launch a privileged container, mount the host filesystem, copy ENCFORGE to the host, and run it with nsenter.
  • 05The article recommends upgrading Langflow to 1.9.1 or a current supported release, rotating credentials accessible to Langflow, removing unnecessary Docker socket access, alerting on privileged container behavior, and keeping model artifacts in offline or immutable snapshots.

Sysdig researchers linked a second attack on the same Langflow server to JADEPUFFER, the AI-agent-driven operator it documented earlier in the month. In this activity, the operator deployed ENCFORGE, a new compiled Go ransomware aimed at encrypting AI infrastructure files such as model weights, vector indexes, training datasets, and other host filesystem data. The entry point was CVE-2025-3248, an unauthenticated remote code execution flaw in Langflow versions before 1.3.0 affecting the /api/v1/validate/code endpoint.

ENCFORGE was recovered from the attacker’s command-and-control server as a hidden /.lockd file and was described as a UPX-packed static Go ELF. Its default extension list includes PyTorch and TensorFlow checkpoints, Hugging Face SafeTensors, ONNX, GGUF, GGML, FAISS indexes, Parquet and Arrow datasets, NumPy arrays, and TensorFlow records. The ransomware uses AES-256-CTR, wraps the per-run key with an embedded RSA-2048 public key, renames processed files with a .locked extension, drops ransom notes, and deletes itself after running.

After confirming code execution, the operator found the Docker socket at /var/run/docker.sock and adapted when an initial attempt to pull ENCFORGE failed. Over five minutes and 24 seconds, the operator created and revised six Python scripts through the Langflow RCE channel until it could create a privileged container, mount the host filesystem, copy ENCFORGE through /proc/<pid>/root, and run it on the host with nsenter. The article recommends upgrading Langflow to 1.9.1 or a current supported release, rotating credentials, removing unnecessary Docker socket access, alerting on privileged container behavior, and keeping model weights, vector indexes, and training datasets in offline or immutable snapshots.

  • ENCFORGE’s focus on LoRA adapters, GGUF and GGML weights, FAISS indexes, and training data shows the attacker is deliberately targeting AI infrastructure rather than using a generic file-locking tool.
  • The exposed Docker socket turned a vulnerable Langflow container into host-level control because the operator could create privileged containers with host PID, host networking, and read-write host filesystem mounts.
  • The attacker adapted quickly when its first payload delivery attempt failed, creating and revising six Python scripts in just over five minutes to reach the host through Docker.
  • Because ENCFORGE has no exfiltration capability, leak site, Tor portal, or observed data theft, its extortion pressure depends entirely on whether victims can restore encrypted AI files.
  • Patching Langflow alone is insufficient after compromise because the article states that AI provider keys, cloud credentials, database secrets, and other tokens accessible to the Langflow process may already have been harvested.

Attackers linked to JADEPUFFER broke into a vulnerable Langflow server and used a new program called ENCFORGE to lock up files used by artificial intelligence systems, including model files, search indexes, and training data. Organizations running older Langflow versions are affected, especially if the server can reach important AI files or has access to Docker controls that let attackers take over the host machine. This matters because rebuilding an encrypted production AI model could cost tens or hundreds of thousands of dollars and leave an organization without a clean way to restore its AI systems unless it has protected backups.

Recovery is described as unfinished when servers are restored, because quality and food safety teams must be able to stand behind the product before lines restart. It recommends that operators understand which IT systems production depends on, maintain visibility into plant networks and their connections, and use segmentation and separation to support evidence-based stop, contain, and restart decisions.

  • A food manufacturer may have to halt production because it cannot trust or access traceability, quality, labeling, or logistics records, even when there is no confirmed compromise of plant control systems.
  • In food and beverage operations, recovery from a cyber incident is not complete when servers are restored; production can only resume when quality and food safety teams can stand behind the product again.
  • Perishable inputs and outputs make downtime more costly in food manufacturing because raw materials keep arriving, finished products have shelf lives, and missed retail delivery windows can quickly create visible shelf gaps.
  • The article frames segmentation and separation as tools that buy operators decision-making options during an incident, as illustrated by Fairlife’s US operations being affected while Canadian operations were not.
  • The most actionable distinction is whether an operator can decide to stop or continue based on evidence from its own environment, rather than stopping simply because it lacks visibility into what systems are affected.

Fairlife, a dairy company owned by The Coca-Cola Company, temporarily stopped production across its U.S. operations after a ransomware incident affected some of its systems, including ones related to production; its Canadian operations were not affected and the company said product quality and safety were not impacted. The article explains that even if hackers are not confirmed to have reached the factory machines, food makers may still need to stop because they rely on computer records to know what to make, confirm ingredients and quality, label products correctly, and track where each batch goes. This matters because in food and beverage manufacturing, delays can waste perishable materials, leave store shelves empty, and make it unsafe or irresponsible to keep producing if the company cannot trust its records.
