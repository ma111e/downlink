Is Your SSO Protected Against Modern Credential Attacks?

SSO can reduce password sprawl and centralize access control, but it becomes a high-value target if not hardened. Organizations should protect SSO with strong password policies, phishing-resistant MFA, and tight controls over identity provider admin accounts, keys, secrets, and app permissions.
KEY POINTS
  • 01Single sign-on simplifies access by letting users log into multiple systems with one set of credentials, but that convenience can concentrate risk if the login is compromised.
  • 02Reports said attackers compromised a University of Pennsylvania PennKey SSO account and used it to access internal systems including VPN, Salesforce, Qlik, SAP, and SharePoint, resulting in theft of data on 1.2 million individuals.
  • 03The article says SSO can improve security when configured properly by reducing password sprawl, centralizing access policies, and making it easier to enforce multi-factor authentication.
  • 04The article recommends strong SSO passwords aligned with NIST guidance, including longer passwords and screening new passwords against blocklists of commonly used, expected, or previously compromised passwords.
  • 05The article recommends enforcing MFA consistently for SSO and moving toward phishing-resistant methods such as FIDO2 security keys, WebAuthn, or passkeys, especially for privileged users and sensitive systems.

The article explains that single sign-on, or SSO, simplifies access by allowing users to log into multiple systems with one set of credentials. It says this convenience can also concentrate risk, using the 2025 University of Pennsylvania breach as an example. According to reports cited in the article, attackers compromised a PennKey SSO account and used it to access internal systems including VPN, Salesforce, Qlik, SAP, and SharePoint. The breach resulted in the theft of data on 1.2 million individuals.

The article argues that SSO is not inherently insecure and can improve security when configured and protected properly. It says organizations should treat SSO as a critical security control because one login can open access to many systems. Recommended protections include strong passwords based on current NIST guidance, screening new passwords against blocklists of commonly used or compromised passwords, and avoiding legacy rules such as mandatory complexity requirements and routine password resets. The article also says MFA should be enforced consistently across users, applications, and access scenarios.

The article emphasizes that MFA should be strong enough to withstand modern credential attacks, noting that SMS codes and basic one-time passwords are less strong than phishing-resistant methods such as FIDO2 security keys, WebAuthn, or passkeys. It also says organizations should secure the systems and assets behind SSO, including identity provider administrator accounts, signing certificates, token-signing keys, OAuth secrets, refresh tokens, consent grants, and delegated permissions. The article promotes Specops Password Policy and Specops Secure Access as products for enforcing password policies and adding MFA to SAML and OIDC-based applications. It concludes that properly hardened SSO can reduce password exposure, support centralized access management, improve auditing, reduce helpdesk pressure, and make access easier to govern.

  • NIST guidance cited in the article emphasizes password length, usability, and compromised-password screening rather than older rules such as mandatory complexity and routine resets, which can drive predictable user behavior.
  • The article highlights that MFA strength matters: SMS codes and basic one-time passwords are described as better than passwords alone, but organizations are urged to prioritize phishing-resistant options for privileged users and sensitive systems.
  • The article treats identity provider administrator accounts, signing certificates, token-signing keys, OAuth secrets, refresh tokens, and consent grants as core SSO security assets that need protection alongside user logins.
  • The article notes that attackers may maintain access through risky third-party app permissions, so organizations should restrict user consent, require admin approval for sensitive permissions, and remove stale or overprivileged grants.

The article explains that single sign-on lets people use one login to reach many work systems, which is convenient but risky if that one login is stolen. It points to a University of Pennsylvania breach where attackers reportedly used a compromised PennKey account to access several internal systems and steal data on 1.2 million people. This matters because many organizations rely on this kind of shared login, so they need strong passwords, extra login checks, and close control over the systems that decide who gets access.

Tengu Botnet Reboots Compromised Linux Devices When Defenders Kill Its Process

Nozomi Networks analyzed Tengu, a Mirai-derived Linux botnet that persists through multiple startup mechanisms and can abuse hardware watchdogs to reboot devices when its main process is killed, giving it another chance to relaunch. The malware spreads via Telnet credential brute force and supports DDoS, proxying, command execution, updates, and additional ELF or APK payloads.
KEY POINTS
  • 01Nozomi Networks Labs analyzed Tengu, a Mirai-derived botnet that can use a compromised Linux device's hardware watchdog to trigger a reboot when defenders kill its main process.
  • 02Tengu was observed reaching Nozomi honeypots through Telnet credential brute force and includes samples for i386, amd64, MIPS, ARM, PowerPC, and m68k architectures.
  • 03The botnet supports 25 DDoS methods and can run a SOCKS5 proxy, execute shell commands, collect system and network data, update itself, and retrieve additional ELF or APK payloads.
  • 04Tengu uses multiple persistence mechanisms, including a detached guardian process, fake systemd service, init and RC scripts, shell startup file changes, an immutable installed binary, and a cron-based routine that Nozomi said appears unfinished or broken.
  • 05The analyzed sample was configured to communicate with a C2 server at 64[.]89.163.8 over TCP port 9931, while URLhaus independently recorded malicious Mirai-related hosting at that address but did not identify the files as Tengu.

Nozomi Networks Labs analyzed a new Mirai-derived botnet called Tengu that can use a compromised Linux device’s hardware watchdog to trigger a reboot when defenders kill its main process. The reboot gives Tengu’s other persistence mechanisms another chance to relaunch the malware. Nozomi observed the dropper reaching its honeypots through Telnet credential brute force.

Tengu supports 25 distributed denial-of-service methods and can also run a SOCKS5 proxy, execute shell commands, collect system and network data, update itself, and retrieve additional ELF or Android APK payloads. Nozomi listed architecture-specific samples for i386, amd64, MIPS, ARM, PowerPC, and m68k, but did not identify a specific vendor, device model, operator, infection count, or real-world DDoS victims. The report shows what Tengu can do, not how widely it has spread.

The malware uses several persistence and self-defense techniques, including a detached guardian process, a fake systemd service, init and RC scripts, shell startup file changes, and marking its installed binary immutable. It can also overwrite ELF headers of reboot and shutdown utilities with the string ELFOOD, which may interfere with normal restart or shutdown commands. The analyzed sample was configured to communicate with 64[.]89.163.8 over TCP port 9931, and URLhaus independently recorded malicious Mirai-related hosting at that address, though it did not identify those files as Tengu.

  • Tengu’s watchdog abuse turns a common defensive action—killing the malware process—into a recovery opportunity for the botnet because the device may reboot and allow other persistence mechanisms to relaunch it.
  • The article stresses that Tengu’s capabilities are well documented, but its real-world footprint is not: Nozomi names no device model, operator, infection count, or DDoS victims.
  • Defenders may not be able to rely on normal reboot or shutdown commands on infected devices because Tengu overwrites the ELF headers of hardcoded reboot and shutdown utilities.
  • URLhaus data supports that 64[.]89.163.8 hosted Mirai-related malicious files, but it does not prove those files were Tengu or that the C2 service and IPFS gateway were reachable.
  • Nozomi’s cleanup guidance implies that simply removing the visible malware process is insufficient; suspected devices should be checked across systemd services, init scripts, shell startup files, and cron-related paths before being returned to service.

Researchers at Nozomi Networks found a harmful program called Tengu that can take over poorly secured Linux-based internet-connected devices, especially ones reachable through Telnet with weak or default passwords. It is unusual because if someone stops its main program, it can force the device to restart so its hidden startup tricks may bring it back. Affected people and organizations are those with exposed devices such as internet-connected equipment or possibly Android TV boxes, though the article says no specific vendor, model, victim count, or real-world attack targets were confirmed. This matters because infected devices can be used to overwhelm websites and services with traffic, relay activity through the device, run commands, and download more harmful files.

24,650 Internet-Exposed BMCs Disclose IPMI Password Hashes Before Login

Researchers found 24,650 internet-exposed BMC/IPMI interfaces leaking password-derived hashes before login due to the unpatchable IPMI v2.0 flaw CVE-2013-4786, enabling fast offline password cracking. Organizations should remove IPMI from the public internet, block UDP 623, and rotate factory/default BMC passwords.
KEY POINTS
  • 01Lava found 36,872 internet-exposed server-management interfaces running IPMI, and 24,650 of them disclosed password-derived authentication hashes before login.
  • 02The exposure is tied to CVE-2013-4786, an information disclosure flaw in the IPMI v2.0 specification that allows remote attackers to obtain password hashes and perform offline password guessing attacks.
  • 03More than 30% of the returned hashes were associated with passwords recoverable using common wordlists and predictable factory chassis-sticker formats, according to researcher Michael Katchinskiy.
  • 04Lava said the exposure affected modern Supermicro and HPE servers operated by GPU providers, including systems still using factory-issued passwords.
  • 05Recommended mitigations include blocking UDP port 623 at the network edge, rotating factory-issued passwords during provisioning, restricting BMC access to a private management network, and disabling legacy or weak options such as IPMI 1.5.

Cybersecurity researchers at Lava found 36,872 internet-exposed server-management interfaces running IPMI, with 24,650 disclosing password-derived authentication hashes before login. The issue is tied to CVE-2013-4786, a high-severity information disclosure flaw in the IPMI v2.0 specification. Dell has said the problem is inherent to IPMI v2.0 and has no patch.

The flaw allows an unauthenticated remote party that can reach UDP port 623 to request an authentication response and test password guesses offline. Lava said more than 30% of returned hashes were associated with passwords recoverable using common wordlists and predictable factory chassis-sticker formats. The exposure affected modern Supermicro and HPE servers operated by GPU providers, including systems still using factory-issued passwords.

BMCs can control power, firmware, remote console access, operating system installation, and system recovery, and they run independently of the host operating system. Lava warned that in modern AI data centers, a single exposed BMC could potentially put multiple organizations’ workloads at risk through shared infrastructure or lateral movement. Recommended mitigations include blocking UDP port 623, rotating factory-issued passwords, disabling legacy or weak IPMI options, restricting BMC access to a private management network, and applying network access controls.

  • Dell’s advisory says the hash disclosure issue is inherent to the IPMI v2.0 specification and has no patch, making exposure reduction and access control more important than waiting for a software fix.
  • Lava’s tests found that HPE iLO factory passwords could be recovered within a minute on modern GPU hardware, while Supermicro factory passwords could be recovered in about an hour despite being uniquely assigned.
  • A significant subset of exposed BMCs returned authentication material even for an empty username, with 6,240 matching a weak password candidate.
  • The risk is amplified in modern AI data centers because a single exposed BMC in a shared bare-metal environment can potentially put multiple tenants’ workloads at risk.
  • The article notes evidence that threat actors are already targeting exposed BMC interfaces, including ransomware operators leaving an extortion note on an HPE iLO 4 login page.

Researchers found more than 36,000 server management interfaces reachable from the public internet, and about 24,650 of them can reveal password-based login clues before anyone signs in. This affects organizations running exposed server hardware from vendors such as Supermicro and HPE, including some GPU providers and AI data centers. It matters because these built-in management controllers can control servers at a very deep level, so if attackers guess weak or factory-set passwords, they could take over systems, stay hidden even after rebuilds, and put multiple organizations’ workloads at risk.

OPEN SOURCE ↗

This is a specific, high-impact research finding involving tens of thousands of internet-exposed BMC/IPMI interfaces, many of which disclose password-derived authentication material before login. It is broadly relevant because BMC compromise can bypass normal security controls, persist after rebuilds, and affect AI and bare-metal infrastructure, with the article also noting evidence that exposed BMC interfaces are already being targeted.

Two Joyfill npm Beta Releases Compromised to Deliver DEV#POPPER Remote Access Trojan

Two beta releases of Joyfill npm packages were compromised with an import-time implant that uses blockchain transactions to retrieve payloads and ultimately deploys a DEV#POPPER remote access trojan. Any system that imported the affected versions should be treated as potentially compromised, with credentials rotated and hosts investigated for persistence and C2 activity.
KEY POINTS
  • 01Two beta releases, @joyfill/layouts@0.1.2-2773.beta.0 and @joyfill/components@4.0.0-rc24-2773-beta.4, contained a malicious JavaScript implant that runs when the package is loaded rather than during installation.
  • 02The @joyfill/layouts implant can retrieve encrypted code through Tron, Aptos, and BNB Smart Chain transactions and reaches a recovered 77 KB Node.js remote-access trojan.
  • 03The recovered final payload can collect host information, open a Socket.IO remote-control channel, execute supplied JavaScript or shell commands, upload files, read clipboard data, and modify developer-tool files for persistence.
  • 04The @joyfill/components release contained the same malicious injection in multiple bundled files, but its published Rollup bundle limited normal execution by preventing the loader from resolving network dependencies.
  • 05The article recommends treating any machine that imported the affected versions as potentially compromised, isolating the host, preserving logs and dependency artifacts, and rotating reachable credentials from a separate uncompromised machine.

Two beta releases in the @joyfill npm namespace, @joyfill/layouts@0.1.2-2773.beta.0 and @joyfill/components@4.0.0-rc24-2773-beta.4, contained a malicious JavaScript implant. The implant runs when the package is loaded, not through an npm install lifecycle hook, so npm install --ignore-scripts does not prevent execution after import. Joyfill packages are used for embedding forms, documents, and PDFs into web and mobile applications, and the affected releases were beta versions.

Static analysis found that the primary branch of the implant resolves encrypted code through Tron, Aptos, and BNB Smart Chain transactions and reaches a recovered 77 KB Node.js remote-access trojan. A parallel branch launches a detached Node.js process, requests a boot payload from 23[.]27[.]13[.]43/$/boot, sends the marker header Sec-V: A9-0135-3, decrypts the response, and evaluates it. The loader has PolinRider-family indicators, while the recovered final JavaScript matches DEV#POPPER malware-family behaviors and command patterns described in the article.

The recovered payload can collect host information, establish a Socket.IO remote-control channel, execute supplied JavaScript or shell commands, upload files, read clipboard data, and modify developer-tool files for persistence. The article says any machine that imported the affected versions should be treated as potentially compromised, including development environments, CI runners, test tooling, server-side rendering systems, and build systems. Recommended actions include removing the affected versions from lockfiles, caches, mirrors, build images, and deployment artifacts; pinning to verified earlier versions; isolating affected hosts; preserving logs and dependency artifacts; and rotating reachable credentials from a separate uncompromised machine.

  • The compromise bypasses the common protection of using npm install --ignore-scripts because the implant runs when the module is imported, not during package installation.
  • The payload selection can be changed without publishing a new npm package because the loader retrieves pointers and encrypted code through public blockchain transactions.
  • The two affected packages’ weekly download counts overlap because @joyfill/components depends on @joyfill/layouts, and the affected versions were beta releases, so overall package popularity does not indicate how many users installed the compromised versions.
  • Source maps attribute the injected code to bundled source files, showing the implant was present at build time rather than added only to the final npm tarball.
  • The detached Node.js branch can keep running after the importing build, test, or command exits, making short-lived development or CI activity still capable of leaving an active malicious process behind.

Two beta versions of Joyfill software packages used by developers were secretly changed so that simply loading them could run hidden code. People and teams who installed and used those exact beta versions may have exposed their computers, build systems, or testing systems to a tool that lets an attacker control the machine, steal files, read clipboard data, and collect credentials. This matters because the affected packages are part of software development work, so a compromised developer computer or build system could put many other projects and secrets at risk.

Compromised npm Packages: @joyfill/components and @joyfill/layouts Ship an Obfuscated Remote Access Trojan

Malicious beta releases of @joyfill/components and @joyfill/layouts on npm contained an obfuscated import-time remote access trojan that could steal developer credentials and persist in common developer tools. Anyone who installed the affected 2773 prerelease versions should treat the environment as compromised, remove them, reinstall clean dependencies, and rotate exposed credentials.
KEY POINTS
  • 01On July 28, 2026, malicious beta versions of the Joyfill npm packages @joyfill/components and @joyfill/layouts were published to the npm registry.
  • 02The malicious code was injected into built distribution bundles and runs when an application imports the package, so npm install --ignore-scripts does not prevent execution.
  • 03The payload exposes Node.js require and module on the global object, resolves a command and control server through a public blockchain transaction, opens a Socket.IO remote access channel, and stages a Python credential stealer.
  • 04Affected versions include @joyfill/components 4.0.0-rc24-2773-beta.4 through beta.6 and @joyfill/layouts 0.1.2-2773.beta.0 through beta.2.
  • 05The article advises anyone who installed the affected 2773 prerelease versions to treat those environments as compromised, remove the versions, pin to known good releases, reinstall from a clean lockfile, and rotate exposed credentials.

On July 28, 2026, malicious beta versions of the Joyfill npm packages @joyfill/components and @joyfill/layouts were published to the npm registry. The affected versions were @joyfill/components 4.0.0-rc24-2773-beta.4, beta.5, and beta.6, and @joyfill/layouts 0.1.2-2773.beta.0, beta.1, and beta.2. StepSecurity says the packages are legitimate projects that were hijacked, and that the malicious code appears only in the published tarballs. The article rates the issue as Critical and says any repositories, CI/CD pipelines, or developer machines that installed the 2773 prereleases should be treated as compromised.

The payload was injected into built distribution bundles and runs when an application imports the package, rather than during installation, so npm install --ignore-scripts does not stop it. The code exposes Node.js require and module on the global object, uses obfuscation, resolves a command and control server through public blockchain transactions, opens a Socket.IO remote access channel, and stages a Python credential stealer. The trojan includes commands for host information, file upload and download, directory listing, and arbitrary code execution, and it attempts persistence by modifying files used by developer tools such as VS Code, Cursor, Discord, GitHub Desktop, and the global npm CLI. The article recommends removing the compromised versions, pinning to known good releases, reinstalling from a clean lockfile, inspecting affected developer tool files, reviewing network logs, and rotating credentials that were present on affected machines.

  • Using npm install --ignore-scripts would not have stopped this compromise because the payload was embedded in the package entry bundles and triggered only when the package was imported.
  • The malicious code appeared only in the published tarballs and not in matching source changes, making comparison against clean sibling releases an important way to confirm the injection.
  • The payload used blockchain transactions to discover its live command and control server, allowing the operator to avoid placing the real server address directly in the package.
  • The campaign specifically targeted developer workstations by inserting persistence into tools such as VS Code, Cursor, Discord, GitHub Desktop, and the global npm CLI.
  • StepSecurity’s sandbox detonation did not observe live C2 traffic, but the article attributes this to the likely takedown of the operator’s C2 and on-chain configuration after public disclosure.

Two legitimate Joyfill software packages on npm, @joyfill/components and @joyfill/layouts, had harmful beta versions published that ran hidden code when an app used them. Repositories, build systems, and especially developer laptops that installed the affected 2773 prerelease versions may have been exposed, because the code could let an attacker control the machine and steal saved passwords, developer tokens, browser data, and wallet keys. The bigger risk is that a trusted software dependency can quietly turn into a way to compromise developers and the projects they work on.
