  • 02The attack required a Python Apache Beam pipeline using --save_main_session without an explicit staging location, allowing a malicious replacement pickle file to execute on Dataflow workers.
  • 03Successful exploitation could expose the Dataflow worker service account’s identity and access token and enable code execution, data theft, or access to other GCP resources available to that account.
  • 04Google added ownership validation to Apache Beam Python SDK version 2.75.0 and deployed server-side checks that reject default staging buckets owned by another project.
  • 05Google also rolled out SHA-256 integrity verification for staged artifacts so Dataflow workers abort when a staged file has been modified after upload.

Varonis Threat Labs identified a cross-tenant Google Cloud Dataflow issue in which an attacker could calculate and claim a project’s predictable default staging-bucket name before the project used it. The affected scenario involved Apache Beam Python pipelines that did not specify a staging location and were the project’s first Dataflow job in that region to use the default bucket. If the job also used --save_main_session, the attacker could replace the uploaded Python session file with a malicious version. This could cause attacker-controlled code to run on the victim’s Dataflow workers without the attacker having access to the victim’s project.

The malicious session file could retrieve the worker service account’s identity and access token from the instance metadata server and send them to an attacker-controlled endpoint. The resulting impact depended on the worker service account’s permissions and could include credential theft, access to other GCP resources, data manipulation, or data exfiltration. Google addressed the issue with Apache Beam Python SDK ownership checks, Dataflow server-side validation that default staging buckets belong to the submitting project, and SHA-256 integrity checks for staged artifacts. The article notes that explicitly configured staging and temporary buckets remain the customer’s responsibility to secure, and that write access to staging storage should be treated like write access to source code.

  • The same malicious session file could execute on additional workers created later through autoscaling, not only on the workers initially launched for the job.

Researchers found that pre-October 2026 Windows Server domain controllers could be vulnerable to NTLM relay to LDAP even with LDAP signing enforced, by reusing an attacker-controlled signed LDAP session and stacking a victim bind with a privileged LDAP operation. KEY POINTS
  • 01Researchers described an NTLM relay technique that bypassed required LDAP signing by reusing an existing signed LDAP connection whose session key was known to the attacker.
  • 02The attack placed a victim’s final NTLM authentication message and a malicious LDAP modification request in the same signed SASL record, causing the domain controller to verify the record under the attacker’s original session while executing the modification as the victim.
  • 03The technique targeted plain LDAP on TCP port 389 and did not directly apply to LDAPS on TCP port 636 because TLS protects the connection differently and channel binding applies there.
  • 04The researchers tested domain controllers running Windows Server 2016 and later and reported that they were vulnerable until Microsoft’s October 2026 cumulative update, KB5126646.
  • 05Microsoft’s LDAP fix tracks identity changes on an LDAP connection and discards remaining data in a signed SASL record when the identity changes during processing.

Researchers described an NTLM relay technique that bypassed required LDAP signing on Windows Server domain controllers before Microsoft’s October 2026 update. An attacker could first establish a signed LDAP session using credentials or, where accepted, an anonymous NTLM SASL context, retaining a session key they controlled. They could then coerce a victim, such as a domain controller or server, to authenticate over SMB and relay that authentication through the existing LDAP connection.

The attack worked by placing the victim’s final authentication message and a malicious LDAP request into the same signed SASL record. The domain controller verified that record using the attacker-controlled session key, completed authentication as the victim, and then processed the malicious request with the victim’s permissions. This could enable computer-account takeover techniques such as resource-based constrained delegation or shadow credentials, potentially leading to DCSync and complete domain and forest compromise.

The technique applied to plain LDAP on TCP port 389 and did not directly work against LDAPS on port 636, where TLS protects the connection differently. Microsoft’s October 2026 fix, KB5126646, tracks identity changes during processing and discards remaining requests in a signed record if the connection identity changes. The article recommends patching domain controllers and servers, enforcing LDAP signing and channel binding together, restricting LDAP on port 389 where possible, and reducing NTLM use.

  • LDAP signing failed in this case because the server verified a whole protected data record only once, then allowed the connection’s authenticated identity to change before processing another request in that same record.
  • The Windows SMB client’s request for NTLM message signing, normally an obstacle to SMB-to-LDAP relaying, was required for the described reauthentication technique to work; HTTP/WebDAV authentication did not produce the same result.
  • Enforcing LDAP signing and channel binding together was still insufficient before the patch when plain LDAP on TCP port 389 remained reachable, because channel binding applies only to TLS-protected LDAP connections.
  • Microsoft’s fix did not change NTLM cryptography; it added connection identity tracking so the server discards any remaining requests after an identity switch occurs within a signed record.
  • The article states that an attacker could establish the initial signed LDAP session using valid domain credentials or, where accepted, an anonymous NTLM SASL context, potentially reducing the privileges needed to begin the attack.

CVE-2026-73570 is an unauthenticated Zimbra RCE flaw where a malformed SMTP recipient is logged and then executed by Swatchdog through an unsafe Perl shell call, granting code execution as the zimbra user. Upgrade to Zimbra 10.1.20 or later and monitor for suspicious child processes spawned from Swatchdog’s SNMP shell command.

  • 02A malformed recipient is written to /var/log/zimbra.log, where the Swatchdog daemon can match attacker-controlled text to a service-status pattern.
  • 03Swatchdog passes the service value into a Perl backticked command that invokes /bin/sh, allowing arbitrary commands to run as the zimbra user.
  • 04The article states that upgrading to Zimbra 10.1.20 or later is the only complete fix.
  • 05Elastic’s detection rule looks for a shell started by the Swatchdog Perl script that launches a process other than snmptrap.

CVE-2026-73570 is an unauthenticated command-injection vulnerability affecting unpatched Zimbra installations, fixed in Zimbra 10.1.20 and later. An attacker can send a specially malformed SMTP recipient address that Postfix records in /var/log/zimbra.log. The Swatchdog monitoring daemon can interpret attacker-controlled log text as a service-status message and invoke an SNMP notification command containing the injected content.

The vulnerable Swatchdog Perl code passes the service value through a backticked command, causing /bin/sh to execute arbitrary commands as the zimbra user. According to the article, that account can read every mailbox on the server and send mail as any local identity, enabling identity abuse and further targeting from the compromised mail server. The article recommends upgrading to Zimbra 10.1.20 or later and detecting exploitation by monitoring for processes other than snmptrap launched from the Swatchdog-related shell process.

  • Several public proofs of concept can appear to fail because they write payloads that Swatchdog does not match, which could lead testers to incorrectly conclude that a server is patched.
  • A successful exploit can be detected by looking for a process other than snmptrap launched by the shell that Swatchdog starts for its normal SNMP notification command.
  • The command runs as the zimbra user, an account that the article states can read every mailbox on the server and send email as any local identity.
  • The article’s test used an outbound callback to confirm command execution without making additional on-disk changes on the target.

The article explains a flaw in older Zimbra email servers that lets an outsider run commands on the server simply by sending a specially malformed email recipient address. Organizations using Zimbra versions before 10.1.20 are affected, because the server can mistakenly treat text recorded in its activity log as a command to run. This matters because someone who takes over the server can read mailboxes, send email while pretending to be local users, and use that access to target other people or systems.

New Evidence Shows LiteLLM Secret-Stealing Workflows Ran 11 Days Before Supply Chain Attack

Socket found that attackers ran malicious GitHub Actions workflows in the LiteLLM repository on October 10 and 12, 2026—up to 11 days before the malicious PyPI release—to exfiltrate organization and environment secrets. LiteLLM later linked the stolen GitHub token from the October 10 workflow to approval of the October 21 malicious release.
KEY POINTS
  • 01Socket recovered two malicious LiteLLM commits from October 10 and October 12, 2026, that added a GitHub Actions workflow named .github/workflows/cache.yml.
  • 02The workflows ran from temporary ci-tmp branches that were created and deleted the same day, allowing them to execute without remaining in the repository’s main branch history.
  • 03The October 10 workflow targeted six organization-level secrets, including GH_TOKEN and a GitHub App private key, while the October 12 workflow targeted 14 additional repository, organization, and environment-scoped secrets.
  • 04Both workflows encoded collected secrets and sent them to separate webhook.site endpoints, while using error suppression so the GitHub Actions jobs would report success even if transmission failed.
  • 05LiteLLM stated that its audit logs linked the GH_TOKEN stolen by the October 10 workflow to approval of the malicious October 21, 2026 LiteLLM release.

Socket reported that malicious GitHub Actions workflows ran in the BerriAI/litellm repository on October 10 and October 12, 2026, before the October 21 release-pipeline compromise that published malicious litellm==1.107.0 artifacts. The workflows were added through short-lived ci-tmp-<hex> branches that were created, used, and deleted within minutes, leaving the files absent from main. Repository Actions performance metrics recorded one successful cache.yml run on each date, placing confirmed malicious workflow activity at least 11 days before the release attack. LiteLLM later said its audit logs linked the GH_TOKEN stolen on October 10 to approval of the October 21 malicious release.

The October 10 workflow collected six organization-level secrets, including GH_TOKEN, a GitHub App private key, and API keys, then encoded them and sent them to a webhook.site endpoint. The expanded October 12 workflow used six jobs, including five bound to named GitHub Environments, to access 14 additional repository, organization, and environment-scoped secrets such as database, Redis, Linear session, and secret-scanning credentials. Both workflows used a trailing || true so their GitHub Actions jobs would report success even if the external transmission failed. Although Socket could reconstruct the activity using logs, metrics, surviving commits, and environment deployment records, it could not confirm whether the collectors received the data, how the initial access was obtained, or whether additional workflow cycles occurred.

  • Deleting the temporary branches did not erase all evidence: GitHub’s activity log, Actions performance metrics, surviving commit objects, and environment deployment records allowed Socket to reconstruct the workflow activity.
  • The October 12 workflow’s use of real environment names indicates that the attacker had enumerated LiteLLM’s environment inventory before creating the workflow, since binding jobs to those environments unlocked their separately scoped secrets.
  • A successful GitHub Actions run does not prove the stolen data reached the attacker, because both workflows used "|| true" to hide errors from the outbound request; however, the article notes that the expanded October 12 collection and lack of repeated targets are consistent with the earlier delivery succeeding.
  • The workflow did not need to modify the main branch to access secrets: a push to a temporary branch in the upstream repository was sufficient to trigger the workflow and make repository and environment secrets available.
  • The activity log identifies the authenticated account used for the branch operations, but it cannot establish whether that account holder acted personally or whether its session, access token, or SSH key had been stolen.

Attackers secretly added short-lived automated tasks to LiteLLM’s GitHub code repository on October 10 and 12, 2026, then used them to copy passwords, access keys, and login information to an outside website before deleting the temporary branches. The stolen information included credentials for GitHub, databases, AI services, Linear, and other internal systems, affecting LiteLLM and potentially its users and service accounts. This matters because the attackers had access for at least 11 days before a malicious LiteLLM software release was published, showing how a small hidden change in a software project can expose many connected services.

Cloudflare Introduces a Faster TypeScript Compiler Written in Rust

Cloudflare is bringing tsrs, a Rust port of the TypeScript compiler, into its Oxc toolchain, claiming up to 8× faster type checking and about 70% lower memory use than TypeScript 7.0 in matched tests. The project is working with Microsoft’s TypeScript team to maintain compatibility and upstream performance improvements, while also enabling browser and Cloudflare Worker use through WebAssembly.

  • 01Cloudflare announced that it is bringing tsrs, a Rust port of the TypeScript compiler, into its Oxc toolchain, with VoidZero taking on development and maintenance.
  • 02Cloudflare reports that tsrs is up to eight times faster and uses about 70% less memory than TypeScript 7.0 when compared using the same number of type-checking workers.
  • 03Microsoft’s TypeScript team is collaborating with tsrs maintainers, and some optimizations identified in tsrs are being incorporated into the official TypeScript compiler for TypeScript 7.1.
  • 04The tsrs project is being combined with Theo Browne’s tsc-rs work and is still addressing compatibility differences from the official compiler, including the order in which errors are reported.
  • 05The @tsrs/wasm package can check in-memory project files in browsers, but its current WebAssembly version runs on one thread and does not support watch mode or an editor language server.

Cloudflare announced that it is bringing tsrs, a Rust port of the TypeScript compiler, into its Oxc toolchain, with its VoidZero team taking responsibility for development and maintenance. The project began at Owner.com, where checking a large TypeScript backend consumed enough time and memory to make running multiple coding agents on a laptop impractical. Cloudflare says tsrs is up to eight times faster and uses about 70% less memory than TypeScript 7.0 when tested with the same number of type-checking workers.

The TypeScript team is collaborating with tsrs maintainers to understand performance improvements and determine which ones are safe to adopt upstream. Cloudflare notes that the eightfold figure is against TypeScript 7.0, while the TypeScript 7.1 beta is itself reported as up to 2.5 times faster than 7.0. tsrs also has a WebAssembly package that can check in-memory project files in a browser, although its current build is single-threaded, lacks watch-mode and editor language-server support, and has a 4 GiB memory limit per instance.

  • The reported performance gap should be interpreted carefully: tsrs’s headline eightfold comparison is against TypeScript 7.0, while Cloudflare says the TypeScript 7.1 beta is already up to 2.5 times faster than 7.0.
  • The TypeScript team says much of tsrs’s speed advantage is not solely due to Rust, and optimizations found by the Rust-port maintainers are already helping improve the official compiler.
  • For large projects and multiple separate AI-agent workspaces, reducing type-checking memory use can be as important as reducing runtime because each workspace may otherwise consume CPU and memory independently.
  • Although AI agents helped produce compiler ports quickly, tsrs’s practical value depends on ongoing compatibility work, including tracking TypeScript changes and resolving behavior differences such as diagnostic ordering.
  • Rust’s WebAssembly build enables in-browser checking of project files, but the current implementation is limited to one thread, lacks watch mode and language-server support, and is capped at 4 GiB of memory per instance.

Cloudflare is taking over development of tsrs, a version of the TypeScript code-checking tool rewritten in Rust, which it says can check large software projects much faster while using far less computer memory. This matters to developers and companies with large TypeScript applications, especially those running several AI coding assistants at once, because checking code can otherwise consume so much processing power and memory that laptops struggle. The team is working with Microsoft to keep the new tool consistent with the official TypeScript tool and to feed useful speed improvements back into it. A version that runs in web browsers could eventually let people check code directly on their own device instead of sending it to another server.
