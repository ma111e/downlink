Injective SDK on npm infected with cryptocurrency wallet stealer

Hackers compromised Injective Labs’ GitHub repository to publish malicious npm versions of its SDK and related packages that stole crypto wallet private keys and seed phrases when wallet functions were used. Developers who installed the affected version should assume wallets and secrets may be compromised, move funds to new wallets, and rotate credentials.
KEY POINTS
  • 01Hackers compromised a GitHub account belonging to a legitimate Injective Labs SDK project contributor and used it to publish malicious version 1.20.21 of the @injectivelabs/sdk-ts npm package.
  • 02The malicious package stole cryptocurrency wallet private keys and mnemonic seed phrases when developers used SDK functions that generate or import wallet keys.
  • 03The attacker also published version 1.20.21 for 17 other packages associated with the project, pinning all of them to the compromised SDK version.
  • 04Socket reported that the malicious package version was downloaded 310 times before it was deprecated, and Ox Security warned that 87 dependent packages had a cumulative download count of just over 112,000.
  • 05The legitimate account owner detected the compromise within minutes, reverted the changes, and published a clean release, version 1.20.23.

Hackers compromised a GitHub account belonging to a legitimate contributor to the Injective Labs SDK project and used it to publish a malicious npm package. The affected package was version 1.20.21 of @injectivelabs/sdk-ts, a TypeScript/JavaScript SDK used to build applications on the Injective blockchain. Security companies Socket, Ox Security, and StepSecurity detected the supply-chain attack.

The package has 50,000 weekly downloads and is used by developers building cryptocurrency wallets, trading bots, decentralized exchanges, DeFi applications, and payment tools. The attacker also published version 1.20.21 for 17 other packages associated with the project, pinning all of them to the compromised SDK version. Socket said the malicious version was downloaded 310 times before it was deprecated, while Ox Security reported that 87 dependent packages had a cumulative download count of a little over 112,000.

The malware activated when developers used SDK functions that generate or import wallet keys, rather than when the package was installed. It captured mnemonic seed phrases and private keys, encoded them in base64, and sent them through an HTTP POST request to an Injective Labs public infrastructure endpoint to make the traffic appear legitimate. The legitimate account owner detected the compromise within minutes, reverted the changes, and published a clean version, 1.20.23, while developers who suspect compromise were advised to transfer cryptocurrency to new wallets and rotate all secrets in their environment.

  • The malware did not run on installation, so compromise depends on whether developers used SDK functions that generate or import wallet keys after installing the affected packages.
  • The malicious code sent stolen wallet data to an Injective Labs public infrastructure endpoint, which made the outbound traffic appear legitimate.
  • Deprecation did not fully eliminate exposure because Socket reported that the malicious npm version was deprecated rather than removed and the malicious GitHub release artifacts were still available.
  • The attacker amplified the impact by publishing the same malicious version number across 17 related packages and pinning them to the compromised SDK version.

Hackers took over a legitimate contributor’s GitHub account for Injective Labs and used it to publish a tainted version of software that developers use to build apps on the Injective blockchain. The affected package was downloaded hundreds of times and could secretly copy the secret words and private keys that control cryptocurrency wallets when developers used wallet features. This matters because those secrets can let attackers move a victim’s cryptocurrency to their own devices, so affected developers are urged to move funds to new wallets and change other secrets.

Dormant GitHub Accounts Help Attackers Blend In While Mapping Corporate Orgs

Datadog Security Labs warns that attackers are using years-old dormant GitHub “ghost” accounts and compromised tokens to quietly enumerate corporate GitHub orgs, repos, and users via the GitHub API. Most activity targets public data for reconnaissance, but some cases escalated to cloning private repositories.
KEY POINTS
  • 01Datadog Security Labs warned of several overlapping campaigns systematically enumerating corporate GitHub organizations, repositories, and user accounts through the GitHub API.
  • 02The operators use automated scraping tools with custom or legitimate-sounding user agents, GitHub “ghost” accounts that are often years old, and compromised OAuth tokens or personal access tokens from legitimate users.
  • 03More than 50 dormant accounts and dozens of legitimate accounts with exposed or compromised personal access tokens were used to facilitate the enumeration.
  • 04The GitHub “ghost” accounts were created two to five years ago and left inactive for long periods before being used to issue API traffic across multiple organizations.
  • 05Most activity involved public data, but Datadog confirmed a few scenarios where attackers went beyond enumeration and cloned a private repository belonging to a single organization.

Datadog Security Labs warned of several overlapping campaigns systematically enumerating corporate GitHub organizations, repositories, and user accounts through the GitHub API. The operators rely on automated scraping tools with custom or legitimate-sounding user agents. They also use GitHub “ghost” accounts that are often years old, along with compromised OAuth tokens and personal access tokens from legitimate users.

Most of the activity targets public data, but Datadog said some cases went beyond public information enumeration. In a few scenarios, data access was confirmed and attackers took steps to clone a private repository belonging to a single organization. The campaign used more than 50 dormant accounts and dozens of legitimate accounts whose personal access tokens were exposed unintentionally or compromised through some other method.

The “ghost” accounts were created two to five years ago and intentionally left inactive for long periods before being used to issue API traffic across multiple organizations. Datadog said this helps the activity blend into normal GitHub API usage, especially because many API requests hit public endpoints and return successful responses. The concern is the aggregate pattern of accounts moving in sync across companies’ GitHub organizations over weeks, and in the worst case shifting from enumeration to cloning.

  • The use of GitHub accounts created two to five years earlier shows the operators deliberately built or preserved credibility over long periods before using the accounts for scraping.
  • The activity is difficult to spot because individual requests often look normal, hit public endpoints, and may not require authentication at all.
  • The main warning sign is not a single suspicious request but coordinated behavior across multiple accounts and companies over weeks.
  • Reconnaissance against public GitHub data can still create real risk because it can map an organization’s repositories, members, relationships, and project activity.
  • The same campaigns that mostly enumerate public data have, in some confirmed cases, progressed to cloning private repositories.

Datadog Security Labs says attackers are using old, inactive GitHub accounts and stolen access keys from real users to quietly look through companies’ GitHub pages and accounts. They mostly collected public information about company projects and the people connected to them, but in a few cases they also copied private code from a company. This matters because the activity can help attackers map how an organization works and, in the worst cases, reach sensitive software that was not meant to be public.

New GigaWiper Windows Backdoor Bundles Disk Wiping, Fake Ransomware, and Spyware

Microsoft analyzed GigaWiper, a Windows backdoor also tracked as BLUERABBIT, that combines spying and remote-control features with multiple destructive wipers disguised partly as ransomware. Defenders should focus on early detection and offline backups because once deployed, the malware can irreversibly destroy systems rather than enable recovery or ransom payment.
KEY POINTS
  • 01Microsoft analyzed a destructive Windows backdoor called GigaWiper that combines three older destructive programs into operator-selectable commands.
  • 02The same malicious files are tracked by Binary Defense as BLUERABBIT, and both reports list the same four hashes and matching command servers.
  • 03GigaWiper can wipe the physical drive, run fake ransomware based on Crucio that encrypts files without saving a key, or overwrite the Windows drive using a Go rewrite of FlockWiper.
  • 04The backdoor can also take screenshots, record the screen, open a hidden VNC session, collect system details, manage programs and services, edit the registry, and wipe Windows event logs.
  • 05Microsoft recommends watching for signals such as a recurring OneDrive Update scheduled task, RabbitMQ or Redis traffic from ordinary desktops, and processes using takeown and icacls on Windows boot files outside maintenance windows.

Microsoft analyzed a destructive Windows backdoor called GigaWiper, which combines three older destructive programs into operator-selectable commands. The same malicious files are also tracked by Binary Defense as BLUERABBIT, with both reports listing the same four hashes and matching command servers. Binary Defense, citing Google’s Threat Intelligence Group, ties the malware to a likely Iran-nexus group aimed at Israeli organizations, while Microsoft names no country.

GigaWiper can wipe a physical drive and its partition table, run fake ransomware based on Crucio that encrypts files with a key it never saves, or overwrite the Windows drive using a Go rewrite of FlockWiper. The article emphasizes that these actions leave no recovery path except rebuilding from clean backups, because wiped drives and files encrypted without a saved key cannot be restored. Microsoft also found links between GigaWiper, Crucio, and FlockWiper, including a recurring “GRAT” tag in debug paths and function names.

The backdoor also has spyware and remote-control functions, including screenshots, screen recording, hidden VNC access, system collection, process and service management, registry editing, and event log wiping. It hides as a OneDrive Update scheduled task, stores information under a OneDrive registry path, and uses RabbitMQ, Redis, and MinIO for command traffic, results, and exfiltration. Microsoft recommends watching for specific signs such as the recurring OneDrive Update task, RabbitMQ or Redis traffic from ordinary desktops, and unusual use of takeown and icacls on Windows boot files, along with blocking known command servers and enabling protective Microsoft security features.

  • GigaWiper’s use of RabbitMQ, Redis, and MinIO for command traffic and exfiltration can make malicious activity blend in on networks where those business services are already normal.
  • The fake ransomware component is especially destructive because it encrypts files but does not save the key, meaning payment or negotiation cannot restore the data.
  • The same malware being tracked as both GigaWiper and BLUERABBIT shows that defenders may need to correlate vendor reports by hashes and command servers rather than relying only on malware names.
  • The implant’s combination of spying, remote control, and multiple destructive options means finding it does not reveal whether the operator intends theft, surveillance, or system destruction.
  • Specific host and network signals, such as a one-minute OneDrive Update scheduled task and RabbitMQ or Redis traffic from ordinary desktops, give defenders concrete ways to look for activity before the wiper commands are used.

Microsoft found a harmful Windows program called GigaWiper that attackers can use after they have already broken into a computer. It can secretly watch what someone is doing, steal information, and then destroy the computer’s data in several ways, including by pretending to be ransomware even though there is no way to pay or recover the files. The same files were also reported under the name BLUERABBIT, and one report links it to a likely Iran-connected group targeting Israeli organizations. This matters because affected organizations can lose machines and data completely, so the broader risk is not just theft but lasting disruption.

Fake Braintree NuGet Package Skims Credit Cards and Harvests Merchant Credentials

A malicious NuGet typosquat, Braintree.Net, impersonated PayPal Braintree’s official SDK while stealing live payment card data, Braintree merchant API keys, and host secrets through a companion DependencyInjector.Core package. Any organization that used the affected packages should remove them, rotate credentials, investigate possible card-data exposure, and block the attacker domain.
KEY POINTS
  • 01Socket’s AI scanner flagged a malicious NuGet package named Braintree.Net that masqueraded as PayPal Braintree’s official .NET SDK and routed stolen data to api.348672-shakepay[.]com.
  • 02Confirmed malicious Braintree.Net versions 3.35.8 through 3.36.1 intercepted live payment card data, including full card numbers, CVVs, expiration dates, customer IDs, amounts, operations, gateways, card types, and timestamps.
  • 03The typosquat stole Braintree merchant credentials by sending merchantId, publicKey, and privateKey values to the attacker endpoint when a production gateway was configured.
  • 04Starting with Braintree.Net 3.36.0, the package depended on DependencyInjector.Core, which used module initializers to collect environment variables, appsettings JSON contents, cloud and container metadata, dependencies, and loaded assemblies on assembly load.
  • 05Socket recommended removing Braintree.Net, replacing it with the official Braintree package, rotating Braintree merchant credentials, auditing for DependencyInjector.Core, SipNet, and SipNet.OpenAI.Realtime, and hunting for outbound POSTs to api.348672-shakepay[.]com.

Socket’s AI scanner flagged a suspicious NuGet package, Braintree.Net, masquerading as the official PayPal Braintree .NET SDK, with the first malicious version published on July 3, 2026. The package copied the surface API, README content, metadata, and project URL of the legitimate Braintree library while using a different package name and version scheme. Socket’s Threat Research team found that affected versions routed stolen data to attacker-controlled infrastructure at api.348672-shakepay[.]com.

The malicious package intercepted live payment card data and stole Braintree merchant API credentials when used in production. Its added CardOperationLogger hooked payment-related methods to send card numbers, CVVs, expiration dates, customer IDs, amounts, and related transaction details to /api/card. Its modified BraintreeGateway.PrivateKey setter sent the merchantId, publicKey, and privateKey to /api/account when the gateway was configured for Braintree’s production environment.

Starting with Braintree.Net 3.36.0, the package also depended on DependencyInjector.Core, which used module initializers to run on assembly load and harvest environment variables, configuration files, cloud and container metadata, dependencies, and loaded assemblies. The article also identifies related affected packages, including DependencyInjector.Core, SipNet, and SipNet.OpenAI.Realtime, and notes that some were affected transitively. Recommended actions include removing Braintree.Net, replacing it with the official Braintree package, rotating Braintree credentials, treating production card data as potentially disclosed, auditing dependency graphs, blocking the attacker domain, and hunting for outbound POSTs to api.348672-shakepay[.]com.

  • The package’s reported popularity was misleading: roughly 11 million of its approximately 14 million downloads came from 120 empty placeholder versions, while the confirmed malicious releases had only about 334 real installs.
  • The payment-card and merchant-credential theft paths activated only for Braintree production environments, which reduced the chance of discovery during sandbox or development testing.
  • The companion DependencyInjector.Core harvester ran on assembly load through module initializers, so victim applications could leak environment and configuration secrets without calling any malicious API directly.
  • The attacker used different hiding strategies for different payloads: the card and account theft endpoints were plaintext strings, while the broader analytics/report endpoint was XOR-obfuscated.
  • SipNet became malicious through a manifest-only dependency change for .NET 8, .NET 9, and .NET 10 targets, while its own DLL remained a clean recompile of SIPSorcery.

A fake software package called Braintree.Net was uploaded to NuGet to look like PayPal Braintree’s real payment library, but it secretly sent credit card details, merchant login keys, and other server secrets to an attacker-controlled website. The people most affected are developers and businesses that accidentally installed this fake package, especially if they used it in real payment systems. This matters because stolen card numbers, CVVs, and merchant keys can lead to fraud, exposure of customer payment data, and access to sensitive business systems.
