ShinyHunters hacked Clop leak site using Grav CMS path traversal flaw

ShinyHunters breached and defaced Clop’s leak site by exploiting an unauthenticated path traversal flaw in outdated Grav CMS 1.7.43. Grav has backported the fix as version 1.7.53.4 and urges all 1.7 users to upgrade.
KEY POINTS
  • 01ShinyHunters breached and defaced Clop’s previous Tor leak site, after which Clop moved the site to a new onion address.
  • 02ShinyHunters said it exploited an unauthenticated path traversal flaw in Grav CMS 1.7.43 that could write uploaded files outside the intended temporary upload directory.
  • 03Grav confirmed the flaw as CVE-2026-42608 and said it affects Grav core rather than the Form plugin.
  • 04Grav 2.x releases had already been protected, but the fix was not initially backported to the Grav 1.7 branch.
  • 05Grav released version 1.7.53.4 with the backported fix and urged users still running the 1.7 branch to upgrade.

ShinyHunters breached and defaced Clop’s previous Tor-based data leak site, prompting Clop to announce a new onion address. ShinyHunters claimed it stole source code, Grav CMS plugins, server logs, and private keys for Clop’s Tor service, then demanded payment. Clop denied having a relationship or negotiations with ShinyHunters and disputed that the compromised server contained valuable operational or financial data.

Grav confirmed that the breach used CVE-2026-42608, an unauthenticated path traversal flaw in Grav core affecting the older 1.7 branch. The issue allowed a form-related identifier to include directory-traversal sequences, causing uploaded files to be written outside Grav’s intended temporary upload directory. Grav 2.x had already received the fix, but it was not initially backported to 1.7; Grav has now released version 1.7.53.4 and urges 1.7 users to upgrade.

  • The affected input was in Grav core, so updating or checking the Form plugin version alone would not address the issue; the installed Grav core version is what determines exposure.
  • Although Grav 2.x had been protected for months, the missing backport left older 1.7 installations vulnerable until Grav released version 1.7.53.4.
  • The fix uses a strict allowlist for form identifiers, accepting only letters, numbers, commas, underscores, and hyphens up to 64 characters, which prevents directory-traversal strings from being used in upload paths.
  • Clop said the compromised server contained only website content and no operational or financial data, while ShinyHunters claimed it obtained source code, plugins, logs, and Tor service private keys.

ShinyHunters broke into and replaced the Clop ransomware group’s public leak website after finding that its site software had not been fully updated. The weakness let someone use a website form to place files outside the folder where uploads were supposed to go. The software maker, Grav, has released an update for older sites using version 1.7, and owners should install it because the same flaw could affect other outdated Grav websites.

OPEN SOURCE ↗

The article documents exploitation of CVE-2026-42608 against Clop’s Grav CMS 1.7.43 site and confirms that older Grav 1.7 deployments were exposed until version 1.7.53.4. It provides a concrete update target and identifies that the flaw is in Grav core, not the Form plugin.

Elementor WordPress flaw lets attackers create admin accounts

Elementor versions 4.3.0 and 4.3.1 contained a CSRF flaw that could let attackers trick logged-in WordPress administrators into creating attacker-controlled admin accounts. Sites should update to Elementor 4.3.2, which fixes the issue.
KEY POINTS
  • 01Elementor versions 4.3.0 and 4.3.1 contain a cross-site request forgery flaw that can allow an unauthenticated attacker to create administrator accounts.
  • 02An attacker can exploit the issue by persuading a logged-in WordPress administrator to open a malicious link that triggers a permitted REST API action using the administrator's session.
  • 03The flaw stems from Elementor's Editor Events module bypassing WordPress REST nonce validation when the request URI contains the elementor/v1/events/ path, including in attacker-controlled query parameters.
  • 04Patchstack reported the issue to Elementor on September 22, and Elementor released a fix in version 4.3.2 two days later.
  • 05Users are advised to update to Elementor 4.3.2, which prevents the query-string bypass.

A cross-site request forgery flaw in Elementor Website Builder versions 4.3.0 and 4.3.1 could allow an unauthenticated attacker to create an administrator account on a WordPress site. The attacker must trick a logged-in administrator into opening a malicious link, which causes the administrator’s active session to perform a permitted WordPress REST API action. Elementor is active on 10 million websites, and the affected versions may be used by up to 2 million sites.

Patchstack said the issue arises because Elementor’s Editor Events module bypasses WordPress REST nonce validation when a request URI contains the elementor/v1/events/ path. Since attackers can place that path in query parameters, they can append it to requests aimed at other REST endpoints and make a logged-in user execute actions within that user’s permissions. The attack requires no JavaScript, attacker-controlled webpage, or submitted form, and links may be sent through email, chat, or site comments.

Patchstack reported the flaw to Elementor on September 22 after receiving it from researcher Saggre, and Elementor released version 4.3.2 two days later. The update prevents attackers from triggering the validation bypass through the query string. Users of Elementor are advised to upgrade to version 4.3.2 as soon as possible.

  • The attack can be delivered as a single link through email, chat, or a site comment and does not require JavaScript, a malicious webpage, or a submitted form.
  • Opening the link makes a logged-in WordPress user perform any REST API action allowed by that user’s existing permissions, so an administrator can be induced to create an attacker-controlled administrator account.
  • Only Elementor 4.3.0 and 4.3.1 contain the affected Editor Events proxy, but WordPress.org statistics indicate those versions may be used by up to 2 million sites.
  • Earlier Elementor releases are not affected by this specific issue, although the article notes that some of those older versions have other flaws that are already actively exploited.

A flaw in Elementor, a widely used WordPress website-building add-on, could let an attacker create their own administrator account on a website. The attacker would need to persuade someone already signed in as a site administrator to open a malicious link. The problem affects Elementor versions 4.3.0 and 4.3.1, which may be installed on up to 2 million sites, and a fix is available in version 4.3.2. An unauthorized administrator account could give an attacker control over the affected website.

OPEN SOURCE ↗

This reports a concrete, high-impact flaw in Elementor versions used by up to 2 million WordPress sites that can enable creation of attacker-controlled administrator accounts through a single malicious link. A fix is available in version 4.3.2, making prompt review and patching relevant for affected site operators.

A bipartisan coalition of 44 state attorneys general settled a lawsuit with Labcorp over a 2019 data breach affecting 10.2 million of the company’s customers. Labcorp will pay a $2.3 million fine and undertake broad reforms to its data-security practices. The breach originated at American Medical Collection Agency (AMCA), a debt collector that worked with Labcorp, and the wider incident affected 27.5 million people nationwide.

The settlement requires Labcorp to create an incident-response plan for vendor security failures, limit the data it shares with vendors, and establish a team to track vendor compliance with security practices. Labcorp must also add cybersecurity requirements to vendor contracts, require regular compliance audits from data collectors, and retain an independent expert to assess its information security. It must additionally separate data that debt collectors often combine for several clients, while AMCA’s earlier $21 million penalty was suspended after the company went bankrupt.

  • The settlement focuses heavily on third-party oversight, requiring Labcorp to build a vendor-risk team, impose security terms in contracts, and obtain routine audits from data collectors.
  • Labcorp must create a response plan specifically for security failures at vendors, recognizing that incidents at outside partners can expose its customers’ information.
  • The required separation of data held by debt collectors addresses the risk created when one collector combines information from multiple clients.
  • AMCA was previously ordered to pay a $21 million fine, but that penalty was suspended after the company went bankrupt, making the later settlement with Labcorp a separate avenue for accountability.

Labcorp agreed to pay $2.3 million and improve how it protects customer information after a 2019 incident involving its debt-collection partner, American Medical Collection Agency. Information belonging to 10.2 million Labcorp customers may have been exposed, while the wider incident affected 27.5 million people across the country. The settlement requires Labcorp to share less information with outside companies, check those companies more closely, and have a plan for responding when a partner fails to keep data safe.

Threat Actors Use Google Ads To Target Ledger Users

Zscaler identified a Ledger phishing campaign using fraudulent Google Ads and a rotating Google Cloud Storage, Vercel, and Google Sites redirect chain to steal users’ secret recovery phrases. The fake Ledger page collected wallet seed phrases through a bogus device-verification process, allowing attackers to access victims’ cryptocurrency without their physical hardware wallets.
KEY POINTS
  • 01In August 2026, Zscaler ThreatLabz identified fraudulent Google ads targeting Ledger hardware wallet users in the United States, Europe, and parts of Asia.
  • 02The ads sent users through Google Cloud Storage and changing Vercel-hosted redirects to Google Sites pages that displayed a fake Ledger page in an iframe.
  • 03The phishing page imitated Ledger’s interface and used a false device-verification process to ask users for their secret recovery phrases.
  • 04Submitted recovery phrases were sent to an attacker-controlled Vercel domain, potentially allowing attackers to restore victims’ wallets and transfer funds without the physical Ledger device.
  • 05The phishing page collected device metadata and interaction data, used an invisible hCaptcha widget during submission, and loaded a Cloudflare Web Analytics beacon.

In August 2026, Zscaler ThreatLabz analyzed a phishing campaign that used fraudulent Google ads to target Ledger hardware wallet users in the United States, Europe, and parts of Asia. The ads appeared under a long-standing, Google-verified advertiser profile and displayed google.com with a “10L+ visits” count that appeared to refer to Google rather than the phishing destination. Users who clicked the ads were routed through Google Cloud Storage and Vercel before reaching Google Sites pages that displayed fake Ledger content in an iframe.

The Vercel redirect domain appeared to change every 15–20 minutes, while the attackers continued using the same Google Cloud Storage page. The phishing site imitated Ledger’s interface, collected device and interaction data, and guided users through a fake device-verification process before asking for their secret recovery phrase. Submitted phrases were sent to an attacker-controlled Vercel endpoint, allowing attackers to restore compatible wallets and transfer funds without possessing the victim’s physical Ledger device.

  • The malicious ads appeared under a long-standing Google-verified advertiser profile with no observed prior malicious advertising, and the displayed “10L+ visits” count appeared to apply to google.com rather than the phishing destination.
  • The attackers could change the Vercel redirect domain approximately every 15–20 minutes while continuing to use the same Google Cloud Storage page, complicating domain-reputation-based detection.
  • The fake recovery-phrase form used the official 2,048-word BIP-39 English wordlist to provide autocomplete suggestions, making the credential-collection interface appear more credible.
  • After each recovery-phrase submission, the site displayed an “Invalid seed” error and requested another entry, but ThreatLabz did not observe server-side logic that compared the two submissions.
  • The phishing page recorded device details and visitor interactions such as keystrokes, touches, and mouse movements before sending data to a Vercel-hosted endpoint, which ThreatLabz noted could distinguish real visitors from automated analysis tools.

Researchers found fake Google ads aimed at people looking for Ledger cryptocurrency wallets. The ads led to convincing copycat Ledger pages that asked users to enter their secret recovery phrase, a set of words that can restore access to a wallet. Anyone who provides this phrase could have their cryptocurrency taken, even if they still possess their physical Ledger device. The attackers frequently changed parts of the web links they used, making the scam harder to identify and block.
