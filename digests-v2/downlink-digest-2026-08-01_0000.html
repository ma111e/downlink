Rails patches critical Active Storage flaw with RCE potential

Rails patched a critical Active Storage vulnerability (CVE-2026-66066) that can let unauthenticated attackers read arbitrary server files via crafted image uploads when libvips is used, potentially exposing secrets that enable remote code execution. Admins should urgently update Rails and libvips, rotate exposed credentials, and investigate for compromise.
KEY POINTS
  • 01Rails maintainers patched CVE-2026-66066, a critical Active Storage vulnerability that can let an unauthenticated attacker read arbitrary files from a Rails application and potentially escalate to remote code execution.
  • 02The flaw is exploitable when libvips is used and a vulnerable application allows image uploads from untrusted users, enabling attackers to upload a specially crafted image.
  • 03CVE-2026-66066 affects Active Storage before 7.2.3.2, 8.0.x before 8.0.5.1, and 8.1.x before 8.1.3.1, while Rails 6.x is affected only if Active Storage has been configured outside its defaults.
  • 04Rails recommends upgrading to libvips 8.13 or later and rotating the Rails secret_key_base, database credentials, Active Storage service credentials, and any other secrets accessible to the application process.
  • 05The Rails team initially withheld technical details but later published full details and forensic investigation tooling after public proof-of-concept exploits became available quickly.

Rails maintainers patched CVE-2026-66066, a critical vulnerability in the Active Storage framework. The flaw can allow an unauthenticated attacker to read arbitrary files from a Rails application and potentially escalate to remote code execution. Active Storage is the built-in Rails component used for handling file uploads and attachments.

According to the Rails security bulletin, the issue is exploitable when libvips is used and the server allows image uploads from untrusted users. An attacker could upload a specially crafted image and access application files, including the process environment. Those files may contain secret_key_base, database credentials, cloud storage credentials, and other secrets accessible to the application process.

CVE-2026-66066 affects Active Storage before 7.2.3.2, 8.0.x before 8.0.5.1, and 8.1.x before 8.1.3.1, while Rails 6.x is affected only if Active Storage has been configured outside its defaults. Rails recommends upgrading to libvips 8.13 or later and rotating exposed secrets, with a temporary block option available only for systems using libvips 8.13 or later. The Rails team published full technical details and forensic tooling after public proof-of-concept exploits appeared quickly, and Akamai warned that compromise of secret_key_base can translate into full remote code execution on the underlying server.

  • The risk is higher in common deployment paths because libvips is the default processor in official Rails Docker images and in Debian and Ubuntu setups, while ImageMagick users are not affected by this vector.
  • Credential rotation is a required recovery step because successful exploitation may expose the Rails secret_key_base, database credentials, cloud storage credentials, and other secrets available to the application process.
  • For systems already using libvips 8.13 or later, administrators can temporarily block the vulnerable functionality with VIPS_BLOCK_UNTRUSTED or Vips.block_untrusted(true), but there is no workaround for apps using older libvips versions.
  • The Rails team accelerated disclosure of technical details and forensic tooling because public proof-of-concept exploits appeared quickly, changing the risk balance from withholding details to helping defenders investigate.
  • Akamai warned that compromise of secret_key_base can let attackers forge session cookies, sign global IDs, and manipulate serialized data, which can translate into full remote code execution on the server.

Rails fixed a serious problem in its Active Storage file upload feature that could let someone who is not logged in upload a specially made image and read files from the server. This mainly affects Rails apps that accept image uploads from untrusted users and use libvips, including setups based on official Rails Docker images and Debian or Ubuntu. The danger is that those files may contain secret keys and passwords, which could let an attacker take over the application or reach databases, cloud storage, and other services.

This is a critical patch for widely deployed Rails software with unauthenticated arbitrary file read and potential remote code execution, and public proof-of-concept exploits appeared quickly. It is especially urgent because common Rails Docker, Debian, and Ubuntu setups may use the affected libvips path, and exposed secrets may require credential rotation and forensic investigation.

Hijacked Hotel Wi-Fi Pushes Fake Updates to Deliver Surveillance Malware

Microsoft says Russian-linked Storm-2945, a sub-cluster of Midnight Blizzard/APT29, is hijacking hotel Wi-Fi captive portals to redirect travelers to fake updates and Microsoft device-code login flows that deliver CornFlake surveillance malware or steal cloud access. Travelers should avoid installing anything offered through captive portals and use always-on full-tunnel VPNs where possible.
KEY POINTS
  • 01Microsoft says a fake browser update served over hijacked hotel Wi-Fi has been used to deliver CornFlake, a remote access trojan that can capture webcam images, microphone audio, and keystrokes.
  • 02Researchers track the operation as CaptiveCrunch and Microsoft attributes it to Storm-2945, assessed as an operational sub-cluster of Midnight Blizzard, also known as APT29 and Cozy Bear.
  • 03On compromised networks investigated by ReliaQuest, attackers with administrative control of the captive portal gateway could forge DNS answers and redirect a laptop’s automatic connectivity check to a fake browser or operating system update.
  • 04Since July 16, some CaptiveCrunch landing pages have redirected guests into Microsoft’s device code authentication flow, where entering an attacker-supplied code on Microsoft’s legitimate sign-in page can grant the attacker-controlled session MFA-satisfied access.
  • 05Microsoft reports that CornFlake can steal browser cookies and saved passwords, scan removable media, open a remote shell, and maintain persistence through a Registry Run key, a scheduled task, and a watchdog.

A fake browser update served through hijacked hotel Wi-Fi has been used to deliver CornFlake, a remote access trojan that can capture webcam images, microphone audio, and keystrokes. Microsoft tracks the operation as CaptiveCrunch and attributes it to Storm-2945, which it assesses as an operational sub-cluster of Midnight Blizzard, also known as APT29 and Cozy Bear. Microsoft has observed the traffic manipulation since early May across hospitality networks in several countries, but it has not named a hotel, venue, or captive portal vendor.

On networks investigated by ReliaQuest, the captive portal gateway also acted as the DNS resolver assigned to connected devices, allowing attackers with administrative control to forge DNS answers and redirect traffic. The gateway could send a laptop’s automatic connectivity check to a fake browser or operating system update page, but it did not silently infect endpoints; victims still had to download or execute the payload. Some pages used ClickFix instructions that told victims to open a terminal or Windows utility and run an attacker-supplied command.

Since July 16, some CaptiveCrunch landing pages have redirected guests into Microsoft’s device code authentication flow, where entering an attacker-supplied code on Microsoft’s legitimate sign-in page can grant MFA-satisfied access to an attacker-controlled session. Microsoft’s analysis says CornFlake can steal browser cookies and saved passwords, record clipboard contents, scan removable media, open a remote shell, and maintain persistence through a Registry Run key, a scheduled task, and a watchdog. Researchers also identified ChocoShell, an in-memory PowerShell stealer that collects Microsoft 365 and Azure Active Directory access and refresh tokens, plus Web Account Manager tokens, from Token Broker cache files.

  • The hijacked hotel gateway does not silently infect devices; users still have to download, execute, or run attacker-supplied instructions, making traveler awareness and refusal of captive-portal update prompts a critical control.
  • An always-on full-tunnel VPN is specifically recommended because it sends DNS queries through corporate resolvers before the hotel gateway can answer them, reducing the attackers’ ability to redirect traffic from the local network.
  • The campaign also targets cloud account access through Microsoft’s legitimate device code authentication flow, so compromise can occur even without installing malware if a guest enters the attacker-supplied code.
  • Microsoft found common equipment and management systems across affected networks, suggesting the issue may involve shared services in parts of the captive portal ecosystem rather than only isolated hotel compromises.
  • Public reporting does not quantify how often redirects led to successful malware execution, device-code approval, or stolen accounts, so the known activity is significant but its real-world success rate remains unclear.

Attackers took control of some hotel Wi-Fi sign-in systems and used them to send guests to fake browser or computer update pages. If a traveler followed the prompts, their device could be infected with spying software that can record things like webcam images, microphone audio, typing, screenshots, saved passwords, and online account access. Microsoft links the operation to a Russian government-associated hacking group, and the concern is that travelers in several countries could be tricked through networks they normally trust while away from home.

OPEN SOURCE ↗

This is a must-read because it reports active in-the-wild traffic manipulation on hotel Wi-Fi networks by a named Russian-linked threat cluster, delivering surveillance malware and attempting Microsoft device-code credential theft. The campaign affects travelers across hospitality networks in several countries and includes actionable defensive guidance such as avoiding captive-portal update prompts, using full-tunnel VPNs, and restricting device code authentication.

Adobe Campaign Classic CVSS 10.0 Flaw Could Run Code Without User Interaction

Adobe released security updates for Campaign Classic to fix a maximum-severity CVSS 10.0 flaw that could allow arbitrary code execution without user interaction, plus a high-severity SQL injection bug. Users should update to ACC v7 7.4.3 build 9398, with additional Adobe Bridge fixes also available.
KEY POINTS
  • 01Adobe released security updates for Campaign Classic to address a maximum-severity flaw tracked as CVE-2026-48449 with a CVSS score of 10.0.
  • 02CVE-2026-48449 is described as an incorrect authorization issue that could allow arbitrary code execution in the context of the current user without requiring user interaction.
  • 03The Campaign Classic update also fixes CVE-2026-48448, a high-severity SQL injection flaw with a CVSS score of 8.6 that could allow arbitrary file reads.
  • 04Adobe said it is not aware of any of the Campaign Classic flaws being exploited in the wild.
  • 05Adobe also released updates for Adobe Bridge to fix eight critical-rated flaws that could lead to privilege escalation and arbitrary code execution.

Adobe released security updates for Campaign Classic, its enterprise-focused marketing automation platform, to address a maximum-severity security flaw that could result in arbitrary code execution. The flaw is tracked as CVE-2026-48449 and has a CVSS score of 10.0. Adobe described it as an incorrect authorization issue that could allow code execution in the context of the current user without requiring user interaction.

The Campaign Classic update also fixes CVE-2026-48448, a high-severity SQL injection vulnerability with a CVSS score of 8.6. Adobe said this issue could enable arbitrary file reads. The company said it is not aware of any of the flaws being exploited in the wild, and both Campaign Classic issues have been addressed in ACC v7 7.4.3 build 9398 for Windows and Linux.

Adobe also shipped updates for Adobe Bridge to fix eight critical-rated flaws that could lead to privilege escalation and arbitrary code execution. The listed Bridge issues include untrusted search path, incorrect authorization, path traversal, and out-of-bounds write vulnerabilities. Adobe credited security researchers Kieran, also known as “kaiksi,” and “yjdfy” for discovering and reporting the Bridge flaws, and advised users to apply the latest updates for optimal protection.

  • The most urgent action is specifically to upgrade Adobe Campaign Classic v7 deployments on both Windows and Linux to version 7.4.3 build 9398, which is the fixed release named by Adobe.
  • The Campaign Classic flaws are especially serious because one could run code without any user interaction, while the other could enable arbitrary file reads, giving defenders two different impact paths to consider when prioritizing patching.
  • Although Adobe says it has not seen exploitation in the wild, the CVSS 10.0 rating means the Campaign Classic update should be treated as a top-priority preventive fix rather than deferred until attacks are reported.
  • Adobe Bridge users also need attention because the same update cycle fixes multiple critical-rated issues, including flaws tied to arbitrary code execution and privilege escalation.

Adobe released fixes for serious security problems in Adobe Campaign Classic, a marketing automation platform used by enterprises, and also fixed several problems in Adobe Bridge. The most serious Campaign Classic issue could let someone run their own code without the user doing anything, and another issue could let someone read files they should not access. Adobe says it has not seen these problems being used in real attacks, but users are advised to install the latest updates to stay protected.

Hackers Poison Adform Script to Swap Crypto Wallet Addresses Across Customer Sites

Attackers compromised Adform’s shared JavaScript tracking file to swap Bitcoin, Ethereum, and Tron wallet addresses on customer websites, creating a supply-chain risk for visitors who copied or entered crypto addresses. Adform removed the code and advises users to clear browser caches and verify wallet addresses before sending funds.
KEY POINTS
  • 01Attackers modified Adform’s trackpoint-async.js JavaScript file served from s2.adform.net to rewrite Bitcoin, Ethereum, and Tron wallet addresses on customer sites.
  • 02Adform detected the incident on July 27, 2026, removed the malicious code, notified affected clients, reported it to authorities, and advised users to clear browser caches and verify wallet addresses before sending funds.
  • 03The captured malicious code operated only while an affected page remained open and was not designed to install software or establish persistence, according to Adform.
  • 04The captured sample watched copy, cut, paste, and input events, rewrote text nodes and form fields, and attempted an HTTP request to 84.32.102.230:7744 with the page hostname and path.
  • 05The public scope remains unclear, including how many websites carried the altered file, how many visitors were exposed, how attackers reached Adform’s deployment path, and whether any funds were diverted.

Attackers modified a JavaScript file served by advertising technology company Adform, turning it into browser-side code that rewrote cryptocurrency wallet addresses. Adform detected the incident on July 27, 2026, removed the malicious code, notified affected clients, and reported it to authorities. Anyone who visited a site carrying the affected script on July 27 and copied a Bitcoin, Ethereum, or Tron address may have pasted a different address inserted by the malicious code instead.

The compromised resource was trackpoint-async.js, served from s2.adform.net, and Adform’s tracking code can run on one page, several sections, or across an entire website. Because the same shared resource could be used by unrelated downstream sites, the article describes the incident as a supply-chain compromise. The public scope remains unclear, including how many websites carried the altered file, how many visitors were exposed, how the attackers reached Adform’s deployment path, and whether any funds were diverted.

A captured sample contained two malicious blocks appended to the legitimate library, with replacement strings obfuscated using a six-byte XOR key. The code watched clipboard and input-related events, rewrote text nodes and form fields, hooked value setters for input and textarea elements, and attempted an HTTP request to 84.32.102.230:7744 with the page hostname and path. Adform says the code was not designed to install software or establish persistence and operated only while an affected page remained open, and it advised people to clear browser caches and check wallet addresses before sending funds.

  • Clearing the browser cache is specifically important because the altered Adform file may remain cached even after Adform removed the malicious code.
  • The address replacement was not limited to clipboard copying, because the captured script also rewrote values entered into input fields, textareas, contenteditable elements, and programmatic writes to form values.
  • A single compromised shared Adform resource could affect unrelated downstream websites without each site being separately breached, because Adform’s tracking code can be deployed across one page, multiple sections, or an entire website.
  • The exposure window cannot be confidently estimated because Adform’s notice identifies July 27 as the affected date while Kevin Beaumont reported seeing malicious activity via Adform over the prior week.
  • Traditional reputation checks may have provided little warning at the time, as Beaumont reported that the file and associated URLs, domains, and IP addresses had no VirusTotal detections when he checked.

Hackers changed a JavaScript file from Adform, an advertising technology company, so that websites using it could silently replace Bitcoin, Ethereum, or Tron wallet addresses with the hackers’ addresses. People who visited an affected site on July 27 and copied or typed a crypto wallet address may have pasted or submitted a different one without realizing it. This matters because one changed address at payment time could send money to the wrong place, and the same shared file may have reached many unrelated customer websites.

Coldcard Hardware Wallet Flaw Linked to $70 Million Bitcoin Theft in 41 Minutes

A Coldcard hardware wallet firmware flaw caused some devices to generate weak, predictable Bitcoin seeds, and researchers linked it to a 41-minute theft of about $70 million in BTC. Updating firmware is not enough for already-created seeds; affected users must create a new seed on patched firmware and move funds.
KEY POINTS
  • 01An attacker drained 1,196 Bitcoin addresses in 41 minutes on July 30, taking 1,082.65 BTC worth about $70.2 million at the time.
  • 02Galaxy Research mapped the sweep and tied it to a firmware flaw in Coldcard, the Bitcoin-only hardware wallet made by Canadian firm Coinkite.
  • 03Block traced the flaw to a March 2021 firmware integration error that routed seed generation to a deterministic software pseudorandom number generator instead of the STM32 hardware random number generator.
  • 04Coinkite shipped emergency firmware for affected Coldcard models and release tracks on July 31, but installing it does not repair an existing seed.
  • 05Coinkite advised owners with exposed seeds to generate a new seed on patched firmware and move their coins, because restoring an old seed to updated firmware or another wallet carries the weakness forward.

An attacker drained 1,196 Bitcoin addresses in 41 minutes on July 30, taking 1,082.65 BTC worth about $70.2 million at the time. Galaxy Research mapped the sweep and tied it to a firmware flaw in Coldcard, the Bitcoin-only hardware wallet made by Canadian firm Coinkite. No one has named the attacker, and Galaxy warned that the sweep pattern identifies the operator, not necessarily the theft, because such a movement can look like an owner moving coins.

The flaw came from a March 2021 firmware integration error that routed seed generation to a deterministic software pseudorandom number generator instead of the STM32 hardware random number generator. Block traced the issue to Coldcard’s production configuration and said an attacker who can determine or sufficiently constrain device-specific and timing information can reproduce candidate output streams offline, then compare derived addresses with public blockchain data. Coinkite estimated effective entropy at roughly 40 bits on the Mk3 and about 72 bits on the Mk4, Mk5, and Q, while Block did not provide one practical figure or a brute-force benchmark.

Coinkite shipped emergency firmware for every affected model and release track on July 31, but installing it does not repair an existing seed. The company told owners with exposed seeds to generate a new one on patched firmware and move their coins, because restoring an old seed to updated firmware or another wallet carries the weakness forward. Exposure depends on the firmware running when the seed was created, and affected ranges include Mk3 versions 4.0.1 through 4.1.9 according to Coinkite, Mk2 and Mk3 versions 4.0.0 through 4.1.9 according to Block, Mk4 and Mk5 before 5.6.0, Q before 1.5.0Q, and listed edge builds before their fixed versions.

  • Exposure depends on the firmware version running when the seed was created, not the firmware version installed on the device now.
  • Updating Coldcard firmware does not make an already-created weak seed safe, and restoring that old seed to another wallet carries the weakness forward.
  • Coinkite says seeds created with at least 50 fair, independent, private dice rolls are not at risk from this bug alone, but users should migrate if the number or privacy of rolls is uncertain.
  • A strong, unique BIP-39 passphrase creates a separate wallet that the seed words alone cannot reach, but Coinkite still recommends replacing the seed.
  • Multisig only helps when the required signing group is not made entirely from affected devices.

An attacker moved about $70 million in Bitcoin from 1,196 addresses in 41 minutes, and researchers linked the incident to a flaw in Coldcard hardware wallets made by Coinkite. The flaw meant some wallets created secret recovery words in a way that could be guessed under the right conditions, especially depending on the device model and the software version used when the wallet was first set up. People who created Coldcard wallets on affected versions may need to make a new wallet on fixed software and move their coins, because simply updating does not fix old recovery words. This matters because a mistake in how a wallet creates its secrets can put large amounts of cryptocurrency at risk even years later.

OPEN SOURCE ↗

This is a specific, high-impact incident involving a reported $70 million Bitcoin theft tied to a concrete Coldcard firmware flaw, with emergency firmware and migration guidance for affected users. It is especially important for professionals working with cryptocurrency custody, hardware wallets, or secure random-number generation, though its direct operational relevance is narrower than widely deployed enterprise software.

Even the Unsubscribe Link Installed a Remote-Access Tool

A phishing email disguised as a legitimate e-card rewrote every link, including Unsubscribe and Privacy, to a ScreenConnect remote-access installer, while passing SPF, DKIM, DMARC, and URL reputation checks. The key lesson is that clean authentication, reputable infrastructure, and legitimate software can still combine into a high-risk remote-access phishing attempt.
KEY POINTS
  • 01A data-protection analyst at a regional nonprofit health system received an e-card-themed email that used real greeting-card artwork hotlinked from the vendor's own image network.
  • 02Nearly every link in the email, including Help, About, Privacy, Terms, and Unsubscribe, was rewritten to a ScreenConnect remote-support installer requesting guest access.
  • 03Microsoft routed the message to Junk with spam confidence level 5, while Themis flagged it at 90 percent confidence and automatically resolved it as phishing.
  • 04SPF, DKIM, DMARC, ARC, and composite authentication all passed because the attacker sent the message from a free consumer mailbox they controlled.
  • 05Automated URL reputation checks returned clean verdicts because the links used legitimate ScreenConnect platform infrastructure, and the installer was signed commercial remote-support software rather than scanner-defined malware.

A data-protection analyst at a regional nonprofit health system received an email that looked like a legitimate e-card notification. The message used real greeting-card artwork hotlinked from the vendor’s own image network, but nearly every link in the body had been rewritten to download a ScreenConnect remote-support installer requesting guest access. This included not only the main button, but also social icons, Help, About, Privacy, Terms, and Unsubscribe.

Microsoft routed the message to Junk with spam confidence level 5, and Themis flagged it at 90 percent confidence and automatically resolved it as phishing. Automated URL reputation checks rated both destination links clean, because the abused ScreenConnect platform domain was legitimate and long established. The article emphasizes that the vendor was not breached; rather, its self-service platform was used as designed by an account that should not have existed.

The attack passed SPF, DKIM, DMARC, ARC, and composite authentication because the sender used a free consumer mailbox it actually controlled. The payload was not a fake sign-in page or scanner-defined malware, but signed commercial remote-support software delivered in an unsolicited greeting-card email. The article maps the activity to MITRE ATT&CK techniques for spearphishing links, user execution of a malicious file, and remote access software abuse.

  • The strongest signal was not any single suspicious link but the message-level pattern that nearly every anchor in the template, including boilerplate links users may trust more than the main button, resolved to the same installer.
  • Email authentication offered no protection in this case because the attacker did not spoof a domain; the checks accurately confirmed control of the sending mailbox while saying nothing about whether the message was safe.
  • Domain reputation failed structurally because a long-established remote-support platform’s clean parent-domain history could be inherited by short-lived self-service subdomains created for abuse.
  • The payload avoided typical phishing indicators by delivering legitimate signed remote-support software instead of a fake login page or scanner-defined malware.
  • The article highlights Junk routing as insufficient containment because users may retrieve messages from Junk when they are expecting legitimate mail.

A data-protection analyst at a regional nonprofit health system received an email that looked like a real greeting card, but nearly every link in it, even Unsubscribe and Privacy, led to a remote-access installer that could give someone outside the organization control of a computer. The email looked trustworthy because it used real greeting-card images, came from a real free email account, and passed standard checks that only prove the sender controls the account. This matters because a hospital or health system can be put at risk by an ordinary-looking message that uses legitimate tools in the wrong way, bringing an attacker one step closer to systems used in care and operations.

It is not a major breach, critical patch, or named threat actor operation, but the technique is actionable and shows how standard reputation and authentication checks can miss dangerous messages.
