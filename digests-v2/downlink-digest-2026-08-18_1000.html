CoSnitch: When Your AI Assistant Becomes Its Own Whistleblower

The key takeaway is that AI assistants with broad enterprise access can become silent data-theft channels when trusted workflows like links, connectors, and web summarization are abused.

Varonis Threat Labs uncovered a one-click vulnerability chain in Microsoft Copilot Personal called CoSnitch, which could exfiltrate enterprise data through a trusted Copilot workflow without obvious red flags. The researchers said Copilot surfaced its own weakness during normal use through a method they call meta-hacking. Varonis disclosed CoSnitch to Microsoft in December 2025, and patches were shipped on August 18, 2026.

CoSnitch was made possible by three Microsoft Copilot issues: automatic prompt execution, data exfiltration to external servers, and persistent memory poisoning through web summarization. The automatic execution issue used a ?q= URL parameter together with an undocumented autorun parameter so an attacker-supplied prompt could run on page load with no confirmation. Once triggered, Copilot could process the injected prompt using the victim’s active session, connected apps, and memory.

The article explains that an injected prompt could query connected services such as Gmail, Drive, Calendar, and OneDrive, encode retrieved results into a URL, and use Copilot’s built-in URL-fetch capability to send data to an attacker-controlled webhook. It also describes how a crafted webpage summarized by Copilot could place attacker instructions into the user’s persistent memory store. Varonis said it saw no evidence that the attack had been exploited in the wild and recommended auditing Copilot connectors, treating Copilot as a privileged insider, reviewing link-delivery risks, and verifying monitoring coverage.

  • The persistent memory poisoning survived password changes, session revocation, and device re-enrollment, meaning standard incident-response steps would not remove the injected instructions.
  • The attack chain did not require breaking Gmail, Google Drive, Calendar, OneDrive, or OAuth because it abused access the user had already granted to Copilot.

Blockchain Dead Drop Resolvers Explained

Malware increasingly uses public blockchains as dead drop resolvers, fetching live C2 addresses from smart contracts or transaction data instead of hardcoding infrastructure. Defenders should hunt for non-browser processes making blockchain RPC calls and decode the contract or memo responses to identify the active C2.
KEY POINTS
  • 01A dead drop resolver is a mechanism where malware fetches its command-and-control address at runtime from a third-party, attacker-controlled location instead of hardcoding it.
  • 02The article describes eight unrelated malware families across EVM, Solana, and TON blockchains that use blockchain-based dead drop resolver techniques.
  • 03The August 2026 ChainDrop, also called “mini Shai-Hulud,” compromised more than 440 npm packages and used an Ethereum eth_call dead drop to resolve its command-and-control destination.
  • 04Blockchain dead drop resolvers are difficult to disrupt because public blockchains resist censorship, allow operators to update one contract value to redirect deployed malware, and let traffic blend with legitimate cryptocurrency services.
  • 05The article recommends detecting these threats by examining the RPC URL, contract address, function selector, decoded result, and process context of suspicious blockchain RPC calls.

The article explains blockchain dead drop resolvers, a technique where malware fetches its command-and-control address at runtime from an attacker-controlled location instead of hardcoding it. It describes eight unrelated malware families across EVM, Solana, and TON blockchains using this core trick. One highlighted case is the August 2026 ChainDrop, also called “mini Shai-Hulud,” npm supply-chain compromise, which affected more than 440 npm packages and used an Ethereum eth_call dead drop.

The technique matters because public blockchains make the command-and-control pointer harder to disrupt, allow operators to update one contract value to redirect deployed loaders, and let traffic blend into high-reputation cryptocurrency services. EVM-based variants use read-only JSON-RPC eth_call requests to public nodes, while Solana variants pull payloads from memo fields in transactions and TON variants call get_domain on smart contracts. The decoded values can include IPs, URLs, domains, JavaScript, bash stagers, or other command-and-control pointers.

The article recommends hunting by extracting the RPC URL, contract address, function selector, decoded result, and process context from suspicious blockchain RPC calls. It emphasizes that the decoded result is the key artifact for blocking and pivoting, while process context helps distinguish malware from benign wallet or browser activity. Netskope states that Netskope One Threat Protection Intrusion Prevention System detects blockchain dead drop resolver RPC patterns.

  • For EVM-based cases, the combination of contract address and four-byte function selector is a practical hunting discriminator because different selectors on the same dispatcher contract can return different payloads.
  • A blockchain dead drop may become stale even when the contract remains live, as shown by ChainDrop returning 0x after operators cleared the stored value.
  • RPC provider blocking alone is weak for this technique because ChainDrop used multiple interchangeable Ethereum RPC providers while relying on the same on-chain source of truth.
  • Process context is critical for reducing false positives: the same blockchain call may be benign from a browser or wallet but suspicious from non-browser processes such as node, bun, or curl.
  • For Solana memo-based dead drops, reproducing the payload may require increasing the transaction lookup limit or pinning a specific signature because the latest transaction on the wallet can change over time.

The article explains how several malware families, including an August 2026 compromise of more than 440 npm software packages, hide where they should send stolen data by reading it from public blockchains instead of storing it inside the malicious program. This affects people and organizations that use compromised software packages or fake tools, because the malware can quietly look up a fresh destination for its operators. It matters because public blockchains are hard to take down, the traffic can look like normal cryptocurrency-related web traffic, and attackers can change the destination without replacing the malware.

A critical unauthenticated SQL injection in GeoServer’s GeoTools jsonArrayContains handling can let attackers compromise PostGIS-backed public map services, potentially escalating to OS command execution depending on database privileges. An unauthenticated SQL injection vulnerability exists in the jsonArrayContains filter function in GeoTools, the geospatial library that underpins GeoServer. The flaw affects OGC filter evaluation against PostGIS data stores, where a request-supplied value is written into generated SQL without escaping. It is tracked as GitHub security advisory GHSA-mqjf-5f49-2fjh, had no CVE identifier at the time of writing, and was publicly disclosed on August 12, 2026. Internet-wide scans showed probing activity within hours of disclosure, though observed activity so far was described as reconnaissance rather than compromise.

The issue matters because GeoServer WMS and WFS endpoints are often published without authentication for public mapping applications. Through WFS 1.0, the injection can allow a second PostgreSQL statement to execute at the top level of the query, and impact depends on the database role GeoServer uses. If that role is a PostgreSQL superuser or has pg_execute_server_program privileges, exploitation can escalate to operating system command execution on the database host; otherwise, an attacker can still read and write data accessible to that database user. Affected deployments require PostGIS 12 or greater and a queried layer exposing a string or JSON field, conditions that are not externally visible.

Patches are available in GeoServer 3.0.1, 2.28.5, and 2.27.6, with corrected GeoTools versions 35.1, 34.5, and 33.6. The article warns that the earlier mitigation for CVE-2023-25158 does not work for this regression, so teams should verify their actual GeoServer and GeoTools versions. Recommended actions include inventorying internet-facing GeoServer instances, restricting WMS and WFS access, disabling WFS 1.0 where possible, auditing PostgreSQL privileges, identifying risky PostGIS-backed layers, and reviewing logs for unexpected CQL filter parameters.

  • External scanning can identify GeoServer exposure but cannot confirm exploitability because the required PostGIS version and exposed field types are not visible from outside the application.
  • The article emphasizes that many GeoServer instances may be missed by normal security processes because they are often project-specific map services run by business, operations, regional, or departmental teams rather than core IT.

A newly disclosed flaw in GeoServer, software used to publish online maps, can let anyone who can reach certain map services tamper with database requests and possibly run commands on the database computer.
