TELESHIM Abuses Telegram for C2 in Attacks Against Middle East Governments

TAGSbindcloakcontrol-flow-flatteningcpuiddll-side-loadingeast-asiaenvironmental-keyingmiddle-eastmixed-boolean-arithmeticmixedkeyopaque-predicatesreflective-loadingtelegram-apiteleshimwindows-management-instrumentationzscaler-threatlabz

In plain words

Researchers found a new hacking campaign aimed at government organizations in the Middle East, likely coming from an East Asia-linked attacker. The attackers used Telegram, a widely used messaging service, to secretly send instructions to infected computers so the activity would look more normal online. This matters because it shows government systems are being targeted with carefully built tools designed to stay hidden, steal information, and work only on the intended victims’ machines.

Summary
A suspected East Asia-linked threat actor is targeting Middle East government entities with a multi-stage malware campaign that uses Telegram for command-and-control to blend in with legitimate traffic. The attack deploys new malware families including TELESHIM, MIXEDKEY, and BINDCLOAK, with heavy obfuscation and environment-based payload locking to evade analysis and run only on intended targets.

Cybersecurity researchers at Zscaler ThreatLabz identified a fresh malicious campaign targeting government entities in the Middle East. The activity deployed previously unreported malware families named TELESHIM, MIXEDKEY, and BINDCLOAK. Zscaler said the campaign used a multi-stage attack chain to establish and maintain access on infected systems, with TELESHIM abusing the Telegram API for command-and-control communication to blend in with legitimate internet traffic.

The attack begins with an ISO file containing a legitimate executable, RegSchdTask.exe, which is used to sideload a rogue DLL named AsTaskSched.dll. That DLL is a 32-bit Windows backdoor called TELESHIM, which retrieves next-stage components through Telegram. Later stages include a second DLL side-loading chain using GoProAlertService.exe and pthreadVC2.dll, with pthreadVC2.dll acting as the MIXEDKEY reflective loader to decrypt and execute another file.

TELESHIM and MIXEDKEY use heavy obfuscation techniques, and TELESHIM also checks for virtualization-based analysis environments. The final payload is protected by two layers of XOR encryption, including environmental keying based on the infected machine’s volume serial number, so it detonates only on intended targets. The attack culminates in BINDCLOAK, a 64-bit C2 implant written in C++ that contacts cert.hypersnet[.]com, and Zscaler assessed with moderate-to-high confidence that the campaign originated from East Asia while not attributing it to any known group.

  • The campaign used Telegram for command-and-control specifically to blend malicious traffic with legitimate internet activity, making ordinary-looking platform traffic part of the attacker’s concealment strategy.
  • The final payload was protected with environmental keying based on the infected machine’s volume serial number, which means the malware was designed to run only on intended targets and resist analysis elsewhere.
  • The observed operator activity occurred only between 4 a.m. and 12 p.m. UTC, with most commands between 7 a.m. and 11 a.m. UTC, giving defenders a concrete time window associated with this campaign’s post-compromise actions.
  • The attack chain repeatedly used DLL side-loading with legitimate executables, including RegSchdTask.exe and GoProAlertService.exe, showing that trusted-looking binaries were central to the intrusion sequence.
Key Points
  • 01Zscaler ThreatLabz detected a campaign targeting government entities in the Middle East that deployed previously unreported malware families named TELESHIM, MIXEDKEY, and BINDCLOAK.
  • 02The attack chain begins with an ISO file containing a legitimate executable, RegSchdTask.exe, which sideloads a rogue DLL named AsTaskSched.dll that acts as the 32-bit Windows backdoor TELESHIM.
  • 03TELESHIM abuses the Telegram API for command-and-control communication and supports messages for registering infected hosts, executing commands, exfiltrating results, and downloading and running secondary payloads as scheduled tasks.
  • 04TELESHIM and MIXEDKEY use heavy code obfuscation techniques, and TELESHIM also checks for virtualization-based analysis environments using methods such as CPUID hypervisor detection and Windows Management Instrumentation RAM speed checks.
  • 05Zscaler assessed with moderate-to-high confidence that the campaign originated from East Asia, but it has not attributed the activity to any known threat actor or group.

GitHub Adds 3-Day Dependabot Cooldown to Limit Poisoned Package Adoption
thehackernews.com · 27 Jul 2026 08:01 UTC openai-codex / gpt-5.5
TAGSbundependabotgithubmicrosoftnpmpnpmpypirubyvisual-studio-codeyarn

In plain words

GitHub is changing Dependabot so it normally waits at least three days before suggesting routine software dependency updates, instead of immediately pulling in a brand-new release. This affects projects that use Dependabot to keep the outside software parts they rely on up to date. The delay matters because attackers can sometimes publish a poisoned version of a popular package, and even if it is removed quickly, fast automatic updates can spread it to many projects before anyone catches it. Security fixes will still be sent right away, and GitHub says this delay is only one safety layer, not a complete defense.

Summary
GitHub is adding a default three-day cooldown for Dependabot version-update pull requests to reduce the chance that projects quickly adopt newly published malicious packages. Security updates will still be delivered immediately, and GitHub says the delay should be used alongside other supply-chain safeguards.

GitHub has announced a new cooldown mechanism in Dependabot that allows the tool to wait at least three days after a release is published before opening a pull request. The default three-day cooldown applies only to version updates, which are used to keep software dependencies up to date. Security updates will still be pushed immediately, allowing Dependabot to issue an alert and open a pull request to move a project to a patched version.

GitHub said the change is meant to reduce the risk from poisoned versions of popular packages that may be published by threat actors and quickly pulled into downstream projects before being removed from a registry. The company described three days as a balance between getting past the window where most of these attacks occur and not delaying dependency updates longer than necessary. It also said the cooldown setting in dependabot.yml can still be configured differently to fit a project’s needs.

GitHub emphasized that the cooldown should be only one layer of defense alongside measures such as pinning dependencies with lockfiles, disabling install scripts in CI, scoping build pipeline tokens, and reviewing updates before they merge. The company noted that cooldowns are designed for short-lived malicious releases and do little against longer-running threats such as dormant backdoors, maintainer sabotage, or compromised build systems. The article also notes that similar cooldown controls have appeared across VS Code, Ruby, Bun, npm, pnpm, and Yarn, while PyPI plans to block adding new files to package releases after 14 days.

  • GitHub’s choice of a three-day default is explicitly meant to outlast the period in which most short-lived poisoned package attacks are detected, without delaying routine dependency updates longer than necessary.
  • The cooldown does not protect against slower or more persistent supply-chain threats such as dormant backdoors, maintainer sabotage, or compromised build systems, so it is targeted at only one attack pattern.
  • GitHub is preserving immediate Dependabot security updates, showing that the new delay is designed to reduce risky routine upgrades without slowing fixes for known security issues.
  • The article indicates a broader ecosystem shift toward time-based defenses, with similar cooldown or release-locking measures appearing across VS Code, Ruby, Bun, npm, pnpm, Yarn, and PyPI.
Key Points
  • 01GitHub has announced a new Dependabot cooldown mechanism that can wait at least three days after a release is published before opening a pull request.
  • 02The three-day default cooldown applies only to Dependabot version updates, while security updates will continue to be pushed immediately with alerts and pull requests for patched versions.
  • 03GitHub said the cooldown is intended to reduce the spread of poisoned package versions that are published, quickly adopted by downstream projects, and later removed from registries.
  • 04GitHub emphasized that the cooldown should be used alongside other defenses such as lockfiles, disabling install scripts in CI, scoped build-pipeline tokens, and review before merging updates.
  • 05The article notes that similar cooldown controls have been announced in ecosystems including VS Code, Ruby, Bun, npm, pnpm, and Yarn, while PyPI plans to block new files from being added to package releases after 14 days.

The AI Industry Is Betting on Open Weights

In plain words

Many major AI companies, including NVIDIA, Microsoft, Meta, Google, IBM, Mistral, Hugging Face, Mozilla, and the Linux Foundation, signed a letter urging Washington not to restrict AI models that organizations can download and run themselves. The article says this matters because these models have become strong enough to compete with top closed services, while one closed model from Anthropic was suddenly shut off worldwide after a U.S. government order. Companies, governments, and other organizations that depend on AI could be affected because a service they rely on can become unavailable, get more expensive, or be limited by someone else. The broader issue is whether AI should be controlled by a few providers or be more widely available so organizations can keep control of their data, costs, and reliability.

Summary
Major AI companies are rallying behind open-weight models as a strategic alternative to closed frontier APIs, arguing they improve sovereignty, cost control, resilience, and security. The push gained urgency after open models rapidly improved and a government-ordered Anthropic shutdown showed how fragile dependence on closed models can be.

NVIDIA CEO Jensen Huang posted on X for the first time on July 24 with a policy letter arguing that Washington should not restrict open-weight AI. Microsoft CEO Satya Nadella also wrote that open-weight models are essential to a healthy AI ecosystem. The letter, Open Weights and American AI Leadership, launched with 25 signatures and has grown to 50, including NVIDIA, Microsoft, Meta, Google, IBM, Dell, Mistral, Hugging Face, Mozilla, and the Linux Foundation.

The article says the case for open weights is landing now because open models have become strong enough to matter and dependence on closed models has shown new risks. Moonshot AI’s Kimi K3, a 2.8 trillion parameter open-weight model, took the top spot in the Frontend Code Arena and landed just behind Claude Fable 5 on a long-horizon evaluation from Artificial Analysis. On June 12, the U.S. government forced Anthropic to pull Claude Fable 5 days after launch, and Anthropic shut it off worldwide within about 90 minutes because it could not verify nationality in real time.

The letter frames open weights around sovereignty, arguing that organizations should control their own data, adapt models to their needs, and deploy them wherever business requirements demand. It also argues that openness can improve safety and security by avoiding single points of failure and letting defenders use comparable capabilities to test, simulate, and respond. The article notes limits to that argument, including that released weights cannot be recalled, modified versions are hard to trace, and high benchmark scores do not necessarily prove reliability in real security work.

  • The article frames open weights as a business-continuity issue, because a closed frontier model that teams had wired into production was shut off worldwide within about 90 minutes after a U.S. government order.
  • The coalition is notable because it includes companies with very different incentives, such as NVIDIA, Microsoft, Mistral, CrowdStrike, Palo Alto Networks, and the Linux Foundation, indicating that support for open weights has moved beyond open-source advocates into a broad industry position.
  • The article presents sovereignty as both an economic and regulatory argument, since organizations can avoid recurring frontier API costs while keeping sensitive data on their own infrastructure in sectors such as finance.
  • The security argument for open weights is explicitly defensive rather than permissive: the letter says defenders need comparable AI capabilities to test, simulate, and respond when attackers use advanced AI.
  • The article highlights a tension in the open-weights case by noting that released weights cannot be recalled, modified versions are hard to trace, and strong benchmark results do not necessarily prove reliability in real security work.
