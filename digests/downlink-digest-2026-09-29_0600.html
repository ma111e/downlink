In plain words

Apple released updates to fix a flaw in its graphics software that has been used in highly targeted attacks against some iPhone users. A harmful file could take advantage of the flaw to run unwanted code on affected iPhones, iPads, and Macs. The updates cover many newer and older devices, and installing them promptly helps protect users from possible ongoing attacks.

Summary
Apple patched an actively exploited CoreGraphics out-of-bounds write zero-day that can enable arbitrary code execution through a maliciously crafted file. Users should promptly update affected iPhones, iPads, and Macs to iOS/iPadOS 26.7.1 or macOS Tahoe 26.7.1 and Sequoia 15.8.1.

Apple released security updates for a CoreGraphics out-of-bounds write flaw, tracked in the article as CVE-2026-20700, that may have been exploited in extremely sophisticated attacks against specifically targeted iOS users. Meta Product Security discovered the issue in CoreGraphics, Apple’s framework for graphics, image rendering, and text drawing. Apple said that processing a maliciously crafted file could lead to arbitrary code execution.

The affected devices include iPhone 11 and later, multiple iPad generations, and Macs running macOS Sequoia 15.8.1 or Tahoe 26.7.1. Apple addressed the issue with improved bounds checking in iOS and iPadOS 26.7.1, macOS Tahoe 26.7.1, and macOS Sequoia 15.8.1. Although the reported attacks were highly targeted, the article advises users to install the updates promptly to reduce the risk of ongoing attacks.

  • Although Apple described the reported exploitation as limited to specific targeted individuals, the affected-device list spans both older and newer iPhones, iPads, and Macs, making prompt updates broadly relevant.
  • The flaw can be triggered by processing a maliciously crafted file, meaning the issue is tied to handling content rather than requiring physical access to a device.
  • Apple’s fixes cover multiple current operating-system branches, including iOS/iPadOS 26.7.1 and both macOS Tahoe 26.7.1 and Sequoia 15.8.1, so Mac users on either supported version need an update.
  • The article says this is the second zero-day Apple has fixed in 2026 that was exploited in the wild, following a dyld issue patched in February.

In plain words

A flaw in the official Python software kit for connecting AI applications to outside tools could let a malicious server steal the login information an application uses for a real online service. It affects applications that use the kit to connect over the web to servers they do not fully control while holding these login details; locally connected applications and servers built with the kit are not affected. Stolen information could let an attacker obtain access with the same permissions as the application, and long-lasting secret credentials may remain usable until they are replaced. Updating to the fixed versions, setting the expected login service for certain automated connections, and replacing credentials if an untrusted server was used can reduce the risk.

Summary
A high-severity flaw in the official MCP Python SDK could let malicious MCP servers redirect OAuth exchanges and steal client secrets, authorization codes, and PKCE verifiers. Users should upgrade to versions 1.30.0 or 2.2.0, configure an explicit issuer for machine-to-machine OAuth providers, and rotate credentials if untrusted servers may have been used.

A flaw in affected versions of the official MCP Python SDK could let a malicious MCP server obtain OAuth credentials used by an application to access a real service. The server could redirect the client to an attacker-controlled token endpoint or provide login details that appear to reference the legitimate service while sending credentials elsewhere. The exposed information includes the client secret, authorization code, and PKCE proof key.

Cycode demonstrated that the stolen information could be exchanged for a valid access token carrying the permissions granted to the application, while the client secret could remain usable until changed. The issue affects HTTP MCP clients using specified OAuth providers when they connect to servers they do not fully control, but does not affect SDK-built MCP servers, local stdio clients, or clients using their own tokens. Versions 1.30.0 and 2.2.0 add issuer checks, although users of the two automated OAuth providers must also explicitly configure the expected issuer; organizations that may have used untrusted servers should rotate client secrets and revoke tokens.

  • For the two automated OAuth providers, upgrading alone does not prevent the problem unless the application is also configured with the expected login-service address using issuer=.
  • In the interactive sign-in case, a user may approve a genuine login page while the malicious server still receives the credentials needed to complete the exchange.
  • The 1.30.0 release uses a standard Python deprecation warning for the missing issuer setting, and Python hides that warning by default.
  • Previously stored OAuth client registrations must be cleared after upgrading because older registrations are not linked to a specific login service.
  • On vulnerable versions, the only stated mitigation is to connect only to MCP servers that are fully trusted.
Key Points
  • 01A flaw in affected versions of the official MCP Python SDK could allow a malicious MCP server to redirect OAuth token exchanges and receive a client secret, authorization code, and PKCE proof key.
  • 02The issue affects HTTP MCP clients using OAuthClientProvider, ClientCredentialsOAuthProvider, PrivateKeyJWTOAuthProvider, or the deprecated RFC7523OAuthClientProvider when they can connect to servers they do not fully control.
  • 03Cycode demonstrated that stolen credentials could be used to obtain a valid access token from the real login service with the permissions granted to the application.
  • 04The issue is fixed in MCP Python SDK version 1.30.0 for the 1.x line and version 2.2.0 for the 2.x line.
  • 05Users of ClientCredentialsOAuthProvider or PrivateKeyJWTOAuthProvider must also supply an explicit issuer setting, while users who may have contacted untrusted servers should rotate client secrets and revoke tokens.

This is a high-severity, concrete credential-theft flaw in the official MCP Python SDK, with clear affected versions and patches. It is especially relevant to organizations using HTTP MCP clients and machine-to-machine OAuth providers, though no active exploitation has been reported.
