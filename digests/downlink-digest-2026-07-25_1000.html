Fastjson 1.x RCE Vulnerability Targeted in Attacks With No Patched Available
thehackernews.com · 25 Jul 2026 12:52 UTC openai-codex / gpt-5.5

In plain words

Attackers are trying to abuse a serious flaw in Fastjson, a Java tool used by some applications to handle JSON data. The risk applies to organizations running Fastjson versions 1.2.68 through 1.2.83 in certain Spring Boot applications packaged as executable fat-JAR files, when outside users can send data to the affected code and SafeMode is not turned on. If exploited, an attacker could make the application run their code without logging in, using the same access the Java process already has. As of July 25, there was no fixed Fastjson 1.x release, so affected organizations are told to turn on SafeMode, use the restricted build, or move to Fastjson2.

Summary
Attackers are targeting CVE-2026-16723, a critical Fastjson 1.x RCE affecting certain Spring Boot fat-JAR deployments, and no patched Fastjson 1.x release was available as of July 25. Organizations should migrate to Fastjson2 or enable SafeMode/use 1.2.83_noneautotype as a mitigation.

Security firms ThreatBook and Imperva say attackers are targeting CVE-2026-16723, a critical flaw in Alibaba’s Fastjson library for Java. In affected Spring Boot applications, a malicious JSON request can execute code without authentication, with the privileges of the Java process. Alibaba assigned the vulnerability a CVSS score of 9.0, and the confirmed chain affects Fastjson 1.2.68 through 1.2.83 under specific deployment conditions.

The exploit requires a Spring Boot executable fat-JAR, a network-reachable path that sends attacker-controlled JSON to an affected parser, and SafeMode left at its disabled default. Alibaba said AutoType can remain disabled and no classpath gadget is required, and it verified the chain on Spring Boot 2.x, 3.x, and 4.x with JDK 8, 11, 17, and 21. The issue stems from Fastjson’s type-resolution path, where an attacker-controlled @type value can lead to a class-resource lookup and loading of attacker-controlled bytecode in a compatible Spring Boot fat-JAR.

As of July 25, Alibaba had not released a fixed Fastjson 1.x version, and The Hacker News found no patched Fastjson 1.x artifact in GitHub tags or Maven Central. Organizations that cannot migrate immediately should enable SafeMode with -Dfastjson.parser.safeMode=true or use com.alibaba:fastjson:1.2.83_noneautotype, while Alibaba lists migration to Fastjson2 as the long-term fix. ThreatBook reported in-the-wild exploitation and Imperva reported activity against several sectors and countries, but neither vendor published attack counts, raw requests, execution evidence, named victims, or confirmed compromises.

  • The exploit can work even when AutoType remains disabled and no classpath gadget is present, so defenses or assessments focused only on prior Fastjson AutoType issues may miss this case.
  • Binding JSON input to a fixed class is not enough protection if that class contains an Object or Map field, because the payload can be nested there.
  • Deployment format is a major factor: Alibaba lists Spring Boot executable fat-JARs as affected, while plain non-fat JARs, generic uber-JARs, and Tomcat or Jetty WAR deployments are listed as unaffected.
  • There is a mismatch between vendor reports of observed exploit activity and CISA’s July 23 ADP assessment, which marked exploitation as none and did not list the flaw in the Known Exploited Vulnerabilities catalog as of July 25.
  • Fastjson 1.2.83, previously recommended as an upgrade for a separate 2022 AutoType bypass, is now itself within the affected range for CVE-2026-16723.
Key Points

  • 02The confirmed vulnerability chain requires Fastjson 1.2.68 through 1.2.83, a Spring Boot executable fat-JAR, a network-reachable path that sends attacker-controlled JSON to an affected parser, and SafeMode left disabled.
  • 03Alibaba had not released a fixed Fastjson 1.x version as of July 25, and organizations that cannot migrate immediately should enable SafeMode or use com.alibaba:fastjson:1.2.83_noneautotype.
  • 04Alibaba lists migration to Fastjson2 as the long-term fix, and the article states Fastjson2 is not affected because it does not use the same resource-probing or annotation-based trust path.
  • 05ThreatBook reported in-the-wild exploitation, while Imperva reported activity against several sectors, but neither vendor published attack counts, raw requests, execution evidence, named victims, or confirmed compromises.

A criminal group linked to Cl0p is breaking into internet-facing PTC Windchill and FlexPLM systems, which are used by organizations in manufacturing, automotive, aerospace, and retail. In plain words

Researchers published working code showing how a logged-in GitLab user who can add files to a project could make an unpatched self-managed GitLab server run commands. This affects GitLab Community and Enterprise editions from 15.2.0 through several later versions, with fixed versions listed as 18.10.8, 18.11.5, and 19.0.2. It matters because the commands run as the account behind GitLab’s web service, which may be able to reach source code, secrets, service credentials, CI/CD data, and internal services.

Summary
Researchers published a working proof-of-concept for a GitLab RCE chain that lets any authenticated user with project push access run commands as the git user on unpatched self-managed instances. The flaw was fixed in GitLab 18.10.8, 18.11.5, and 19.0.2, but it was not initially labeled as a security fix, so operators should verify and upgrade immediately.

Security researchers at depthfirst published working exploit code on July 24 for a GitLab flaw that GitLab patched on June 10. The exploit runs commands as the git user on any self-managed GitLab 18.11.3 server that has not taken the update. Any authenticated user who can push to a project can use the chain, without administrator rights, CI or runner access, victim interaction, or access to anyone else’s project.

The chain uses crafted Jupyter notebooks and GitLab’s notebook diff rendering to reach two memory corruption bugs in Oj, a Ruby JSON parser implemented largely in native C. One bug leaks a heap pointer through the diff, and another can overwrite a parser callback so the payload points to system(). GitLab’s ipynbdiff renderer passes repository-controlled .ipynb JSON to Oj::Parser.usual.parse inside a long-lived Puma worker, placing attacker-controlled data inside the application process.

GitLab did not classify the fix as a security fix in the June 10 patch release, and the issue has no CVE, CVSS score, or mention of the notebook-diff chain. Affected versions include GitLab CE/EE 15.2.0 to 18.10.7, 18.11.0 to 18.11.4, and 19.0.0 to 19.0.1, with fixed versions 18.10.8, 18.11.5, and 19.0.2. The article says commands run as the account behind Puma, with possible reach including source code, Rails secrets, service credentials, CI/CD data, and internal services the application can talk to.

  • Operators who reviewed GitLab’s June 10 patch release only by its security-fix table may have missed the urgency, because the relevant Oj 3.17.3 update was listed under bug fixes instead of security fixes.
  • For Helm and Operator deployments, the article says the version that matters is the GitLab version inside the Webservice image running Puma, not the chart or Operator version.
  • GitLab installations on versions 15.2 through 18.9 do not receive a backport because they are outside GitLab’s security-maintained patch trains, so those deployments must move to a supported release.
  • The public exploit is not drop-in against arbitrary targets because it was built for GitLab 18.11.3 on x86-64 and depends on version-specific gadget offsets, register state, and jemalloc behavior.
  • Although the exploit can run commands as the git user, the article notes that its real-world impact depends on install isolation, with possible reach including source code, Rails secrets, service credentials, CI/CD data, and internal services accessible to the application.
Key Points
  • 01Security researchers at depthfirst published working exploit code on July 24 for a GitLab flaw that GitLab patched on June 10.
  • 02Any authenticated user who can push to a project can exploit the issue by committing crafted Jupyter notebooks and opening their commit diffs to ultimately run commands as the git user.
  • 03GitLab did not list the Oj 3.17.3 update as a security fix in the June 10 patch release, and the issue has no CVE, CVSS score, or mention of the notebook-diff chain.
  • 04Affected versions include GitLab CE/EE 15.2.0 to 18.10.7, 18.11.0 to 18.11.4, and 19.0.0 to 19.0.1, as well as Oj gem versions 3.13.0 to 3.17.1.

The Phish Zoom Signed With Its Own DKIM Key

In plain words

An attacker created a Zoom account with a scam message as the account name, so Zoom’s own sign-in email repeated that message and sent it with Zoom’s real branding and approval. The email was then forwarded to a company chief operating officer and claimed a fake PayPal charge of $986.37, pushing the person to call a phone number controlled by the scammer. This matters because the message looked technically genuine and had no bad link or attachment, showing that even real-looking emails from trusted brands can be used to trick people into calling scammers.

Summary
Attackers abused Zoom’s own sign-in email template by placing a PayPal callback scam in the account name field, causing Zoom to DKIM-sign a genuine-looking phishing message that passed DMARC. The key takeaway is that valid email authentication proves origin and integrity, not that the content is safe.

An attacker created a Zoom account and set the account name to a scam message claiming a PayPal account would be auto-debited $986.37 for a Zoom monthly renewal. When the attacker triggered a Zoom sign-in verification email, Zoom inserted that account name into its standard email template and signed the finished message with its production DKIM key. The resulting email passed DKIM and DMARC because Zoom genuinely signed the content before delivery.

The message was then resent to a company chief operating officer through a brand-new privacy-protected domain, mailjetstream[.]com, which had no relationship to Zoom’s mail platform and no SPF record. The email contained Zoom’s real branding and a legitimate Zoom link, but the payload was the callback number +1-805-600-1572. There was no malicious link or attachment, which left URL sandboxes, attachment detonation, and domain-reputation engines with little to detect.

The article emphasizes that a valid DKIM signature proves the message was signed by the domain’s key and was not modified in transit, but it does not prove the content is trustworthy. It identifies the scam as a telephone-oriented attack delivery, or TOAD, designed to move the victim from email to a phone call with a live operator. The broader takeaway is that authenticated brand email can still be hostile when user-controlled fields are echoed into transactional messages, so behavioral analysis must evaluate the message content and delivery path rather than treating authentication as a verdict.

  • Email defenses that allow-list messages solely because they are signed by a trusted brand such as zoom.us can miss attacks where the brand itself was tricked into signing attacker-supplied text.
  • Transactional emails that echo user-controlled fields such as account names, notes, or memo lines can become a vehicle for signed scam content if those fields are not constrained or context-checked.
  • The presence of Resent headers and a new, unrelated envelope domain can reveal weaponization even when the visible brand assets and cryptographic signature are authentic.
  • Callback scams can evade common email filtering because the dangerous action is moved outside the email message and into a phone call, leaving only a phone number and social pressure in the email body.
  • A mismatch between the expected purpose of an email and its text, such as a Zoom sign-in code email discussing PayPal auto-debits, is an important detection signal even when the message’s technical authentication passes.

  • 02Zoom rendered the attacker-controlled account name into its standard sign-in-code email template and signed the finished message with its production DKIM key for zoom.us.
  • 03The resent message passed DMARC because the Zoom DKIM signature was aligned, even though the envelope domain mailjetstream.com had no SPF record and no relationship to Zoom's mail platform.
  • 04The only attack payload was the callback number +1-805-600-1572, with no malicious link or attachment for URL sandboxes, attachment detonation, or domain-reputation engines to analyze.
  • 05The article states that a valid DKIM signature proves the signing key and message integrity, but not whether the message content is safe or trustworthy.

Summary
CTM360 found that insurance phishing campaigns are evolving from simple credential theft into real-time account hijacking, with attackers using fake portals to relay logins and OTPs to legitimate insurance sites during the victim’s session. The research highlights the InsureOTP Kit and abuse of Google Ads and disposable hosting infrastructure to run coordinated, brand-impersonation campaigns across multiple regions.

CTM360 investigated insurance-focused phishing operations that have moved beyond collecting credentials for later use. The campaigns synchronize attacker activity with victims in real time, allowing attackers to authenticate against legitimate insurance portals while victims unknowingly complete the login process.
