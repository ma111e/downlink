LiteLLM compromised again: infostealer and RAT found in version 1.107.0
aikido.dev · 21 Oct 2026 13:05 UTC openai-codex / gpt-5.6-terra

In plain words

A fake, harmful version of LiteLLM, a tool used to connect software to AI services, was published online along with its official Docker image. Anyone who installed or ran version 1.107.0 may have had passwords, cloud-account access, private keys, browser data, and AI-service keys copied from their computer. It also lets the attacker remotely run new commands on affected machines later, meaning the risk can continue even after the original installation. People and organizations that used this version should assume their secrets may be exposed and replace them.

Summary
LiteLLM version 1.107.0 and its corresponding Docker images were compromised to install an infostealer and persistent Python RAT that can steal credentials and execute attacker commands. Anyone who installed or ran the affected release should treat secrets as exposed, investigate affected hosts, and rotate credentials immediately.

LiteLLM version 1.107.0 was compromised after malicious code was inserted into Python wheels published on PyPI, and the official litellm/litellm:1.107.0 Docker image was also affected. The article says users who installed that version on any platform, or ran the affected Docker image through versioned or moving tags, should assume credentials may be compromised. PyPI quarantined the package version, but the article states that the compromised Docker image remained available on Docker Hub.

The attacker used a maturin build configuration directive to add files from a cook/ directory that was absent from the source tarball and GitHub repository. A .pth file caused a credential-stealing script to run at Python startup, while sitecustomize.py started a background process that checked hourly for and ran attacker-provided Python code. The infostealer collected browser passwords, private keys, cloud and developer credentials, environment variables, and LiteLLM database data, then sent it to an attacker-controlled domain. The article identifies /tmp/.pc_once_72129118c59f5636c0bb and /tmp/remote_code_loader.lock as signs that the credential theft or remote-command component ran.

  • The malicious files were added during the wheel-building process through a maturin configuration directive, so the source tarball and GitHub repository did not contain the injected directory or its contents.
  • A 12-byte .pth file caused the infostealer to run automatically whenever Python started, meaning execution did not require a user to import LiteLLM after installation.
  • The affected Docker exposure extended beyond the explicitly versioned image because the article says the latest, main-latest, and main-stable tags could also pull the compromised image.
  • The presence of /tmp/.pc_once_72129118c59f5636c0bb indicates the credential-stealing routine has already run, while /tmp/remote_code_loader.lock indicates the remote-command daemon ran or may still be active.
  • The infostealer attempted to obtain credentials available directly from cloud instances by querying AWS, GCP, and Azure metadata endpoints, in addition to reading credential files from disk.
Key Points
  • 01LiteLLM version 1.107.0 was compromised through malicious code injected into Python wheels published on PyPI, and its official Docker image for the same version was also affected.
  • 02The malicious package installed files that automatically ran whenever Python started, including an infostealer that collected credentials and secrets and a background program that could execute attacker-provided code.
  • 03The infostealer collected browser passwords, SSH keys, cloud credentials, environment variables, LiteLLM database contents, and other developer and CI/CD secrets, then sent the data to an attacker-controlled website.
  • 04The remote-access component checked every hour for code supplied by the attacker and ran it with the permissions of the affected Python process.
  • 05PyPI quarantined LiteLLM 1.107.0, but the article states that the compromised litellm/litellm:1.107.0 Docker image remained available on Docker Hub.

It is immediately actionable for anyone who installed or ran the affected release because cloud, browser, developer, CI/CD, and LiteLLM secrets may have been exposed.

In plain words

A company received an email that pretended to be from one of its vendors and asked it to send future payments to a new bank account. The links in the email led to the real vendor, so ordinary link checks found nothing wrong, but the sender’s web address was a close imitation and the attached bank documents had conflicting details and signs of recent editing. This matters because finance staff may approve payments based on emails that look convincing, sending money to criminals even when no harmful link or file is detected.

Summary
A vendor bank-change BEC email used a newly registered lookalike domain while embedding genuine vendor website and email links, so hover checks and URL scans appeared clean. The fraud was exposed by sender-domain scrutiny and contradictory, recently edited PDF metadata rather than any malicious link or payload.

A diversified holding company received a vendor bank-change request from mackaycomm[.]com, a lookalike domain registered 28 days before the email. The sender claimed that the vendor and its sister business had consolidated payments into a new bank account and attached supporting PDFs. Although the signature displayed the lookalike domain, its website links led to the real vendor site and its email link opened a message addressed to a real vendor employee.

Because the links pointed to genuine destinations, URL scanners marked them clean, and neither PDF contained scripts, launch actions, embedded files, or link objects. The attached Chase letter displayed a 2026 date but had a 2025 source creation date and was modified on the send morning, while the second PDF was a 2019 scan edited on the same morning. The documents also conflicted on the bank branch, the signer’s job title, and phone information.

The lookalike domain authenticated successfully as itself with SPF and DKIM, while recipient-side authentication failures were attributed to the victim’s gateway rather than message tampering. A human analyst classified the message as malicious and removed all four copies from mailboxes, but a later automated re-analysis labeled it safe based on the clean genuine-site links. The article emphasizes checking sender and CC domains, comparing document metadata and printed dates, and confirming unexpected bank changes through an existing vendor contact.

  • A clean link scan can be accurate yet still provide no protection when an attacker uses genuine destinations in a copied email signature.
  • The lookalike sender domain passed SPF and DKIM as itself, showing that successful email authentication does not establish that a sender is the legitimate vendor being impersonated.
  • Comparing PDF metadata with printed dates and email timing exposed evidence of same-day document alteration that link and attachment-payload checks could not detect.
  • Cross-checking details between supposedly supporting documents revealed contradictions in the bank branch, job title, and phone region, making the documents more revealing together than individually.
  • Calling a vendor contact already on file to verify an unexpected bank-account change is necessary because the fraudulent request can contain no malicious URL, file behavior, or obvious technical indicator.

How Tenable brought multi-language support to security detectors with agentic translation
tenable.com · 21 Oct 2026 13:00 UTC openai-codex / gpt-5.6-terra
TAGSarabicfrenchgermanhindiitalianjapanesemandarin-chineseportuguesespanishtenabletenable-one-ai-exposure

In plain words

Tenable changed its AI security product so it can recognize dangerous or harmful requests in 10 languages without first translating every request into English. It created carefully checked training examples in nine additional languages, helping the system preserve the meaning of suspicious messages such as attempts to bypass AI safeguards. This matters to organizations using AI across different countries and languages, because people trying to misuse AI can write in languages other than English, and slower translation steps can add cost and miss important meaning.

Summary
Tenable replaced its costly translate-then-detect workflow with a multilingual security detection model trained using an agentic, label-preserving translation pipeline. The resulting Tenable One AI Exposure detectors support 10 validated languages with substantially lower latency and cost while matching or improving detection quality.

Tenable redesigned its AI security detection workflow to support threats and harmful content written in 10 validated languages, rather than translating each non-English request into English before evaluating it. The previous translate-then-detect approach added latency, recurring translation costs, operational overhead, and risk that a translation could obscure security-relevant meaning. The new approach uses one multilingual model that detects threats directly in English, Spanish, German, French, Italian, Portuguese, Mandarin Chinese, Japanese, Arabic, and Hindi.

To create reliable multilingual training and test data, Tenable built an agentic translation pipeline that supplies the task, data label, and target language to a frontier model, then has independent judges check fluency, meaning, and label preservation. Translations that fail are refined, while sensitive items refused by the frontier model are handled by a controlled open-source model and subjected to the same quality gate. Tenable reports that the native model runs in tens of milliseconds, is roughly 20–800 times faster per item than its former process, uses under 1 GB of memory rather than 12–14 GB, and matched or exceeded translate-then-detect performance in the evaluations described.

  • Translation quality for security data depends on preserving the original safety label, because a translation can soften malicious intent or change a dangerous request into something that appears benign.
  • Tenable found that multilingual pretraining allowed it to test whether English-only training generalized to other languages before paying to create translated data, and to translate only for languages where performance lagged.
  • The pipeline addresses a data-coverage problem caused by AI refusals: when a frontier model declines to translate sensitive material, a controlled open-source model handles the item and its result still must pass the same quality checks.
  • Creating multilingual training and benchmark data was a one-time expense of under $10,000 according to Tenable, unlike a production translation service whose cost grows with each customer request.
Key Points
  • 01Tenable replaced its translate-then-detect approach with a single multilingual model that natively detects AI threats, harmful content, and policy risks in 10 validated languages.
  • 02The company used an agentic translation pipeline in which a frontier LLM creates label-aware translations, independent judges assess fluency and meaning preservation, and failed items are refined or handled by a controlled open-source model after refusals.
  • 03Tenable reports that native multilingual detection operates in tens of milliseconds, is roughly 20 to 800 times faster per item than the prior translation-based process, and uses less than 1 GB of memory versus 12 to 14 GB.
  • 04The multilingual model matched or exceeded translate-then-detect AI-threat detection on 9 of 10 languages and overall, and led on every language for the harmful-content detection evaluation described in the article.
  • 05Tenable states that its model may read and flag attacks in thousands of languages beyond the 10 it formally validated, but says that broader capability requires further testing before it can be relied upon.

This is a vendor technical and product-focused account of building multilingual AI security detection, not a report of an active incident, vulnerability, or urgent patch. It offers useful implementation and evaluation details, but its relevance is primarily to teams evaluating or developing multilingual AI safety tooling.
