Mini Shai-Hulud hits openapi-react-query-codegen: 10 malicious npm versions
mend.io · 29 Aug 2026 16:19 UTC openai-codex / gpt-5.5
TAGSbunghsa-9pvf-vcx3-x239githubgithub-actionsmend-iomini-shai-huludmsc-2026-11522node-gypnpmnpm-trusted-publishingopenapiopenapi-react-query-codegenp00pabootreact-queryslsa

In plain words

An attacker got ten harmful versions of a popular npm package, @7nohe/openapi-react-query-codegen, published by abusing the project’s release process rather than stealing a maintainer’s account. People and organizations that installed those versions could have had developer, cloud, and software publishing credentials exposed, and the package gets about 150,000 downloads a week. The bigger lesson is that even “officially” published software can be dangerous if the automated process that publishes it can be tricked.

Summary
Ten malicious versions of @7nohe/openapi-react-query-codegen were published to npm after an attacker abused a GitHub Actions issue_comment release workflow to mint trusted publishing tokens without stealing maintainer credentials. Some versions executed without install scripts via node-gyp, so affected users must check for the listed versions and payload files, update to a clean release, and rotate exposed credentials.

On August 28, 2026, ten malicious versions of @7nohe/openapi-react-query-codegen were published to npm between 20:00 and 20:21 UTC. The package generates React Query hooks from an OpenAPI schema and has roughly 150,000 weekly downloads. The latest tag pointed to malicious version 3.0.4 during the window, and npm removed all ten versions on August 29 while restoring latest to 3.0.2.

The attacker did not need a stolen npm token or hijacked maintainer account, but instead abused a GitHub release workflow triggered by issue_comment events. The workflow lacked an author association check, checked out pull request head code from a fork, and had id-token: write, allowing npm trusted publishing tokens to be minted through OIDC. All ten releases had valid SLSA provenance attestations because they were produced by the project’s real release workflow, so provenance did not separate malicious artifacts from legitimate builds.

The malicious releases used two execution paths, which makes detection more complicated. Eight versions included binding.gyp and 3FWCvzduYZg.js, with four of them executing through the native build path without any install script, while two prereleases had a malicious preinstall but no payload files. The payload targeted cloud, registry, CI, developer, and AI assistant configuration surfaces, and the article recommends auditing lockfiles and install logs, updating to a clean version, rotating reachable credentials, reviewing AI assistant configuration files, and checking similar release workflow patterns.

  • Valid SLSA provenance did not distinguish the malicious releases from legitimate builds because the artifacts were produced by the project’s genuine release workflow.
  • Disabling or scanning only for install scripts would not have caught all affected versions because four releases executed through the native build path using binding.gyp despite having no install hook.
  • Detection must combine package-specific file indicators, such as binding.gyp and 3FWCvzduYZg.js, with direct lockfile checks for the two prereleases that did not include those payload files.
  • All ten malicious versions were removed from npm, so a pinned affected lockfile now fails with a 404 during npm ci, which is described as a safe outcome but not a self-explanatory one.
  • The payload referenced multiple AI coding assistant configuration files and included a Model Context Protocol-shaped server stub, making review of assistant configuration files a specific remediation step.
Key Points
  • 01On August 28, 2026, ten malicious versions of @7nohe/openapi-react-query-codegen were published to npm between 20:00 and 20:21 UTC, with the latest tag pointing to malicious version 3.0.4 during that window.
  • 02The attacker abused a GitHub Actions release workflow triggered by issue_comment events that checked out pull request code and had id-token: write permission, allowing npm trusted publishing tokens to be minted without a stolen npm token or hijacked maintainer account.
  • 03Eight of the malicious releases contained a multi-stage loader that targeted cloud, registry, and developer credentials, while two prerelease versions used a preinstall script but did not include the payload files.
  • 04Four affected versions had no install script and executed through node-gyp evaluation of a malicious binding.gyp file, so scanning only for install hooks would miss them.
  • 05The article recommends auditing lockfiles and install logs for the ten affected versions, updating to a clean version, rotating credentials reachable from affected machines or runners, and reviewing AI assistant configuration files for unexpected changes.

Nothing to Block: A 1990s Domain and a Google Form
ironscales.com · 29 Aug 2026 11:00 UTC openai-codex / gpt-5.5
TAGScisafbi-ic3googlegoogle-docsgoogle-formsironscalesnistt1078t1566-002t1598-003themisverizon-dbir
82
In plain words

A general manager at a national in-home care services provider received a fake payment notice that came from a real, long-established business email account and linked to a form hosted by Google. Because both the sending email account and the Google form looked legitimate, the usual trust checks did not clearly warn that it was a scam. This matters because people can be tricked into giving away information or access even when a message appears to come from trusted places, and losses from this kind of business email fraud can be very large.

Summary
A phishing email sent from a compromised, decades-old legitimate mailbox passed SPF, DKIM, and DMARC and used a Google Forms link for credential harvesting, leaving no obvious reputation-based indicators to block. The key takeaway is that clean authentication and trusted hosting do not prove an email is safe; detection must evaluate message content, sender relationship, and behavior.

A general manager at a national in-home care services provider received an unbranded payment notice that appeared to report a settled debit request. The message contained a plain bordered table with a customer identifier, paid date, BILLPAY memo, and check and draft reference number, but no dollar amount. Its only hyperlink was labeled as a way to view transaction details and resolved through a Google Forms shortlink to a form hosted on Google’s own domain.

The email came from a legitimate property-management business domain registered in the late 1990s, and the recipient’s mail system recorded DKIM, SPF, and DMARC passes with an intact relay chain. The article says these clean results occurred because the mailbox was real and had been taken over, allowing the operator to inherit the domain’s authentication and reputation. The destination also offered little reputation signal because the collection page was hosted on Google’s document platform.

The article highlights several signs in the message itself, including a mismatch between the reference number in the subject line and the one in the body, the missing payment amount, and visible sender and recipient fields that matched each other while actual delivery went elsewhere. IRONSCALES’ Themis Adaptive AI classified the message as credential theft at 83 percent confidence and labeled the recipient as high value based on content and behavior rather than infrastructure indicators. The incident is mapped to MITRE techniques for spearphishing links, phishing for information through a link, and use of valid accounts.

  • Clean SPF, DKIM, and DMARC results can be a downstream consequence of account takeover, so they should not be treated as evidence that a message is safe.
  • A trusted destination domain can hide malicious intent when attackers use a legitimate platform such as Google Forms as the data-collection endpoint.
  • The missing payment amount was part of the lure’s design, because it created a reason for the recipient to click the transaction-details link.
  • A mismatch between the reference number in the subject line and the reference number in the body was a visible clue that the payment notice was fabricated.
  • A self-addressed visible sender and recipient, combined with actual delivery to another mailbox, indicated a blind-copied blast from the hijacked mailbox rather than normal correspondence.
Key Points
  • 01A general manager at a national in-home care services provider received an unbranded payment notice from a legitimate property-management business domain registered in the late 1990s.
  • 02The email passed DKIM, SPF, and DMARC because it was sent from a real compromised mailbox rather than from spoofed infrastructure.
  • 03The single hyperlink in the message was a Google Forms shortlink that redirected to a form page on Google's own document platform.
  • 04The lure used fabricated transaction details, including a customer identifier, paid date, BILLPAY memo, and reference number, while omitting the payment amount and showing a mismatch between the subject and body reference numbers.
  • 05IRONSCALES' Themis Adaptive AI classified the message as credential theft at 83 percent confidence based on content and behavior rather than infrastructure reputation signals.
