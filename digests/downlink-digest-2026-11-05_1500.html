Summary

Administrators should check affected Linux servers for its indicators, replace compromised binaries, upgrade CWP, rotate credentials, and investigate for additional malware.

Researchers at QiAnXin XLab discovered CWPdoor, a Linux backdoor distributed through a trojanized version of cwpsrv, the web server used by Control Web Panel (CWP). The malware was identified after researchers captured an updater-like script on June 29 that replaced legitimate cwpsrv binaries for versions 1.15.10 and 1.24.0. The script attempts to hide its activity by restoring timestamps, deleting temporary files, and clearing command-history logs.

CWPdoor remains inactive until an attacker sends a specially constructed HTTP request containing an encrypted command, timestamp, and RSA signature. It checks that the request is recent, validates the signature, executes the command through a helper process, and suppresses the triggering request from access logs. XLab said more than 340,000 CWP instances were publicly exposed over the prior month and recommended checking for the ngx_http_integrity_helper Unix socket, suspicious cwpsrv helper processes, and X-Ngx-Integrity strings; confirmed victims should replace the binary, update CWP, rotate credentials, and investigate for additional malware.

  • CWPdoor is designed to remain inactive until it receives an authenticated request, making it less likely to be noticed through ordinary server behavior.
  • Its command, timestamp, and signature are cryptographically bound together and accepted only within a five-minute window, which provides authorization checks and limits replay of captured requests.
  • The malware modifies logging so the request that triggers command execution does not appear in normal access logs, reducing the usefulness of routine log review alone.
  • A malicious cwpsrv sample associated with the campaign had zero VirusTotal detections when found in an archive with Ebury, while XLab stated that real victims already exist in the wild.
  • Administrators have concrete hunting indicators beyond the cwpsrv binary itself: the ngx_http_integrity_helper Unix socket, unexpected cwpsrv helper processes, and X-Ngx-Integrity strings embedded in the server binary.

In plain words

A newly disclosed OpenSSH flaw can let someone sign in to certain Linux accounts that were meant to reject password logins, simply by entering an unusually long password. It affects some systems using Alpine Linux and other Linux versions built with musl, when password sign-in is enabled and a particular account is marked as having no usable password. Summary
A flaw dubbed “sshole” in OpenSSH on musl-based systems can let attackers log into accounts whose /etc/shadow password field is set to * by submitting an oversized password, under specific non-PAM password-authentication configurations. Administrators should update to OpenSSH 10.6p2 or disable SSH password authentication immediately.

A newly disclosed flaw dubbed “*sshole” affects certain OpenSSH servers on musl-based Linux distributions, including Alpine Linux, OpenWrt, Buildroot, and Yocto. It can allow an attacker to log in to an account configured to reject password authentication by submitting an oversized password. The issue has existed since 2016 and was discovered by security researcher Ozgun Kultekin.

The flaw occurs when musl’s crypt() function returns an asterisk for password-hashing failures, including passwords over its 256-byte limit, and OpenSSH compares it to an asterisk stored for a password-disabled account. Exploitation requires a musl-based system, disabled PAM authentication, enabled SSH password authentication, an account with an asterisk password field, and another account with a valid password hash. OpenSSH 10.6p2 fixes the issue, while administrators unable to update can disable SSH password authentication as a mitigation.

  • A 2016 OpenSSH change intended to prevent attackers from identifying valid usernames through response-time differences created the condition that enables this login bypass on affected musl-based systems.
  • The flaw is limited to accounts with an asterisk as their stored password value and does not allow password bypass for accounts that have valid password hashes.
  • Alpine Linux’s official AWS and Azure images reportedly include an affected default alpine account with passwordless doas privileges, so a successful login could lead to root access.
  • Administrators can look for possible exploitation by checking logs for “Accepted password” entries for accounts, such as alpine, whose password field is set to an asterisk.
Key Points
  • 01A flaw dubbed “sshole” can allow oversized passwords to log into certain password-disabled accounts on musl-based Linux systems running affected OpenSSH configurations.
  • 02The issue occurs because musl’s crypt() function returns an asterisk when hashing fails for passwords longer than 256 bytes, and OpenSSH may match that result against an asterisk stored in the account’s password field.
  • 03Exploitation requires musl-based Linux, disabled PAM authentication, enabled SSH password authentication, an account whose password field is an asterisk, and another account with a valid password hash.
  • 04The vulnerability does not bypass passwords for accounts with valid password hashes, and systems using glibc or PAM authentication are not affected.
  • 05OpenSSH 10.6p2 fixes the issue; administrators can also mitigate it by disabling SSH password authentication.
