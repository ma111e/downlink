In plain words

Ruby on Rails released updates for a serious flaw in apps that accept user-uploaded images and use ImageMagick to handle them. A malicious upload could let an outsider write files onto a server or, in some setups, read secrets such as passwords and database details. This could lead to someone taking control of an affected app or accessing connected systems, so teams should update Rails promptly; a free temporary patch is also available for teams that cannot update right away.

Summary
Rails 8.0.5.2 and 8.1.4.1 fix a critical Active Storage/ImageMagick flaw (GHSA-f3w6-w445-fwh9) that can let unauthenticated attackers write or potentially read server files through malicious uploads. Upgrade immediately and ensure MiniMagick is at least 5.1, or apply Socket’s free interim patch if upgrading is delayed.

Ruby on Rails released versions 8.0.5.2 and 8.1.4.1 on November 4, 2026, addressing 21 vulnerabilities including critical Active Storage issue GHSA-f3w6-w445-fwh9. The flaw affects applications that process untrusted Active Storage uploads with ImageMagick through the :mini_magick variant processor when the system ImageMagick policy does not block dangerous file handlers. A crafted upload may let an unauthenticated attacker write arbitrary files to the server and, for applications using Active Storage’s Disk service, potentially read files accessible to the application process.

The disclosure of sensitive files, including secret_key_base, application credentials, and database secrets, could lead to remote code execution or access to connected systems. Active Storage automatically analyzes attached files, meaning exploitation does not require a separate preview, transformation, or explicit analysis request. Rails recommends upgrading promptly, updating MiniMagick to version 5.1 or later where required, reviewing ImageMagick policy settings, and rotating potentially exposed credentials. Socket also provides a free Certified Patch for this specific flaw as an interim option, although it does not address the other vulnerabilities fixed in the Rails releases.

  • Exploitation can occur as soon as an attachment is added because Active Storage automatically analyzes uploaded files, without requiring a separate image preview or transformation request.
  • Teams applying the Rails fix to applications using MiniMagick must also use MiniMagick 5.1 or later, or affected applications will raise an exception during startup.
  • Organizations using Active Storage’s Disk service are advised to rotate potentially exposed credentials because the flaw may permit reading files accessible to the application process.
  • Socket’s free Certified Patch is limited to GHSA-f3w6-w445-fwh9 and does not remediate the other 20 issues addressed by the Rails releases.

CVE-2026-123158 (*sshole): OpenSSH Password Authentication Bypass on Alpine Linux
stepsecurity.io · 06 Nov 2026 22:30 UTC openai-codex / gpt-5.6-terra

In plain words

The article examines a flaw in older OpenSSH software on Alpine Linux and similar systems that can let a remote person sign in to certain accounts that were meant to allow key-based access only. It only works under a narrow set of settings, including enabled password logins, a specific kind of passwordless account, and another account on the same machine with a real password. This matters because Alpine is widely used in container images and automated software-building systems, where an exposed remote-login service could give an intruder access to the system. Updates are available, and turning off password logins or using the alternative login-checking setup also prevents the issue.

Summary
A flaw in unpatched OpenSSH on musl-based systems such as Alpine Linux can let attackers log into eligible passwordless accounts using an overlong password when password authentication is enabled and PAM is not used. Upgrade to Alpine’s patched OpenSSH packages, restart sshd, and disable password authentication or enable PAM where immediate patching is not possible.

CVE-2026-123158, also called *sshole, is an OpenSSH password-authentication bypass affecting unpatched musl-based systems such as Alpine Linux when PAM is not used. Under specific conditions, a network attacker can log in to an eligible account with a * shadow-password field by submitting an overlong password. The issue affects systems with PasswordAuthentication yes, an SSH-permitted passwordless target account, and at least one local account with a real SHA-crypt password hash; root also requires PermitRootLogin yes.

The article’s Alpine VM and Docker tests with OpenSSH 10.3_p1-r1 confirmed that passwords of 257 bytes or more could bypass authentication after an initial failed attempt in the same connection. Accounts with real password hashes were not affected, and testing showed that PAM with UsePAM yes blocked the bypass. OpenSSH fixed the problem in 10.6p2, and Alpine issued patched packages for all branches, including older unsupported releases.

The article highlights practical risks for Alpine-based container images, remote-debugging environments, and CI/CD runners that expose sshd. It also warns that version-banner checks can falsely identify Alpine systems as vulnerable because Alpine backported the fix without changing the upstream-reported OpenSSH version. Recommended actions are to upgrade and restart sshd, disable password authentication where possible, or use the PAM package with UsePAM yes if an immediate upgrade is not possible.

  • A scanner that submits only one long password per connection can miss affected systems, because the tested bypass required a failed password attempt followed by the long password within the same connection.
  • The article’s tested client and askpass setup could deliver passwords only up to 1023 bytes even though the server-side code separately accepts up to 1024 bytes, showing that client-side limits can distort vulnerability testing results.
  • OpenSSH version banners can produce false positives on Alpine because the distribution backported the fix without changing the reported upstream version, so installed package revisions or behavioral testing are more reliable indicators.
  • Authentication logs can reveal the pattern through a failed password event followed by a successful password login for an account whose shadow password field is `*` in the same session.
  • Fresh Alpine 3.24 installations of openssh-server receive the patched package from the current repository; the main container risk is older pinned images, cached build layers, internal registry copies, or mirrored package repositories.
Key Points
  • 01CVE-2026-123158 affects unpatched OpenSSH on musl-based systems without PAM, including Alpine Linux, and can allow login to eligible accounts whose shadow password field is `*` using an overlong password.
  • 02The bypass requires PasswordAuthentication to be enabled, an SSH-permitted target account with a `*` shadow password field, and at least one local account with a real SHA-crypt password hash; direct root login also requires PermitRootLogin yes.
  • 03In the authors’ Alpine VM and Docker tests using pre-fix OpenSSH 10.3_p1-r1, a 257-byte or longer password succeeded only after an initial failed authentication attempt in the same connection.
  • 04OpenSSH fixed the issue in version 10.6p2, while Alpine backported fixes to supported and unsupported branches; Alpine 3.24 received the fix in openssh-server 10.3_p1-r2.
  • 05For systems that cannot immediately upgrade, the article says disabling password authentication or using the PAM package with UsePAM yes blocked the bypass in testing.
