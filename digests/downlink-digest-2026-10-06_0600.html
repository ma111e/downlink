In plain words

The FBI removed an Accenture contractor after the contractor reportedly did not install a security update on an FBI job-site system run by Oracle. A group called ShinyHunters allegedly used that weakness to obtain personal details belonging to thousands of FBI employees. The case shows how one missed update at an outside service provider can put a major government agency and its workforce at risk, and the FBI says its investigation may lead to more arrests.

Summary
The FBI removed an Accenture contractor after an unpatched Oracle PeopleSoft platform was allegedly exploited by ShinyHunters, exposing personal information of thousands of FBI employees.

The FBI removed an Accenture contractor after determining that a contractor failed to install a security patch issued for a third-party-managed platform. The incident allegedly enabled ShinyHunters to obtain personal details belonging to thousands of FBI employees through the bureau’s job portal. The FBI said it has taken steps to reduce further risk and protect its workforce.

Reuters reported that the platform was Oracle PeopleSoft, though the FBI did not publicly name the third-party organization. Google-owned Mandiant assessed that ShinyHunters exploited a bypass for CVE-2026-35273 by using URL encoding to evade a web application firewall rule protecting the vulnerable Environment Management Hub endpoint. The FBI said two ShinyHunters members have been arrested, that it is pursuing further leads with partners, and that more arrests are likely.

  • The FBI attributed the incident to a missed patch that had been explicitly issued to secure the third-party-managed platform, highlighting patch implementation as the stated failure point.
  • ShinyHunters reportedly bypassed a web application firewall rule through URL encoding, meaning the protective rule did not prevent access to the vulnerable Environment Management Hub endpoint.
  • The breach involved a platform managed by a third party, but the FBI said it removed the contractor after its review, showing that contractor actions had direct consequences for the agency.
  • The FBI said two ShinyHunters members have already been arrested and that additional arrests are likely as it pursues further leads.
Key Points

93
In plain words

Atlassian disclosed a serious weakness in eight self-hosted versions of its workplace software that can let anyone on the network read certain files without signing in, if they know the exact file location. Businesses and organizations that run these products on their own servers are affected, while Atlassian’s online cloud customers have already been protected. The risk is that exposed files may contain sensitive information, so organizations should install the available updates quickly or temporarily keep the systems off the public internet.

Summary
Atlassian disclosed CVE-2026-21589, a critical unauthenticated path-traversal flaw affecting eight self-hosted Data Center products that can expose known files in application directories. Organizations should immediately upgrade to fixed releases or restrict public access and apply temporary blocking rules.

Atlassian disclosed CVE-2026-21589 on October 5, rating it 9.3 out of 10 under CVSS 4.0. The flaw affects eight self-hosted Atlassian Data Center products and lets an unauthenticated attacker read specific files from an application’s web root directory when the attacker knows the exact file name and path. Atlassian said sensitive files may be present in that directory in some configurations, though the advisory does not identify them.

The affected products are Bitbucket, Confluence, Jira Software, Jira Service Management, Bamboo, Crowd, Crucible, and Fisheye Data Center, and Atlassian published fixed versions for each. Its cloud products have already been patched, Bitbucket Cloud is not affected, and cloud customers do not need to act. Organizations that cannot upgrade should take instances offline where possible, restrict public network access, or apply temporary rules that block suspicious file-path patterns; Atlassian also recommends reviewing logs for those patterns.

  • The flaw does not allow attackers to browse directory contents, but it can still expose sensitive files when an attacker already knows an exact filename and path.
  • Atlassian’s temporary mitigations differ by product: all eight can use a web application firewall or reverse-proxy rule, while only certain products support Tomcat or Bitbucket-specific configuration changes.
  • The published fix information contains discrepancies, including conflicting Crowd 7.1 versions and a Bamboo version mismatch in the CVE record.
  • Atlassian recommends checking logs for suspicious encoded file-path patterns, but its advisory does not explain how to determine whether a matching request successfully returned a file.
Key Points
  • 01Atlassian disclosed CVE-2026-21589, rated 9.3 out of 10, which allows unauthenticated attackers to read specifically known files in the web application root directories of eight self-hosted Data Center products.
  • 02Affected products are Bitbucket, Confluence, Jira Software, Jira Service Management, Bamboo, Crowd, Crucible, and Fisheye Data Center; Atlassian has published fixed versions for each.
  • 03Atlassian stated that its affected cloud products have already been patched, Bitbucket Cloud is not affected, and cloud customers need take no action.
  • 04Organizations unable to upgrade immediately should restrict publicly reachable instances from external network access or apply Atlassian's temporary URL-blocking rules.
  • 05Atlassian advises customers to review access logs for suspicious file-path requests, although it said it cannot confirm whether individual self-hosted instances were affected.
OPEN SOURCE ↗
JUSTIFICATION

This is a critical, vendor-confirmed patch advisory for an unauthenticated file-access flaw affecting eight self-hosted Atlassian Data Center products. Internet-exposed instances should be upgraded or restricted promptly, and organizations should review logs for suspicious requests.

In plain words

People who were not authorized used a Danish company’s allowed access to look up personal records for about 8.8 million people in Denmark, including living people, those who moved abroad, and those who have died. The information included names, addresses, and personal ID numbers, although protected names and addresses were not included. This could make scams and identity fraud more convincing, so authorities are investigating and advising people not to share passwords, one-time codes, or card details with unexpected callers or messages.

Summary
Unauthorized actors used a Danish company’s legitimate access to the Central Person Register to retrieve names, addresses, and CPR data for roughly 8.8 million people. Authorities have revoked the access, launched an investigation, and urged residents to watch for targeted fraud and enable credit warnings.

Unauthorized parties used a private Danish company’s legitimate access to Denmark’s Central Person Register (CPR) to obtain names, addresses, and personal identification numbers for approximately 8.8 million people. The affected records include living residents, people who moved abroad, deceased people, and others, representing about four in five of the roughly 11 million people in the register. The Ministry of Digitalization said the figure is not yet final and that protected names and addresses were not included.

The access lasted about 10 days in September and was detected after a register administration employee noticed unusual activity on October 2. Datatilsynet said a very large number of automated lookups were made to identify valid CPR numbers, while authorities have not said how the unauthorized parties accessed the company’s systems, whether they retained or used the data, or who they are. The company’s access has been stopped, police and Datatilsynet are investigating, and residents are being urged to watch for convincing scams, avoid sharing MitID or payment details, and consider setting a credit warning through borger.dk.

  • The affected total represents about four in five of the approximately 11 million people recorded in the register, because it includes former residents and deceased people as well as current residents.
  • A credit warning does not prevent lending automatically: it signals participating companies to perform extra identity checks, and it may take several days to reach their systems.
  • Companies are supposed to receive register data only for people they have already identified, yet the article says the lookups covered roughly 8.8 million records; officials have not explained how that occurred under the access rules.
  • A CPR number is intended to help identify a person but, according to official guidance, should not be used as the only proof of identity.
Key Points
  • 01Unauthorized parties accessed names, addresses, and personal identification numbers for approximately 8.8 million people in Denmark’s Central Person Register through a private company’s legitimate lookup access.
  • 02The unauthorized access lasted about 10 days in September, and unusual activity was detected by a register administration employee on October 2.
  • 03The register administration stopped the company’s access, reported the incident to Denmark’s data protection authority, Datatilsynet, and police are investigating.
  • 04The accessed data did not include the names and addresses of people who had registered name-and-address protection, according to the Ministry of Digitalization.
  • 05Authorities advise people to be alert to unexpected messages and calls, never share MitID information or one-time codes, and consider setting a credit warning through borger.dk.

In plain words

Google has temporarily stopped paying rewards for reports of security flaws in much of its open-source code, including Go, Angular, Flutter, Bazel, and Protocol Buffers, because it received a large number of automated reports that were mostly not real problems. People who find issues that could let someone alter project code or published software packages can still report them for rewards, and some other Google programs may also apply. This matters because pausing rewards could make it harder to encourage people to report genuine flaws in widely used building blocks of software, while Google tries to reduce the flood of inaccurate reports.

Summary
Google has temporarily stopped accepting reward-eligible product vulnerability reports for its open-source projects, including Go and Angular, after a surge in mostly invalid automated submissions. Supply-chain compromise reports and other reward programs remain available while Google reworks the OSS VRP, with an update planned by Q1 2027.

Google has temporarily paused reward-eligible product vulnerability reports for its Open Source Software Vulnerability Reward Program (OSS VRP), effective October 1. The company said the move followed a significant rise in automated submissions, the vast majority of which were invalid. The pause affects flaws in Google-maintained open-source projects such as Go, Angular, Flutter, Bazel, and Protocol Buffers, while reports filed before October 1 are unaffected.

Supply-chain compromise reports, including issues that could permit tampering with a project’s source code or published packages, remain eligible for rewards. Researchers may also be able to use the Cloud VRP for certain Google Cloud repositories, submit accepted fixes through the Patch Rewards Program, or report issues through other applicable Google reward programs. Google removed previously listed product-vulnerability reward amounts from its rules and said it will provide an update in the first quarter of 2027, but did not state when submissions will resume or whether unrewarded reports will still be accepted.

  • Google removed the published product-vulnerability reward amounts from its public rules on September 30, one day before publicly announcing the pause.
  • The pause does not clearly state whether Google will continue to accept product vulnerability reports without paying a reward.
  • Researchers who submit patches through Google’s Patch Rewards Program must have the patch accepted by maintainers and keep it in place for one month before submitting it for payment.
  • Google had already tightened evidence requirements for some OSS VRP reports in March 2026, and the Go project later warned that unreviewed reports generated by large language models would not be credited.
  • Angular’s published security policy still directs reporters to the OSS VRP and does not list another reporting channel, despite the program’s product-vulnerability pause.
Key Points
  • 01Google paused acceptance of reward-eligible product vulnerability reports for its open-source software on October 1 after a significant rise in automated submissions, most of which it said were invalid.
  • 02The pause affects reports involving projects such as Go, Angular, Flutter, Bazel, and Protocol Buffers, while reports submitted before October 1 are unaffected.
  • 03Google continues to accept and reward reports of supply-chain compromises, such as weaknesses that could allow tampering with project source code or published packages.
  • 04Researchers may still use the Cloud Vulnerability Reward Program for some Google Cloud repositories, submit accepted security patches through the Patch Rewards Program, or use other applicable Google reward programs.
  • 05Google said it plans to provide an update in the first quarter of 2027, but did not state when product vulnerability report submissions will resume.

Nikkei disclosed that unknown attackers accessed two employee email accounts in separate incidents involving Google Workspace and Microsoft 365. In September, attackers accessed a different employee’s Microsoft 365 account and sent 9,000 phishing emails containing links to malicious websites. The messages targeted Nikkei staff and interviewees who had been in contact with several employees.
