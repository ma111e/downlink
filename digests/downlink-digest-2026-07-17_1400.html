In plain words

Researchers say a Chinese cybercrime subgroup called CylindricalCanine broke into DigiCert by tricking support staff into opening a fake customer screenshot file. DigiCert customers with certain approved software-signing orders were affected because the attackers accessed codes needed to obtain certificates, which are digital approvals that make software look trusted. This matters because the stolen certificates were used to make harmful programs appear legitimate, helping them avoid detection and putting people and organizations at greater risk of running malicious software.

Summary
Researchers attributed DigiCert’s April 2026 breach to CylindricalCanine, a GoldenEyeDog subgroup that compromised support analyst workstations via a malicious “screenshot” file and stole EV code-signing certificate access. The attackers used the certificates to sign Golden Gh0st RAT/Zhong Stealer malware, highlighting the risk of certificate abuse in malware delivery.

Cybersecurity researchers at Expel attributed the April 2026 DigiCert security incident to CylindricalCanine, a subgroup of GoldenEyeDog, also known as APT-Q-27, Dragon Breath, and Miuuti Group. DigiCert said the threat actor contacted its support team through a customer chat channel and delivered a ZIP file disguised as a customer screenshot, which contained a malicious .scr executable. The attackers gained access to two support analyst workstations and used a customer-support portal function to access initialization codes for approved but pending EV Code Signing certificate orders.

DigiCert revoked 60 certificates issued by several certificate authorities, and 27 of them were explicitly linked to the threat actor. The article says the stolen or abused certificates were used to sign Zhong Stealer malware artifacts, helping the malware appear more trustworthy. DigiCert said the issue stemmed from a threat model that did not account for initialization codes being visible to a compromised support analyst account through the portal function.

Expel said CylindricalCanine commonly distributes files disguised as screenshots through phishing emails or support-portal submissions. The attack chain uses a link to download additional payloads, triggers DLL side-loading through a legitimate executable, displays a decoy PDF with an HTTP 503 error, and then loads an encrypted payload. The final malware, Golden Gh0st RAT, can set up persistence, steal sensitive data, create a SOCKS proxy tunnel, log keystrokes, take screenshots, execute shell commands, drop more payloads, and clear Windows Event logs.

  • DigiCert said the critical weakness was not certificate issuance approval itself, but that initialization codes visible inside an internal support portal were functionally sufficient, together with approved orders, to obtain EV Code Signing certificates.
  • The incident shows that customer support channels can become a direct path into high-value internal systems, because the initial payload was delivered through a customer chat interaction rather than a conventional email-only phishing route.
  • CylindricalCanine’s use of decoy screenshot-themed files and a fake HTTP 503 PDF indicates the attack chain was designed to look like a normal support troubleshooting exchange while malware executed in the background.
  • DigiCert’s mitigation focused on masking initialization codes from proxied users in both the UI and API, showing that sensitive support-portal data exposure can matter as much as account compromise in certificate abuse scenarios.

  • 02DigiCert said the threat actor contacted its support team through a customer chat channel on April 2, 2026, and delivered a ZIP file disguised as a customer screenshot that contained a malicious .scr executable.

In plain words

A new botnet called NadMesh is finding publicly reachable AI and developer tools, such as ComfyUI, Ollama, n8n, Gradio, Docker, Jenkins, Redis, and MCP services, and trying to steal the keys and login tokens stored on those machines. The people affected are teams that put these tools on the internet without strong access controls, especially when the machines can connect to AWS accounts, Kubernetes clusters, registries, models, or other cloud services. This matters because the attackers are not mainly after the computer itself; they want the access it has, which could let them reach wider cloud systems and keep stealing new credentials if the infected machine is not fully cleaned first.

Summary
The new Go-based NadMesh botnet is scanning exposed AI and developer services to steal AWS keys, Kubernetes tokens, Docker credentials, and model/tool access rather than just hijacking compute. Organizations running ComfyUI, Ollama, n8n, Gradio, MCP, Docker, Jenkins, Redis, or similar services should remove them from the public internet, enforce authentication, check persistence paths, and revoke exposed credentials.

A Go botnet called NadMesh appeared in early July and is scanning exposed AI services such as ComfyUI, Ollama, n8n, Open WebUI, Langflow, and Gradio. QiAnXin’s XLab named the malware after the “n4d mesh controller” string in its source and published analysis of the botnet, its operator panel, and observed traffic. The operator’s dashboard claimed 3,811 unique AWS keys, while XLab’s sensors saw distinct source IPs pushing NadMesh rise to around 139 per day in the first week of July.

The article says NadMesh is primarily after cloud and platform access rather than the infected host itself. It collects cloud keys from environment variables, Kubernetes service account tokens, and files including ~/.aws/config, .env, and ~/.docker/config.json. XLab’s observed exploit traffic was led by Docker API remote code execution at 30.31% and Jenkins script console remote code execution at 22.28%, while MCP command execution appeared at 0.78%.

NadMesh uses adaptive scanning, repeatedly prioritizing subnets and IPs that previously produced hits and blacklisting targets that absorb ten deployment attempts without returning results. The article says the agent persists in three ways, uses Garble obfuscation, UPX packing, and random padding, and therefore does not share one stable hash across builds. It advises operators to place exposed services behind authentication or remove them from the public internet, check specified drop paths, isolate infected hosts, and revoke credentials the host could access.

  • NadMesh’s own dashboard metrics are internally inconsistent, so XLab’s sensor data and observed exploit traffic provide a more reliable view than the operator’s claimed bot counts or success totals.
  • Although NadMesh is positioned around exposed AI services, XLab’s traffic chart shows most observed exploit attempts still target Docker APIs and Jenkins consoles, with MCP command execution accounting for only 0.78% of observed traffic.
  • The botnet’s success scoring explicitly excludes Ollama and AWS harvesting, meaning the operator’s scoreboard does not count some of the most important data the campaign is stealing.
  • The article emphasizes that credential revocation alone is insufficient because NadMesh uses three persistence methods, so new credentials could be stolen again if the host is not cleaned first.
  • NadMesh’s scanning logic prioritizes networks and hosts that previously produced results, while blacklisting targets that absorb repeated deployment attempts without response as suspected honeypots.

In plain words

A problem in OpenSSL, software widely used to protect internet connections, could let someone make a server waste a lot of memory by sending only a tiny amount of data. This can slow or crash services that rely on OpenSSL, including web servers like NGINX and Apache, language tools such as Node.js and Python, and databases like MySQL and PostgreSQL. OpenSSL has released fixed versions, and the article says organizations should update because even though this does not steal data, it can still disrupt services and hurt trust.

Summary
OpenSSL has quietly fixed a DoS flaw called HollowByte that lets unauthenticated attackers bloat server memory using an 11-byte TLS handshake payload. Organizations should update OpenSSL packages to the fixed versions as soon as possible, especially on servers using software like NGINX or Apache.

A vulnerability dubbed HollowByte allows unauthenticated attackers to trigger a denial-of-service condition on OpenSSL servers with a malicious payload of just 11 bytes. The OpenSSL team has fixed the issue without assigning an identifier and has backported the patch to older releases. Because OpenSSL is widely used for secure internet communication, the article says organizations should prioritize moving to a fixed version.

Okta’s Red Team explained that vulnerable OpenSSL versions allocate memory based on the declared length in a TLS handshake message before receiving and checking the payload. An attacker can open a TLS connection and send a small malicious input whose header claims that a much larger message body will follow. Repeating this across many connections can force the server to allocate significant memory while the worker thread waits for data that never arrives.

Okta said glibc may keep freed small-to-medium allocations for reuse instead of immediately returning them to the operating system, which can leave the server bloated even after connections drop. In Okta’s NGINX tests, low-capacity environments could be depleted of memory, while higher-spec servers could lose up to 25% of memory with attack bandwidth below security alerting thresholds. The issue is fixed in OpenSSL 4.0.1 and backported to 3.6.3, 3.5.7, 3.4.6, and 3.0.21, which grow the buffer only when data arrives.

  • The attack can remain below security alerting thresholds while still causing higher-spec servers to lose up to 25% of their memory.
  • Restarting the affected process is the only way to fully reclaim memory once the server remains bloated after the attack.
  • The issue was treated as a hardening fix rather than a security vulnerability, but Okta still recommends immediate upgrades to distribution OpenSSL packages.
  • glibc’s memory handling can worsen the impact because it may keep freed small-to-medium allocations for reuse instead of immediately returning them to the operating system.
Key Points
  • 01A vulnerability dubbed HollowByte allows unauthenticated attackers to trigger a denial-of-service condition on OpenSSL servers with a malicious payload of just 11 bytes.
  • 02Vulnerable OpenSSL versions allocate memory based on the declared length in a TLS handshake header before receiving and validating the payload.
  • 03Okta researchers said repeated connections with randomized claimed sizes can cause heap fragmentation and make a server’s Resident Set Size climb continuously, even after the attacker disconnects.
  • 04The open-source OpenSSL library is embedded in software including NGINX, Apache web servers, Node.js, Python, Ruby, PHP, MySQL, and PostgreSQL.
  • 05The issue has been fixed in OpenSSL 4.0.1 and backported to versions 3.6.3, 3.5.7, 3.4.6, and 3.0.21.
