In plain words

The article warns about Java4Shell, a serious flaw in some versions of Java that can let an outsider take control of an affected application before logging in. It may affect organizations using common products such as Keycloak, Jira, Confluence, Jenkins, Artifactory, and PingFederate when they run on certain newer Intel or AMD computers. Because Java is widely used for internet-facing business services, a successful attack could give criminals access to systems, data, or credentials. Organizations should install the November 17, 2026 Java updates promptly or use the temporary startup setting described in the advisory.

Summary
CVE-2026-114938 (“Java4Shell”) is a critical OpenJDK Base64-decoder flaw that can enable pre-authentication RCE on AVX-512 VBMI-capable x86-64 systems. Organizations should immediately upgrade to patched JDK builds or temporarily start JVMs with -XX:-UseBASE64Intrinsics and restart all Java workloads.

CVE-2026-114938, also called Java4Shell, is a critical heap memory-corruption flaw in OpenJDK’s hardware-accelerated Base64 decoder that was publicly disclosed on November 17, 2026. The issue can be reached when applications decode attacker-controlled Base64 data, and researchers demonstrated pre-authentication remote code execution in default deployments of Keycloak, Jira, Confluence, Artifactory, Jenkins, and PingFederate. The article also reports post-authentication remote code execution in products including Apache Kafka Broker, Solr, Elasticsearch, Gerrit, and Netflix Spinnaker, plus a client-side TLS attack affecting Java clients connecting to malicious servers.

The flaw occurs in an optimized x86-64 decoding routine used by the HotSpot C2 compiler on CPUs supporting AVX-512 VBMI, where malformed Base64 padding can cause a 62-byte write outside the intended heap memory area. It affects OpenJDK 17.0.6 and later and specified Oracle Java SE, Oracle GraalVM, and downstream OpenJDK builds, while ARM64 and older x86-64 processors without the required instruction support are not affected. Organizations are advised to install patched JDK releases and restart JVMs; where updates are delayed, they can temporarily disable the affected path with -XX:-UseBASE64Intrinsics.

  • Exposure is hardware-dependent: administrators can check Linux /proc/cpuinfo for avx512f, avx512bw, avx512vbmi, and bmi2 to determine whether a host can execute the vulnerable decoder path.
  • Disabling Base64 intrinsics with -XX:-UseBASE64Intrinsics is the recommended temporary workaround because it forces Java to use safer non-hardware-accelerated code; -XX:UseAVX=2 is limited to x86-64 systems and will prevent ARM64 JVMs from starting.
  • Reverse-proxy request-body buffering can disrupt some multi-connection heap-grooming techniques, but the article states it does not fully protect against single-request chains such as Elasticsearch or WebSocket tunnels.
  • The risk is not limited to servers: the article describes a client-side TLS attack path affecting Java clients that connect to a malicious server.
  • Possible warning signs include bursts of Base64 parsing errors, repeated JVM crash logs referencing StubRoutines::base64_decodeBlock, and Java processes launching unexpected shells or reconnaissance commands.
Key Points
  • 01CVE-2026-114938, called Java4Shell, is a critical OpenJDK Base64 decoder flaw that can cause a 62-byte heap out-of-bounds write on certain x86-64 CPUs.
  • 02The issue affects OpenJDK 17.0.6 and later and certain Oracle Java SE, Oracle GraalVM, and downstream OpenJDK builds that use the affected Base64 decoder.
  • 03Researchers demonstrated pre-authentication remote code execution in default configurations of Keycloak, Atlassian Jira, Atlassian Confluence, JFrog Artifactory, Jenkins, and PingFederate.
  • 04The vulnerable code path requires x86-64 CPUs with avx512f, avx512bw, avx512vbmi, and bmi2 support; ARM64 systems and older x86-64 CPUs without AVX-512 VBMI are not affected.
  • 05Organizations should install patched Java builds and restart JVMs, or temporarily disable Base64 intrinsics with -XX:-UseBASE64Intrinsics if patching is delayed.

    In plain words

    F5 disclosed a serious flaw in nginx, widely used software that runs websites and routes web traffic, when it is configured to use the newer HTTP/2 web connection method. An unauthenticated person on the internet could potentially use the flaw to read or alter the server’s memory, crash the service, steal information, or take control of the affected server. Organizations using vulnerable nginx versions with HTTP/2 enabled, including web servers, reverse proxies, containers, and products that include nginx, should update to the fixed releases or turn off HTTP/2 until they can patch.

    Summary
    F5 disclosed CVE-2026-123007, a critical unauthenticated HTTP/2 flaw in nginx that can enable remote code execution on affected servers with HTTP/2 enabled. Upgrade to nginx 1.31.9 or 1.30.7 (or the applicable fixed NGINX Plus release) immediately, or disable HTTP/2 until patching is complete.

    F5 disclosed CVE-2026-123007, a critical vulnerability in nginx’s HTTP/2 implementation that can allow an unauthenticated remote attacker to read and overwrite memory in an nginx worker process and potentially achieve remote code execution. The flaw affects nginx Open Source 1.9.5 through 1.30.6 and 1.31.0 through 1.31.8, along with several NGINX Plus releases, where HTTP/2 is enabled. HTTP/1.1-only servers are not affected through this path. Researchers have confirmed working unauthenticated remote code execution against affected builds, although no exploitation in the wild had been reported at the time of the notice.

    The issue is an integer underflow in HTTP/2 flow-control accounting that can result in out-of-bounds memory reads and writes when queued data frames are handled after a stream ends. Possible consequences include worker-process crashes, disclosure of memory contents such as heap and library addresses, and potential access to data or backend systems reachable from nginx. F5 fixed the issue in nginx Open Source 1.31.9 and 1.30.7, plus NGINX Plus 37.3.0.1 and 37.0.8.1, and organizations are advised to update and restart nginx or perform a supported live binary upgrade. If patching is delayed, disabling HTTP/2 mitigates this flaw, but it does not address several other vulnerabilities fixed in the same release.

    • A reported nginx version alone may not establish exposure because Linux distribution packages can include a backported fix without changing the displayed nginx version, so installed package versions should be checked against distribution security advisories.
    • A configuration reload does not replace the running nginx executable, and existing HTTP/2 connections can remain on old worker processes; a restart or supported live binary upgrade is required after updating.
    • The vulnerable HTTP/2 code has been present since nginx 1.9.5 in 2015, making long-lived deployments and bundled nginx installations relevant to the review.
    • Although researchers confirmed working unauthenticated remote code execution, the article notes that an exploit may require substantial HTTP/2 traffic on one connection and may be less reliable over slow networks or proxied HTTP/2 connections.
    • Disabling HTTP/2 mitigates CVE-2026-123007 but does not address the additional high-severity flaws fixed in the same release.
    Key Points
    • 01F5 disclosed CVE-2026-123007, a critical integer-underflow flaw in nginx HTTP/2 flow-control accounting that can allow unauthenticated remote code execution.
    • 02The issue affects nginx Open Source 1.9.5 through 1.30.6 and 1.31.0 through 1.31.8, plus specified NGINX Plus releases, only when HTTP/2 is enabled.
    • 03F5 fixed the flaw in nginx Open Source 1.31.9 and 1.30.7 and in NGINX Plus 37.3.0.1 and 37.0.8.1.
    • 04Organizations should identify nginx deployments, verify whether HTTP/2 is enabled, apply the relevant update, and restart nginx or perform a supported live binary upgrade.
    • 05If patching must be delayed, the article recommends disabling HTTP/2 by removing the HTTP/2 setting from affected nginx server configuration.

An attacker abused a weakness in Optimizely, a service many websites use to test and customize pages, to place harmful code on customer websites. More than 450 website domains may have served this code to visitors, including sites in banking, shopping, travel, media, and other industries. The code could swap cryptocurrency payment addresses, try to collect card details and website cookies, take screenshots, and attempt to target some iPhones and iPads. This matters because one trusted outside service can put many unrelated websites and their visitors at risk at the same time.

Summary
Attackers exploited Optimizely Web Experimentation’s signup flow to inject malicious JavaScript into customer snippets, potentially exposing visitors to cryptocurrency wallet replacement, payment-card skimming, cookie theft, screenshots, and iOS exploit delivery. Organizations should audit Optimizely Project JavaScript and access logs, rotate credentials and tokens, and strengthen CSP and third-party script monitoring.

On November 16, 2026, an attacker exploited a weakness in Optimizely Web Experimentation’s account signup flow to alter the Project JavaScript field in customer projects. Because this field runs custom code on pages that load an Optimizely snippet, the attacker’s JavaScript was delivered to website visitors through legitimate Optimizely delivery paths, including its CDN. Optimizely said it blocked the vulnerable path, fixed the issue, removed injected code, ended active sessions, revoked tokens, reset affected account access, and notified customers.

ThreatLabz identified more than 450 unique domains and over 3,000 URLs serving the malicious script across industries including banking, e-commerce, travel, retail, media, and telecommunications. The injected loader commonly retrieved a second-stage payload, track.js, from attacker-controlled infrastructure, where it could replace cryptocurrency wallet addresses, collect JavaScript-accessible cookies, capture screenshots, and monitor payment-card data entered directly on compromised pages. The payload also attempted to load iOS- and iPadOS-focused exploit components for some iPhone and iPad visitors, while most of its activity remained limited to the browser context of the compromised website.

  • The cookie theft and screenshot behavior was conditional: the payload performed it only after replacing a valid cryptocurrency wallet address when the related page element was visible.
  • The payment-card skimmer could monitor card data entered directly into compromised pages, but it could not read details entered within secure cross-origin payment frames such as hosted Stripe or Adyen fields.
  • Most of the payload’s activity was limited to the affected website’s browser page and could not directly access unrelated tabs, other websites’ cookies, local files, or browser-wide activity.
  • The iPhone and iPad branch represented a potentially broader risk because a successful iOS or WebKit exploit could exceed the normal restrictions placed on website code.
  • Because malicious code was served through legitimate Optimizely snippets and its CDN, affected websites may already have trusted and allowed the delivery path used by the attacker.
