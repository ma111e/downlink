In plain words

Researchers at Cyera found a serious weakness in PostgreSQL, a widely used database behind services from companies like Netflix, Instagram, Spotify, and Uber. A normally low-risk backup account could be abused to make the database run an attacker’s code, give the attacker full control of the database, and leave a hidden way back in. This matters because PostgreSQL is used to store things like financial records, medical records, government data, customer information, and application secrets, so a successful attack could expose sensitive data and help attackers move further into a server.

Summary
Cyera researchers found a critical PostgreSQL flaw, CVE-2026-6471, that lets low-privilege replication accounts load arbitrary plugins and gain remote code execution, superuser access, and persistence. Organizations should patch immediately, audit replication accounts, and restrict replication access and outbound SMB/NFS traffic.

Cyera Research discovered a critical PostgreSQL vulnerability, CVE-2026-6471, which the article calls PostGREShell. The flaw affects every PostgreSQL version since 9.4 and was present from 2014 until the recent security update. The article says a low-privilege account with the REPLICATION attribute can load and execute arbitrary code on the database server.

The issue is in PostgreSQL’s logical replication output plugin loading path. The article says plugin names supplied through CREATE_REPLICATION_SLOT are passed directly to the loader without the validation used by the SQL LOAD command, allowing paths such as traversal strings and Windows UNC paths. On Windows, PostgreSQL can load a DLL from an attacker-controlled SMB share, while Linux and macOS scenarios depend on NFS automounting or an attacker already being able to write a file to disk.

After code execution, the attacker can escalate to PostgreSQL superuser by using internal functions and directly modifying pg_authid, bypassing normal SQL permission checks. The article says the attacker can then read database contents, run operating system commands, access files, write files where the postgres user can, and install persistence through pg_hba.conf changes, shared_preload_libraries, and repeated privilege changes. It recommends applying the PostgreSQL security update, auditing REPLICATION accounts, restricting replication access in pg_hba.conf, blocking outbound SMB and NFS, and monitoring suspicious replication activity.

  • The vulnerable code path existed because PostgreSQL applied library-name restrictions to the SQL LOAD command but not to the replication path, even though both ultimately load executable plugins into the server process.
  • The article says the core fix is only two lines of C, making the long exposure since 2014 notable because the missing security check was small but in a widely used path.
  • The practical risk differs by platform: Windows can be exploited with only network access through an SMB-hosted DLL, while many Linux, macOS, Docker, and Kubernetes cases require the attacker to already have a way to place a local shared library.
  • The article highlights replication accounts as an overlooked security risk because they are common in backup, standby, CDC, and monitoring setups but can become a path to full database and server compromise.
  • The persistence mechanisms described are layered so that fixing only one change, such as reverting superuser privileges or cleaning pg_hba.conf, may still leave another backdoor in place.
