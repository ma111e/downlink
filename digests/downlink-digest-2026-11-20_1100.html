In plain words

A flaw in the Linux software used to run virtual computers on shared servers allowed a person controlling one virtual machine to read large amounts of the physical server’s memory and, in testing, change a small part of it. It affects servers using AMD processors where customers are allowed to run virtual machines inside their own virtual machines, including affected DigitalOcean systems before they were patched. This matters because memory on a shared server can contain information belonging to other customers, so the flaw could break the separation that keeps tenants’ data apart.

Summary
CVE-2026-99312 is a critical AMD-specific Linux KVM flaw that can let a root-level guest VM access or alter host memory when nested virtualization is enabled, potentially exposing other tenants on shared cloud hosts. Operators should apply the host-kernel fix and reboot, or disable nested virtualization until patched.

CVE-2026-99312 is a Linux KVM flaw affecting AMD hosts with nested virtualization enabled that can allow someone with root access in a guest virtual machine to access the physical host’s memory. Terra Security researchers demonstrated reading approximately 127 GB of host memory from a DigitalOcean Droplet, including a host kernel version banner. In a separate test on their own bare-metal AMD server, they wrote 32 selected bytes into a live host-kernel memory page.

The issue occurs when an INIT reset stops a nested virtual machine and KVM fails to restore a memory-management pointer for the outer virtual machine. That pointer can reference freed memory that, once reused, can be filled with forged entries directing the processor to arbitrary host physical-memory pages. Upstream fixes reset this state during every INIT and are available in stable kernel 7.3.5 and long-term kernels 6.18.64 and 6.12.118. Operators must update and reboot affected host kernels, or disable nested virtualization until patched; updating guest operating systems does not resolve the issue.

  • The flaw originated in a 2022 security patch for CVE-2022-3344, which corrected one reset-state issue but did not restore a related memory pointer, leaving the defect present for nearly four years.
  • Updating guest operating systems provides no protection because the vulnerable code runs on the physical host; the host must install a fixed kernel and reboot before the protection takes effect.
  • Disabling nested virtualization is the only stated temporary mitigation, but it prevents customers from running virtual machines inside their own virtual machines.
  • Severity assessments differ substantially: the Linux kernel CVE team assigned an 8.8 score, Red Hat initially assessed it as Moderate at 5.6 and denial-of-service only, while DigitalOcean treated it as critical for its shared-cloud environment.
  • The article states that nested virtualization is enabled by default in the kvm_amd module, meaning vulnerable AMD KVM hosts may be exposed unless an operator deliberately changed that setting.

In plain words

The article argues that companies are increasingly preparing to let AI assistants help run their security teams, especially with routine tasks such as gathering information and sorting alerts. Rather than giving AI full control at once, it says companies should allow it to make only low-risk, easily reversible decisions until it has shown reliable results. This affects security leaders, analysts, employees, and business operations because an AI mistake—such as shutting down an important system or disabling the wrong account—can disrupt work, while moving too slowly can leave real threats unchecked. The broader challenge is gaining time and capacity from AI without giving a powerful automated system more access than can be safely monitored and undone.

Summary
SOC teams should grant AI agents autonomy incrementally by workflow stage and action risk, using reversibility, blast radius, and verifiable evidence to determine when human approval is needed. Agents should earn—and lose—authority through measured performance, dry runs, audit trails, rollback plans, and privileged-identity governance.

Security leaders are preparing to give AI agents more authority in security operations, with 36% of surveyed CISOs comfortable with autonomous low-risk actions today and 60% expecting to be within a year. The article argues that autonomy should not be treated as a single choice between AI suggestions and full AI control. Instead, teams should separately decide how much authority an agent receives for collecting evidence, analyzing alerts, recommending responses, and executing changes.

The recommended decision framework evaluates each action by its reversibility, potential blast radius, and the strength of verifiable evidence behind it. Read-only tasks such as querying security logs and enriching indicators can be fully autonomous, while disruptive actions such as isolating production servers or disabling accounts should require greater human involvement. Agents should earn expanded authority through measured agreement with analysts, test-mode dry runs, complete evidence trails, and defined rollback plans, and should lose autonomy after declining performance, major environment changes, or serious mistakes.

The article also warns that human approval can become a rubber stamp if reviewers cannot quickly inspect the evidence, reasoning, and alternatives the agent considered. It recommends managing a SOC AI agent as a privileged identity, with its own credentials, narrowly scoped permissions, logging of every query and action, and monitoring comparable to that used for new administrative accounts. This approach is intended to help organizations gain analyst capacity from AI while limiting the business disruption that could result from an incorrect, manipulated, or compromised agent.

  • Treating AI autonomy as a single choice between “suggest” and “act” can stall adoption; the article recommends assigning different autonomy levels to individual stages and actions instead.
  • A human approval step can become ineffective if reviewers lack concise, verifiable evidence and simply approve requests to keep work moving; the article suggests a reviewer should be able to verify a verdict in one or two minutes.
  • Autonomy should be reduced as well as increased: falling agreement rates, major environment changes such as a new EDR deployment or cloud migration, or one serious miss should trigger a demotion.
  • The article frames a SOC AI agent’s permissions as an additional source of risk, meaning it should be managed like a new privileged account with its own identity, narrowly scoped permissions, and monitoring of every tool call and action.

  • 02The article divides AI SOC work into evidence collection, analysis and verdicts, response recommendations, and response execution, arguing that each stage can have a different degree of automation.
  • 03Organizations should decide an AI agent’s permitted autonomy for each action by considering whether the action can be reversed, its potential business impact, and the quality of evidence supporting it.
  • 04Human approval is only meaningful when reviewers receive the collected evidence, the reasoning linking it to the decision, and the alternative explanations or checks the agent ruled out.
