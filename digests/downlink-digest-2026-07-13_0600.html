In plain words

The United States and eight allied countries warned that Russian government-linked hackers are trying to break into important networks by finding weak or poorly set up routers, the devices that direct internet traffic. The groups most at risk include energy, communications, defense, healthcare, financial services, and state and local government services. This matters because access to those networks could affect essential services people and organizations rely on every day, and the agencies are urging organizations to strengthen or replace vulnerable equipment.

Summary
Cybersecurity agencies from the U.S. and allied countries warn that Russian FSB-linked hackers are targeting critical infrastructure by abusing weakly configured routers, especially those using default SNMP settings and Cisco Smart Install flaws. Organizations are urged to harden network devices by upgrading to SNMPv3, disabling Smart Install, blocking risky traffic, patching firmware, and replacing end-of-life equipment.

Cybersecurity agencies from the United States and eight other countries issued a joint warning that Russian state hackers are targeting vulnerable and poorly configured routers to infiltrate critical infrastructure networks. The advisory was co-authored by the NSA, FBI, and CISA, along with agencies from Australia, the United Kingdom, Canada, New Zealand, Estonia, Finland, France, and Italy. It attributes the activity to hackers from the Russian Federal Security Service Center 16.

The group, tracked under names including Berserk Bear, Energetic Bear, Crouching Yeti, Dragonfly, Ghost Blizzard, and Static Tundra, scans internet-connected IP address ranges for routers using default or common SNMP authentication strings. The hackers then issue commands using spoofed IP addresses to copy device configuration files and exfiltrate them through the Trivial File Transfer Protocol to actor-controlled servers. The FBI also warned in August 2025 that the same group had been targeting critical infrastructure using CVE-2018-0171 in Cisco IOS and Cisco IOS XE Smart Install since November 2021.

The sectors most at risk include energy, communications, defense industrial base, healthcare, financial services, defense, and state and local government services. The advisory urges network defenders to upgrade to SNMPv3, disable Cisco Smart Install, enforce strong unique passwords, block TFTP and SNMP traffic at edge firewalls, update software and firmware, and replace end-of-life devices. The article also notes a separate law enforcement disruption of FrostArmada, an APT28-attributed campaign that infected 18,000 routers across 120 countries and altered DNS settings to steal Microsoft 365 logins and OAuth tokens.

  • The activity relies heavily on basic router misconfigurations, such as default or common SNMP authentication strings, meaning simple hygiene gaps can expose critical infrastructure networks to a state-linked actor.
  • The advisory highlights that attackers are not only exploiting new issues but also long-known weaknesses, including Cisco Smart Install and CVE-2018-0171, which the FBI said the group has used since November 2021.
  • Blocking TFTP and SNMP traffic at edge firewalls is singled out as a concrete defensive step because the attackers use SNMP to find and command routers and TFTP to exfiltrate configuration files.
  • Replacing end-of-life devices is part of the recommended mitigation, showing that unsupported network equipment remains a practical entry point in critical infrastructure environments.

In plain words

A security company found that one phishing operator accidentally left his server open to the internet, exposing tools and records that led researchers to three schemes aimed at stealing access to Microsoft 365 accounts. The victims were mostly company email accounts across multiple countries, and the attackers used tricks that could let them keep using stolen access even after a password reset. This matters because the tools came from public code and cheap services, meaning people with limited skill can now run convincing campaigns that get around common login protections.

Summary
A misconfigured phishing server exposed three Microsoft 365 phishing operations using Evilginx-based kits and device-code phishing to steal and refresh session tokens, showing how low the barrier has become for MFA-resistant account compromise. Defenders should pair phishing-resistant MFA with Conditional Access policies that block or tightly restrict Microsoft device code flow.

A live Microsoft 365 phishing operator accidentally left a Python web server exposed on a public port with directory listing enabled, revealing tools and records from the operation. Lexfo used the exposed files to pivot to two more phishing operators, uncovering three campaigns in total. Each campaign used a custom fork of the open-source Evilginx proxy cloned from public GitHub, and the largest had been running for more than a year with victims that were overwhelmingly corporate mailboxes.

The campaigns used two different ways to get around normal account protections: one proxied live Microsoft logins, while another abused Microsoft’s legitimate OAuth device code flow. The device code version led victims to enter a real code at microsoft.com/devicelogin and complete MFA on Microsoft’s own page, allowing the attacker’s backend to collect the resulting token. The article says these techniques require different defenses, with phishing-resistant MFA helping against Evilginx-style proxying and Conditional Access policies needed to block or restrict device code flow.

The exposed server included phishing configurations, credential-harvesting logs, remote management installers, combolists, backup archives, and Telegram session files. The article links the first operation to codemado, an Egyptian actor running infrastructure on picis.net and using a bulk mailer called MaDoO Blaster, while the other forks are tied to mail-argenta’s red-queen and saroula01’s black-queen. Lexfo also found signs of AI-assisted development around the phishing frameworks, especially in scripts and phishlets, and the report concludes that public repositories, cheap kits, and model-assisted custom code have lowered the barrier to running these campaigns.

  • Phishing-resistant MFA such as FIDO2 keys and passkeys can stop the Evilginx reverse-proxy approach, but the article says they do not stop device code phishing because the victim completes the sign-in on genuine Microsoft infrastructure.
  • Microsoft 365 defenders need different controls for the two techniques described: phishing-resistant MFA for Evilginx-style proxying and Conditional Access policies to block or restrict device code flow.
  • The article highlights that password resets may not end the risk from captured Microsoft session cookies, because one Evilginx fork set a one-year cookie lifetime and stolen tokens were repeatedly refreshed.
  • For detection, the article says investigators should hunt on the sign-in log’s “Original transfer method” field because sessions that began with device code flow can remain tagged that way even when later refresh events no longer show the current protocol.
  • Lexfo found that the clearer evidence of AI assistance was mostly in scripts, phishlets, and other supporting code around the Evilginx forks, not in major changes to the core framework itself.
Key Points
  • 01Lexfo found a publicly exposed Python web server with directory listing enabled that revealed phishing configurations, credential-harvesting logs, remote management installers, combolists, backup archives, and the operator’s Telegram session files.
  • 02The exposed server led researchers to three Microsoft 365 phishing operations, each using a custom fork of the open-source Evilginx proxy cloned from public GitHub repositories.
  • 03One operation attributed by Lexfo to the Egyptian actor codemado used an Evilginx adversary-in-the-middle proxy, SimpleHelp remote console access, the picis.net domain, and a bulk mailer called MaDoO Blaster.
  • 04The red-queen Evilginx fork from the Nigerian operator mail-argenta modified HTML attributes and URL rewriting behavior to evade checks and detection, and set a one-year lifetime on captured Microsoft session cookies.
  • 05The black-queen fork by saroula01 used Microsoft’s legitimate OAuth device code flow, where victims entered a real device code at microsoft.com/devicelogin and completed MFA on Microsoft’s own page while the attacker’s backend collected the resulting token.

In plain words

Netskope tested a new Anthropic AI model, Claude Mythos, on software that Netskope builds and ships, asking it to find real flaws and then prove them on clean test machines instead of just describing possible problems. The model found issues in Netskope’s Windows software and in open source code that Netskope products use, while also helping show which fixes mattered most. This matters because Netskope customers rely on this software in sensitive parts of their networks, and the same kind of AI help could also be used by attackers, so finding and fixing these problems first can reduce real-world risk.

Summary
Netskope used Anthropic’s Claude Mythos in self-verifying vulnerability research workflows against its own products, where separate model instances had to reproduce crashes or validate fixes before findings counted. The key takeaway is that frontier AI can now independently drive much of the vulnerability research loop, producing reproducible kernel, open-source, and binary-diff findings when grounded in strong verification harnesses.

Netskope tested Anthropic’s Claude Mythos preview in self-verifying vulnerability research workflows against software that Netskope builds and ships. The company asked the model to choose targets, prove bugs against real systems, have a second copy of itself verify the proof on clean machines, and explain how the findings fit together. Across three tracks, the model produced 9 kernel memory corruption findings, 17 previously unreported bugs in open source code used by Netskope products, and four confirmed n-day fixes reconstructed from a binary diff.

The article emphasizes that claims only counted as findings when independent verification could reproduce them from concrete evidence, such as a crashing input or a small proof of concept. In kernel driver testing, the model had to satisfy every runtime precondition between an entry point and unsafe code, then reproduce each crash three times from a clean snapshot. In open source testing, a separate Mythos instance rebuilt current upstream code and confirmed AddressSanitizer crashes, while binary-diff testing required the same reproducer to crash an older build and run cleanly on the latest build.

Netskope says the main value was the repeatable harness rather than the individual bugs, because it turns offensive research into a release gate for its own products. The model also generated useful lab notes, cached dead ends, improved the scaffolds, and produced a privilege escalation chain analysis showing how three confirmed n-days could combine on a default secure Windows 11 host. The company states that several issues were already fixed and the rest are in remediation or coordinated disclosure.

  • The most productive improvement was not prompt tuning but using the model’s own lab notes to change the scaffolds, because the article says Mythos sometimes moved faster than the existing harness could support.
  • Dead-end hypotheses were treated as durable results rather than discarded, which let later runs avoid repeated failures and even revive parked findings when the privilege scope changed.
  • Independent verification was central to controlling false positives, with fresh model instances receiving only reproducible artifacts rather than the original reasoning or transcript.
  • The article shows that asking the model to inspect recent security fixes was especially effective, leading it to find incomplete fixes in open source code paths that were similar to already patched ones.
  • The binary-diff workflow produced more than isolated bug reports by combining confirmed findings into a privilege escalation chain analysis and identifying which fix could break the chain.
Key Points
  • 01Netskope used Anthropic’s Claude Mythos preview to run self-verifying vulnerability research against software that Netskope builds and ships.
  • 02Across three tracks, the model produced 9 kernel memory corruption findings behind a strict reachability bar, 17 previously unreported bugs in open source code used by Netskope products, and four confirmed n-day fixes reconstructed from a binary diff.
  • 03For kernel driver testing, a finding only counted when the model satisfied every runtime precondition between the entry point and unsafe sink and reproduced the crash three times from a clean snapshot.
  • 04For open source testing, findings had to be confirmed by a separate copy of Mythos in a clean sandbox against current upstream code using AddressSanitizer crashes.
  • 05For binary-diff testing, a patch-diff finding counted only if the same reproducer crashed the older build and ran cleanly on the latest build.
