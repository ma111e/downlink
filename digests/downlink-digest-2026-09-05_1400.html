In plain words

Attackers broke into JetBrains’ Cadence cloud service by using a serious flaw in a JetBrains TeamCity server that had not been fixed. People who used Cadence may be affected because the attackers could have seen names, email addresses, project code, stored passwords or keys, and files in JetBrains cloud storage. JetBrains is telling affected users to change any passwords and secret keys connected to Cadence and to treat past Cadence work as possibly unsafe. This matters because exposed names, emails, code, and cloud keys can lead to targeted scams, impersonation, and unauthorized access to other connected services.

Summary
JetBrains says attackers exploited an unpatched critical TeamCity flaw to breach its Cadence service and access a 2024 server backup containing credentials, source code-related data, logs, and AWS secrets. Cadence users should rotate all credentials and treat prior executions, inputs, outputs, and synced project data as potentially compromised.

JetBrains is urging Cadence users to revoke and rotate all credentials after unidentified threat actors exploited a critical TeamCity vulnerability to breach affected Cadence environments. Cadence is a JetBrains-hosted cloud computing service that integrates with PyCharm through an optional plugin for running machine learning and heavy workloads on cloud GPUs. JetBrains said users should treat all executions, including their inputs and outputs, as potentially untrusted.

The attack involved CVE-2026-63077, a deserialization of untrusted data vulnerability in TeamCity with a CVSS score of 9.8. The flaw can allow an unauthenticated attacker with access to a TeamCity server to bypass authentication checks and run operating system commands with the privileges of the TeamCity server process. CISA added the vulnerability to its Known Exploited Vulnerabilities catalog on August 5, 2026, and JetBrains discovered the exploitation on August 23, 2026.

JetBrains said the threat actor accessed data in a 2024 Cadence server backup and may have reached storage containing current Cadence users’ email addresses, project source code, and credentials. Confirmed accessed or compromised information included personal data, the full 2024 backup, multiple AWS IAM users and associated credentials or secrets, and files in S3 buckets within JetBrains AWS accounts used by Cadence. The intrusion took place between August 8 and 24, 2026, the exploited api.cadence.jetbrains.com server has been taken offline, and JetBrains has invalidated access tokens used by the Cadence plugin in PyCharm.

  • JetBrains explicitly acknowledged that the Cadence server should have been patched as part of its own vulnerability response efforts, making patch process failure a central factor in the incident.
  • The exposed 2024 backup remained sensitive because it contained credentials, configuration, artifacts, logs, and other data that could still affect current users and JetBrains AWS resources.
  • JetBrains warned that source code exposure could include files users uploaded or synchronized from PyCharm to Cadence, so affected users need to review not only stored secrets but also project files and configurations.
  • The remediation scope extends beyond Cadence itself because users are being told to check AWS accounts, S3 buckets, deployment environments, package and container registries, and source code repositories for suspicious activity.
  • JetBrains invalidated all access tokens used by the Cadence plugin in PyCharm, indicating that plugin-based access to Cadence was treated as part of the exposure path.
Key Points
  • 01JetBrains said unidentified threat actors exploited CVE-2026-63077 in TeamCity to breach affected Cadence environments.
  • 02The attackers accessed data contained in a 2024 Cadence server backup and may have reached storage containing current Cadence users’ email addresses, project source code, and credentials.
  • 03JetBrains confirmed that exposed or compromised data included personal data, a full 2024 Cadence server backup, multiple AWS IAM users and associated credentials or secrets, and files stored in S3 buckets within JetBrains AWS accounts used by Cadence.
  • 04The intrusion took place between August 8 and August 24, 2026, and the exploited Cadence server api.cadence.jetbrains.com has since been taken offline.
  • 05JetBrains urged Cadence users to revoke or rotate all credentials and secrets that may have been used to run Cadence executions and to treat all executions, inputs, and outputs as potentially untrusted.

Over 5,400 hacked sites serve ClickFix payloads stored on the blockchain

In plain words

Researchers found that more than 5,400 hacked small-business websites, mostly built with WordPress and PrestaShop, were being used to trick visitors with fake CAPTCHA pages. The pages tell people to paste a command into Windows, which can download and run harmful code on their computers. This matters because the attackers hide and update that code using blockchain-based storage that is difficult to take down, and hundreds of infected websites are being used each day.

Summary
Researchers found over 5,400 compromised mostly WordPress and PrestaShop sites serving ClickFix lures that pull payloads from BNB Smart Chain smart contracts, making the infrastructure harder to take down and easy for attackers to update. The campaign has evolved to use a WebRTC stager that opens a covert encrypted channel to receive and execute code in the browser.

A cybercriminal operation is using thousands of compromised small-business websites to deliver ClickFix payloads stored in smart contracts on the BNB Smart Chain Testnet. Researchers identified more than 5,400 hacked sites, mostly built on WordPress and PrestaShop, that were injected with a script pulling the next-stage payload from a blockchain smart contract. Netskope said the initial compromise method remains unknown.

The injected script shows visitors a fake CAPTCHA and tells them to open the Windows Run dialog and paste a PowerShell command. If followed, the command downloads and executes the final payload on the machine. Because the payload is stored in a smart contract, the attacker can modify it at any time, and the EtherHiding technique provides infrastructure that is difficult to take down.

Netskope reported that the campaign later replaced the ClickFix payload with a WebRTC data-channel stager. This newer payload creates a covert encrypted channel to the attacker, receives JavaScript code from a hardcoded command-and-control address, buffers it in browser memory, and executes it dynamically without saving it to disk. Netskope warned that the operation uses more than 300 infected websites every day and recommended blocking BSC Testnet RPC endpoints and monitoring for non-web UDP traffic associated with WebRTC.

  • Using the BNB Smart Chain Testnet gives the attackers a free, resilient place to store and update malicious payloads, making takedown harder than if the code were hosted on ordinary attacker-controlled servers.
  • The campaign’s move from a ClickFix payload to a WebRTC data-channel stager shows that changing only the smart contract content can alter the behavior of thousands of already-compromised websites without reinfecting them.
  • Because the newer stager assembles and executes received JavaScript in browser memory without saving it to disk, defenders may need to look beyond file-based detections for signs of this activity.
  • Netskope’s recommended blocking of the entire BSC Testnet RPC endpoint pool and monitoring for non-web UDP traffic linked to WebRTC are concrete detection and prevention steps tied directly to this campaign.
Key Points

  • 02The injected script displays a ClickFix lure with a fake CAPTCHA that instructs visitors to open the Windows Run dialog and paste a PowerShell command, which downloads and executes the final payload.
  • 03Netskope reported that the threat actor later replaced the ClickFix payload in the smart contract with a WebRTC data-channel stager that establishes a covert encrypted channel to the attacker and executes received code.
  • 04The WebRTC stager receives JavaScript code from a hardcoded command-and-control address, buffers it in browser memory, and executes it dynamically without saving it to disk.
  • 05Netskope warned that the operation uses more than 300 infected websites every day, with telemetry showing nearly 400 websites calling the BSC Testnet RPC endpoint daily in August and an all-time peak of 536.

In plain words

Trezor said 67,000 U.S. customers had personal and order information exposed after a break-in at its shipping provider, ShipMonk, even though Trezor says ShipMonk had assured it the data was deleted. The exposed details include names, email addresses, phone numbers, shipping addresses, and order numbers from purchases between November 2019 and August 2021, but Trezor says its hardware wallets were not affected. This matters because criminals could use the leaked information to send convincing scam emails or letters, make fake calls, impersonate Trezor, or create physical safety risks for affected people.

Summary
Trezor says a ShipMonk breach exposed personal and order data for another 67,000 U.S. customers, despite prior assurances that the data had been deleted. The hardware wallets themselves were not affected, but customers should watch for phishing, scam calls, and other social engineering attempts.

Trezor disclosed that another 67,000 U.S. customers were impacted by a breach at its shipping provider ShipMonk. The exposed information includes customer names, email addresses, phone numbers, shipping addresses, and order numbers from between November 2019 and August 2021. Trezor said the incident does not affect the security of its hardware wallets.

The exposure is in addition to 13,689 customers Trezor disclosed last month as having had data either fully or partially exposed. Trezor said it had repeatedly requested and received written assurance from ShipMonk that the data had been deleted in line with its contract, data policy, and past communications. The company said it deletes or anonymizes customer purchase data after 90 days because that window covers delivery, returns, refunds, and replacements.

ShipMonk informed Trezor of the breach on August 10, 2026, following unauthorized access to its systems, but has not publicly acknowledged the incident. The break-in involved zero-day exploitation of CVE-2026-72898, a critical SQL injection flaw in Metabase, and Holborn said ShinyHunters is said to be behind the breach. Trezor warned affected customers that the leaked information could be used for scam emails, fraudulent calls or letters, company impersonation, and potentially physical security risks.

  • Written assurances from a third-party provider did not prevent customer data from remaining in ShipMonk’s systems, showing that contractual deletion commitments can fail in practice.
  • The newly disclosed exposure involved older order data that should have fallen outside Trezor’s stated 90-day retention window, making the incident larger than the breach Trezor initially described last month.
  • The breach created risks beyond online scams because exposed shipping addresses and phone numbers could also expose affected customers to physical security risks.
  • The incident shows how a flaw in a business tool used by a service provider, Metabase, can expose sensitive customer data belonging to that provider’s clients.

In plain words

Broadcom released fixes for two serious problems in VMware Workstation and VMware Fusion, programs used to run virtual computers inside a regular computer. A person who already has administrator control inside one of those virtual computers could use these problems to run code on the main computer that hosts it. People using VMware Workstation or Fusion versions 25H2 or 26H1 are affected, and Broadcom says the issues are fixed in version 26H1u1 with no workaround available. This matters because VMware products are often targeted, and the article notes recent real-world attacks against other VMware flaws soon after they became public.

Summary
Broadcom patched two VMware Workstation and Fusion flaws, including a critical VMXNET3 integer-overflow bug that lets an attacker with admin rights inside a VM execute code on the host. Users should upgrade to VMware Workstation 26H1u1 or VMware Fusion 26H1u1 because no workarounds are available.

Broadcom has released security updates for two flaws affecting VMware Workstation and VMware Fusion. One of them, CVE-2026-59346, is a critical integer-overflow vulnerability with a CVSS score of 9.3. Broadcom said a malicious actor with local administrative privileges on a virtual machine using a VMXNET3 virtual network adapter may exploit the issue to execute code on the host.

The second flaw, CVE-2026-59347, is a stack-based buffer-overflow vulnerability in HGFS with a CVSS score of 8.1. It can be exploited by an actor with local administrative privileges on a virtual machine to execute code as the virtual machine’s VMX process running on the host. In both cases, exploitation requires the attacker to already have local administrative privileges, which the article notes could be obtained through a separate compromise such as phishing or weak user configurations.

The vulnerabilities affect VMware Workstation and VMware Fusion versions 25H2 and 26H1. Broadcom said there are no workarounds and that the flaws have been patched in VMware Workstation 26H1u1 and VMware Fusion 26H1u1. The article says there is no evidence these flaws have been exploited in the wild, but notes that VMware products have been a frequent target and that two VMware vCenter flaws were actively exploited as recently as last month.

  • Both flaws require local administrative privileges inside the virtual machine, so the practical risk depends heavily on whether an attacker can first gain or abuse privileged access through another compromise such as phishing or weak user configurations.
  • There are no Broadcom-provided workarounds for either vulnerability, making an upgrade to VMware Workstation 26H1u1 or VMware Fusion 26H1u1 the only stated mitigation path.
  • The critical flaw is tied specifically to virtual machines using the VMXNET3 virtual network adapter, which gives affected users a concrete configuration detail to check when assessing exposure.
  • The article highlights that recent VMware vCenter flaws were exploited only five calendar days after public disclosure, underscoring the urgency of patching even though these Workstation and Fusion flaws have not been observed in the wild.
