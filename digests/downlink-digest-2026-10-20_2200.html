In plain words

Eight eMudhra digital certificates had their secret keys compromised, which could let attackers create convincing fake website identities and secretly intercept or alter online traffic. Cloudflare says it updated its apps and services to reduce the risk, but some customers may still need to update software or trust settings on systems they manage. This matters broadly because many browsers, operating systems, and online services trusted these certificates, so the problem can affect many kinds of internet connections.

Summary
Eight compromised eMudhra intermediate certificate keys could enable forged certificates and TLS traffic interception for any domain, prompting Cloudflare to deploy mitigations and release updates for WARP/Cloudflare One and cloudflared. Customers should update affected software and trust stores, rebuild and restart applications as needed, and never disable certificate verification to bypass resulting errors.

Cloudflare learned at approximately 17:00 UTC on October 19, 2026, that private keys associated with eight eMudhra intermediate certificates were compromised. The certificates were widely trusted by browsers, operating systems, and Cloudflare. Because the compromised keys can create forged certificates for any domain, an attacker could impersonate servers and intercept or modify traffic.

Cloudflare said it prioritized protecting critical services before public disclosure and found no active exploitation on its services during its review. It released updates for Cloudflare One Clients, including WARP and the 1.1.1.1 app, and Cloudflare Tunnel, also known as cloudflared, while deploying mitigations across CDN, Developer, and Zero Trust products. Customers using Cloudflare Zero Trust Gateway with an up-to-date client are automatically protected, but some customers may need to update software or trust configurations on systems they operate.

The company advised developers to update relevant dependencies, rebuild affected images, and reload, restart, or redeploy applications as required. It cautioned that updating an SDK alone may not change certificate-verification behavior because verification can occur in an HTTP library, language runtime, operating system, or custom trust configuration. Cloudflare also warned not to disable certificate verification when errors appear, because that would remove the authentication protection the updates are meant to restore.

  • Updating an SDK alone may not protect an application, because certificate checks can instead be performed by its HTTP library, programming-language runtime, operating system, or a custom trust configuration.
  • A successful browser or curl check does not demonstrate that every application on a device is protected, because each application may use a different certificate-verification path.
  • Browser maintainers could respond quickly using rapid certificate-revocation mechanisms such as Chrome CRLSets, while many other systems require software, image, trust-store, and service updates.
  • Certificate errors following remediation should not be resolved by disabling certificate verification, because doing so removes the authentication protection the updates are intended to restore.

JUSTIFICATION

This is a high-impact certificate-trust incident involving compromised private keys for eight eMudhra intermediate certificates, which could enable forged certificates for any domain and interception or modification of traffic. It has broad relevance because the certificates were trusted by browsers, operating systems, and many software stacks, and remediation may require updates to clients, dependencies, trust stores, and applications.
