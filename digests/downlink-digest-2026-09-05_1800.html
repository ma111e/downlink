Unpatched Magento and Adobe Commerce Zero-Day Exploited to Backdoor Online Stores

In plain words

Attackers are breaking into online stores that use Magento Open Source and possibly Adobe Commerce by using a newly found weakness that Adobe has not yet fixed. The break-in can let them run their own program on the store’s server and keep access there, even without logging in. This matters because these stores handle shopping sessions, payment-related systems, admin accounts, and other sensitive credentials, and the article says real stores have already been compromised while no official patch is available.

Summary
Attackers are actively exploiting an unpatched zero-day in Magento Open Source and Adobe Commerce, dubbed StyleSmuggler, to gain unauthenticated code execution and install persistent backdoors on online stores. With no official Adobe patch or CVE yet, admins should urgently look for the published indicators and consider temporary mitigations such as disabling GraphQL and hardening PHP execution.

Attackers are actively exploiting a new unpatched vulnerability in Magento Open Source and Adobe Commerce that Sansec named StyleSmuggler. Sansec said the flaw allows malicious code to run on an online store’s server without logging in, and attacks began on September 4. As of September 6, Adobe had not published an advisory, CVE identifier, patch, or workaround.

Sansec said all current versions are affected, including 2.4.9, and reproduced the unauthenticated chain on clean Magento Open Source 2.4.7, 2.4.8, and 2.4.9 installations. Disrex Group separately handled two compromised Magento Open Source stores and said patch status was irrelevant for those incidents because the stores were breached before defenses for the flaw existed. The researchers’ interim advice includes temporarily disabling GraphQL for stores that can do so until Adobe releases a fix.

The attack first plants PHP code in a Magento-written file and then makes Magento execute it by triggering a standard “Payment Transaction Failed Reminder” email. The backdoor has been seen as a non-root process named [kworker/u:8:0], with a binary under ~/.local/share/.gvfsd/gvfsd-user and cron entries that restart it every five minutes. Disrex said defenders should search both var/report/ and var/log/system.log, preserve evidence before cleanup, remove the cron entry before killing the process, flush session storage, and rotate sensitive credentials.

  • Patch status alone did not protect the compromised stores, because one victim was running Magento Open Source 2.4.8 and another earlier victim had Adobe’s July and August 2026 security updates applied.
  • Sansec’s published check of var/report/ could miss infections, because Disrex found both of its cases were poisoned through var/log/system.log instead.
  • Scanning only the store document root can miss the implant, because Disrex said eComscan reported Store A clean while the backdoor was installed one directory above the document root under the account’s home directory.
  • Removing the cron entry after killing the process may fail, because Disrex said the implant re-added the cron entry within a second of removal and recommends removing the cron entry before killing the process.
  • Blocking only the attacker address in Sansec’s advisory would have stopped less than a quarter of the traffic Disrex observed, because Disrex recorded 26 distinct source addresses across the two stores.
