In plain words

Drupal fixed a serious flaw called Fail2Install that could let anyone take control of a running website without needing an account, if they can briefly disrupt its connection to its data store. Attackers have already used it against real sites, and thousands of internet-facing Drupal sites may be on affected versions, including older versions that will not receive a fix. A successful takeover can give an attacker their own administrator account and potentially let them run commands on the website’s server, putting the site’s data, passwords, and visitors at risk. Site owners need to update to a fixed Drupal release, block the installation page, and check for signs that their site was altered.

Summary
Drupal’s actively exploited Fail2Install flaw (CVE-2026-132165) lets unauthenticated attackers reopen the installer on vulnerable live sites by inducing database connection failures, potentially taking over the site and executing code. Upgrade to Drupal 10.6.22, 11.3.22, or 11.4.13 or later immediately, block access to /core/install.php, and investigate affected sites for compromise.

Drupal released versions 10.6.22, 11.3.22, and 11.4.13 on November 18, 2026, to fix CVE-2026-132165, a highly critical flaw in its core installer known as Fail2Install. The flaw is actively exploited, with live-site exploitation reported as early as November 19 and CISA adding it to its Known Exploited Vulnerabilities catalog on November 24. An unauthenticated attacker can potentially reopen the installer on an already running site, take over administration, and run code on the server.

The bug occurs because affected installer checks can interpret a temporary database connection error as evidence that Drupal is not installed, while a later successful connection in the same request allows installation to continue. Public research demonstrated causing these temporary failures by exhausting database connections or the server’s available outgoing network ports. Drupal’s patch makes database-verification errors stop the installer, but the article says site owners should also block /core/install.php, prevent the web server from writing to settings.php and code directories, and investigate affected sites for connection-refusal bursts, installer requests, altered settings, or suspicious files.

  • The flaw relies on a timing race in which the database rejects the installer’s early connection attempts but accepts a later one during the same request, causing a live site to appear uninstalled.
  • The fixed Drupal releases close the installer re-entry issue but do not change the Apache rule that can execute a planted PHP file through a URL ending in /core/x.php, so preventing the web server from writing to code directories remains a separate safeguard.
  • Public Drupal version banners generally expose only the major release, such as “Drupal 11,” so external scans cannot distinguish a patched 11.4.13 site from a vulnerable 11.4.12 site.
  • The required database connection exhaustion produces conspicuous evidence, including database refusal errors and large spikes in HTTP 500 responses, making correlated installer requests and database errors a strong detection signal.
  • Blocking only the exact nginx path /core/install.php is insufficient on some configurations because requests such as /core/install.php/foo may still invoke the installer.
Key Points
  • 01Drupal’s actively exploited Fail2Install flaw, tracked as CVE-2026-132165, can allow an unauthenticated attacker to reopen the installer on a live site by causing temporary database connection failures.
  • 02Affected Drupal versions include releases before 10.6.22, 11.0.0 through 11.3.21, and 11.4.0 through 11.4.12; Drupal 8.9 and 9 are also reported as affected but are end of life.
  • 03Drupal fixed the issue in versions 10.6.22, 11.3.22, and 11.4.13 by making database-verification errors stop the installer instead of treating them as an uninstalled site.
  • 04CISA added CVE-2026-132165 to its Known Exploited Vulnerabilities catalog on November 24, 2026, after exploitation on live sites was reported as early as November 19.
  • 05Drupal recommends upgrading core and blocking access to /core/install.php on installed sites, while the article also advises checking affected sites for database connection refusal bursts, installer requests, changed settings, and suspicious PHP files containing SQLite databases.
