ASM Has a Silent C, and It Stands for Change Management

In plain words

The article says companies are changing their technology so quickly that security teams can lose track of what is newly exposed or no longer protected, especially as more employees use AI to set up tools and services. The people affected are security teams and large organizations with many internet-facing systems, because a new mistake can be found and used by attackers before anyone inside notices. The broader risk is that closed support tickets or long asset lists can create false confidence unless companies repeatedly check what changed, which changes matter, and whether fixes actually worked.

Summary
The article argues that attack surface management should be treated as continuous change management, not just vulnerability tracking, because AI-driven self-service infrastructure is making assets and misconfigurations appear faster. Effective ASM needs frequent discovery, business context, change-aware prioritization, deeper validation, and proof that fixes actually worked.

The article argues that attack surface management should be understood as a change management function, not only as a way to support vulnerability management. It says security teams must respond to both external changes, such as new CVEs or public proof of concepts, and internal changes, such as new MCP servers, public API updates, or storage bucket policy changes. The author says this shift matters because AI-assisted self-service infrastructure is allowing more people across organizations to deploy technology, creating more frequent opportunities for risky misconfigurations.

The article highlights a less-discussed exploit window: the time between a misconfiguration going live and an attacker finding it. It says this window is shrinking while gaps are opening more often, because the number of people able to deploy to production has increased. To keep up, the author says ASM programs need structural discovery that treats the attack surface as a graph of related assets and dependencies, along with rapid run frequency that can reveal changes close to when they occur.

The author also says ASM platforms need business and technology context to separate meaningful security changes from routine infrastructure churn, such as dynamic IP changes caused by CDNs, load balancers, and cloud providers. The article argues that prioritization should be recalculated whenever the environment changes and should direct deeper testing toward the assets that matter most. It concludes that remediation must include confirming whether fixes actually worked, because roughly 25% of issues marked resolved still leave the underlying risk open.

  • Security teams should challenge the word “continuous” in ASM tools because the article says some platforms use it for partial, periodic runs spaced weeks or more apart.
  • Daily discovery without context can make teams “drown faster,” because frequent scanning increases alert volume unless the platform can distinguish meaningful security changes from routine infrastructure churn.
  • Dynamic IP changes from CDNs, load balancers, and IaaS/PaaS providers can make the same applications look like new alerts unless the ASM platform recognizes that the underlying asset has not meaningfully changed.
  • A theoretical vulnerability can drop in priority when tested against the real environment, such as when a WAF blocks an SQL injection attempt against an application that appears vulnerable by version.
  • Remediation tracking should not stop when a ticket is closed because the article says about 25% of issues marked resolved still leave the underlying risk open.
Key Points
  • 01The article argues that attack surface management should be viewed as a change management function rather than only as support for vulnerability management.
  • 02The author says the time between a misconfiguration going live and an attacker finding it is shrinking, while such gaps are appearing more often because more people can deploy to production with AI-assisted self-service infrastructure.
  • 03The article states that an attack surface should be treated as a graph of related assets and dependencies, not simply as a list of assets.
  • 04The author says daily discovery has become a baseline expectation, citing a 2025 SANS survey in which 59% of respondents preferred daily scan frequency.
  • 05The article says remediation should include re-validating fixes because roughly 25% of issues marked resolved still leave the underlying risk open.
