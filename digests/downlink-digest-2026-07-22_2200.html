wp2shell hits WordPress: detecting pre-auth RCE from plugin drop to command execution
elastic.co · 23 Jul 2026 00:00 UTC openai-codex / gpt-5.5
TAGScve-2026-60137cve-2026-63030elastic-defendicex0-wp2shell-pocpre-authentication-rcesans-iscsearchlight-cybersql-injectionweb-shellwordpress-corewordpress-rest-apiwp2shell

In plain words

Researchers disclosed wp2shell, a flaw in WordPress that can let outsiders take control of some websites before logging in, and public test tools appeared within hours. The article says WordPress versions 6.9.0 to 6.9.4 and 7.0.0 to 7.0.1 are exposed to the full takeover chain, so internet-facing sites on those versions should be treated as possibly compromised until updated. This matters because attackers are already scanning for it, and successful use can leave behind hidden website code and allow commands to run on the server.

Summary
WordPress wp2shell is a pre-authentication RCE chain affecting WordPress 6.9.0–6.9.4 and 7.0.0–7.0.1, with public PoCs already leading to scans and exploitation. Patch to 6.9.5 or 7.0.2 immediately and hunt for web-server-spawned shells, suspicious plugin PHP files under wp-content, and batch REST API access-log indicators.

Searchlight Cyber disclosed wp2shell on July 17, 2026, describing it as a pre-authentication remote code execution chain in WordPress Core tracked as CVE-2026-63030 and CVE-2026-60137. Public proof-of-concept tools appeared on GitHub within hours, and scanning followed immediately. The article says Elastic has observed the same host footprint in customer telemetry, including PHP and web server runtimes spawning shells, new plugin directories under wp-content/plugins/, and access-log markers from stock tooling.

The affected WordPress versions for the full pre-authentication RCE chain are 6.9.0 to 6.9.4 and 7.0.0 to 7.0.1, with fixes in 6.9.5 and 7.0.2. The article explains that wp2shell abuses WordPress Core’s REST batch endpoint through route confusion, with public chains nesting batches to bypass method restrictions and reach a pre-authentication SQL injection primitive. Tooling can then escalate to administrator access and upload a plugin-backed webshell, or in other observed activity write a webshell directly to disk through SQL INTO OUTFILE.

Elastic ran the public Icex0 PoC in a lab and mapped the resulting activity to Elastic Defend and SIEM detections. The lab showed apache2 staging plugin files, creating wp2shell plugin directories, spawning dash from the plugin working directory, and running commands such as id, whoami, hostname, cleanup commands, uname, cat /etc/passwd, and SUID file enumeration. The article recommends patching first, hunting fresh indicators such as batch endpoint requests and wp2shell paths, and relying on behavioral detection because attackers can rename plugins, rewrite payloads, or place webshells outside the plugin directory.

  • A missing wp2shell_<hex> plugin directory does not prove a host is clean, because the Icex0 PoC removes its own plugin directory and staged zip after execution.
  • The most durable detection opportunity is not the wp2shell plugin name or User-Agent, but the web server process crossing into command execution by spawning a shell such as dash, bash, or sh.
  • The PHP plugin-directory file creation rule can catch the plugin-upload chain early, but it will not catch variants that write webshells elsewhere, such as under wp-content/cache/.
  • Repeated PoC shell invocations can create multiple different wp2shell_<hex> plugin directories on the same host because each invocation generates a fresh random plugin name.
  • If immediate patching is not possible, the article recommends temporarily blocking anonymous access to /wp-json/batch/v1 and /?rest_route=/batch/v1, while warning this may break legitimate batch consumers.
Key Points
  • 01Searchlight Cyber disclosed wp2shell on July 17, 2026 as a pre-authentication remote code execution chain in WordPress Core tracked as CVE-2026-63030 and CVE-2026-60137.
  • 02The article states that WordPress versions 6.9.0 to 6.9.4 and 7.0.0 to 7.0.1 are exposed to the full pre-authentication RCE chain, while fixed versions are 6.9.5 and 7.0.2.
  • 03Elastic observed public proof-of-concept activity producing consistent host behavior, including web server or PHP runtimes spawning shells, new plugin directories under wp-content/plugins/, and access-log markers such as POST requests to the batch REST endpoint.
  • 04In Elastic’s lab run of the Icex0 PoC, the exploit staged plugin files under wp-content, executed commands through apache2 spawning dash, and triggered alerts for PHP file creation, payload execution by a web server, and suspicious or unusual command execution.
  • 05The article recommends patching first, hunting fresh indicators such as wp2shell_<hex> plugin directories and batch endpoint requests, and relying on behavioral detections because attackers can rename plugins or change payload locations.

Find Unused, Stale, and OIDC-Replaceable GitHub Actions Secrets Across Your GitHub Organization
stepsecurity.io · 22 Jul 2026 22:45 UTC openai-codex / gpt-5.5
TAGSactions-secretawsazureghostactiongithub-actionsgoogle-cloudharden-runnermegalodonnpmopenid-connectpypisecret-exfiltrationshai-huludstepsecurity
55
In plain words

The article announces new StepSecurity dashboard features that help organizations using GitHub find stored GitHub Actions secrets, see which workflow files use them, and identify ones that are unused, old, or can be replaced with short-lived sign-in methods instead of permanent keys. This matters because recent attacks like GhostAction and Megalodon stole thousands of these stored secrets from many repositories, and attackers can use long-lived stolen tokens to publish malicious software or access services. Teams affected are organizations with many GitHub repositories and workflows, especially those that have accumulated old credentials faster than they clean them up.

Summary
StepSecurity added organization-wide GitHub Actions secret usage tracking to show which repository secrets are unused, stale, or replaceable with OIDC. The key takeaway is that teams can now identify and remove or migrate long-lived secrets before attackers steal them from workflows.

StepSecurity announced new capabilities in the Actions Secret section for finding unused, stale, and OIDC-replaceable GitHub Actions secrets across a GitHub organization. The Repository Secrets tab now adds usage tracking, secret status, and OIDC replaceability to the existing organization-wide inventory and rotation tracking. The dashboard includes summary cards for total secrets, unused secrets, stale secrets, and secrets that can be replaced with OIDC.

The article says this matters because campaigns such as GhostAction and Megalodon stole GitHub Actions secrets from large numbers of repositories, and organizations often accumulate long-lived credentials faster than they remove them. Each secret now has a Usage Status of Active, Stale, Unused, or Unknown, and referenced secrets show the repository, workflow file, consuming action, last run conclusion, and a GitHub run link. The analysis detects direct references, bracket and dynamic lookups, bulk access through toJSON(secrets), and secrets consumed through reusable workflows called with secrets: inherit.

The OIDC column flags secrets that could be eliminated by switching to short-lived authentication for each workflow run instead of storing a static secret. Detection covers actions that support OIDC federation, including aws-actions/configure-aws-credentials, google-github-actions/auth, and azure/login, as well as registry publishing tokens for npm and PyPI. StepSecurity says the feature helps teams build deletion lists for unused secrets, identify stale credentials tied to workflows that have not run in over 90 days, and plan OIDC migrations.

  • The article highlights that deleting unused GitHub Actions secrets can directly reduce incident response burden, because every unused credential removed is one less secret that must be rotated after a theft campaign.
  • A secret marked unused should not be deleted blindly, because StepSecurity's unused status reflects analyzed GitHub Actions workflows only and the secret might still be consumed by an external system through the API.
  • Stale secrets are especially actionable because they point to credentials tied to workflows that have not run in over 90 days, making them likely leftovers from retired pipelines that can be deleted or rotated.
  • OIDC migration is presented as a way to remove durable publishing and cloud credentials entirely, so an attacker stealing workflow data would not obtain a long-lived token like those abused in npm-focused supply chain attacks.
  • Usage context changes secret inventory from a static list into an incident response tool, because teams can identify exactly which workflows use an affected credential type and rotate or delete secrets with confidence.
Key Points
  • 01StepSecurity's Actions Secret Repository Secrets tab now adds usage tracking, secret status, and OIDC replaceability to its organization-wide inventory of GitHub Actions secrets.
  • 02The dashboard shows summary cards for total repository secrets, unused secrets, stale secrets whose referencing workflows have not run in over 90 days, and secrets that can be replaced with OIDC authentication.
  • 03Each secret is assigned a Usage Status of Active, Stale, Unused, or Unknown, and referenced secrets show the repository and workflow file, consuming action, last run conclusion, and a link to the GitHub run.
  • 04The analysis detects direct secret references, bracket and dynamic lookups, bulk access through toJSON(secrets), and secrets consumed inside reusable workflows called with secrets: inherit.
  • 05The OIDC column flags secrets that can be replaced with OIDC for supported actions such as aws-actions/configure-aws-credentials, google-github-actions/auth, azure/login, and registry publishing tokens for npm and PyPI.
