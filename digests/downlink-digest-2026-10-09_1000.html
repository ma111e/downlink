In plain words

Attackers are trying to abuse a recently fixed weakness in SonicWall SMA1000 devices, which organizations use to let employees and partners securely reach internal company systems from elsewhere. The issue affects SMA1000 6210, 7210, and 8200v models, and could let an outsider make the device access internal functions and take actions without permission. This matters because these devices are used by service providers, large companies, and government agencies, and similar SonicWall weaknesses have previously been used to install harmful software and in ransomware incidents.

Summary
Attackers are attempting to exploit the newly patched maximum-severity CVE-2026-102255 SSRF flaw in SonicWall SMA1000 appliances, potentially reaching internal services and performing unauthorized actions. Organizations using affected SMA1000 6210, 7210, and 8200v devices should apply SonicWall’s patch immediately.

Attackers are attempting to exploit CVE-2026-102255, a maximum-severity vulnerability in SonicWall SMA1000 appliances that SonicWall patched three days before the report. The flaw affects the Appliance WorkPlace interface on SMA1000 6210, 7210, and 8200v models, but not SonicWall SMA 100 Series devices or SSL-VPN services on SonicWall firewalls. SonicWall said an unauthenticated remote attacker could cause the appliance to make requests on their behalf, reach internal functions, and perform unauthorized operations.

Previdian’s honeypot network observed requests against the WorkPlace Extraweb interface that used a crafted OPTIONS request to target the appliance’s internal CouchDB service at 127.0.0.1:5984. The requests attempted to access a CouchDB design document’s _rewrite function and included an HTTP Basic Authorization header with admin:admin credentials, although Previdian has not confirmed that any systems were successfully compromised. Shadowserver tracks more than 400 SMA1000 appliances exposed online, while the number that are patched or honeypots is unknown. SMA1000 gateways are widely used by managed service providers, large companies, and government agencies, and prior SMA1000 zero-day attacks were linked by CISA to ransomware gangs.

  • Although the observed activity is consistent with exploitation attempts, Previdian said it has not confirmed that any attempt successfully compromised a system.
  • The new flaw targets the same WorkPlace interface involved in earlier SSRF issues, but uses a different technique: a crafted OPTIONS request intended to reach the appliance’s internal CouchDB service.
  • The attempted request included the default-looking admin:admin credentials and sought to invoke a CouchDB rewrite function, indicating that the activity targeted internal application behavior rather than the public-facing interface alone.
  • More than 400 SMA1000 devices are visible online, while it remains unknown how many have been patched, which makes the potential exposed population difficult to determine.
  • SMA1000 appliances have a recent history of zero-day abuse, including attacks linked by CISA to ransomware gangs, raising the operational significance of new exploitation attempts against the platform.

The affected products are ProFTPD, ONLYOFFICE Docs, Strapi, Apache Struts, and ISC BIND. The flaws include issues that can enable arbitrary file access, remote code execution, disclosure of sensitive user details, command execution, or denial of service.

  • CISA's deadline gives U.S. federal agencies a specific required action: apply patches or discontinue use of affected products by October 11, 2026.

In plain words

Attackers appear to have taken over two GitHub accounts and added a fake “security audit” file to 346 software projects, including an Uber project and the popular Pyxel project. When the file runs, it sends saved passwords and access keys, plus keys accidentally left in project files or old project versions, to an attacker-controlled internet address. This affects not only the compromised account owners but also organizations and users of projects they could edit, because stolen publishing keys could be used to distribute harmful software updates or access cloud services and private data.

Summary
A new GhostAction campaign used compromised GitHub maintainer accounts to inject malicious GitHub Actions workflows into 346 repositories, stealing configured CI/CD secrets and scanning current files plus full Git history for cloud and AI credentials. Organizations should remove the workflow, rotate exposed credentials, investigate workflow runs and egress to the hardcoded collector IP, and secure affected maintainer accounts.

Socket reported that on October 8, 2026, compromised GitHub accounts henrywoo and kitao added a malicious workflow named .github/workflows/security-audit.yml to 346 repositories. The file, presented as a security audit, had no security function and sent collected data to the hardcoded address 193.32.204[.]199. Affected repositories included Uber-owned uber/athenadriver and the popular kitao/pyxel. Socket said the workflow remained on default branches it checked as of October 9 and had run successfully in affected repositories.

This GhostAction variant retains the campaign’s earlier ability to collect GitHub Actions secrets named in repository workflows, including package-publishing credentials. It also performs a new search of checked-out files and reachable Git history for 13 patterns covering AWS, AI-service, source-control, SaaS, and cloud API credentials. The workflow uses a full Git checkout and captures lines surrounding AWS key identifiers, which can include nearby secret access keys needed to form usable credential pairs. Socket reported no malicious package versions on PyPI or crates.io at the time of writing, but recommended removing the workflow, rotating exposed credentials, reviewing workflow and audit logs, and securing affected maintainer accounts.

  • The malicious workflow was customized with the exact GitHub Actions secret names used by each repository, indicating that the operators first examined existing workflow files before committing the payload.
  • Fetching complete Git history lets the workflow search credentials that were removed from the current version of a project but remain reachable through old branches or tags.
  • The payload captures lines surrounding AWS key identifiers because the identifier alone cannot authenticate, while a nearby secret key may form a usable credential pair.
  • The 279 affected forks in the henrywoo namespace can exfiltrate credentials from a fork owner’s own repository history if Actions are enabled and a push occurs.
  • Every execution reports its repository identifier even when no credentials are found, giving the operator a record of reachable execution environments.
Key Points

  • 02The workflow runs on pushes and can collect GitHub Actions secrets named in existing workflows before sending them to the hardcoded IP address 193.32.204[.]199.
  • 03This GhostAction variant also searches checked-out files and complete reachable Git history for AWS, AI-service, source-control, SaaS, and cloud API credentials.
  • 04The workflow uses a full Git checkout and context around AWS key identifiers to capture nearby information that may include corresponding secret access keys.
  • 05Socket reported that the malicious workflow remained on the default branches it checked as of October 9, 2026, and it had not observed malicious package releases to PyPI or crates.io at that time.

A European aerospace and industrial engineering firm received three French device-renewal phishing emails on 15 May 2026 that impersonated Crédit Agricole. The messages claimed that recipients needed to renew a trusted device by 16 May under a purported PSD2-related security requirement and linked to portail-client-mail[.]net, which was not a Crédit Agricole domain. IRONSCALES Themis classified the incident as credential theft with 88 confidence, and all three messages were mitigated within seconds.

Two captures of the same destination produced different results: one displayed a Crédit Agricole-branded CAPTCHA security-verification page, while another displayed a French location-blocking notice that showed the visitor’s detected country and IP address. Every recorded link verdict was clean, illustrating that a URL verdict reflected only the page response shown to that request at that time and location. SPF, DKIM, DMARC, and composite authentication also passed because the messages were sent through an abused bulk-mail account at a US technical college, while visually identical subjects used different invisible Unicode characters that could defeat exact-match rules.

  • A clean URL verdict reflected only the response the destination chose to show a particular request at a particular time and network location, rather than proving the destination was safe.
  • The geo-restriction page unusually exposed its own filtering by displaying the detected country and IP address that it had blocked, providing direct evidence that location-based access control was deliberate.
  • The three emails used visually identical subject lines with different invisible trailing Unicode characters, which can defeat exact-match rules by making the strings differ at the byte level.
  • Valid SPF, DKIM, and DMARC results established that the message was genuinely sent through the abused college bulk-mail account, but did not establish that the message itself was legitimate.
  • The article recommends preserving the actual page response and re-inspecting links from different locations and times, rather than relying on a single URL verdict.
