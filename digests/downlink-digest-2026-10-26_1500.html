In plain words

Attackers used a secret key accidentally saved in an AI coding helper’s settings to gain access to LiteLLM’s software-release systems, steal more login credentials, and publish a harmful version of the LiteLLM package. For about two hours, anyone who installed that version could have had passwords, cloud access keys, developer keys, and other sensitive information taken from their computer. The incident matters because automated coding tools can quietly handle powerful credentials, so one exposed key can spread from a developer’s computer to many organizations that trust and use the same software.

Summary
A leaked master key in an OpenCode agent configuration enabled attackers to steal GitHub tokens, abuse CI workflows to harvest more secrets, and publish the credential-stealing LiteLLM 1.107.0 package. The incident shows that coding agents and unmanaged, long-lived credentials create a major supply-chain risk unless identities are scoped, short-lived, monitored, and kept out of local configs and CI secrets.

On October 21, 2026, attackers published a poisoned litellm==1.107.0 release to PyPI, Docker Hub, and GitHub Container Registry after gaining access to LiteLLM’s release pipeline through stolen credentials. The PyPI package was available for about two hours, while Docker images remained available until 14:20 UTC. The malicious code ran whenever Python started, including in processes that did not import LiteLLM, and searched hosts for cloud credentials, SSH keys, tokens, .env files, shell history, browser passwords, and AI-provider keys.

The compromise began when an OpenCode configuration file containing a LiteLLM Agent Platform master key was committed to a public repository on May 27 and the key was not revoked after the commit was removed. On October 10, the attacker used that key to retrieve agent configurations, obtain a LiteLLM organization owner’s GitHub CLI token, and create GitHub Actions workflows that sent repository secrets to an external webhook service. The article argues that the incident illustrates a growing insider-risk problem: coding agents and automation can access long-lived, overly broad credentials that are not properly inventoried, limited, or monitored.

The article recommends keeping long-lived credentials out of coding-agent and MCP configurations, revoking leaked keys before cleaning repository history, and using short-lived, narrowly limited identities for automation. It also recommends avoiding personal GitHub tokens in CI secrets, using GitHub-provided tokens or GitHub App tokens where possible, and protecting sensitive CI environments with branch restrictions and approval rules. Detection signals include credentials used from unfamiliar networks or clients, multiple people’s tokens used from one location, and tokens suddenly performing unusual administrative actions.

  • Deleting a public commit did not eliminate the danger because the exposed master key remained valid, while deleted commits can persist in forks and public archives.
  • The leaked key was not itself a GitHub credential, but it could access agent configurations containing an organization owner’s GitHub token, showing how one broadly powerful key can expose other credentials.
  • The malicious LiteLLM package ran whenever Python started, including in programs that never imported LiteLLM, greatly expanding the number of processes exposed after installation.
  • The article recommends treating unusual credential behavior as an early warning sign, such as a token appearing from a new network or client, several users’ tokens being used from one location, or a credential suddenly performing uncommon administrative actions.
  • The article argues that the practical impact of a poisoned dependency depends not only on the package but also on every credential the affected computer can access.
Key Points
  • 01A master key for LiteLLM’s internal Agent Platform was committed to a public repository in an OpenCode configuration file on May 27 and remained valid for about four and a half months after the commit was removed.
  • 02On October 10, an attacker used the leaked master key to retrieve managed-agent configurations and obtain a GitHub CLI OAuth token belonging to a LiteLLM GitHub organization owner.
  • 03The attacker added GitHub Actions workflows that collected and sent repository secrets, including maintainers’ GitHub CLI tokens and database and Redis credentials, to an external webhook service.
  • 04The poisoned litellm==1.107.0 release was available on PyPI from 11:39 to 13:23 UTC on October 21, 2026, and its Docker images remained available until 14:20 UTC.
  • 05The malicious package executed code whenever Python started and searched affected machines for cloud credentials, SSH keys, tokens, .env files, shell history, browser passwords, and LLM-provider keys before sending them to an attacker-controlled domain.
