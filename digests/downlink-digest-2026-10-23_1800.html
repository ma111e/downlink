New Evidence Shows LiteLLM Secret-Stealing Workflows Ran 11 Days Before Supply Chain Attack
socket.dev · 23 Oct 2026 21:00 UTC openai-codex / gpt-5.6-terra
TAGSaws-bedrockgitguardiangithubgithub-actionslinearlitellmopenaipypitogether-aiwebhook-site
92
In plain words

Attackers secretly added short-lived automated tasks to LiteLLM’s GitHub code repository on October 10 and 12, 2026, then used them to copy passwords, access keys, and login information to an outside website before deleting the temporary branches. The stolen information included credentials for GitHub, databases, AI services, Linear, and other internal systems, affecting LiteLLM and potentially its users and service accounts. This matters because the attackers had access for at least 11 days before a malicious LiteLLM software release was published, showing how a small hidden change in a software project can expose many connected services.

Summary
Socket found that attackers ran malicious GitHub Actions workflows in the LiteLLM repository on October 10 and 12, 2026—up to 11 days before the malicious PyPI release—to exfiltrate organization and environment secrets. LiteLLM later linked the stolen GitHub token from the October 10 workflow to approval of the October 21 malicious release.

Socket reported that malicious GitHub Actions workflows ran in the BerriAI/litellm repository on October 10 and October 12, 2026, before the October 21 release-pipeline compromise that published malicious litellm==1.107.0 artifacts. The workflows were added through short-lived ci-tmp-<hex> branches that were created, used, and deleted within minutes, leaving the files absent from main. Repository Actions performance metrics recorded one successful cache.yml run on each date, placing confirmed malicious workflow activity at least 11 days before the release attack. LiteLLM later said its audit logs linked the GH_TOKEN stolen on October 10 to approval of the October 21 malicious release.

The October 10 workflow collected six organization-level secrets, including GH_TOKEN, a GitHub App private key, and API keys, then encoded them and sent them to a webhook.site endpoint. The expanded October 12 workflow used six jobs, including five bound to named GitHub Environments, to access 14 additional repository, organization, and environment-scoped secrets such as database, Redis, Linear session, and secret-scanning credentials. Both workflows used a trailing || true so their GitHub Actions jobs would report success even if the external transmission failed. Although Socket could reconstruct the activity using logs, metrics, surviving commits, and environment deployment records, it could not confirm whether the collectors received the data, how the initial access was obtained, or whether additional workflow cycles occurred.

  • Deleting the temporary branches did not erase all evidence: GitHub’s activity log, Actions performance metrics, surviving commit objects, and environment deployment records allowed Socket to reconstruct the workflow activity.
  • The October 12 workflow’s use of real environment names indicates that the attacker had enumerated LiteLLM’s environment inventory before creating the workflow, since binding jobs to those environments unlocked their separately scoped secrets.
  • A successful GitHub Actions run does not prove the stolen data reached the attacker, because both workflows used "|| true" to hide errors from the outbound request; however, the article notes that the expanded October 12 collection and lack of repeated targets are consistent with the earlier delivery succeeding.
  • The workflow did not need to modify the main branch to access secrets: a push to a temporary branch in the upstream repository was sufficient to trigger the workflow and make repository and environment secrets available.
  • The activity log identifies the authenticated account used for the branch operations, but it cannot establish whether that account holder acted personally or whether its session, access token, or SSH key had been stolen.
Key Points
  • 01Socket recovered two malicious LiteLLM commits from October 10 and October 12, 2026, that added a GitHub Actions workflow named .github/workflows/cache.yml.
  • 02The workflows ran from temporary ci-tmp branches that were created and deleted the same day, allowing them to execute without remaining in the repository’s main branch history.
  • 03The October 10 workflow targeted six organization-level secrets, including GH_TOKEN and a GitHub App private key, while the October 12 workflow targeted 14 additional repository, organization, and environment-scoped secrets.
  • 04Both workflows encoded collected secrets and sent them to separate webhook.site endpoints, while using error suppression so the GitHub Actions jobs would report success even if transmission failed.
  • 05LiteLLM stated that its audit logs linked the GH_TOKEN stolen by the October 10 workflow to approval of the malicious October 21, 2026 LiteLLM release.

Python packages are also vulnerable to the Node2Shell Brotli flaw (CVE-2026-111497)
aikido.dev · 23 Oct 2026 20:45 UTC openai-codex / gpt-5.6-terra
TAGSaiohttpbrotlibrotlicfficve-2026-111497httpxnodejsout-of-bounds-writepypipythonrequestsscrapyurllib3
89
In plain words

A flaw in widely used Brotli software for Python can be triggered when an app receives specially crafted compressed web data. It affects Python setups with older Brotli or brotlicffi packages, including apps that use common web-request tools such as requests without directly using Brotli themselves. Because the flaw can involve untrusted internet data and may cause unsafe behavior in an app, affected users should update to Brotli 1.2.1 or brotlicffi 1.2.1.0 and rebuild any affected containers.

Summary
Python environments using Brotli 1.2.0 or earlier or brotlicffi 1.2.0.x are vulnerable to CVE-2026-111497, a Brotli decoder memory-safety flaw reachable through compressed HTTP traffic. Upgrade to Brotli 1.2.1 or brotlicffi 1.2.1.0 and rebuild affected environments and container images.

CVE-2026-111497, known as Node2Shell in Node.js and Python2Shell in this article’s Python context, affects the Brotli decoder compiled into the PyPI Brotli and brotlicffi packages. Python environments running Brotli 1.2.0 or earlier or brotlicffi 1.2.0.x are affected, while Brotli 1.2.1 and brotlicffi 1.2.1.0 contain the fix. Applications may be exposed even without directly importing these packages because HTTP clients such as urllib3, requests, httpx, aiohttp, and Scrapy can use them automatically when installed.

An attacker may reach the decoder by providing a malicious Brotli-compressed response to an outbound request or by sending a Brotli-compressed request body to an application. The issue arises during Brotli block switching, where vulnerable code can mishandle a malformed stream and continue decoding with an invalid state, leading to an out-of-bounds write. The upstream fix changes the decoder to return explicit error codes and stops decoding malformed block switches; affected users should upgrade packages, regenerate lockfiles, rebuild containers and bundled wheels, and check all deployed environments.

  • An application can be exposed even if its own code never imports Brotli, because installed HTTP client libraries can automatically decode Brotli responses when Brotli bindings are present.
  • Removing Brotli and brotlicffi is a temporary mitigation that eliminates the vulnerable decoder and causes affected HTTP clients to fall back to gzip and deflate.
  • Simply removing "br" from outbound Accept-Encoding is weaker protection because a malicious server can still send a Brotli-encoded response and urllib3 decodes based on the response header.
  • Updating a dependency alone is insufficient for containerized deployments, because images and bundled wheels built with vulnerable versions remain affected until they are rebuilt.
  • Dependency-scanning tools may not detect this issue yet because the article states that advisory databases had not mapped the CVE to the affected PyPI packages.
Key Points
  • 01CVE-2026-111497 is a Brotli decoder flaw that affects Python packages Brotli 1.2.0 and earlier and brotlicffi 1.2.0.x.
  • 02The patched releases are Brotli 1.2.1 and brotlicffi 1.2.1.0.
  • 03Python applications can reach the vulnerable decoder through malicious Brotli-compressed responses from outbound HTTP requests or Brotli-compressed inbound request bodies.
  • 04urllib3, requests, httpx, aiohttp, and Scrapy may automatically use Brotli decoding when Brotli or brotlicffi is installed.
  • 05As of October 23, the article states that pip-audit, Dependabot, and Safety do not flag the affected Python packages because advisory databases have not mapped the CVE to them.
