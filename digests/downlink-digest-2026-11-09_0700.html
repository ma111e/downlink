Emerging Threat: (CVE-2026-123158) OpenSSH Password Authentication Bypass on musl Linux
cycognito.com · 09 Nov 2026 08:43 UTC openai-codex / gpt-5.6-terra
TAGSalpine-linuxbuildrootcve-2026-123158cycognitomuslopensshopenwrtpamsshhole
85
In plain words

The article describes a flaw called “sshhole” that can allow someone on the internet to sign in to certain computers without knowing the account password. It mainly affects Alpine Linux and some other lightweight Linux systems using particular OpenSSH settings, while common systems such as Debian, Ubuntu, Fedora, and Red Hat Enterprise Linux are not affected. This matters because an exposed computer could be taken over, especially if the compromised account can gain full control; organizations should install the available fixes, restart the affected service, and limit who can reach it.

Summary
CVE-2026-123158 (“sshhole”) can let remote attackers bypass password authentication on vulnerable OpenSSH sshd instances built with musl and without PAM, especially Alpine Linux hosts. Patch to a fixed vendor package, restart sshd, and disable password authentication or restrict SSH access until remediation is confirmed.

CVE-2026-123158, known as “sshhole,” is a high-severity OpenSSH password authentication bypass affecting sshd built with the musl C library and without PAM, or with PAM disabled. An attacker able to reach an affected SSH service can log in without knowing an account password under specific conditions. The issue affects OpenSSH versions before 10.6p2 in the affected build configuration and has public reproduction labs available.

The primary affected platform is Alpine Linux, whose openssh-server package is built this way by default, although some OpenWrt and Buildroot systems may also be exposed depending on their builds. Exploitation requires password authentication to be enabled, a target account password field in /etc/shadow to be exactly “*”, and another local account to have a SHA-crypt hash; accounts locked with “!” are not affected. Alpine has issued backported package fixes for supported releases 3.16 through 3.24, but defenders must restart sshd after updating. The article recommends disabling password authentication, auditing affected password fields, reviewing SSH logs, restricting TCP/22 access, and identifying musl-based OpenSSH systems with PAM disabled until patching is confirmed.

  • A host reporting an older OpenSSH version may already be fixed because Alpine backported the patch while retaining older upstream version numbers, so package release information is more reliable than the version string alone.
  • Version-based exposure inventories cannot distinguish musl-based builds from glibc-based builds and therefore can both overstate and misidentify systems at risk.
  • The affected account condition is unusually specific: password fields containing exactly “*” are exposed under the stated conditions, while accounts locked with “!” are not affected.
  • CyCognito’s observed asset set was not a list of confirmed vulnerable hosts, and its dedicated active test did not confirm exploitability for any of those assets.
  • Installing an updated package is insufficient by itself because the running sshd service must be restarted for the fix to take effect.
Key Points
  • 01CVE-2026-123158, also called “sshhole,” is an OpenSSH password-authentication bypass affecting sshd built with musl without PAM or with UsePAM disabled.
  • 02An attacker who can reach an affected SSH service can log in without knowing a password when password authentication is enabled, a target account’s /etc/shadow entry is exactly “*”, and another local account has a SHA-crypt hash.
  • 03Alpine Linux is the primary affected platform, while Debian, Ubuntu, Fedora, and Red Hat Enterprise Linux are outside the affected glibc-and-PAM configuration.
  • 04OpenSSH 10.6p2 fixes the flaw, and Alpine has backported patches for supported branches 3.16 through 3.24, though sshd must be restarted after updating.
  • 05Until patching is confirmed, the article recommends disabling password authentication on exposed musl-based hosts, auditing /etc/shadow for exactly “*” entries, and restricting TCP/22 access to trusted networks or a bastion host.

JUSTIFICATION

This is a high-severity, remotely reachable OpenSSH authentication-bypass advisory with available patches and potentially severe host-compromise impact on affected musl-based deployments, particularly Alpine Linux. It is narrowly conditional and does not report confirmed exploitation in the observed asset set, but warrants prompt review by teams operating exposed SSH services.

In plain words

LNbits, a service that helps run Bitcoin payment wallets, told everyone using its software to turn off their servers after criminals exploited a flaw and took money from at least one operator. One reported loss was 2,285,545 satoshis, worth about 0.023 Bitcoin, and users of a related Telegram payment bot cannot access their funds until the problem is fixed. The project also shut down its own hosted service while it prepares fixes, showing that people can lose access to digital money when wallet software has a serious security problem.

Summary
LNbits urged all operators to immediately shut down their Bitcoin Lightning wallet servers after active exploits drained funds from at least one instance. Patches were expected within 24–48 hours, while the project’s hosted my.lnbits.com service was taken offline.

LNbits urged all operators of its free, open-source Bitcoin Lightning wallet servers to shut them down amid a wave of attacks. The project said it had several security fixes to release and initially advised operators to disable its Paywall add-on while it investigated a possible bug. About 80 minutes later, it issued the broader shutdown notice covering LNbits servers, not Lightning nodes or other wallet software.

One operator, Kevin Ravensberg, reported that new accounts exploited his server to withdraw 2,285,545 satoshis, or about 0.023 Bitcoin, before he could stop it. He said the attack ran from 09:22 to 14:00 UTC, beginning more than three hours before LNbits issued its first warning, and users of his BitTipBot Telegram bot could not access funds while fixes were pending. LNbits also shut down all instances on its my.lnbits.com hosted service, while a developer estimated patches would be available within 24 to 48 hours; as of 09:00 UTC, the project had not publicly identified the exact extension used or said how many servers were affected.

  • The reported theft began more than three hours before LNbits issued its first public warning, indicating that at least one server was exposed before operators were told to take defensive action.
  • LNbits moved from advising operators to disable only the Paywall add-on to calling for all servers to be shut down within about 80 minutes, reflecting a rapid expansion of the response scope.
  • Although security testers reportedly confirmed the exact extension used in the reported incident, the project had not publicly identified it, leaving operators without confirmation of whether Paywall was the exploited component.
  • Users of BitTipBot could not access their funds while fixes were pending, illustrating that a security issue at the wallet-server layer could directly interrupt users’ access to digital money.
Key Points
  • 01LNbits urged all operators of its open-source Bitcoin Lightning wallet servers to shut them down amid a wave of attacks while it prepares security fixes.
  • 02An operator reported that attackers used an exploit to withdraw 2,285,545 satoshis, about 0.023 Bitcoin, from his server before it was shut down.
  • 03LNbits initially told operators to disable its Paywall add-on, then issued a broader shutdown notice about 80 minutes later.
  • 04LNbits took its hosted my.lnbits.com instances offline and said services would return within 24 hours, while a developer estimated patches would be available within 24 to 48 hours.
  • 05The project had not publicly identified the exact add-on used in the reported incident or said how many servers were affected as of 09:00 UTC.

Taiwan-Based Hacker Used BOSSAI AI Agents to Steal Taipei Emergency Dispatch Records
thehackernews.com · 09 Nov 2026 09:01 UTC openai-codex / gpt-5.6-terra

In plain words

Researchers say a person in Taiwan used AI programs to search many organizations for weak security and obtain emergency call records in Taipei, along with other personal and medical information. People needing fire or ambulance help, patients, borrowers, university communities, and Mexican phone customers may be affected by the exposed or taken data. The case matters because AI helped one person examine many targets quickly, while the successful incidents mainly involved systems that had been left openly accessible or poorly protected.

Summary
Acronis researchers say a Taiwan-based attacker used locally run, safety-stripped AI agents to steal Taipei emergency dispatch records and target poorly secured systems in Taiwan, Mexico, and Thailand. The case shows AI can scale reconnaissance and exploitation, but the compromises largely relied on exposed APIs, default credentials, SQL injection flaws, and unpatched systems.

Acronis Threat Research Unit said a single attacker based in Hualien City, Taiwan, used a 12-agent AI setup called BOSSAI to target hundreds of organizations in at least 11 countries. The most serious confirmed activity involved Taiwan, where the agents pulled emergency dispatch records for seven Taipei districts from a 119 emergency-services API. The records included incident times, response types, case status, and street-level locations, while a separate Taipei fire department platform exposed patient data from 2018, including ECG readings and ambulance video footage, without a login.

The agents also accessed a fire-dispatch technology vendor’s database administration panel using default root credentials, extracted data from a Taiwanese lending firm and three Thai universities through SQL injection, and collected about 206,800 Mexican home-phone records containing names and addresses. Commercial models including Grok and MiniMax M3 generally refused direct attack requests, so the attacker primarily used locally run versions of DeepSeek, GLM, and Qwen with safety training removed. The operation also showed limitations: agents produced false positives, invented flaws, and failed against systems with enforced logins, valid-session requirements, or properly filtered endpoints.

  • The BOSSAI agents did not communicate directly with one another; the attacker manually copied one agent's output into another, showing the operation still depended on human coordination.
  • AI-generated scanning results were unreliable: more than half of one tool's high- and critical-severity findings were false positives or incorrectly classified, and the main attack agent also claimed results that had not occurred.
  • The agents succeeded mainly against systems with existing weaknesses, but failed when login controls, valid-session requirements, or properly filtered endpoints were in place.
  • The attacker's operational server exposed extensive evidence of the campaign, including agent conversations, command history, credentials, tools, and victim data, which enabled Acronis's attribution work.
Key Points
  • 01Acronis researchers said a single attacker based in Hualien City, Taiwan, used a setup called BOSSAI with AI agents to target hundreds of organizations in at least 11 countries.
  • 02The agents extracted emergency dispatch case records for seven Taipei districts from a public-facing 119 emergency-services API, including incident times, response types, case status, and street-level locations.
  • 03The agents found a Taipei fire department platform that exposed patient data from 2018, including ECG readings and ambulance video footage, without requiring a login.
  • 04Commercial AI models generally refused direct requests to conduct attacks, so the attacker used locally run safety-stripped versions of DeepSeek, GLM, and Qwen for most attack activity.
  • 05The confirmed compromises largely involved weak protections, including exposed data, default root credentials, SQL injection points, and unpatched Oracle databases.

JUSTIFICATION

This is a concrete, multi-country AI-assisted intrusion operation that reportedly exposed Taipei emergency dispatch and patient data and affected organizations in Taiwan, Thailand, and Mexico. It is broadly relevant because it documents both how locally run safety-stripped AI models were used and which existing weaknesses enabled successful access.
