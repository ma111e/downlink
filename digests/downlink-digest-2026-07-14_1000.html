Cybersecurity researchers discovered 11 old, Microsoft-signed UEFI shim applications that could be abused to bypass Secure Boot on most systems using UEFI. ESET said an attacker exploiting one of these vulnerable applications can execute untrusted code during system boot. The affected shims expose any UEFI-based machine that trusts Microsoft’s “Microsoft Corporation UEFI CA 2011” third-party UEFI certificate authority certificate, regardless of the installed operating system.

The shim is a lightweight, open-source UEFI bootloader used to help Linux distributions boot when Secure Boot is enabled. The article explains that UEFI firmware validates the shim against the Microsoft CA, the shim validates a second-stage bootloader such as GRUB 2 using its embedded vendor certificate, and GRUB 2 validates the kernel using the same vendor certificate. ESET said outdated but still trusted shims can be used to execute arbitrary code at boot, enabling UEFI bootkits such as Bootkitty, HybridPetya, or BlackLotus even when Secure Boot is enabled.

Microsoft revoked the impacted bootloaders as part of its June 2026 Patch Tuesday update after responsible disclosure in February. CERT/CC said vendor-specific bootloaders had not been updated after upstream vulnerabilities became public and fixed, leaving vulnerable components signed and trusted because they had not been revoked through the Microsoft-signed DBX revocation list. ESET warned that expiration of the Microsoft Corporation UEFI CA 2011 certificate does not affect Secure Boot verification unless bootloaders signed with the expired certificate are explicitly revoked by hash.

  • The risk comes from old shim binaries still being trusted, not from a new vulnerability, meaning an attacker only needs a copy of an unrevoked Microsoft-signed shim to undermine Secure Boot.
  • The expiration of the Microsoft Corporation UEFI CA 2011 certificate does not by itself stop previously signed bootloaders from working; explicit revocation by hash is still required.
  • The attack can bypass both the MOK denylist and Secure Boot Advanced Targeting by replacing an up-to-date shim with an older signed shim that does not enforce newer protections.
  • Because the malicious code can run before the operating system and security tools start, it can evade built-in controls and EDR products while enabling persistence across reboots and, in some cases, operating system reinstallation.
