Go With the Flow: Taking a Shadow Dependency in GCP Dataflow Cross Tenant
varonis.com · 23 Oct 2026 13:18 UTC openai-codex / gpt-5.6-terra
TAGSapache-beambucket-squattinggooglegoogle-cloud-dataflowgoogle-cloud-storagepickle-deserializationsave-main-sessionvaronis

In plain words

Researchers found that someone could reserve a predictable Google Cloud storage location before another company used it, then use that location to replace a file needed by the company’s data-processing job. This could let the attacker run their own instructions on the victim’s Google Cloud workers and steal access credentials or reach other cloud resources. The risk affected organizations using certain Python-based Google Cloud Dataflow jobs that had not yet created their default storage location in a given region. Google has deployed checks to ensure the storage location belongs to the right organization and to detect altered files.

Summary
Varonis found that attackers could squat predictable Google Cloud Dataflow staging buckets and, by replacing a Python pickled session artifact, achieve cross-tenant code execution on victim Dataflow workers. Google has globally mitigated the issue with bucket ownership validation and staged-artifact integrity checks.

Varonis Threat Labs found a cross-tenant Google Cloud Dataflow issue involving predictable default staging-bucket names in Apache Beam’s Python SDK. An attacker who knew a target’s GCP project ID and likely region could create the corresponding bucket first in an attacker-controlled project. If the victim later ran its first eligible Dataflow job in that region without specifying a staging location, Beam could reuse the attacker-owned bucket.

The attack also required a Python pipeline using --save_main_session, which stages a pickled session file for Dataflow workers. An attacker with write access to the squatted bucket could detect the legitimate file, replace it with a malicious pickle, and cause workers to run attacker-controlled code when they loaded it. Google has rolled out Python SDK ownership checks, server-side validation for default staging buckets, and SHA-256 integrity checks for staged artifacts, while warning that explicitly configured buckets must still be secured because they remain part of the code supply chain.

  • A target’s GCP project ID, which is often publicly visible or guessable, was sufficient to calculate the future default staging-bucket name because the naming scheme used the project ID and region deterministically.
  • The exposure was limited to a project’s first Dataflow use of the default bucket in a region: once the project had created that bucket, another party could no longer claim the name.
  • Beam’s Java SDK already verified bucket ownership, while the Python SDK did not perform that check before the reported fix.
  • Google’s server-side ownership enforcement protects customers using older or pinned Beam SDK versions, rather than requiring every affected customer to upgrade first.
  • Explicitly configured staging and temporary buckets remain outside the automatic ownership checks, so their write permissions must be treated like control over the pipeline’s source code.
Key Points
  • 01Varonis Threat Labs identified a cross-tenant Google Cloud Dataflow issue in which predictable default staging-bucket names could be squatted by an attacker.
  • 02The attack required a Beam Python SDK pipeline using --save_main_session, no explicitly configured staging bucket, and the project’s first default-bucket Dataflow job in the relevant region.
  • 03An attacker could replace the staged pickled_main_session file with a malicious Python pickle that executes code when Dataflow workers deserialize it.
  • 04Successful exploitation could expose the Dataflow worker service account’s identity and access token and enable code execution on workers, including autoscaled workers.
  • 05Google globally deployed default-bucket ownership validation and SHA-256 integrity verification for staged artifacts, including protections for older or pinned Beam SDK versions.

JUSTIFICATION

This is a concrete cross-tenant Dataflow code-execution finding that could expose highly privileged cloud service-account tokens without initial access to a victim project. Although exploitation had narrow prerequisites and Google has globally mitigated it, it is broadly relevant to organizations using Google Cloud Dataflow and Apache Beam Python pipelines.

In plain words

Researchers found a new data-stealing program called Aokigahara that searches infected Windows computers for passwords, browser information, cryptocurrency wallet data, email settings, and files. It also looks for saved sign-ins and access information for AI tools such as Claude, ChatGPT, Cursor, GitHub Copilot, and Gemini, as well as developer and cloud-service accounts. This matters because stolen access can expose private chats, source code, and cloud resources, let criminals use paid AI services, or be sold to others.

Summary
Check Point researchers identified Aokigahara, an infostealer that expands traditional browser, wallet, and credential theft to target AI application sessions, developer tools, cloud credentials, Git data, and SSH keys. Stolen tokens from tools such as Claude, ChatGPT Desktop, Cursor, GitHub Copilot, and Gemini CLI could enable unauthorized access to AI services, source code, and cloud environments.

Check Point Research identified Aokigahara, a newly observed information-stealing program that may previously have been known as Kamidere or Stygian. It collects browser credentials and cookies, cryptocurrency wallet data, screenshots, clipboard contents, email and VPN information, and selected files from Windows systems. Its most notable capability is dedicated collection of authentication files, session data, and configuration files associated with AI applications and developer tools.

Aokigahara targets Claude, ChatGPT Desktop, Codex, Cursor, Windsurf, GitHub Copilot, Gemini CLI, Amazon Q, Kiro, and JetBrains AI Assistant, as well as AWS credentials and single sign-on data. Its developer-focused collection also includes Git credential files, SSH-related files that may contain private keys, and AWS, Azure, and Google Cloud credentials and configuration files. The malware establishes communication with its command-and-control server using an X25519 key exchange and sends AES-256-GCM-encrypted ZIP archives through /gate/handshake, /gate/chunk, and /gate/complete endpoints.

  • Aokigahara keeps all of its collection capabilities embedded in the executable even when configuration settings disable some of them, so a sample’s available code may exceed the functions it is currently configured to run.
  • The malware’s uploads can be distinguished by its use of the /gate/handshake, /gate/chunk, and /gate/complete paths, along with headers such as X-Build-ID, X-Session, X-HWID, and X-Chunk.
  • Its encrypted uploads include the collection-module label in the X-Chunk header, which can identify whether data such as browser information, screenshots, or AI-session files is being sent.
  • The malware uses configuration-controlled language and analysis-environment checks, meaning these anti-analysis behaviors do not necessarily run in every sample or deployment.
  • Aokigahara’s AI-focused collection includes cloud sign-in data and local developer secrets such as Git credentials and SSH private-key-related files, extending its reach beyond AI application accounts alone.
Key Points
  • 01Check Point Research identified Aokigahara, an infostealer that may previously have been known as Kamidere or Stygian.
  • 02Aokigahara collects browser credentials and cookies, cryptocurrency wallet data, screenshots, clipboard contents, email and VPN data, and selected files from infected systems.
  • 03Its aisessions component targets authentication, session, and configuration data for AI and developer tools including Claude, ChatGPT Desktop, Codex, Cursor, Windsurf, GitHub Copilot, Gemini CLI, Amazon Q, Kiro, and JetBrains AI Assistant.
  • 04The malware also collects Git credential files, SSH-related files that may contain private keys, and AWS, Azure, and Google Cloud credential and configuration files.
  • 05Aokigahara establishes a command-and-control session using X25519 key exchange and uploads ZIP archives encrypted with AES-256-GCM through /gate/handshake, /gate/chunk, and /gate/complete endpoints.

A Summons Stamped 2018 That Ends at a OneDrive Login
ironscales.com · 23 Oct 2026 11:00 UTC openai-codex / gpt-5.6-terra
TAGSbunnycdnironscalesmicrosoftsouth-africaspearphishing-attachmentspecial-tribunaluser-execution-malicious-linkweb-formswestern-cape-high-court

In plain words

A South African financial services company received a fake court summons that used real-looking local seals, bilingual wording, and threats of legal action to create urgency. The document’s link led not to court records, but to a page made to look like Microsoft OneDrive that asked the recipient for their email address and password. This matters because stolen work passwords can give criminals access to company accounts, while convincing local details and legitimate web services can make fraudulent messages harder to recognize.

Summary
A phishing campaign impersonated South African courts with a localized summons PDF that linked to a BunnyCDN-hosted fake OneDrive login page designed to steal Microsoft credentials. The key warning sign was the impossible eight-year-old court stamp and the demand to sign in to view a supposed legal document.

A South African financial services firm received a one-page PDF called “Summons” that impersonated the Special Tribunal and the Master of the Western Cape High Court. The document alleged a default court order and threatened execution proceedings, using local details including a bilingual English-Afrikaans stamp and references to the tribunal’s mandate. Its most visible inconsistency was a stamp dated October 2018 on a document dated September 2026.

The PDF contained one live link behind a “VIEW COURT SUMMONS HERE” button, which led to an attacker-controlled BunnyCDN pull zone named hicourtsummons.b-cdn.net. Rather than showing a court document, the site displayed a OneDrive-style page requesting a Microsoft email address and password, with South African B-BBEE compliance files in the blurred background. IRONSCALES automatically identified the message as phishing and quarantined it; the article records no victim click or credential submission.

  • The attachment itself appeared clean because it had no scripts, embedded files, launch actions, or auto-actions; its only active element was a link to the credential-harvesting page.
  • The attacker used a legitimate BunnyCDN shared domain, where the deceptive “hicourtsummons” subdomain was attacker-selected even though the broader b-cdn.net domain belonged to the CDN.
  • The email authenticated cleanly because it was sent from a real South African company’s Microsoft 365 tenant, which the article says may indicate a hijacked account but does not prove it.
  • Localized details such as real government agencies, Afrikaans wording, and B-BBEE compliance-file decoys added plausibility but did not establish authenticity, while the request for a Microsoft sign-in to view a legal document exposed the fraud.
Key Points
  • 01A South African financial services firm received a one-page PDF styled as a court summons that impersonated the Special Tribunal and the Master of the Western Cape High Court.
  • 02The PDF contained one link, behind a “VIEW COURT SUMMONS HERE” button, that opened a BunnyCDN-hosted page at hicourtsummons.b-cdn.net.
  • 03The linked page displayed a OneDrive-style form requesting a Microsoft email address and password, with South African B-BBEE compliance files used as background decoys.
  • 04The court stamp was dated October 2018 while the document was dated September 2026, an eight-year discrepancy highlighted as a clear warning sign.
  • 05IRONSCALES automatically classified the email as phishing and quarantined it, although no victim click or credential submission was recorded.

JUSTIFICATION

This is a concrete credential-harvesting incident using convincing South African legal impersonation, a BunnyCDN-hosted phishing page, and a fake OneDrive login form. It offers actionable indicators and detection lessons, but no victim compromise, active campaign scope, or broadly critical vulnerability is reported.

In plain words

Radiflow and Belden announced a partnership that connects Radiflow’s system for spotting risks in industrial equipment networks with Belden’s system for controlling which devices can connect to those networks. The combined system can automatically limit a device’s access as soon as its risk level changes, rather than waiting for people to make the change manually. This is meant to help manufacturers, energy providers, transportation organizations, and other critical services respond faster and keep important operations running safely.

Summary
Radiflow and Belden announced an integration of Radiflow’s CIARA and iSID OT risk intelligence platforms with Belden’s macmon NAC to automatically restrict network access when an asset’s risk posture changes. The partnership targets industrial and critical-infrastructure operators seeking machine-speed responses to OT threats.

Radiflow and Belden announced a strategic partnership to connect OT risk detection with automated network-access enforcement. The companies launched an integrated solution combining Radiflow’s CIARA and iSID platforms with Belden’s macmon NAC. They said the integration is intended to eliminate manual handoffs between identifying an exposure and restricting access.

CIARA maps OT network topology and applies AI-driven threat intelligence to identify critical exposures as they emerge. iSID provides real-time OT event context, while CIARA supplies macmon with current risk scores for individual assets and network zones. macmon can then automatically adjust access rights when an asset or zone’s risk posture changes.

The partnership is aimed at industrial operators in manufacturing, energy, transportation, and critical infrastructure. Radiflow and Belden said the combined offering is designed to reduce response times and limit cyber risk while avoiding disruption to operations. The companies cited Radiflow’s deployments at more than 20,000 sites and said the partnership will serve joint customers across Europe, APAC, and North America.

  • The integration is designed to make access-control decisions using risk scores for both individual assets and network zones, rather than relying only on broad network-wide policies.
  • The partnership addresses a stated operational gap in which identifying OT risks does not automatically lead to a network response and enforcement is often manual.
  • Radiflow says its existing deployment across more than 20,000 sites gives the partnership an established operational footprint for customers in industrial and critical-infrastructure sectors.
