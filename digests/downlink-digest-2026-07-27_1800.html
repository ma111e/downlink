In plain words

A network of infected devices called Dysphoria has taken over about 200,000 routers, cameras, and other internet-connected devices around the world. The people running it use those devices to overwhelm websites and online services with traffic or to pass internet traffic through victims’ devices. This matters because it can cause real online disruptions, and many ordinary device owners may be affected if their equipment has weak passwords, old software, or exposed remote access.

Summary
The Dysphoria botnet has infected about 200,000 routers, cameras, and IoT devices worldwide, using blockchain-based command-and-control to make takedowns harder. It is being used for DDoS attacks and proxy operations, spreading through weak credentials and both new and old device vulnerabilities.

A botnet called Dysphoria has compromised around 200,000 devices worldwide and is being used for distributed denial of service attacks and traffic relay operations. QiAnXin XLab researchers say the botnet has been tracked since the first quarter of 2026 and has undergone frequent updates in only a few months. Its operators claim a maximum DDoS capacity of 4 Tbps on a clearnet site that presents the service as a legitimate stress-tester.

XLab says Dysphoria evolved from the jackskid and fbot malware by adding a covert blockchain-based command-and-control resolution mechanism. The botnet uses Ethereum ENS and Solana SNS domains to retrieve infrastructure information, with C2 addresses hidden inside fake IPv6 strings and recovered using a custom byte-transformation algorithm. Infected clients send fixed 78-byte login and heartbeat packets to the C2 and receive DDoS commands that include duration, type, targets, and configurable flags.

In late June, XLab observed a Dysphoria variant focused only on turning infected devices into network proxies and discarding DDoS functionality. That variant abuses UPnP on compromised devices to create 155 port forwarding rules that expose internal services to inbound internet connections. The malware spreads through weak Telnet and SSH credentials and known vulnerabilities in routers, cameras, and IoT devices, and users are advised to update firmware, change default administrator passwords, disable unnecessary remote access, and strengthen available security settings.

  • Dysphoria’s use of both Ethereum ENS and Solana SNS for command-and-control resolution makes its infrastructure harder to trace and dismantle than a botnet relying only on conventional domains or servers.
  • The botnet is rapidly evolving, with XLab observing multiple iterations since March 25 that added multi-chain support, new domains, a C2 acquisition algorithm, and separation between DDoS and relay-focused variants.
  • One Dysphoria variant removed DDoS features entirely and used UPnP to create 155 port forwarding rules, showing that infected devices can be repurposed from attack traffic generators into exposed proxy infrastructure.
  • Dysphoria’s spread depends on both weak Telnet and SSH credentials and a mix of recent and older device flaws, making firmware updates and removal of default passwords directly relevant defenses for ordinary device owners.
  • Although Dysphoria’s claimed 4 Tbps DDoS capacity is far below the 31.4 Tbps Aisuru/Kimwolf record cited in the article, the article notes it is still enough to cause notable disruptions.

New Certighost PoC exploit lets attackers hijack Windows domains

In plain words

Researchers released a working example of how attackers could abuse a Microsoft Windows domain certificate service flaw called Certighost, which Microsoft fixed in its July 2026 security updates. The issue affects organizations using Active Directory Certificate Services, and a signed-in low-privilege user could potentially trick the system into acting like they control a domain controller, one of the central servers that manages a Windows network. If successful, attackers could gain domain-level control and retrieve highly sensitive account secrets, so organizations are urged to install the latest updates or use Microsoft’s temporary workaround until they can patch.

Summary
A public proof-of-concept exploit for the Certighost AD CS flaw CVE-2026-54121 can let authenticated attackers impersonate a domain controller and potentially compromise an entire Windows domain. Microsoft fixed the issue in July 2026 updates, and admins should patch urgently or temporarily disable the affected chase fallback.

A proof-of-concept exploit has been released for “Certighost,” a Windows Active Directory Certificate Services vulnerability tracked as CVE-2026-54121. Microsoft fixed the flaw in the July 2026 Patch Tuesday security updates. Microsoft said an authenticated attacker could manipulate attributes associated with a machine account and obtain a certificate from Active Directory Certificate Services that allows authentication as that machine via PKINIT.

The researchers who reported the issue, H0j3n and Aniq Fakhrul, said Certighost allowed a low-privileged domain user to impersonate a domain controller and achieve domain compromise in the tested AD CS configuration. In the demonstrated attack, the attacker creates a machine account, submits a certificate request that directs the Certification Authority to attacker-controlled services, and targets a domain controller account. The released certighost.py proof-of-concept automates the process by using the certificate to authenticate as the targeted domain controller, saving Kerberos credentials to a .ccache file, and extracting the account’s NT hash.

The issue involved an AD CS fallback mechanism referred to by the researchers as a “chase,” which used attacker-supplied cdc and rmd values without verifying that the cdc server was a legitimate domain controller. Microsoft’s fix adds validation so the Certification Authority verifies that the cdc server maps to a legitimate domain controller in Active Directory and that the returned identity matches the expected account. For administrators who cannot install the July updates, the researchers said the optional chase fallback can be disabled with certutil, but they stressed this workaround is temporary and has not been fully tested in production environments.

  • The exploit chain can start from a low-privileged domain user because the default ms-DS-MachineAccountQuota setting allows users to create machine accounts that are valid domain principals.
  • The flaw depends on an optional AD CS fallback mechanism, so organizations that cannot immediately apply the July 2026 updates can temporarily reduce exposure by disabling the chase fallback with certutil and restarting CertSvc.
  • The researchers warned that the workaround has not been fully tested in production environments, making patching the recommended fix rather than relying on the configuration change.
  • The attack abuses trust in attacker-supplied certificate request values by directing the Certification Authority to attacker-controlled services that return false directory information for a targeted machine account.
Key Points
  • 01A proof-of-concept exploit for the Windows Active Directory Certificate Services vulnerability known as Certighost, tracked as CVE-2026-54121, has been released publicly.
  • 02Microsoft fixed CVE-2026-54121 in the July 2026 Patch Tuesday security updates after researchers H0j3n and Aniq Fakhrul reported it on May 14, 2026.
  • 03The vulnerability allowed an authenticated attacker to manipulate attributes tied to a machine account and obtain a certificate that could authenticate as that machine via PKINIT.
  • 04The researchers demonstrated that a low-privileged domain user could impersonate a domain controller and use the resulting Kerberos credentials to perform a DCSync attack and retrieve the krbtgt account’s credentials.
  • 05Microsoft’s fix adds validation so the Certification Authority verifies that the server specified in the cdc attribute maps to a legitimate domain controller and that the returned identity matches the expected account.

NVIDIA also released a research tool called NOOA that can help test and track what an AI agent does, but it can also run AI-written code that could damage files or expose private data unless it is kept inside a separate locked-down environment. This matters because Hugging Face recently had an intrusion involving an autonomous AI system, and the company said running a capable AI model on its own computers helped it investigate without sending sensitive attack data elsewhere. The wider issue is whether companies can build safer AI systems together, but the new alliance has not yet published how it will be run, what members must contribute, or what it will deliver next.

Summary
NVIDIA and 36 partners launched the Open Secure AI Alliance to promote open tools for securing AI agents, with NVIDIA’s NOOA framework as the first code contribution. The effort highlights the need for locally controlled defensive AI, but its governance, roadmap, and joint deliverables remain unclear.

NVIDIA and 36 other organizations formed the Open Secure AI Alliance to develop and share open technologies, techniques, and tools for securing software and AI agents. The 37-member group includes Microsoft, Cisco, Cloudflare, CrowdStrike, Hugging Face, IBM, Palo Alto Networks, Red Hat, and the Linux Foundation. Its stated scope covers the full agent stack, including identity, permissions, isolation, guardrails, logs, model formats, multi-model scanning, and secure coding workflows.

The launch includes NVIDIA-labs OO Agents, or NOOA, an Apache 2.0 research framework designed to make agent behavior easier to test, trace, audit, and govern. NOOA represents an agent harness as a Python class, where fields store state, methods expose capabilities, docstrings act as prompts, and type annotations define contracts. The repository warns that NOOA can be configured to execute LLM-generated Python that may transmit private data, delete files, or modify its environment, and says its checks and deny-lists are not a containment boundary.

NVIDIA tied the alliance’s case for locally controlled defensive models to the July intrusion at Hugging Face, where an autonomous agent system compromised parts of the company’s production infrastructure. Hugging Face said it used LLM-driven analysis agents over more than 17,000 recorded actions and ran the open-weight GLM 5.2 model on its own infrastructure after hosted frontier-model APIs initially rejected attack-related material needed for analysis. The article notes that the public record shows a coalition, a policy position, several member commitments, and one identifiable new NVIDIA-maintained code release, while the alliance’s governance, roadmap, first multi-member deliverable, and promised models, weights, and datasets remain undisclosed.

  • NOOA’s own documentation makes clear that its code checks and deny-lists should not be treated as a safety boundary, so any use of LLM-generated Python requires operating-system isolation such as a container, virtual machine, or OpenShell sandbox.
  • The Hugging Face incident supports the value of having a capable model ready to run internally during an investigation, but the article notes that it does not show open models can replace identity controls, isolation, or containment.
  • The alliance announcement names many prominent members and existing projects, but the public record does not yet show whether members are assigning engineers to joint work, contributing only existing tools, or simply endorsing the coalition’s direction.
  • Several technologies highlighted in the alliance announcement, including Safetensors, SPIFFE/SPIRE, Lightwell, MDASH, and Grok Build, existed before the coalition and are described as member projects rather than alliance-created products.

In plain words

The article explains how someone with permission to add software add-ons to an Azure virtual machine could install a legitimate Salt Minion add-on and point it to a server they control, letting them run commands on that machine. This affects organizations that use Azure virtual machines, especially sensitive ones like domain controllers, because several common Azure roles have the needed permission. The broader risk is that normal-looking administration features can be misused to gain powerful access, so organizations need to limit who can use them and watch for signs of this activity.

Summary
An attacker with Azure VM extension write permissions can abuse the legitimate Salt Minion third-party extension to connect a VM to a rogue Salt master and execute commands as root or SYSTEM. Organizations should tightly restrict extension write privileges and monitor Azure Activity Logs and endpoint process activity for Salt Minion installation and command execution.

This article explains how Azure VM command execution can be achieved by abusing the legitimate third-party Salt Minion extension. An attacker with Microsoft.Compute/virtualMachines/extensions/write permission can deploy the Salt Minion extension to a target Azure virtual machine and point it at a rogue Salt Master they control. After the minion connects and its key is accepted, the attacker can push Salt states or run commands on the VM.

The article demonstrates creating a malicious Salt state that retrieves an Azure Managed Identity access token from the VM metadata service and posts it to an out-of-band interaction endpoint. On Linux, the demonstrated command execution runs as root, and the article also notes that arbitrary commands can be run directly through Salt without sending a new state. The technique applies to both Linux and Windows Azure VMs using the salt-minion.linux or salt-minion.windows extension.

The significance is that several built-in and less commonly discussed Azure roles have the extension write permission needed to perform this activity, including Owner, Contributor, Log Analytics Contributor, Virtual Machine Contributor, and others. The article recommends monitoring Azure Activity Logs for VM extension write operations and specifically for Salt Minion extension installation. It also describes Linux detection opportunities through Salt logs, auditd, and process-tree context, while Windows detection relies on process events showing Salt Minion spawning system command processes.

  • The Salt Minion approach is described as simpler than the Chef extension approach because it does not require licensing, cookbook infrastructure, or validation keys.
  • The article highlights several less obvious Azure roles with VM extension write permissions, such as Log Analytics Contributor, VM Restore Operator, and Defender-related server roles, expanding the set of identities that may effectively be able to execute code on VMs.
  • If a sensitive system such as a domain controller is deployed as an Azure VM, anyone who can write extensions to it is effectively a domain administrator according to the article.
  • Auditd alone can show that commands ran as root without an interactive login session, but process-tree context from tools like pspy or EDR is needed to connect that activity back to Salt Minion.
  • The article emphasizes that VM extensions should not be eliminated because they are important for administration, but their abuse should be addressed through tighter permissions and detection around sensitive actions.
