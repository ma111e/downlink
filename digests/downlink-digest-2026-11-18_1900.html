In plain words

The article says that a serious flaw in Java’s built-in Base64 data reader, called Java4Shell, was introduced in an OpenJDK code change in 2021 and disclosed five years later. On certain newer x86-64 computers, specially malformed data could make a program write outside the memory it was allowed to use, potentially letting an attacker take control of it. The company Aikido says its code-review tool found the same problem and suggested a fix when it replayed the original code change, illustrating how automated review could prevent dangerous bugs before software is released. Organizations using affected Java versions should update to Oracle’s fixed releases or use a patched Java image if they cannot update immediately.

Summary
Aikido claims its Deep Review tool would have detected Java4Shell (CVE-2026-114938) in the 2021 OpenJDK pull request that introduced it, including a mitigation essentially matching the upstream fix. Affected Java deployments should upgrade to patched releases, particularly on AVX-512 VBMI-capable x86-64 systems.

Java4Shell (CVE-2026-114938) is described as a critical memory-corruption vulnerability in OpenJDK’s hardware-accelerated Base64 decoder, publicly disclosed on November 17, 2026. The issue originated in an AVX-512 performance optimization merged into OpenJDK in June 2021. According to the article, it can enable remote code execution on x86-64 systems with AVX-512 VBMI support, while ARM systems are not affected.

Aikido recreated the original OpenJDK pull request and ran its Deep Review tool against it, which it says produced three high-severity findings. One finding identified an invalid Base64-padding case that causes an integer underflow and a resulting write beyond the allocated Java heap buffer; the suggested fallback to a safer decoder was effectively the same as the later upstream fix. Deep Review also identified an oversized vectorized write and incomplete invalid-character validation in the original implementation, both of which the article says were later corrected upstream. Oracle’s listed fixed releases are 17.0.21.1, 21.0.13.1, 25.0.5.1, and 27.0.1.1, and Aikido offers patched Temurin 17 and 21 images for organizations unable to upgrade immediately.

  • The reported Java4Shell trigger can be as small as 128 valid Base64 characters followed by one extra “=” character, which causes the optimized decoder to perform a full 64-byte write where it should write nothing.
  • The affected code path is limited to x86-64 systems with AVX-512 VBMI support, so ARM systems are not affected by this specific issue.
  • Aikido’s recreated review found two additional defects in the same original implementation: a 64-byte write into a region intended for 48 decoded bytes and an omitted invalid-character check in one input lane.
  • The article states that the recommended mitigation was effectively identical to the eventual OpenJDK upstream fix, differing only in two equivalent comparison terms.
Key Points
  • 01Java4Shell, tracked as CVE-2026-114938, is a critical memory-corruption flaw in OpenJDK’s hardware-accelerated Base64 decoder that may allow remote code execution on x86-64 CPUs supporting AVX-512 VBMI.
  • 02The vulnerable code originated in OpenJDK pull request #4368, an AVX-512 performance optimization merged on June 25, 2021.
  • 03Aikido recreated the original pull request and says its Deep Review tool identified the Java4Shell integer-underflow condition, which could cause the decoder to write past its allocated output buffer.
  • 04Deep Review recommended falling back to a safer decoder when fewer than four input bytes remained, which the article says is effectively the same mitigation as the eventual upstream fix.
  • 05Oracle’s listed fixed Java releases are 17.0.21.1, 21.0.13.1, 25.0.5.1, and 27.0.1.1; Aikido also offers patched Temurin 17 and 21 images.

One expected issue, CVE-2026-115560, is a remote code execution vector involving PHP session upload progress. An application is exposed only when it uses php_binary or php_serialize as its session serialization setting, changes that setting to php at runtime before starting a session, and has session upload progress enabled. PHP advised disabling session.upload_progress.enabled in a setting applied before request parsing, restarting PHP workers, checking code for runtime serialization-handler changes, and upgrading once updates are available.

The article also distinguishes CVE-2026-115560 from PHP2Shell, the separate critical vulnerabilities CVE-2026-109618 and CVE-2026-109619.   • The known CVE-2026-115560 exposure requires a specific sequence of session-serialization settings, so applications that never change the session serialization handler while running can keep session upload progress enabled.
  • Disabling session upload progress with ini_set() or an FPM .user.ini file is not an effective mitigation because the setting must apply before PHP parses the request.
  • Organizations that already disabled session upload progress as mitigation for CVE-2026-109619 do not need to take additional action for that setting.
  • The PHP2Shell fixes released on 21 October do not fix CVE-2026-115560, so systems patched for PHP2Shell still need the November update when it becomes available.

Network threat hunting is the active search for malicious activity in packet data, network flow records, and logs, with the goal of finding evidence before an incident occurs. Unlike endpoint hunting, which relies more heavily on host logs, network hunting examines activity on the wire or in the air. Hunters do not need to inspect every packet manually because tools can index, search, and analyze packet and log data.

Firewalls and intrusion detection or prevention systems can miss threats because adversaries change techniques faster than static signatures, vendor updates, and threat-intelligence feeds can keep up. Behavioral analysis helps hunters compare traffic with normal network baselines to identify unexpected protocols, traffic flows, unusual ports, DNS anomalies, authentication failures, certificate issues, and TLS or SSL irregularities. The article recommends examining internal traffic as well as external connections, using approaches such as crown-jewel analysis, hypothesis-driven hunting, kill-chain mapping, and an assumed-breach mindset. It also encourages newcomers to begin with a single protocol and the tools they already have.

  • Network hunting does not require manually reviewing every captured packet; flow records, logs, indexing, and search tools can narrow the investigation.
  • A connection can be suspicious based on context rather than its destination alone, such as an Accounting employee using SSH to reach a foreign server or unusually large data transfers occurring at 3 a.m.
  • Treating the environment as already compromised can guide hunters to look for evidence across internal traffic, not only for threats entering from outside.
  • Starting with one protocol and existing tools is presented as a practical way for less-experienced analysts to begin threat hunting.
