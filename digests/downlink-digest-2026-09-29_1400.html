    Researchers found a new weakness called Branch Target Reuse that can make a computer briefly follow leftover instructions from old code, allowing information in memory to be revealed. In tests, it let an unprivileged user on Linux recover the root account’s password hash in as little as three to five minutes.     Summary
    Researchers demonstrated Branch Target Reuse (BTR), a Spectre v2 variant that abuses stale CPU branch-prediction data after JIT code reuse to leak a Linux root password hash in minutes. The issue affects tested Intel, AMD, and Arm CPUs; Linux kernel fixes are available, so users should update their OS and firmware.

    Researchers at VUsec and Scuola Superiore Sant’Anna disclosed Branch Target Reuse (BTR), a new Spectre v2 attack variant that can recover a Linux root password hash in minutes. BTR abuses stale CPU branch-prediction information after a just-in-time compiler frees code and places different code at the same memory address. The researchers said this demonstrates that self-modifying-code-based transient-execution attacks can be practical in real-world environments.

    In Linux tests, unprivileged classic BPF programs trained a prediction, then triggered reuse of the old program memory with attacker-crafted code. The resulting speculative execution created measurable cache traces that let the researchers infer data byte by byte and recover a running su process’s root password hash at roughly eight bytes per second, averaging three to five minutes on Raptor Cove and Lion Cove. The issues, tracked as CVE-2026-64507 and CVE-2026-64508, have Linux kernel fixes available; VUsec reported confirming the underlying behavior on tested Intel, AMD, and Arm CPUs, and recommends applying operating-system and firmware updates.

    • BTR challenges the long-held assumption that attacks based on dynamically generated and replaced code were impractical because of self-modifying-code behavior in common JIT engines.
    • The Linux proof of concept still recovered the password hash when constant blinding was enabled by encoding attacker-controlled instructions in jump offsets.
    • Although BTR exposed a root password hash rather than the plaintext password, the hash could be attacked offline, with the result depending on the password's strength and hashing method.
    • The researchers found evidence of stale prediction survival in Firefox's SpiderMonkey and a speculative sandbox-check bypass path in GraalVM, but did not complete practical exploits against either engine.
    • According to VUsec, current CPUs lack a mechanism to synchronize branch-prediction state with changed code, which is why the behavior appeared across the Intel, AMD, and Arm processors tested.

Summary

Proof-of-concept Linux kernel exploits recovered a root password hash from fully patched Intel systems, and fixes have been merged for the affected cBPF JIT.

Researchers from VUSec and Scuola Superiore Sant’Anna disclosed Branch Target Reuse (BTR), a new Spectre-v2 variant affecting Just-In-Time (JIT) engines. BTR was evaluated against Mozilla Firefox’s SpiderMonkey, GraalVM, and the Linux kernel’s cBPF JIT, with different exploitability characteristics and leakage rates. The researchers developed two end-to-end Linux kernel proof-of-concept exploits that recovered a root password hash within minutes from a fully patched Intel system using default protections.

BTR exploits stale indirect branch-prediction entries that may remain after JIT-generated code is freed, even though processors restore normal code consistency after code changes. An attacker can cause a code region to be freed and partially reused, then trigger an indirect branch that speculatively jumps to the old location, enabling transient control-flow hijacking and secret disclosure. The technique can bypass software hardening or reach misaligned instruction sequences, although it requires the stale prediction entry to persist and be selected by the processor. Linux mitigations were released and merged as CVE-2026-64507 and CVE-2026-64508, while GraalVM randomized JIT code-cache locations and Mozilla is prioritizing site isolation.

  • BTR can work despite existing software hardening because it redirects speculative execution to an outdated code location, potentially bypassing protections or causing the processor to interpret instructions from a misaligned position.
  • The attack depends on a narrow condition: the processor must retain an old branch-prediction record after code is freed, and must choose that stale record when predicting the next branch.
  • Different affected JIT engines do not present the same risk, as the researchers reported markedly different exploitability characteristics and data-leakage rates across SpiderMonkey, GraalVM, and Linux cBPF JIT.
  • GraalVM's mitigation focuses on reducing reuse of old code-memory regions by randomizing JIT code-cache locations, rather than directly clearing stale processor predictions.

Summary
UnJS has launched upm, a 250 KB TypeScript npm package manager designed for fast installs, embeddable JavaScript use, and safer defaults such as disabled lifecycle scripts and a 24-hour package release cooldown. The prerelease tool supports common npm configuration and existing lockfiles with significant compatibility limits.

Pooya Parsa, a Nuxt contributor and creator of Nitro and UnJS, introduced upm, a TypeScript package manager for the npm registry. upm uses Node.js built-in networking, worker threads, compression, and filesystem tools, and its build is reported as 256 KB on disk and 84.5 KB packed. It provides a JavaScript API, allowing other tools to use its installer or resolver without starting a separate process.

upm supports install, add, remove, run, frozen-lockfile mode, selected .npmrc settings, and imports from several existing lockfile formats when no upm.lock is present. It avoids hoisting undeclared dependencies and uses a shared store with hardlinks where possible. For security, it skips dependency lifecycle scripts by default and applies a configurable 24-hour minimum release age for newly selected versions, although it is still a prerelease with no update command, no Git or local-directory dependencies, and limited peer-dependency handling.

  • upm’s release-age safeguard can cause an installation to select the newest older eligible version instead of the current latest release, or fail entirely when no version in the requested range is old enough.
  • The 24-hour release delay does not protect projects that already have a version recorded in upm.lock or explicitly request an exact new version.
  • Disabling automatic dependency scripts reduces one common risk path, but packages that rely on installation-time builds or downloads may require additional manual setup.
  • upm’s small size may matter in CI because restoring a larger package-manager binary from cache can offset startup-speed advantages, although the article notes that its comparison does not measure complete CI jobs.
  • Projects can test upm against existing package-lock.json, pnpm-lock.yaml, or bun.lock files without replacing them, but this does not work for lockfiles containing workspaces, patches, Git dependencies, or file dependencies.
Key Points

  • 02In the project's benchmarks, upm ranked first overall for cold installs across Nitro, Nuxt, and Next.js tests, while warm-install results placed it fourth behind Bun, aube, and Deno.
  • 03upm supports install, add, remove, run, frozen-lockfile mode, selected .npmrc settings, and installation from package-lock.json, pnpm-lock.yaml, or bun.lock when no upm.lock exists.
  • 04By default, upm skips dependency lifecycle scripts and requires newly selected package versions to be at least 24 hours old, though the release-delay setting can be changed or disabled.
  • 05upm is a prerelease with limitations including no update command, no Git or local-directory dependencies, limited peer-dependency handling, and restricted compatibility with other package-manager lockfiles.
