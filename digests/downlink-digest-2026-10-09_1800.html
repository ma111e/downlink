Credential-Stealing GitHub Actions Workflows Planted in Tens of Thousands of Repositories
thehackernews.com · 09 Oct 2026 19:14 UTC openai-codex / gpt-5.6-terra
TAGSanthropicathenadriverawscredential-harvestingghostactiongitguardiangithubgithub-actionskuafuai-devopsgptopenaipersonal-access-tokenpyxelsocketstepsecurityxmrig

In plain words

Attackers took over GitHub accounts belonging to open-source software maintainers and added fake “security audit” files to thousands of code projects. When those projects run their automated tasks, the files can send passwords, cloud-service keys, and other private access codes from the project’s current files and old code history to the attackers. This affects project owners, their forks and copies, and potentially the companies and people who rely on those projects, because stolen access codes can be used to reach other online services.

Summary
The GhostAction campaign compromised hundreds of GitHub accounts and planted credential-stealing GitHub Actions workflows across tens of thousands of repositories, harvesting CI/CD secrets and credentials from source code and git history. Maintainers should immediately audit for the malicious Security Audit or GitHub Actions Security workflows, revoke compromised GitHub tokens, rotate exposed secrets, and inspect forks.

The GhostAction campaign compromised high-profile GitHub maintainer accounts and used them to add credential-stealing GitHub Actions workflows to repositories. StepSecurity said the account of Pyxel author Takashi Kitao was used against 27 repositories, while Henry Wu’s account was used to push the same workflow to 318 repositories in 16 minutes. Socket reported that, since October 7, 2026, more than 500 GitHub accounts had committed the malicious workflow to tens of thousands of repositories. The campaign previously affected 817 repositories across 327 GitHub users and resulted in the theft of 3,325 secrets.

The malicious files are named security-audit.yml or github_actions_security.yml and pose as security audits while sending collected data to the hard-coded IP address 193.32.204.199 over plain HTTP. They run on manual activation and on any push, check out the full repository history, collect named GitHub Actions secrets, and search current files and past commits for 13 types of credentials, including AWS, GitHub, GitLab, AI-service, cloud, and SaaS keys. The workflows can also pair AWS access key IDs with matching secret access keys, and each run sends a repository identifier even if it finds no credentials. Developers are advised to remove the workflows from every branch, revoke compromised GitHub credentials, rotate exposed secrets, and check forks, which may retain or inherit the malicious files.

  • The workflows use a full repository checkout, allowing them to search old commit history for credentials that may have been deleted from current project files.
  • Because the workflows run on any push, including pushes to any branch or tag, a single later change can trigger credential collection.
  • Forks can retain or inherit the malicious workflow, meaning removing it only from the original repository may not eliminate the risk.
  • Even when no credentials are found, each workflow run sends the attacker a repository identifier, giving the operator visibility into reachable code-project environments.
Key Points
  • 01The GhostAction campaign used compromised GitHub maintainer accounts to add malicious credential-stealing workflows to hundreds of repositories, with more than 500 accounts linked to tens of thousands of affected repositories since October 7, 2026.
  • 02The malicious workflows, named Security Audit or GitHub Actions Security, send collected data to the hard-coded IP address 193.32.204.199 over unencrypted HTTP.
  • 03The workflows can collect named GitHub Actions secrets and scan both project files and the full git history for AWS, AI-service, source-control, SaaS, and cloud credentials.
  • 04StepSecurity reported that the attacker used Takashi Kitao’s account to modify 27 repositories and Henry Wu’s account to modify 318 repositories.
  • 05Developers are advised to remove the malicious workflows from every branch, revoke compromised GitHub credentials, rotate exposed credentials, and inspect forks of infected repositories.

Hackers abuse Google Ads, Bing redirects to push Claude ClickFix attacks

In plain words

Criminals are placing Google search ads that look safer because they show Bing’s real web address, but the links ultimately send people to a fake page for downloading Claude on Mac computers. The fake page shows a real-looking installation command, yet its copy button secretly copies a different command that downloads and runs code from the criminals’ server. This matters because people searching for legitimate AI software could be tricked into running unknown harmful software while warning systems have a harder time detecting the chain of redirects.

Summary
Attackers are using Google Ads that appear to lead to Bing, then chaining Bing click-tracking redirects and compromised WordPress sites to deliver fake Claude for macOS pages. The pages use a ClickFix-style clipboard swap to replace Anthropic’s legitimate install command with a hidden script that downloads and executes attacker-controlled code.

Hackers are abusing Google Ads and Bing search-result redirects to send users searching for “claude mac” to a fake Claude download page. The ad displays the legitimate bing.com domain, then passes through Google’s advertising redirect, Bing’s click-tracking endpoint, and a compromised WordPress site belonging to a South American retailer. Push Security calls the technique “Adception” and says it is designed to evade ad security checks by using Bing’s trusted domain as the destination.

The campaign uses checks for Bing or Google referrers and specific browser headers, while direct visits to the malicious site are sent to a 404 page. The fake macOS installer page displays Anthropic’s legitimate Claude installation command, but its copy button secretly puts a different command in the clipboard. That command downloads a file from an attacker-controlled server and sends it directly to the macOS Z shell for execution; the final payload is unknown.

  • Using Bing’s legitimate click-tracking address as the visible Google Ads destination makes the advertisement appear less suspicious while still enabling a redirect to attacker-controlled content.
  • The fake installer presents Anthropic’s real installation command on the page and in the Terminal message, while silently placing a different command in the clipboard, so users may execute code they never visibly reviewed.
  • The campaign’s layered checks for Bing, Google, browser headers, and direct access mean that simply opening the malicious URL may show only a 404 page rather than the harmful content.
  • Push Security found multiple domains with the same installer interface, command structure, and payload URL pattern, indicating that the AcSig-tracked toolkit is reused across related sites.
Key Points
  • 01Push Security identified a malicious Google ad targeting searches for “claude mac” that displayed the legitimate bing.com domain before leading to a fake Claude download page.
  • 02The ad route passed through Google’s advertising redirect, Bing’s click-tracking endpoint, and a compromised South American retailer’s WordPress site before reaching the malicious site.
  • 03The compromised website and fake Claude page used referrer and browser checks to prevent direct visitors and automated scanners from seeing the malicious content.
  • 04The fake macOS installer page displayed Anthropic’s legitimate Claude installation command, but its copy button placed a different command in the clipboard that downloaded and executed content from an attacker-controlled server.
  • 05The final payload delivered by the campaign is unknown, and Push Security linked several domains using the same ClickFix toolkit, which it tracks as AcSig.

JUSTIFICATION

This is a concrete active malvertising campaign that targets people seeking Claude for macOS and uses trusted Google and Bing redirect infrastructure plus layered cloaking. It is broadly relevant because the clipboard-swapping ClickFix lure can cause users to execute hidden commands while making the malicious chain harder to inspect.

The article explains how criminals misuse well-known company and product names in website addresses and fake login pages to trick people into sharing passwords, payment details, or downloading harmful files. It describes ways companies can spot these scams early by watching for suspicious new web addresses, copied logos and website files, and servers connected to earlier scams. This matters to customers, companies, and service providers because a single fake link can be part of a much larger operation that changes web addresses quickly to avoid being removed.

Summary
Brand protection is an infrastructure-monitoring problem: defenders can use Censys to detect lookalike domains, certificates, cloned web assets, and related phishing infrastructure before and after campaigns go live. Combining continuous monitoring, historical pivots, and evidence-rich takedown requests helps identify entire impersonation operations rather than removing only one malicious domain.

The article presents a Censys-based guide to protecting brands from impersonation infrastructure, including lookalike domains, fake login pages, copied assets, and phishing operations. It opens with an August 2026 campaign in which a PowerShell dropper fetched an encrypted 16.8 MB script disguised as an MP4 file from binance-idexchange[.]com, despite Binance having no connection to it. The example illustrates that attackers may use brand names not only for fake websites but also to disguise malicious network traffic.

The guide explains how public certificate records, domain-name patterns, page titles, copied web assets, analytics IDs, and favicon hashes can reveal impersonation sites. It also describes using host reputation, historical DNS and certificate records, and shared infrastructure attributes to expand a single finding into a larger cluster of related domains and servers. For takedowns, it advises identifying whether an IP address is the true hosting server, a content-delivery edge, or a relay, then submitting evidence such as the URL, first-seen time, screenshot, certificate fingerprint, and copied brand artifact to the appropriate provider.

  • A phishing kit that reuses a company’s real analytics tag can send victim visits into the legitimate company’s marketing data, making unexpected referrer hostnames a potential real-time signal of cloned sites.
  • A certificate found only on an origin server behind Cloudflare can reveal a phishing hostname that is not visible through ordinary scans of the CDN-facing site.
  • A favicon hash can identify copied sites even when attackers host the icon locally, omit a visible page body, or use a bare IP address instead of a recognizable domain.
  • The USPS investigation expanded from one SMS lure to 682 unique lookalike hostnames through historical DNS data, showing that inactive domains can still expose a campaign’s prior infrastructure.
  • For takedowns, the IP address behind a malicious hostname may belong to a CDN edge or relay rather than the actual hosting server, so complaints must be directed differently depending on the infrastructure role.
Key Points
  • 01Brand impersonation relies on internet infrastructure such as domains, certificates, servers, and web pages, which Censys indexes and retains in historical records.
  • 02Certificate Transparency records can expose newly issued public certificates for lookalike domains before a phishing page is fully deployed, but they do not cover plain-HTTP infrastructure or self-signed certificates.
  • 03Attackers may use typosquatted domains, brand-prefixed hostnames on attacker-controlled domains, flattened versions of legitimate domain names, or product names to impersonate organizations.
  • 04Copied page titles, hotlinked or locally copied assets, analytics identifiers, and favicon hashes can help identify phishing sites even when their hostnames do not contain the targeted brand.
  • 05Historical DNS, host, and certificate data can help investigators pivot from one phishing link to related infrastructure and provide evidence for targeted takedown requests.
