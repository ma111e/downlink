From Hijacked PBX to Stolen Trunk: INJ3CTOR3’s Campaign Evolves

In plain words

The INJ3CTOR3 criminal operation is breaking into internet-connected business phone systems and secretly stealing the passwords that let those systems make calls. This affects organizations using FreePBX, Issabel, or Elastix, because criminals can use the stolen phone-service credentials from somewhere else to place expensive calls billed to the victim, even after the infected machine is cleaned or replaced. The article warns that removing the malicious software is not enough: affected organizations also need to change their phone, database, and email passwords after the system is safe.

Summary
INJ3CTOR3’s updated FreePBX malware now exfiltrates SIP trunk, AMI, database, and mail credentials every minute, allowing toll fraud even after an infected PBX is rebuilt. Organizations must isolate and fully eradicate persistence mechanisms before rotating all exposed credentials, especially SIP trunk secrets.

Cyble Research & Intelligence Labs reports that the INJ3CTOR3 toll-fraud campaign against Asterisk-based PBX systems has evolved from using the victim’s own phone system to stealing credentials that can be used elsewhere. The updated FreePBX implant uploads 17 configuration files containing SIP trunk, AMI, database, and mail-relay credentials to two staging hosts every minute while the infection remains active. This means that removing the webshell or rebuilding an affected PBX does not by itself prevent fraud if stolen trunk credentials remain valid.

The campaign targets systems using FreePBX, Issabel, and Elastix and maintains access through cron jobs, cached scripts, shell-profile and boot triggers, backdoor accounts, multiple webshell copies, and immutable file settings. Its webshell can be reached through specially encoded requests that do not reveal the served filename in access logs, while trunks added directly to Asterisk configuration files may not appear in the FreePBX console. The article recommends isolating suspected hosts, preserving evidence, removing persistence mechanisms in the required order, and rotating all exposed credentials only after the host has been cleaned.

  • Changing credentials before removing the implant is counterproductive because its minute-by-minute collection routine can immediately send the replacement secrets to the operator.
  • A clean FreePBX console and access-log search may provide false reassurance: trunks written directly into Asterisk configuration can be absent from the console, and encoded-space requests can reach the webshell without recording the file that served them.
  • The campaign’s rotating hashes, watermarks, gate values, and staging addresses make detections based only on known indicators short-lived; package provenance and behavior-based monitoring are more durable according to the article.
  • Even blocking the two identified staging hosts is insufficient for cleanup, because a local watchdog can run a cached copy of the implant every minute and rebuild webshells while the PBX is offline.
  • The most distinctive credential-theft activity can be detected by monitoring for many configuration-file reads followed by outbound HTTP POST requests, while a decoy configuration file can produce a no-false-positive alert if it is read.
Key Points
  • 01INJ3CTOR3’s updated FreePBX implant uploads 17 configuration files containing SIP trunk, AMI, database, and mail-relay credentials to two staging hosts every minute while the host remains infected.
  • 02Stolen SIP trunk credentials can allow the operator to register with a carrier and place calls from another machine, so disinfecting or rebuilding the PBX alone does not end the risk.
  • 03The September build uses staging hosts 45.95.147.178 and 160.119.69.4, with credential uploads sent to /hima_data/index.php on both hosts.
  • 04The campaign’s persistence includes cron jobs, cached scripts, shell-profile and boot triggers, backdoor accounts, webshell copies, and immutable file settings that can rebuild other components.
  • 05The article recommends isolating a suspected PBX, preserving evidence, removing persistence mechanisms before other components, and rotating exposed credentials only after the host is clean.
