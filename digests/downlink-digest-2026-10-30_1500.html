In plain words

eMudhra, a company trusted to issue the digital certificates that help computers confirm a website’s identity, used extremely weak secret numbers that anyone could quickly recover from public information. This means attackers could create convincing fake website identity documents for any domain and potentially fool older or unpatched software. Cloudflare has blocked these weak certificates in its important systems and has not found evidence that its own connections were intercepted, but many bots, older browsers, and Android’s built-in web viewer still accept them. The incident shows why software updates and fast ways to reject compromised digital certificates are important for the safety of the wider Internet.

Summary
Cloudflare found that eMudhra’s publicly recoverable intermediate CA keys were used to forge certificates within hours of disclosure, though it has seen no evidence of interception against its network. Most modern browsers are patched, but many bots, legacy clients, and Android WebView instances still accept the compromised certificate chain and need updates.

eMudhra’s eight affected intermediate certificate-signing keys were so weak that they could be recovered almost immediately from public certificates. Anyone with those keys could create certificates for any domain that unpatched clients not enforcing Certificate Transparency would accept. Cloudflare describes this as fundamentally different from prior certificate-authority compromises because the keys were publicly recoverable by anyone rather than limited to a particular attacker or organization.

Cloudflare began patching high-impact systems on October 19, including Pingora-based customer origin-facing proxies, and deployed logging to identify connections presenting certificates signed by the weak keys. The company recorded about 22,000 attempted handshakes using the keys and observed forged certificates made within hours of the weakness becoming public, but found no evidence of interception of Cloudflare connections. Its probes indicate that most current browsers are patched, while bots, older browsers, and 30–40% of embedded Android WebView clients still accept the compromised certificate chain; Cloudflare urges affected users and customers to patch.

  • Cloudflare’s logging suggests the observed forged certificates were likely servers’ default certificates rather than active interception attempts, because their domain names did not match the requested sites and identical certificates were presented from multiple Cloudflare locations.
  • The probe data is difficult to interpret because challenge-page traffic is heavily skewed toward unconfirmed bots, and a change in bot classification created an apparent patching trend for Chrome-on-macOS traffic.
  • After an initial period of patching over the first weekend, acceptance of the compromised chain showed little further movement across most measured client groups and large networks.
  • The incident demonstrates that relying on a static list of trusted certificate authorities can delay emergency response, which is why Cloudflare highlights mechanisms that can quickly distribute revocation and certificate-transparency updates.
Key Points
  • 01eMudhra’s eight affected intermediate private keys could be recovered almost instantly from public certificates, enabling anyone to create certificates for any domain that unpatched clients without Certificate Transparency enforcement would accept.
  • 02Cloudflare patched its high-priority systems, including Pingora-based customer origin-facing proxies, beginning on October 19 and completed a source-code analysis within four hours to identify other affected systems.
  • 03After deploying logging on October 21, Cloudflare recorded about 22,000 attempted TLS handshakes using the weak eMudhra keys, including approximately 160 certificates whose listed domain names were unrelated to the requested site.
  • 04Cloudflare found no evidence that the weak keys had been used to intercept its connections, but observed forged certificates dated less than an hour after Mozilla’s bug report became public.
  • 05Probe results indicated that most up-to-date modern browsers were patched, while bots, older browsers, and 30–40% of embedded Android WebView clients continued to accept the compromised certificate chain.

In plain words

A fake version of the Claude Code add-on for VS Code was briefly distributed through Open-VSX and Cursor, even though it appeared to come from the legitimate publisher. When installed, it could give attackers a way to return to a developer’s computer, keep that access after the add-on was removed, and collect information about the machine. Up to 5,000 Cursor users may have received it, so anyone who installed version 2.1.313 during the stated window should remove the leftover files and access settings and change passwords or keys that were available on that computer.

Summary
A trojanized Anthropic Claude Code VS Code extension version 2.1.313 was distributed through Open-VSX and Cursor for about 11 hours, installing SSH backdoor persistence and a reverse tunnel on affected developer machines. Anyone who installed it should treat the host as compromised, remove persistence artifacts, reinstall a clean version, and rotate accessible credentials.

On October 29, 2026, a trojanized version 2.1.313 of Anthropic’s Claude Code VS Code extension was published to Open-VSX and distributed through Cursor’s mirrored marketplace. The build appeared under Anthropic’s legitimate Open-VSX publisher identity but contained a malicious loader embedded in its extension.js bundle. Cursor reported that up to 5,000 users received the compromised version during an approximately 11-hour exposure window.

When the extension module loaded, the malicious code ran under Node.js without requiring a Claude conversation, VS Code API use, or package-manager lifecycle hooks. It added an attacker SSH key, created operating-system-specific persistence, opened a reverse SSH tunnel to 134.209.82.225, and sent machine reconnaissance data to an HTTP beacon. The persistence could remain after the extension was uninstalled, including through a macOS LaunchAgent, a Windows scheduled task or Startup script, and Linux cron entries.

The malicious version was removed from Open-VSX, Cursor’s marketplace, and the Microsoft Marketplace, while clean neighboring releases 2.1.312 and 2.1.314 were verified to contain none of the listed indicators. Users who installed version 2.1.313 are advised to treat their machines as compromised, check for the svc-telemetry SSH key, collect and remove persistence artifacts, and reinstall version 2.1.314 or later. The article also recommends rotating source-control, cloud, SSH, CI/CD, and package-registry credentials reachable from the affected machine, and states that rebuilding the host is safer if the reverse tunnel is confirmed to have connected.

  • The malicious code ran simply when the extension module loaded under Node.js, so no Claude conversation, VS Code API use, or package-install script was required for the payload to execute.
  • Because the compromised build was published under Anthropic’s legitimate Open-VSX publisher identity, users could not have identified it as a simple lookalike or typosquatted extension.
  • A single malicious Open-VSX publication automatically reached downstream consumers such as Cursor’s marketplace, expanding the impact beyond the original registry.
  • The loader collected names of environment variables matching terms such as KEY, TOKEN, SECRET, PASS, AWS, and GCP, which could reveal what credentials were present even without collecting their values.
  • The backdoor could survive extension removal through separate startup mechanisms, meaning uninstalling version 2.1.313 alone was not a complete cleanup.
Key Points
  • 01The Open-VSX release of Anthropic Claude Code extension version 2.1.313 contained a malicious loader in extension.js and was also distributed through Cursor's mirrored extension marketplace.
  • 02The malicious extension added an attacker-controlled SSH key, set up operating-system-specific persistence, opened a reverse SSH tunnel to 134.209.82.225, and sent host reconnaissance data over HTTP.
  • 03Cursor reported that up to 5,000 of its users received the trojanized version during an approximately 11-hour exposure window on October 29, 2026.
  • 04Removing the extension alone does not remove the persistence artifacts, so affected users should check for the svc-telemetry SSH key, remove persistence, and rotate credentials reachable from the machine.
  • 05Clean versions 2.1.312 and 2.1.314 were verified to contain none of the listed malicious indicators.

In plain words

TeamViewer fixed a serious problem in version 15.83 that could let a harmful or hacked computer attack the person who connects to it for remote help or control. The issue affects TeamViewer’s main desktop app on Windows, Linux, and Mac, its Windows portable version, and its Android remote-control app when they are older than version 15.83. An attacker could at least force the helper’s TeamViewer session to close repeatedly and may be able to take control of their computer on some systems, so users should update.

Summary
TeamViewer fixed CVE-2026-111585 in version 15.83, a high-severity flaw that lets a malicious remote host crash—and potentially execute code on—the computer connecting to control it. Users should update TeamViewer clients, Portable, Android Remote Control, and Host installations immediately.

TeamViewer released version 15.83 to fix CVE-2026-111585, a high-severity flaw scored 8.8 that allows the computer being remotely controlled to attack the computer connecting to it. The issue affects TeamViewer Full Client on Windows, Linux, and macOS, Windows Portable, and the Android Remote Control app in versions before 15.83. TeamViewer said it was not aware of exploitation in the wild when it published the fix.

During a remote session, the host supplies screen-size information that the viewer uses to allocate memory, but an arithmetic error can cause the viewer to reserve too little space. Later screen data can then be written beyond that space, crashing the viewer’s TeamViewer session and allowing the host to repeat the crash. Remedio demonstrated running chosen code on Windows after bypassing built-in operating-system defenses, although the demonstration used a host-side stand-in for some attack data and was not entirely network-based.

The attack requires a user to start and accept a remote-control session to the malicious or compromised host, but it needs no password or further click and works in TeamViewer’s default configuration. TeamViewer provides no workaround other than updating to version 15.83 or later; users who had updated to version 15.82 remain affected. The same update also fixes two other high-severity issues, while a separate bulletin addresses six flaws in TeamViewer Remote Management add-ons.

  • The security direction is reversed from a typical remote-control concern: the computer being controlled can target the computer of the person connecting to control it after the session begins.
  • The attack requires no password or additional user action beyond accepting a remote-control session and works in TeamViewer’s default configuration.
  • Users who installed TeamViewer’s September 15.82 security update remain affected, because the flaw persists in every version before 15.83.
  • Although TeamViewer lists code execution as platform-dependent, Remedio’s reported demonstration of running chosen code was limited to Windows and was not performed entirely over the network.
  • The same 15.83 release fixes two additional high-severity issues, including a separate code-execution flaw that affects Linux and macOS.
Key Points
  • 01TeamViewer version 15.83 fixes CVE-2026-111585, a high-severity flaw affecting TeamViewer clients before that version.
  • 02A malicious or compromised computer being remotely controlled can crash the TeamViewer application on the computer used to connect to it.
  • 03The affected products include the TeamViewer Full Client on Windows, Linux, and macOS, TeamViewer Portable for Windows, and the Android Remote Control app.
  • 04Remedio demonstrated code execution on Windows by bypassing operating-system defenses, although its demonstration used a host-side stand-in to provide some attack data.
  • 05TeamViewer said it was unaware of attacks exploiting the flaw when the fix was published, and it provides no workaround other than updating.
