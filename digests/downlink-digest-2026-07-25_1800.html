Malvertising Sends Malware in Pieces, Then Makes the Browser Build the Executable

In plain words

A malicious advertising campaign called SourTrade has been impersonating services like TradingView, Solana, and Luno to target retail traders and cryptocurrency investors in many countries. Instead of sending one ready-made harmful file, the scam sends pieces and makes the person’s web browser put the Windows program together, so each download can look different. This matters because people looking for trading or wallet software through ads may be tricked into downloading dangerous files, and simple checks based only on matching a known file may miss them.

Summary
The SourTrade malvertising campaign impersonates trading and crypto services and makes victims’ browsers assemble unique Windows executables from pieces, limiting simple hash-based detection. Defenders should focus on the full delivery chain, including cloaked landing pages, /config requests, secondary runtime downloads, and ServiceWorker-based file delivery.

A malvertising operation called SourTrade is making victims’ browsers assemble the final Windows executable instead of serving one complete malicious file from a fixed URL. Confiant said the campaign has operated since late 2024 and impersonated TradingView, Solana, and Luno to target retail traders and cryptocurrency investors across 12 countries in 25 languages. The landing pages fingerprint visitors, show suspected researchers and bots an empty page, and present selected targets with a convincing copy of the impersonated service.

The delivery chain registers a ServiceWorker, builds a SharedWorker from JavaScript embedded in the page, requests a /config response, and retrieves a clean Bun runtime from a secondary domain. The configuration supplies executable structures and malicious JavaScriptCore bytecode, while the worker uses AES-CTR to generate pseudorandom bytes and follows a template to assemble the file from multiple sources. Confiant said each victim can receive a different assembled file because rotating values in the /config response changes the hash while retaining the payload code.

The article states that the chain does not rely on a browser vulnerability or remove Mark of the Web, and Confiant’s analysis documents delivery rather than execution inside the browser. The approach limits the value of simple hash-based detections, but the attacker-controlled executable material and bytecode still cross the network. Defenders are advised to examine the full chain, including the ad referral, cloaked landing page, /config request, secondary-domain runtime fetch, and ServiceWorker download.

  • The campaign’s browser-built executable approach is narrower than it may first appear because the attacker-controlled PE material and bytecode still cross the network in the /config response.
  • Mark of the Web is not removed, but the recorded download source points to the landing page rather than the secondary domain that supplied the Bun runtime.
  • The campaign evolved away from loading StreamSaver.js from GitHub Pages while retaining its streaming-download architecture and message names, reducing an external dependency that previously exposed part of the download path.
  • The article cautions that capabilities documented in earlier related campaigns, such as credential theft and wallet theft, cannot yet be assigned to the current files based on the published evidence.

JUSTIFICATION

This is a specific, recent finding about an active malvertising campaign using an unusual browser-based file assembly technique to evade simple hash-based detection. It is broadly relevant to security professionals because it affects how defenders should investigate malicious ads, downloads, ServiceWorker activity, and network-delivered executable components, though it is not a critical patch or confirmed browser exploit.
