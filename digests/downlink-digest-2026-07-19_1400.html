SleeperGem: Compromised git_credential_manager, Dendreo, and fastlane RubyGems Drop a Persistent Backdoor
stepsecurity.io · 19 Jul 2026 16:06 UTC openai-codex / gpt-5.5

In plain words

Attackers published harmful versions of three Ruby software packages that, when used on a developer’s computer, could secretly download and run a hidden program that stays on the machine. People and organizations are affected if those specific package versions were installed or used on a developer machine, and they should assume passwords, keys, and other saved secrets reachable from that computer may have been stolen. This matters because trusted software downloads can be turned into a way to break into real work computers, even when normal automated build systems do not show anything suspicious.

Summary
A coordinated RubyGems supply-chain attack named SleeperGem published malicious versions of git_credential_manager, Dendreo, and a fastlane plugin that evade CI, target developer machines, download a backdoor, and install persistence. Anyone who installed or required these versions should treat the machine and reachable secrets as compromised, remove the artifacts, and rotate credentials.

Between July 18 and July 19, 2026, malicious versions of three RubyGems packages were published to RubyGems.org in a coordinated supply chain attack named SleeperGem. The affected packages were git_credential_manager versions 2.8.0 through 2.8.3, Dendreo versions 1.1.3 and 1.1.4, and fastlane-plugin-run_tests_firebase_testlab version 0.3.2. The releases were published directly to the registry with no matching commit or tag in the source projects, and two of the gems had been dormant for years before suddenly shipping new versions.

Each malicious release acted as a loader that checked whether it was running in a build system and exited if it detected common continuous integration environment variables such as GITHUB_ACTIONS, GITLAB_CI, or CIRCLECI. On a developer machine, the loader downloaded deploy.sh and a native binary from the attacker-controlled Forgejo host git.disroot.org, using Ruby’s built-in HTTP client with certificate verification disabled and a User-Agent of Git. StepSecurity used Harden-Runner in audit mode to capture the network connections, process tree, and file activity, including the require-time behavior of git_credential_manager version 2.8.3.

For git_credential_manager version 2.8.3, the install script copied the downloaded binary into $HOME/.local/share/gcm/, marked it executable, launched it as a background daemon, and installed persistence through both a systemd user service and a cron entry named git-credential-manager. The script also probed the sudo and wheel groups and included a root execution path that could plant a setuid root shell at /usr/local/sbin/ping6 when run as root. The article advises anyone who installed or required the affected gems on a developer machine to treat the machine and every reachable secret as compromised, remove the dropped daemon and persistence, check for the setuid shell, and rotate credentials.

  • Normal CI pipeline installs may show no malicious behavior because the malware deliberately exits when it detects common build-system environment variables, making developer machines the primary place to investigate.
  • RubyGems versions that appear without matching source repository commits or tags, especially after years of project dormancy, were useful signals for identifying the compromised releases.
  • The attackers appeared to iterate across versions: git_credential_manager 2.8.2 downloaded the payload but did not execute it, while 2.8.3 removed that safeguard and ran the full chain.
  • The gem loader itself did not directly handle credential theft; the article states that harvesting and exfiltration live inside the native daemon dropped and launched by the loader.
  • Persistence was installed redundantly through both a systemd user service and a cron entry under the same innocuous service name, so removing only one mechanism may not fully clean the machine.

Hackers abuse ViPNet software to target Russian govt agencies

In plain words

Hackers are abusing part of ViPNet, a Russian security software suite widely used in government and regulated organizations, to place hidden programs on affected computers. Kaspersky says the campaign has hit Russian organizations in government, energy, transport, education, and logistics. This matters because software trusted to protect important networks is being used as a way to secretly run more harmful tools, while the researchers do not say ViPNet’s own update servers were broken into.

Summary
A threat actor dubbed HelloNet is abusing the local update mechanism of Russia’s ViPNet security software to sideload malware against Russian government and critical-sector organizations. Kaspersky says there is no evidence ViPNet’s update infrastructure was compromised, and attribution to a Chinese-speaking APT is low confidence.

An advanced threat actor is abusing the update mechanism for the ViPNet private networking product suite to target Russian organizations, including government agencies. The campaign is dubbed HelloNet and has been active since at least May. Kaspersky says it has impacted organizations in the government, energy, transport, education, and logistics sectors.

ViPNet is a Russian information-security product suite from InfoTeCS that provides VPN, endpoint and network access protection, firewall, certificate management, centralized administration, and secure messaging and file transfer. The software is commonly used in Russia and is certified for use in government and other regulated environments. The article notes that ViPNet’s market reach in Russia, especially among high-value organizations, has made it a frequent target for hackers.

In the latest campaign, attackers placed a malicious file named wtsapi32.dll, dubbed HelloInjector, inside the local ViPNet Update System directory so it would be sideloaded at system startup by the legitimate itcsrvup64.exe process. HelloInjector injects into svchost.exe, runs the HelloProxy payload in memory, and contacts a command-and-control server to receive additional modules including HelloExecutor, HelloCleaner, and HelloBackdoor. Kaspersky does not describe how the attackers gained initial access and does not claim that ViPNet’s update infrastructure was compromised.

  • The campaign abuses a local ViPNet Update System directory and a legitimate ViPNet updater process, but Kaspersky does not claim that ViPNet’s update infrastructure itself was compromised.
  • Because ViPNet is certified for Russian government and regulated environments, abusing it gives attackers a path into high-value organizations that are likely to trust the software.
  • The malware set includes a dedicated log-cleaning component, HelloCleaner, specifically designed to remove ViPNet log data and hide the malicious activity.
  • Kaspersky’s attribution to a Chinese-speaking APT is low confidence because it is based mainly on weak indicators, including an unused sina.com reference and a malware mirror hosted by the University of Science and Technology of China.
  • Traffic on ports 5003 and 5060 for HelloProxy and port 443 for HelloBackdoor is specifically highlighted by Kaspersky as monitoring focus for systems running ViPNet.
Key Points
  • 01An advanced threat actor dubbed HelloNet is abusing the update mechanism for the ViPNet private networking product suite to target Russian organizations, including government agencies.
  • 02Kaspersky says HelloNet has impacted organizations in Russia’s government, energy, transport, education, and logistics sectors.
  • 03Attackers placed a malicious wtsapi32.dll file named HelloInjector inside the local ViPNet Update System directory so it would be sideloaded at system startup by the legitimate itcsrvup64.exe process.
  • 04HelloInjector injects into svchost.exe and runs an embedded payload called HelloProxy in memory, which contacts a command-and-control server to receive additional modules.
  • 05Kaspersky has tentatively attributed the campaign to an unidentified Chinese-speaking APT group with low confidence and recommends monitoring ViPNet systems for traffic on ports 5003, 5060, and 443.
