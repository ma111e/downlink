Researchers escape OpenAI Codex sandbox to run commands on host
bleepingcomputer.com · 20 Sep 2026 12:00 UTC openai-codex / gpt-5.6-terra
TAGSaccomplish-aiapply-patchcodexdockerheapjacknode-replopenaioverpatchv8
84
In plain words

Researchers found two flaws in OpenAI’s Codex coding assistant that could let harmful code in a project take control of a developer’s computer, even when Codex was meant to be tightly restricted. People who use Codex Desktop or its command-line version could be affected simply by opening or asking about someone else’s code project. This matters because a malicious project could launch programs, change startup settings, or reach other powerful tools on the computer without the developer seeing an approval prompt. OpenAI fixed the issues in newer Codex versions, so users should update.

Summary
Researchers disclosed two OpenAI Codex sandbox escapes that could let malicious repositories run commands on a developer’s host, including from read-only mode without user approval. OpenAI patched Heapjack in Codex Desktop 26.818.21641 and Overpatch in Codex CLI 0.149.0; users should update immediately.

Researchers from Accomplish AI found two ways to escape OpenAI Codex’s sandbox, the protections intended to prevent untrusted code from affecting the wider computer. The flaws, called Heapjack and Overpatch, were reported to OpenAI on August 12 and fixed within eight days. Heapjack could allow a malicious code repository to run commands on a developer’s machine when opened and queried in Codex, including in the strict read-only sandbox mode without an approval prompt or visible indication.

Heapjack targeted the node_repl component, which placed trusted and untrusted JavaScript contexts in the same Node.js process and memory heap. Untrusted code could search a memory snapshot for the trusted context’s authorization token, then use the valid token to communicate with an unsandboxed parent process. Overpatch affected Codex CLI’s apply_patch tool, which could be manipulated through a patch naming /tmp to expand write permissions and then modify a user’s .zshrc file through a symlink. According to Accomplish AI, OpenAI fixed Heapjack in Codex Desktop build 26.818.21641 and Overpatch in Codex CLI version 0.149.0, and users should update to those versions or later.

  • Codex Desktop installed the node_repl component in the shared ~/.codex/config.toml file by default, which meant Codex CLI users inherited it even if they had not explicitly enabled it.
  • Heapjack bypassed the intended trust boundary because the secret token used to distinguish trusted code was stored in the same Node.js process memory accessible to untrusted code.
  • Overpatch showed that a patch entry naming /tmp could expand write access to the disk’s root, enabling a separate symlink-based change to modify a user’s .zshrc file.
  • The two flaws shared the same design issue: the restricted environment was allowed to determine or access the mechanism meant to constrain it.
Key Points
  • 01Researchers at Accomplish AI reported two OpenAI Codex sandbox escapes, Heapjack and Overpatch, to OpenAI on August 12, and OpenAI fixed them within eight days.
  • 02Heapjack allowed untrusted code to read a trusted authorization token from a shared Node.js memory space and use it to send requests to an unsandboxed parent process, even in Codex’s read-only mode.
  • 03A malicious repository could exploit Heapjack when a user opened it in Codex and asked a question about its code, potentially running commands on the developer’s machine without an approval prompt or visible indication.
  • 04Overpatch abused Codex CLI’s apply_patch tool in workspace-write mode by naming /tmp in a patch to widen write permissions and then using a symlink to append a line to the user’s .zshrc file.
  • 05According to Accomplish AI, Heapjack was fixed in Codex Desktop build 26.818.21641 and Overpatch was fixed in Codex CLI version 0.149.0.

The Phishing Kit That Emailed Us Its Own Billing Meter
ironscales.com · 20 Sep 2026 11:00 UTC openai-codex / gpt-5.6-terra

In plain words

A fake document-invitation email sent to the chief executive of a US Midwest grocery retailer accidentally included the sender’s own control panel, revealing that it was part of a paid service used to send large numbers of scam emails. The panel showed thousands of intended recipients and logs of successful deliveries to real people at unrelated companies. The email slipped past standard automated checks because it came through legitimate but abused services, but it was stopped shortly after delivery. This matters because criminal email scams can be run like subscription businesses at large scale, putting employees and organizations at risk of having their login details stolen.

Summary
A phishing-as-a-service campaign accidentally pasted its live operator console into a document-invite email, exposing its Enterprise subscription, 138,291 lifetime sends, 4,043 loaded targets, SMTP configuration, and delivery logs. The message passed conventional email authentication and bypassed the recipient gateway, showing why behavioral and content-based detection is needed against legitimate-account abuse and credential-harvesting lures.

A document-invite phishing email sent to the chief executive of a US Midwest grocery retailer on September 4, 2026 accidentally included the live web console of the phishing-as-a-service platform that delivered it. The pasted panel showed an active Enterprise subscription with 23 days remaining, 138,291 lifetime emails, 4,043 loaded leads, one SMTP server, 25 concurrent sends, and zero batch delay. Its delivery log contained fifty successful SMTP 250 responses to distinct recipients across forty-nine domains, and the reported throughput and completion estimates matched the displayed timestamps.

The receiving cloud gateway assigned the email a score of 0.50 against a blocking threshold of 3.0, with the only nonzero signal caused by a non-standard HTTP port exposed in the pasted console log. The message passed SPF at the true inbound edge because it was sent through an abused legitimate provider account, while later authentication failures resulted from the recipient-side mail-routing topology and body rewriting after signing. Detection instead relied on a malicious final destination, exact display-name impersonation, and community reputation similarity; Themis assessed it at 88% confidence, and the single affected mailbox was mitigated six seconds after receipt.

  • The console’s throughput and remaining-time estimates matched the elapsed timestamps, providing evidence that the pasted panel reflected live campaign activity rather than static or fabricated text.
  • The only gateway rule with a nonzero score was triggered by the exposed relay port inside the accidental console log, meaning the leaked operational data—not the lure itself—supplied the message’s entire conventional gateway score.
  • The email passed SPF at the actual inbound edge because it was sent through an abused legitimate provider account, illustrating that successful sender-authentication checks did not establish that the message was safe.
  • The article distinguishes infrastructure controlled by the sender from infrastructure merely abused or compromised, including a legitimate insurance-brand domain, an older relay host, and a compromised personal website.
  • Because custom HTML can be appended to generated phishing templates, kit banners, licence meters, lead-loader lines, and delivery-log patterns can serve as inexpensive high-confidence body-content detection signals.

  • 02The exposed console showed an active Enterprise plan with 23 days remaining, 138,291 lifetime emails, 4,043 loaded leads, one SMTP server, 25 concurrent sends, and no batch delay.
  • 03Its delivery log showed 50 successful deliveries with SMTP 250 responses, while the displayed sending rates and completion estimates were consistent with the log timestamps.
  • 04The recipient gateway assigned the message a total score of 0.50 against a blocking threshold of 3.0, and its only weighted signal came from a non-standard HTTP port shown in the accidentally exposed console log.
  • 05The article states that detection ultimately relied on a malicious final-destination verdict, display-name impersonation, and community reputation similarity, and that the single affected mailbox was mitigated six seconds after receipt.
