In plain words

The article describes a critical flaw in parts of React used by websites that build pages on a server before sending them to visitors. Websites using affected React Server Components tools, often through frameworks such as Next.js, need updated versions; browser-only React apps without a server are not affected. The stakes are high because successful abuse could let an unauthenticated outsider run code on a server, so organizations should update and redeploy affected applications.

Summary
React Server Components packages before 19.0.9, 19.1.10, 19.2.9, and 19.3.1 reportedly contain a critical Flight transport framing flaw that can enable unauthenticated server-side code execution under specific shared-ArrayBuffer conditions. Upgrade affected React/framework dependencies, rebuild and redeploy, and avoid sending multiple typed-array views over a shared ArrayBuffer until patched.

React published CVE-2026-126187 on November 10, 2026, describing a critical unauthenticated remote code execution issue in React Server Components with a CVSS 4.0 score of 9.5. The affected packages are react-server-dom-webpack, react-server-dom-parcel, and react-server-dom-turbopack across specified React 19 release lines. The issue can affect server-side and edge rendering environments, while client-only React applications without a server and applications without an RSC-capable framework or bundler plugin are not affected.

The flaw occurs when a response carries multiple typed-array views over a shared ArrayBuffer, attacker-controlled bytes are present in one view, and a downstream consumer transfers the backing storage. In vulnerable versions, a binary row’s length header can be sent while its payload is silently skipped, allowing the Flight parser to consume later bytes incorrectly and potentially interpret attacker-controlled data as a module-loading row. React fixed the issue in versions 19.0.9, 19.1.10, 19.2.9, and 19.3.1 by copying large typed-array payloads into exact-size buffers before they cross the destination boundary. Organizations should upgrade their framework or direct dependencies, verify resolved versions in lockfiles, rebuild and redeploy affected applications, and avoid transporting multiple shared-buffer views in RSC payloads until updated.

  • The patched Flight parser can still process a deliberately corrupted stream, so the fix depends primarily on the writer no longer emitting a binary-row header without its promised bytes.
  • The vulnerable behavior can occur silently: a transferred or detached shared buffer may cause the writer to retain the binary length header while skipping the now-zero-length payload, without surfacing an error.
  • A smuggled module row can turn data into executable code because a framing mismatch causes the parser to consume later rows as binary data and then resume parsing inside attacker-controlled bytes.
  • Many organizations may not see the affected packages declared directly because they are commonly installed transitively through RSC frameworks, making resolved lockfile versions more important than declared dependencies.
  • A practical stopgap before upgrading is to copy shared typed-array views, such as with sharedView.slice(), before placing them in an RSC payload.

  • 02The affected packages are react-server-dom-webpack, react-server-dom-parcel, and react-server-dom-turbopack in versions through 19.0.8, 19.1.9, 19.2.8, and 19.3.0.

In plain words

Google Cloud says three flaws in newer AMD server chips could let someone who is already able to run a program inside a virtual machine learn information from other programs or the operating system on the same chip core. The issue affects Google Cloud C4D, N4D, H4D, Z4D, and G4 machines using AMD Turin processors, including certain dedicated physical servers. Google has protected against data exposure between separate customers’ virtual machines, but affected customers need operating-system updates and must fully stop and start their virtual machines when the update is available. The flaws show that shared cloud hardware can create privacy risks even when customers’ systems are meant to be isolated.

Summary
Google Cloud warns that three AMD EPYC Turin transient scheduler side-channel flaws could expose data between processes inside a VM; customers must apply guest OS patches and stop then start affected VMs once Google’s CPU-information update is available. Google has already mitigated cross-VM and VM-to-host risks, while bare-metal users need firmware and OS updates.

Google Cloud warned that three AMD EPYC Turin processor flaws could allow code running on the same processor core within a virtual machine to infer data from other processes or the kernel. The affected Google Cloud machine series are C4D, N4D, H4D, Z4D, and G4, including C4D and Z4D bare-metal instances. Google rated the issue Medium and said it has already applied mitigations for attacks between VMs and between VMs and the host. The remaining concern is exposure among processes inside an affected VM.

The flaws are transient scheduler attacks: TSA-SQ (CVE-2024-36350), TSA-L1 (CVE-2024-36357), and CVE-2026-0004, which the Xen Project calls TSA-Fill. AMD says Zen 5 processors, including Turin, are affected differently than previously characterized AMD processors. AMD classifies all three as local attacks with high attack complexity and low privilege requirements, and neither AMD nor Google reported exploitation. None of the flaws was in CISA’s Known Exploited Vulnerabilities catalog at the time of publication.

For affected VMs, customers should install their operating-system vendor’s fix when available, then stop and start the VM after Google updates the CPU information reported to it; Google states that rebooting the guest OS alone is not enough. Bare-metal customers running their own operating system or hypervisor should apply vendor fixes, while GKE node images for Turin-based bare-metal instances are planned and Cloud Run requires no action. For Turin systems on customer-owned hardware, AMD says both platform firmware and OS updates are needed for full mitigation, which may affect performance.

  • For affected Google Cloud VMs, an ordinary reboot is explicitly insufficient; customers must stop and start the VM after Google updates the CPU information it reports.
  • Google has addressed the higher-isolation risks between VMs and between a VM and its host, but processes within the same VM may still be exposed until the guest operating system mitigation is enabled.
  • Customers may face a remediation gap because Google provides no interim action for operating systems whose vendors have not released a fix, and does not explain how to determine when its CPU-information update has reached a VM.
  • As of the article’s publication, none of the three flaws was listed in CISA’s Known Exploited Vulnerabilities catalog, and neither AMD nor Google reported active exploitation.
