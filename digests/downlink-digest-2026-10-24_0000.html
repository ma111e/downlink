One RFQ Number, Two Real Suppliers, 17 Minutes Apart
ironscales.com · 24 Oct 2026 11:00 UTC openai-codex / gpt-5.6-terra
TAGSironscalesmasqueradingmicrosoft-365spearphishing-linkunited-kingdomuser-execution

In plain words

A UK charter airline received two nearly identical requests for quotation from two real aviation suppliers only 17 minutes apart, but both messages used the same fake PDF-style link to an unrelated website. The emails reached engineering employees who would be likely to open an aircraft-related quote request, and the suppliers’ real email accounts appear to have been used. This matters because an email can come from a legitimate company and still be dangerous, so comparing repeated wording, reference numbers, and web links across messages can reveal a coordinated scam that sender checks alone miss.

Summary
Two legitimate aviation suppliers sent near-identical RFQ phishing emails from authenticated Microsoft 365 accounts, revealing a cross-sender campaign only when analysts correlated the shared reference number, template, and landing-page path. Organizations should detect vendor-email compromise by clustering message content and destinations across senders rather than relying solely on sender authentication or reputation.

A UK charter airline received two nearly identical request-for-quotation emails, both using RFQ number 68453, from two different aviation suppliers 17 minutes apart. The messages originated from the suppliers’ own Microsoft 365 tenants, passed authentication at the airline’s gateway, and came from first-time senders. Eight mailboxes across two airline domains received the pair, including a fleet support engineer and an engineering director. A human analyst ultimately resolved both messages as malicious and the copies were removed.

Each email used the same one-line template and a bold, PDF-named link, View_RFQ68453_.pdf, rather than including an attachment. The subject line, Request for Quotation 68453_, and link text used a supplier-specific suffix, while both links led to the same /aerosupply/technic/aviation.html path on an unrelated web-design site. Considered separately, each message looked like an unusual but authenticated vendor email; considered together, the reused reference number, shared template, and identical destination path exposed a coordinated pattern. The article’s practical recommendation is to correlate inbound vendor messages by reference number, template shape, and destination path across senders, because sender authentication alone cannot establish that two legitimate accounts are being used independently.

  • Email authentication confirmed that each message came from the supplier account it claimed to use, but it did not establish that the supplier account was being used legitimately.
  • The campaign became apparent only by correlating content across unrelated senders: the reused RFQ number, matching template, and identical destination path provided the stable links between the emails.
  • The supplier-specific suffix added to the shared RFQ number and PDF-style link made each copy appear tailored while preserving a detectable template pattern.
  • Two first-time supplier emails could appear unremarkable when reviewed separately, but their arrival within 17 minutes and shared content created a materially different signal.
Key Points
  • 01A UK charter airline received two nearly identical RFQ emails numbered 68453 from two different aviation suppliers 17 minutes apart.
  • 02Both messages were sent from within the suppliers’ Microsoft 365 tenants, passed authentication at the airline’s gateway, and came from first-time senders.
  • 03Each email used the same template and a bold PDF-named link, while both links resolved to the same aviation-themed path on an unrelated web-design site.
  • 04Eight mailboxes across two airline domains received the messages, including a fleet support engineer and an engineering director.
  • 05A human analyst resolved both emails as malicious, and the copies were removed, although the record did not establish whether anyone clicked.

In plain words

The article promotes Aikido Security’s AI-based testing service, which tries to break into a company’s website, app, or internet-facing systems in order to find real weaknesses before criminals do. It says companies can run tests against a safe copy of an app, provide test accounts for different kinds of users, and optionally share source code so the service can find more problems. This matters to organizations handling customer data or facing compliance reviews, because weaknesses such as one user being able to view another user’s data can expose sensitive information; the article cites First National Bank of America finding and fixing a serious issue before a customer portal launched.

Summary
Aikido positions its AI pentesting as an add-on to existing security tools, using autonomous agents to test live applications for exploitable logic and access-control flaws that static scanners may miss. Teams can start with a scoped staging assessment and optionally add source-code access and continuous testing on deployments.

Aikido Security presents its AI Pentest as a service that can be added alongside existing code and cloud security tools to test running applications and internet-facing systems. The article says it is intended to find exploitable logic and access-control flaws that deterministic tools may not detect. Organizations define the applications, domains, servers, and user roles in scope, allowlist Aikido testing addresses, and supply credentials for protected areas. The article recommends using a staging or pre-production environment with test data for web application testing.

Repository access is optional, but Aikido says whitebox testing can provide deeper findings and reported seven times more vulnerabilities than greybox testing across more than 1,000 pentests. Findings are validated and include proof-of-concept material, reproduction steps, severity, and estimated remediation time, with retesting available after a fix is deployed. For continuous testing, Aikido Infinite examines configured repository branches and launches targeted tests when it identifies security-relevant changes. The article cites First National Bank of America, which reportedly completed a test in 1 hour and 40 minutes and fixed a high-severity issue before its customer portal went live.

  • Providing accounts for multiple user roles is particularly important because serious authorization problems, such as one user accessing another user’s data, may not appear when testing only as an anonymous visitor or a single account type.
  • The article states that whitebox testing found seven times more vulnerabilities than greybox testing across more than 1,000 pentests, making repository access a high-impact optional configuration choice.
  • A merged code change is not treated as proof that a security issue is resolved; the article recommends retesting the deployed fix to verify that the original issue is gone.
  • Continuous pentesting requires connected repositories because Aikido Infinite examines code changes to determine which changes warrant targeted testing.
  • First National Bank of America reportedly started a pentest within a day, completed it in 1 hour and 40 minutes, and fixed a high-severity issue before its customer portal went live.
Key Points
  • 01Aikido AI Pentest is designed to complement existing code and cloud security tools by testing running applications for exploitable flaws, including logic and access-control issues that deterministic tools may miss.
  • 02To run an Aikido AI Pentest, organizations need an in-scope running application, verified domain ownership, allowlisted pentest IP addresses, credentials for relevant user roles, and defined domains and servers.
  • 03The article recommends testing staging or pre-production environments with test data, while stating that connected repositories are optional and that whitebox testing found seven times more vulnerabilities than greybox testing across more than 1,000 pentests.
  • 04Aikido Infinite continuously evaluates configured repository branches and launches targeted testing when it identifies security-relevant changes, either on deployment or on a schedule.
  • 05Pentest findings include validation, proof-of-concept material, reproduction steps, severity ratings, and estimated remediation time, and can be retested after fixes are deployed.
