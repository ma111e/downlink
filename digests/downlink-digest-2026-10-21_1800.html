    In plain words

    PHP released emergency fixes for two serious flaws that could let someone take control of a website server without logging in. The PHP Foundation says Chainguard published its fixed software packages hours before the planned joint release, while Chainguard says it acted early because it believed attacks and details of the flaws were already spreading. This matters to businesses, hosting companies, and governments that use PHP because early publication can help users protect themselves but can also give criminals clues before other providers have updates ready.

    Summary
    The PHP Foundation says Chainguard broke an embargo by releasing patched container images for two critical PHP RCE flaws hours early, while Chainguard says it acted because exploits were reportedly circulating. The incident exposed strained coordinated-disclosure processes and PHP’s resource constraints in fixing a memory-management issue first identified in 2024.

    The PHP Foundation said Chainguard broke a coordinated security embargo by publishing patched PHP container images more than six hours before the planned October 21 release. The images contained fixes for CVE-2026-109618 and CVE-2026-109619, critical flaws that researchers demonstrated could allow code to run on web servers without logging in. The Foundation said an early public fix could let attackers study the changes while other distributors were still preparing updates.

    Chainguard CEO Dan Lorenc said he authorized the early release after reports from other security vendors of exploits in the wild, as well as public information leaks and Chainguard’s own testing of the fixes. The PHP Foundation said it had inspected public proof-of-concept code but had not identified functional examples by release time, while noting this did not rule out exploitation elsewhere. The disclosure had already been disrupted by leaked CVE identifiers and an accidentally published Calif exploit video, and the Foundation said it is changing its security decision process after a memory-management issue first identified in 2024 remained unresolved amid technical trade-offs and limited resources.

    • The early-release dispute highlights a practical trade-off: publishing a fix can immediately help users update, but it can also allow attackers to compare the repaired software with the prior version while other distributors are still preparing updates.
    • Reports of exploitation were not fully verifiable from the public record described: Chainguard cited reports from unnamed vendors, while the PHP Foundation said it had not found functional public proof-of-concept code by release time.
    • The coordinated release had already been accelerated by a leaked CVE listing and an accidentally published exploit video, showing that disclosure schedules can unravel through multiple separate information leaks before patches are broadly available.
    • PHP said its fix was delayed not simply by lack of awareness, but because potential remedies risked breaking compatibility, introducing denial-of-service problems, or requiring changes in third-party extensions.
    • The Foundation is changing its decision process toward majority votes because consensus requirements had allowed difficult security fixes to remain stalled.

In plain words

PHP released emergency updates for two serious flaws that can let an outsider take control of websites and services that use certain older versions of PHP, the software that helps many websites run. The problem is in PHP itself, so updating a website’s own code or apps such as WordPress will not fix it; the underlying PHP software must be updated. It affects web servers, hosting services, and software containers running affected PHP versions, and attackers have already begun trying to use the flaws. A successful break-in could also reveal passwords, keys, and visitor session information held in the website’s running process.

Summary
PHP2Shell consists of two critical unauthenticated RCE flaws affecting PHP web runtimes; organizations should immediately inventory and upgrade all PHP deployments, including container base images, to patched releases or vendor-backported packages.

PHP released emergency updates on October 21, 2026, for two critical remote code execution flaws collectively called PHP2Shell: CVE-2026-109618 and CVE-2026-109619. Both flaws are rated CVSS v4.0 9.2 and reside in the PHP runtime rather than in applications built on PHP. An unauthenticated attacker can run code as the web worker account, while memory disclosure could expose tokens, keys, and session data from other requests. Exploitation attempts had been observed through watchTowr’s honeypot network as of October 21.

The issue affects PHP installations that serve web requests, including PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, and LiteSpeed, when they run versions below 8.5.12, 8.4.27, 8.3.36, or 8.2.35. Updating applications such as WordPress or Laravel does not fix the runtime flaw; organizations need to identify and patch PHP on hosts, virtual machines, container base images, and provider-managed services. Linux distribution packages may have the fix while retaining older-looking version numbers, so package changelogs should be checked for the CVE IDs. After upgrading, organizations should restart PHP-related services and review logs for unusual multipart requests, memory-limit errors, repeated HTTP 500 responses, or unexplained PHP worker restarts.

  • A fixed Linux distribution package may still show an older-looking PHP version number, so teams should verify the package changelog for the CVE IDs rather than relying only on the displayed version.
  • Container images can carry PHP through official base images, distribution packages, or vendor appliance images without listing it as an application dependency, making runtime inventory especially important.
  • PHP’s suggested configuration mitigations only reduce exposure to certain attack paths and do not make an affected installation safe, so they are not a substitute for upgrading.
  • After patching, teams should confirm that memory_limit and post_max_size still meet application requirements because the fix introduces a hard memory limit that terminates the process when reached.
  • Potential prior exploitation can be investigated through signs such as unusual multipart requests, memory-limit errors, repeated HTTP 500 responses, and unexplained PHP worker restarts.
Key Points
  • 01PHP released versions 8.5.12, 8.4.27, 8.3.36, and 8.2.35 on October 21, 2026, to address two critical remote code execution flaws collectively called PHP2Shell.
  • 02The flaws, CVE-2026-109618 and CVE-2026-109619, can allow an unauthenticated attacker to run code as the web worker account and potentially disclose memory from the worker process.
  • 03Every PHP installation serving web requests is affected, including PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, and LiteSpeed, when running versions below the fixed releases.
  • 04Organizations should inventory PHP runtimes on hosts, virtual machines, container images, and hosting services, then upgrade to a fixed release or a distribution package that includes the patches.
  • 05Updating application code alone does not resolve the issue, and PHP advises restarting Apache, PHP-FPM, and long-running PHP workers after updating.

Compromised eMudhra intermediate certificates
blog.talosintelligence.com · 21 Oct 2026 20:43 UTC openai-codex / gpt-5.6-terra
TAGSapplechromecisco-taloscomodocrypto-x509cve-2026-111943emsign-root-cs-ca-g3emsign-root-tls-ca-g3emudhragomicrosoftmozilla

In plain words

Eight digital certificates from eMudhra, a company that helps prove websites and software are genuine, were found to have easily guessed secret keys. Someone with those keys could create fake certificates to pose as real websites or sign software, potentially letting them intercept or alter information. Major browser makers and Microsoft have blocked the affected certificates, but other software, VPNs, devices, and services may still trust them unless they receive updates. The issue shows why organizations need to update their software and certificate lists as fixes become available.

Summary
Eight eMudhra intermediate CA certificates were compromised by critically weak P-384 key generation, allowing attackers to forge trusted TLS or code-signing certificates. Organizations should apply vendor updates—particularly Go 1.27.3 or 1.26.10—and verify that affected certificate chains are blocked across non-browser systems.

Cisco Talos reported that eight eMudhra intermediate certificate authority certificates were compromised because their private keys were generated with critically weak randomness. The flaw occurred during an April 30, 2025 key-generation activity under the emSign Root TLS CA - G3 and cross-signed Comodo AAA Certificate Services. During a wrap/unwrap step for 24 subordinate CAs, a second set of weak P-384 keys was created and mistakenly used for eight intermediates. eMudhra revoked the affected certificates and stopped issuing certificates under its G3 root.

Six of the affected certificates were used for TLS and have been blocked by Chrome, Mozilla, and Apple, while two code-signing certificates have also been blocked by Microsoft. An attacker with one of the compromised intermediate private keys could issue fraudulent certificates to impersonate websites or services, potentially intercepting or modifying traffic where affected keys remain trusted. Go designated the issue CVE-2026-111943 and released Go 1.27.3 and 1.26.10, which reject certificate chains containing the compromised intermediate keys. Talos recommends updating software and trust stores, particularly for applications, VPNs, embedded devices, and cloud-native environments that may use separate certificate stores or ignore revocation information.

  • Browser-level blocking does not necessarily protect applications that use separate, stale, embedded, or legacy certificate stores and do not check revocations.
  • The Go fixes explicitly reject certificate chains containing the compromised intermediate keys, addressing cloud-native and static-container environments where normal certificate revocation may be ignored.
  • A forged TLS certificate could enable package-registry impersonation, but it would not by itself defeat separate package-integrity controls such as lockfile hashes, checksums, signatures, or provenance verification.
  • Embedded and industrial devices may require vendor updates or other compensating measures because their certificate stores and update mechanisms can be independently managed or limited.
Key Points
  • 01Eight eMudhra intermediate certificates were compromised after a flawed April 30, 2025 key-generation process produced weak P-384 private keys with only 3 to 8 bits of entropy.
  • 02Six affected TLS intermediate certificates have been blocked by Chrome, Mozilla, and Apple, while two affected Microsoft code-signing certificates have also been blocked.
  • 03eMudhra revoked the compromised certificates and stopped issuing new certificates under its emSign Root TLS CA - G3 root.
  • 04The Go project released Go 1.27.3 and Go 1.26.10 for CVE-2026-111943, filtering certificate chains containing the eight compromised eMudhra intermediate keys.
  • 05Cisco Talos had not observed malicious use of the compromised certificates in the wild as of October 21, 2026.

In plain words

Researchers found that a Chinese-speaking operator used AI helpers, automated tools, and shared notes to investigate and try to break into organizations around the world. The targets included financial firms, dating apps, text-message providers, stores, cryptocurrency services, schools, logistics companies, and legal claims systems in countries including South Korea, the United States, Canada, Japan, India, and the United Kingdom. The attacker appeared especially interested in personal records, phone numbers, payment information, and administrator access, which could be sold or otherwise used for profit. This matters because AI can help one person organize and continue many harmful investigations across different computers and targets more quickly.

Summary
Zscaler uncovered a globally targeted, financially motivated campaign in which a Chinese-speaking operator combined the ARTEX penetration-testing framework with AI coding assistants, multiple LLMs, and custom synchronization scripts to automate and persist offensive investigations. The activity sought personally identifiable information, transaction data, administrative access, and payment-related credentials across sectors including finance, dating, SMS, retail, cryptocurrency, and education.

Zscaler ThreatLabz examined an AI-assisted cyberattack environment that combined the ARTEX penetration-testing framework with Claude Code, Codex, Grok, custom automation, and configurations requesting DeepSeek, GLM, and Grok models. The activity was initially associated with attacks against South Korean financial institutions, but recovered prompt histories showed targeting across numerous countries and sectors. The records indicate that the operator used AI tools to organize, conduct, review, and continue investigations across separate systems and accounts.

The operator maintained work and jump servers, synchronized shared instructions and saved notes between AI workspaces, and used project files to track targets, discovered entry points, findings, and evidence. ARTEX was customized with tools including nmap, sqlmap, nuclei, httpx, jadx, apktool, and frida-tools, while a prompt-triggered script supplied project-status context to new AI sessions. Prompts sought personal information, phone numbers, transaction records, administrative access, payment gateway keys, and cryptocurrency-related opportunities, and included questions about selling compromised data. Zscaler assessed the activity as likely financially motivated and reported that the recovered records point to a Chinese-speaking operator.

  • The operator treated AI sessions as a coordinated team: DeepSeek was directed to conduct initial work, while GLM was instructed to review DeepSeek and its subagents for missed attack paths.
  • The recorded model name in a configuration did not reliably establish which model answered a session, because requests were routed through compatible API gateways and account names did not always match the configured model.
  • A prompt-triggered script automatically attached a summary of each project’s status, notes, and saved memory files to new AI requests, allowing later sessions to resume work with prior context.
  • Synchronization scripts copied shared instructions and supporting files across several accounts and servers while using backups and validation checks to avoid replacing modified files.
  • Separate proxy exit addresses were assigned to individual projects, and monitoring tasks were set to restart disrupted tunnels and supporting services.
Key Points
  • 01Zscaler ThreatLabz reported that an operator combined the ARTEX penetration-testing framework with Claude Code, Codex, Grok, custom scripts, and configurations requesting DeepSeek, GLM, and Grok models.
  • 02The operator used work and jump servers, synchronization scripts, and saved project files to share instructions, preserve investigation context, and continue work across accounts and AI sessions.
  • 03Prompt histories from August through October 2026 showed targets in multiple industries and countries, including financial institutions, dating services, SMS providers, retail platforms, cryptocurrency services, educational services, logistics companies, and legal settlement systems.
  • 04The prompts included requests for personally identifiable information, phone numbers, transaction data, payment gateway API keys, administrative access, and methods to obtain NFT gifts without payment.
