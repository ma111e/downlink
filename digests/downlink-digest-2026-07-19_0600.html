Emerging Threat: (CVE-2026-63030, CVE-2026-60137) WordPress Core Unauthenticated RCE via wp2shell
cycognito.com · 19 Jul 2026 08:29 UTC openai-codex / gpt-5.5
TAGScve-2026-60137cve-2026-63030cycognitosql-injectionunauthenticated-rcewordpresswordpress-corewp-json-batch-v1wp-querywp-rest-apiwp2shell
95
In plain words

The article describes “wp2shell,” a pair of flaws in WordPress that together can let someone on the internet take control of certain WordPress sites without needing a login, added features, or help from a user. Sites running WordPress 6.9.0 through 6.9.4 or 7.0.0 through 7.0.1 are affected by the full problem, while 6.8.0 through 6.8.5 still need an update for one of the flaws. This matters because WordPress is used on many public websites, including smaller brand, campaign, regional, and older sites that organizations may no longer closely track, so exposed sites could be compromised even after fixes are available if updates are not confirmed.

Summary
WordPress released fixes for the wp2shell vulnerability chain, which enables unauthenticated remote code execution on default WordPress 6.9.0–6.9.4 and 7.0.0–7.0.1 sites, while 6.8.x sites still need patching for the SQL injection component. Administrators should verify updates to 6.8.6, 6.9.5, or 7.0.2 and review exposed sites for possible compromise.

wp2shell is an unauthenticated remote code execution attack against WordPress core that combines two separately tracked flaws, CVE-2026-63030 and CVE-2026-60137. The article says the chain can let an anonymous attacker run code on a default WordPress installation with no plugins, no valid account, and no user interaction. As of July 18, 2026, a working proof of concept describing the full mechanism had been published, lowering the effort required to probe exposed installations.

CVE-2026-63030 is a REST API batch-route confusion issue in WP_REST_Server::serve_batch_request_v1() affecting the /wp-json/batch/v1 endpoint, which has shipped with WordPress since version 5.6. CVE-2026-60137 is a SQL injection in the author__not_in parameter of WP_Query, the core class that builds most WordPress database queries. The full RCE chain affects WordPress core versions 6.9.0 through 6.9.4 and 7.0.0 through 7.0.1, while WordPress 6.8.0 through 6.8.5 carries only the SQL injection component.

WordPress released fixes in versions 6.8.6, 6.9.5, and 7.0.2 on July 17, 2026, with the 7.1 beta line fixed in 7.1 beta2. The article emphasizes that automatic updates may fail or be disabled, so administrators should confirm the installed version on each site and treat sites that were exposed while vulnerable as potentially compromised until reviewed. CyCognito’s observed exposure spans multiple sectors, with Consumer Discretionary, Industrials, and Communication Services leading the visible affected asset set.

  • The 6.8.x branch could be overlooked if teams track only the full wp2shell RCE chain, because those sites are not exposed to the complete chain but still need 6.8.6 to fix the SQL injection component.
  • The article emphasizes that forced automatic updates reduce risk but are not proof of remediation, because background updates can fail or be disabled and each site’s installed version must be confirmed.
  • CyCognito’s exposure data suggests vulnerable WordPress assets are often secondary properties such as campaign, regional, subsidiary, or product-line sites rather than flagship domains, making inventory gaps a major practical risk.
  • Because the RCE chain requires no plugins, valid account, or user interaction, the usual triage assumption that WordPress risk depends on a vulnerable add-on does not apply for affected core versions.
  • Patching closes the vulnerable path but does not address any compromise that may have happened before the update, so sites that were reachable while running affected versions require review beyond version verification.
Key Points
  • 01wp2shell is an unauthenticated remote code execution chain in WordPress core that combines CVE-2026-63030, a REST API batch-route confusion issue, with CVE-2026-60137, a SQL injection in the author__not_in parameter of WP_Query.
  • 02The full remote code execution chain affects WordPress core versions 6.9.0 through 6.9.4 and 7.0.0 through 7.0.1, while WordPress 6.8.0 through 6.8.5 carries only the SQL injection component.
  • 03WordPress released fixed versions 6.8.6, 6.9.5, and 7.0.2 on July 17, 2026, and the 7.1 beta line is fixed in 7.1 beta2.
  • 04The article says defenders should verify that automatic updates completed, prioritize sites on 6.9.0 or later, restrict or block /wp-json/batch/v1 until patched, monitor logs, and review potentially affected sites for compromise.

SleeperGem: RubyGems supply chain attack targets dormant maintainer accounts
aikido.dev · 19 Jul 2026 08:45 UTC openai-codex / gpt-5.5
TAGSaccount-takeoverci-evasioncirclecidendreodisrootfastlane-plugin-run-tests-firebase-testlabforgejogit-credential-managergit-disroot-orggithub-actionsgitlab-cijenkinsrubygemssleepergemvercel
86
In plain words

Someone took over old RubyGems maintainer accounts and used them to publish new versions of trusted Ruby software packages that downloaded and ran harmful files on developers’ computers. The affected people are mainly developers who installed or loaded these packages, including users of existing projects like Dendreo and fastlane-plugin-run_tests_firebase_testlab. This matters because accounts that look harmless after years of inactivity can be hijacked to spread dangerous code through software people already trust.

Summary
Attackers compromised dormant RubyGems maintainer accounts to publish malicious gem updates that downloaded and executed payloads on developer machines while avoiding CI environments. The incident shows RubyGems is now facing the same dormant-account supply chain abuse long seen in npm and PyPI.

A new RubyGems package named git_credential_manager published four versions in rapid succession and stood out because it downloaded binaries from a Git repository hosted at https://git.disroot[.]org/git-ecosystem/. The repository was on a public Forgejo instance where anyone can create repositories, and the username git-ecosystem made it appear somewhat legitimate. One submitted binary was quickly flagged as malicious by antivirus vendors on VirusTotal.

The article describes how the package evolved over about nine hours. Version 2.8.0 already worked as a dropper by building a URL to the hardcoded Forgejo host, disabling SSL certificate verification, fetching a payload, and executing it with a shell or PowerShell. Later versions made execution quieter, wired the installer into the gem load path so merely requiring git_credential_manager could trigger it, and then uncommented the line that executed the downloaded script.

The attacker also added git_credential_manager as a dependency to new versions of other gems, including Dendreo and fastlane-plugin-run_tests_firebase_testlab, the latter of which had 574,661 total downloads and belonged to a different maintainer. The package included checks for roughly 30 CI-related environment variables, including GitHub Actions, GitLab CI, CircleCI, Travis, Jenkins, and Vercel, and did nothing if one was found. The article frames the incident as RubyGems’ first real taste of dormant maintainer account compromise patterns that npm and PyPI have faced for more than a year.

  • The attacker’s rapid sequence of small version changes shows the malicious delivery mechanism being refined in public, including making Unix execution quieter and later activating execution with a one-line change.
  • The CI-environment checks indicate the package was designed to avoid disposable build systems and instead focus on developer laptops where credentials and local access may be more valuable.
  • Adding the malicious package as a dependency to older trusted gems made the campaign more dangerous than simple typosquatting, because existing users could receive the payload through projects they already trusted.
  • The compromise of fastlane-plugin-run_tests_firebase_testlab, which belonged to a different maintainer than the other affected gems, showed the activity was not limited to a single hijacked RubyGems account.
  • Dormant maintainer accounts that had not updated packages for six or seven years were specifically highlighted as risky because they can look harmless while still retaining the ability to push trusted package updates.
Key Points
  • 01A new RubyGems package named git_credential_manager published four versions in rapid succession and downloaded binaries from a Git repository hosted at https://git.disroot.org/git-ecosystem/.
  • 02Version 2.8.0 of git_credential_manager acted as a dropper by building a hardcoded URL, disabling SSL certificate verification, fetching a payload, and executing it with a shell or PowerShell.
  • 03Version 2.8.2 wired the installer into the gem’s load path so that merely requiring git_credential_manager could trigger the installation flow, and version 2.8.3 uncommented the line that executed the downloaded script.
  • 04The package included a skip_install? check for roughly 30 CI-related environment variables, including GitHub Actions, GitLab CI, CircleCI, Travis, Jenkins, and Vercel, and did nothing when it found one.
  • 05The attacker added git_credential_manager as a dependency to newly published versions of Dendreo and fastlane-plugin-run_tests_firebase_testlab, with the latter belonging to a different maintainer and having 574,661 total downloads.
