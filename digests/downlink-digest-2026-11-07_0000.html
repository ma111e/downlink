In plain words

SonicWall released updates for its network security devices after finding that attackers had already used a flaw to get around an extra login-verification step. The problem affects organizations using certain SonicWall devices for remote access and relying on SAML, a system that manages sign-ins. If left unpatched, someone with the right alternate login credentials could bypass the organization’s usual multi-step login protection, putting internal systems at greater risk.

Summary
SonicWall has patched an actively exploited SonicOS SSL-VPN flaw, CVE-2026-19868, that can let attackers with alternate valid credentials bypass SAML-enforced MFA. Organizations using affected Gen7 or Gen8 firewalls should upgrade immediately, as no workaround is available.

SonicWall released updates for seven SonicOS vulnerabilities, including CVE-2026-19868, an SSL-VPN authentication-bypass issue reported as exploited in attacks. The flaw affects SSL-VPN services configured to use SAML authentication and has a CVSS score of 7.1. SonicWall urged customers to upgrade promptly, and CISA added the flaw to its Known Exploited Vulnerabilities catalog.

CVE-2026-19868 can allow someone with valid credentials for an alternate authentication method to bypass SAML controls, potentially including SAML-enforced multi-factor authentication. The affected releases are SonicOS Gen7 7.3.3-7015 and earlier and Gen8 8.2.2-8015 and earlier; fixes are available in versions 7.3.4-7013 and 8.2.3-8015. The update also addresses six other flaws, including two management-interface issues rated 8.8 and pre-authentication buffer overflows that could cause denial-of-service conditions.

  • The actively exploited flaw is limited to SonicOS SSL-VPN deployments configured for SAML authentication, so this configuration is the relevant exposure condition rather than SSL-VPN use alone.
  • The bypass requires valid credentials through an alternate authentication method, meaning the reported issue circumvents SAML protections rather than providing unauthenticated access.
  • The same update also addresses two 8.8-severity management-interface flaws that can permit unauthorized operations by unauthenticated attackers under specific conditions.
  • SonicWall provides no workaround, making upgrades to SonicOS 7.3.4-7013 or 8.2.3-8015 the stated mitigation path.
  • The alert follows multiple reported 2026 exploitation campaigns targeting SonicWall SMA1000 remote-access appliances, including incidents involving zero-days and remote code execution.

In plain words

A setting in Anthropic’s Claude Code can save a full command after a developer chooses “Yes, and don’t ask again,” including any password or access key typed into that command. Apiiro found 1,122 publicly available GitHub copies of this settings file containing 1,379 secrets, affecting at least 63 organizations and potentially allowing access to databases, servers, cloud accounts, and software-development accounts. Deleting the file later may not be enough because old versions and copied projects can still preserve the information, so affected groups need to replace exposed passwords and keys before removing the files.

Summary
Claude Code can save secrets embedded in approved shell commands to .claude/settings.local.json, leading Apiiro to find 1,379 exposed credentials across 1,122 public GitHub copies. Organizations should immediately rotate any exposed credentials, audit repository history and forks, and ensure these local settings files are ignored and scanned.

Apiiro found that Claude Code can store passwords, tokens, and API keys in plain text within .claude/settings.local.json when users approve a command with “Yes, and don’t ask again.” The file can save the exact command offered for approval, including any secret typed into it. Apiiro identified 1,122 public copies containing at least one secret, with 1,379 different secrets across those files.

The exposed material included 379 database passwords, 43 SSH logins for public servers, 42 GitHub, GitLab, and npm tokens, and 23 AWS keys. Removing a file does not eliminate the exposure from git history or forks; Apiiro found 734 additional secrets in older versions and matching secrets in 211 forks. The researchers advise organizations to rotate all credentials ever stored in these files, search current and historical repositories, stop tracking the local settings file, add it to project .gitignore files, and avoid placing secrets directly in commands.

  • Claude Code’s automatic exclusion is stored only in one user’s global Git settings, so it does not protect collaborators or prevent a file already committed to a project from being shared.
  • Common secret-scanning tools missed a substantial portion of the exposed files: gitleaks and TruffleHog together failed to flag 215 of the 1,122 files containing secrets, largely because passwords embedded in command lines do not match known key formats.
  • The scope grows beyond currently visible files: historical versions, forks, shared Claude settings files, and saved agent chat logs brought Apiiro’s total to 2,539 secrets across 1,994 repositories.
  • Using an approval pattern such as “npm run:*” or referring to a secret through a variable such as “$DB_URL” can avoid saving the actual secret in an approved command rule.
Key Points
  • 01Claude Code can store a full approved shell command, including passwords or access keys entered in it, in .claude/settings.local.json when a user selects “Yes, and don’t ask again.”
  • 02Apiiro found 1,122 public copies of .claude/settings.local.json containing at least one secret, with 1,379 distinct secrets identified across those files.
  • 03The exposed secrets included 379 database passwords, 43 SSH logins for public servers, 42 GitHub, GitLab, and npm tokens, and 23 AWS keys.
  • 04Removing a settings file from a repository does not remove secrets from git history or repository forks, where Apiiro found 734 additional secrets in older file versions and matching secrets in 211 forks.
  • 05Apiiro recommends rotating every password, token, and key a settings file has held before removing the file from tracking and adding it to the project’s .gitignore.

Summary
A phishing email impersonating Ecuador’s Diners Club Club Miles used the recipient’s full legal name and work email but left the card-number field blank, revealing that attackers had identity-list data rather than account information. The case shows why personalized details and passing email authentication do not establish legitimacy.

A Spanish-language phishing email impersonating Diners Club del Ecuador’s Club Miles program was delivered to a distribution manager at the Latin American subsidiary of a global construction chemicals manufacturer. The message used the recipient’s four-part uppercase legal name and work email address, although his employer’s directory only held a shorter two-part name. It claimed that 9,447 miles were expiring, but left the field labeled “Número de Tarjeta” blank.

The article argues that the filled name and email fields, alongside the missing card number, show the sender had identity data rather than demonstrated card-account data. The sender domain, clubsmiles.org, was registered on 17 October 2026, used SendGrid infrastructure, and linked to clubmiles.lat, which had a malicious verdict. Although the email passed SPF, DKIM, and DMARC at the recipient-side gateway because the attacker controlled its own domain, IRONSCALES quarantined it after Themis scored it at 90 confidence; a later request to release the message did not change the malicious verdict.

  • A personalized lure can reveal the limits of an attacker’s data: in this case, the filled legal-name and email fields contrasted with an empty card-number field, indicating the sender had identity details but not demonstrated card-account details.
  • Passing SPF, DKIM, and DMARC only established that clubsmiles.org was authorized to send its own email; it did not establish that the domain had any legitimate connection to Diners Club.
  • Authentication failures observed after the recipient gateway re-injected the message into Exchange Online were described as a mail-routing artifact, so treating them as evidence of attacker tampering would misdirect the investigation.
  • A genuine brand’s real callback number and an anti-fraud warning can be copied into a fraudulent message to make it appear safer, so verification should use contact details independently looked up by the recipient.
  • The later request to release the quarantined email showed that the use of a full legal name made the impersonation convincing enough for someone to believe it was legitimate.
