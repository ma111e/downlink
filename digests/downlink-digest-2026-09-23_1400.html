In plain words

Attackers have been using two linked flaws in MikroTik routers to take complete control of devices that can be reached from the public internet, without needing a password or key. The problem affects organizations and people who configured these routers to allow remote access through SSH, a common method for managing a device from elsewhere. Someone who takes over a router can create their own administrator account and may copy configuration data, so owners should install MikroTik’s updates and check whether their devices were altered before the fix.

Summary
CERT Polska says attackers are actively chaining two MikroTik RouterOS SSH flaws, CVE-2026-67279 and CVE-2026-86060, to gain full administrator access to Internet-exposed routers without credentials. Administrators should urgently update RouterOS, restrict public SSH access, and investigate devices for indicators such as failed logins using the username "-2" or unauthorized "ops" accounts.

CERT Polska’s technical analysis identifies the MikroTrick attack chain as two MikroTik RouterOS SSH flaws, CVE-2026-67279 and CVE-2026-86060. When chained, they allow attackers to take full administrative control of Internet-exposed routers without a password, SSH key, or completed authentication. Evidence in logs indicates the chain was exploited before MikroTik released patches on September 3. MikroTik fixed the flaws in RouterOS versions 6.49.21, 7.23.4, and 7.24.2.

The first flaw lets an unauthenticated SSH client reach the command stage by forcing key renegotiation during login, while the second makes the RouterOS login program treat the username “-2” as an option. This enables the attacker to supply a chosen username and a full-administrator privilege level through the SSH session, opening a privileged console. CERT Polska cited indicators including failed SSH logins for “-2,” unauthorized “ops” administrator accounts, and activity involving IP addresses 82.192.72.4 and 103.102.31.18. Patching stops the attack but does not remove prior changes, so administrators who find indicators should isolate and reset affected devices, rebuild from a trusted configuration, and change credentials.

  • Updating RouterOS prevents further use of the chain but does not undo accounts, configuration changes, or data theft that may have occurred before patching.
  • The RouterOS Flagged status can detect only selected signs of compromise, so a device not marked as flagged cannot be assumed to be clean.
  • A failed SSH login for the unusual username "-2" is a particularly useful investigation clue because it reflects the argument-handling behavior used in the observed attack chain.
  • The two flaws have complementary roles: one bypasses the normal point at which SSH verifies identity, while the other turns access to the login process into a fully privileged console.
  • The risk is concentrated on devices whose SSH service is reachable from untrusted public networks; MikroTik says its default home configuration does not expose SSH to the internet.

In plain words

The article describes how Google’s Kubernetes Config Connector can let a person with limited access to one part of a company’s software system make major changes in its Google Cloud account. If the connector has very broad permissions and that person is allowed to submit a certain configuration file, they could give themselves control over the entire Google Cloud organization without having Google Cloud login credentials. This affects organizations that use this setup, especially those that give the connector organization-wide power, because a small access mistake can turn into full control of cloud resources and data.

Summary
Google Kubernetes Config Connector can become a confused-deputy privilege-escalation path: anyone allowed to create IAMPolicyMember resources in a managed namespace may be able to use KCC’s broad Google Cloud service-account permissions to grant themselves organization-level ownership. Mitigate it by least-privileging KCC identities, using namespace-scoped accounts, and tightly restricting who can submit IAM-related KCC resources.

Google Kubernetes Config Connector (KCC) lets developers describe Google Cloud resources in Kubernetes YAML files while KCC uses its own Google service account to make the corresponding cloud API calls. This avoids distributing Google Cloud credentials to developers, but it can create a privilege-escalation path when KCC’s service account has broad project, folder, or organization permissions. Researcher Justin O’Leary named the issue ConfigConfusion.

A user who can create IAMPolicyMember resources in a KCC-managed namespace can submit a YAML file that grants an attacker-controlled service account a Google Cloud role, potentially including roles/owner for an entire organization if KCC is permitted to assign it. Kubernetes checks whether the user may create the resource, and Google Cloud checks whether KCC’s service account may make the IAM change, but neither system verifies whether the Kubernetes user should be allowed to request that cloud action. Google considers this behavior a configuration outcome rather than a KCC flaw, and recommends limiting KCC’s permissions, using separately scoped service accounts in namespaced mode, restricting IAM-related KCC resources to approved teams, and monitoring high-level IAM changes made by KCC.

  • Removing cloud credentials from developers can shift risk rather than eliminate it, because a shared controller identity may have far more authority than any individual developer.
  • Kubernetes permissions and Google Cloud permissions can each appear properly configured in isolation while their combination creates a path to organization-level control.
  • The practical mitigation is to limit both the controller’s cloud permissions and the Kubernetes users allowed to submit IAM-related configuration, since either control alone does not address the full authorization gap.
  • AWS Controllers for Kubernetes and Azure Service Operator v2 reduce the potential impact by separating or scoping controller identities, although the article says they do not remove the underlying confused-deputy risk.

  • 02The ConfigConfusion technique, identified by researcher Justin O'Leary, allows a user who can create IAMPolicyMember resources in a KCC-managed namespace to grant IAM roles using KCC's Google Cloud permissions.

Summary
Eclypsium’s InfraTrust report warns that attackers are increasingly exploiting enterprise infrastructure management platforms, including Cisco FMC and ISE, to gain broad control over managed devices. Organizations should urgently patch, restrict access to, and monitor these high-value administrative systems, many of whose flaws are already listed in CISA’s KEV catalog.

Eclypsium’s September InfraTrust Pulse tracked 158 new infrastructure security advisories from 17 vendors between August 25 and September 17, covering 1,699 vulnerabilities. Forty-two advisories were rated critical, eight included a maximum CVSS score of 10.0, and 71 could be exploited remotely without authentication. Five advisories included flaws later added to CISA’s Known Exploited Vulnerabilities catalog. The report says attackers are increasingly targeting management software that controls network devices, making these platforms high-value targets.

Cisco Secure Firewall Management Center and Cisco Identity Services Engine were among the affected management platforms. CVE-2026-20079, an actively exploited FMC authentication-bypass flaw, can allow an unauthenticated attacker to execute scripts and commands as root, and it was chained with CVE-2026-20316 in attacks linked to three threat clusters, including incidents that deployed Qilin ransomware. The report also highlighted actively exploited SonicWall SMA 1000 flaws that can be chained for unauthenticated remote code execution, as well as critical issues affecting Check Point, Arista, Cisco Nexus 9000, and other management products. Separately, the Linux kernel privilege-escalation flaw CopyFail appeared in 19 advisories from six vendors, illustrating how one upstream defect can create many separate remediation tasks.

  • Infrastructure management consoles are especially consequential targets because they can configure many devices, store their credentials, and provide a single path for making changes across an organization’s network.
  • Cisco published a shared indicator of compromise for two FMC flaws in July while stating it was unaware of exploitation of CVE-2026-20079; the vulnerabilities were later confirmed to have been chained in attacks.
  • SonicWall recommends re-imaging affected physical SMA 1000 appliances or redeploying virtual appliances after compromise rather than trying to clean them in place.
  • A single Linux kernel flaw, CopyFail, generated 19 separate vendor remediation tasks, showing that organizations may need to track the same underlying issue through many different vendor advisories and schedules.
  • Some severe issues involve services reachable by default, such as the Cisco Nexus 9000 debug ports associated with CVE-2026-20212, while Arista said the affected P4Runtime and gNPSI features are disabled by default.
